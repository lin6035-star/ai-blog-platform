**两条已定的产品决策（2026-10-17）**：
- **游客 AI 保留，不扣用户账单**（游客本来也没有钱包）。但「免费」必须配闸门（阶段 1.1），否则等于把免费 LLM 网关挂到公网——实测伪造 IP 头即可无限调用。
- **取消不退款**：用户主动发起又取消，不退。落地语义为「取消后按**实际已消耗 token** 结算」，而不是「按预扣硬上限全扣」——预扣是按硬上限占的，实测可能放大 100 倍以上，全扣会炸。

**排序原则**：先消「钱和崩」（阶段 1）→ 再消「不可用」（阶段 2）→ 然后「账算不清」（阶段 3）→ 「数据悄悄错」（阶段 4）→ 「体验与次要安全」（阶段 5）。阶段 0 必须最先做，否则后面所有改动混在一个脏 diff 里，无法单独回滚。

## 阶段 1 · AI 止血与游客闸门（约 1 天，最高优先级）

目标：让「上线被刷爆账单」和「200 并发拖垮整站」两条风险消失，**不改 SSE 输出时序**。

### 1.1 游客 AI：保留免费，补四道闸门（半天）

现状（`04-AI-Agent.md` P0-1）：游客走 `streamGuestChat`（`AiMessageServiceImpl.java:242-244`），不计费、usage 丢弃（`:3757/3950`），唯一门禁是按 IP 5 次/分钟（`AiRateLimitInterceptor.java:74-91`），而 IP 来自客户端可写的 `CF-Connecting-IP`/`X-Forwarded-For`（`ClientIpUtils.java:12-24`）。实测伪造头可无限刷。

保留游客免费，必须补：

1. **每 IP 日额度**：Redis `ai:guest:daily:{ip}:{yyyyMMdd}` 计数（TTL 到当天结束），默认 **10 次/天**（可配 `blog.ai.guest.daily-limit`）；超限返回 429 + 引导登录。
2. **全站游客日预算熔断**：Redis `ai:guest:global:{yyyyMMdd}` 计数，默认 **2000 次/天**（可配 `blog.ai.guest.global-daily-limit`）；超限后游客 AI 整体关闭到次日 0 点，**登录用户不受影响**。这一步是防分布式/代理池刷的兜底。
3. **可信 IP**：见 1.3（必须在 1.1 之前或同批完成，否则上面两个额度都能伪造绕过）。
4. **全局限流/并发**：见 1.4（游客免费保留后这是必需项，不是可选项）。
5. **游客用量记账**：游客 usage 不能再丢——至少写 Redis 当日累计 + `[GUEST-AI]` 日志（含估算 token、IP 哈希），用于预算熔断和事后排查「被刷了没有」。
6. 实现位置建议：额度/预算判定放在 `AiRateLimitInterceptor` 的 guest 分支（Controller 之前拦截，不进入业务流）；用量累加放在游客流结束时。

**验证**：
- 同 IP 第 11 次游客请求 → 429；
- 伪造 `CF-Connecting-IP`/`X-Forwarded-For` → 计数仍按真实 IP 走；
- 全局计数到上限后游客 429、登录用户正常；
- Redis 里能看到当日游客用量。

### 1.2 前端 SSE token 读取统一（15 分钟）

- `blog-frontend/src/api/ai.ts:735` / `:883`：目前只读 `localStorage.getItem('blog_token')`；改为复用 `utils/request.ts` 里已有的 `readAuthToken()`（先 localStorage 再 sessionStorage）。
- **为什么必须现在做**：不勾「记住我」的登录用户 token 在 sessionStorage，当前会退化成游客（不落库、不计费、Workflow 401）——相当于正常用户也在走免费通道。

**验证**：不勾记住我登录 → AI 聊天正常落库、能计费；Workflow 确认不 401。

### 1.3 可信 IP 链（30~40 分钟）

- `utils/ClientIpUtils.java`：信任顺序改为 **`X-Real-IP` 优先**，最省事且安全的版本：
  - 只信任 `X-Real-IP`（由 Nginx 用 `$remote_addr` **覆盖**写入，客户端伪造不了）；
  - `X-Real-IP` 为空时 fallback `request.getRemoteAddr()`；
  - **不再**直接信任客户端发来的 `CF-Connecting-IP` / `X-Forwarded-For`（若确有 Cloudflare，后续按可信代理网段做，不在这阶段）。
- `deploy/nginx.conf`：保留 `proxy_set_header X-Real-IP $remote_addr;`；**删除/不再透传** `CF-Connecting-IP $http_cf_connecting_ip`（这行是把客户端头原样转发）。

**验证**：带伪造 `CF-Connecting-IP`/`X-Forwarded-For` 连续请求 AI → 仍按真实 IP 计数；登录限流、密码重置限流同样不再被绕过。

### 1.4 全局限流闸门（1 小时）

- 在 `AiRateLimitInterceptor` 增加**全局每分钟上限**（Redis INCR，例如 120 次/分钟全站 AI 请求）和**全站并发上限**（Redis `INCR`/`DECR` 包住请求，或本地 `Semaphore`；超限 429/503）。
- 目的：分类器仍同步占 Tomcat 线程（`AiMessageServiceImpl.java:299-301`，plus 路径 7~12s），用闸门把同时占用的线程数压到可控范围。
- **分类器异步化（真正修 P0-2）不在这阶段做**：会改变 SSE 事件时序（首包延迟/事件顺序），风险高于收益，放到阶段 5 之后单独评估。

**验证**：并发压测（脚本 50 并发）时 AI 请求开始 429，普通文章接口仍正常。

## 阶段 2 · 可用性：Nginx 与 SSE（半天）

### 2.1 Nginx 三项（`deploy/nginx.conf`）

```nginx
# 放在 location /api/ 之前
location /api/ai/ {
    proxy_pass http://blog_backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;          # SSE 关键
    proxy_cache off;
    proxy_read_timeout 600s;      # 长任务
    proxy_send_timeout 600s;
}

# server 块内
client_max_body_size 15m;         # 后端上传上限 10MB
```

- 不改 HTTPS/域名，等阶段 6。
- `location /` 的静态资源缓存分层（index.html 不缓存、hashed 资源强缓存）也放到阶段 6 一起，因为它和发布脚本绑定。

### 2.2 后端 async 超时（10 分钟）

- `application.yml` 增加 `spring.mvc.async.request-timeout: 600s`（当前未配置，Spring MVC 会沿用 Tomcat 默认 30s，长流可能被截断——`02-部署运维.md` P1-9 标注待实测，配上是低风险确定收益）。
- 可选保险：SSE 响应加 `X-Accel-Buffering: no` 响应头。

### 2.3 验证

- `nginx -t` 通过；本地起 Nginx 反代 8080，`curl -N` 观察分块下发（不是攒到最后一次性）；
- 上传一张 >1MB 图片成功；

### 实测中发现并修复的额外问题（P0 级）
**SSE 请求的 ASYNC dispatch 会让 `HandlerInterceptor.preHandle` 执行两次**，导致所有 AI 限流/额度计数翻倍：
- 游客日额度配 2 实际只放行 1 次（6 个请求把 IP 计数推到 7）；
- **原有 chat 桶「10 次/分钟」实际上只有 5 次**——这是改造前就存在的隐性 bug，只是之前没人把额度配到 2 验证过。
