## 0. 结论速览

**按现在仓库里的部署资产上线，有三件事会在上线当天直接可见：**

1. **AI 流式基本不可用**：Nginx 没有为 `/api/ai/**` 做 SSE 配置（`proxy_buffering` 默认 on、`proxy_read_timeout` 默认 60s、无 `proxy_http_version 1.1`），后端也没有发 `X-Accel-Buffering: no`。用户会看到「AI 回复憋很久、然后一次性蹦出来」或「进度事件全程不实时」，长任务撞 60s 直接 504/连接中断。
2. **>1MB 的图片上传必然失败**：Nginx 未设 `client_max_body_size`（默认 1m），而后端按 10MB 校验（`LoginServiceImpl:209/254`）。手机拍的头像/正文插图基本都 >1MB，全部被 Nginx 以 413 挡掉，且返回 HTML 错误页，前端拿不到业务提示。
3. **HTTPS 在这套资产里不成立**：`nginx.conf` 只有 `listen 80`，没有证书、没有 80→443 跳转、没有 HSTS；仓库里也不存在任何 TLS 资产。如果实际靠 Cloudflare 终止 TLS，那它必须同时满足「源站 80/8080 不可直连」——而当前 systemd 让后端监听所有网卡、Nginx 监听公网 IP，两个条件都没有资产保证。

**分级统计**：P0 × 3、P1 × 10、P2 × 12。另有「已登记复核」5 条（`docs/capability-audit-2026-08-06.md`、`docs/security/sensitive-config-externalization-design.md` 等已登记，本次确认仍然存在，不重复计为新发现）+ 「跨任务提示」2 条。

> 已知问题处理原则：`docs/` 里已登记且已修复的**不报**；已登记但仍存在、且上线会炸的**单列并标注「已登记」**，避免与既有登记混淆。

## 1. P0 级（上线即踩雷）

### P0-1 Nginx 完全没配 SSE：AI 流式会「憋字」并在长任务上 504

**位置**：`blog-system/deploy/nginx.conf:28-37`

**证据（配置原文，全文里没有任何 SSE 相关指令）**：

```nginx
    # API 反向代理到后端
    location /api/ {
        proxy_pass http://blog_backend;
        proxy_set_header Host $host;
        proxy_set_header CF-Connecting-IP $http_cf_connecting_ip;
        proxy_set_header CF-IPCountry $http_cf_ipcountry;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
```

后端是 SSE（`text/event-stream`）：

- `AiController.java:60-63`：`@PostMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE) public Flux<AiChatEventVO> streamChat(...)`
- `AiWorkflowController.java:55/67/84`：approve / reject / retry 三个流式接口，同样 `TEXT_EVENT_STREAM_VALUE`
- 后端**没有**设置 `X-Accel-Buffering` 头（全仓库 grep 无此字符串），所以只能靠 Nginx 侧配置关闭缓冲

**上线后的具体表现**（按严重程度递增）：

1. **进度事件不实时**：Agent / Workflow 的事件是稀疏的（思考步骤、任务步骤可能间隔几秒到几十秒），Nginx 默认 `proxy_buffering on` 会把这些小响应体攒在 `proxy_buffers`（默认 4k/8k）里，**流结束或攒满才下发**。用户看到的是「AI 一直在转圈，然后内容一次性全出来」，整个 Agent 过程动画/步骤全废。
2. **普通聊天「憋字」**：token 是 50~200 字节的小 chunk，同样先被攒着；语速慢时明显一顿一顿。
3. **60s 直接断**：Nginx 默认 `proxy_read_timeout 60s`（相邻两次读之间的间隔）。而应用配置单次 LLM 调用 `read-timeout: 60s`（`application.yml:101-102`），Agent 任务还可能在准入队列里排队（8 在跑 + 32 排队），**排队期间一个字节都不发**。超过 60s 无数据 → Nginx 返回 504，前端 `ai.ts:858-860` 走 `onError(new Error('连接意外中断'))`。
4. 另外 `proxy_http_version` 默认 1.0、未清空 `Connection`，上游连接无法 keep-alive，流式场景行为更不可控。

**修复建议**（部署配置，本次只读不改）：

```nginx
# 放在 location /api/ 之前，AI 流式单独一段
location /api/ai/ {
    proxy_pass http://blog_backend;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_buffering off;          # 关键：SSE 不攒包
    proxy_cache off;
    gzip off;                     # 不要压缩 SSE
    proxy_read_timeout 3600s;     # 覆盖 Agent 长任务/排队等待
    proxy_send_timeout 3600s;
}
```

> 后端侧也可以发 `X-Accel-Buffering: no` 做兜底，但那属于代码改动；本项目当前部署形态下，**Nginx 侧必须配**，因为后端没有任何相关响应头。

**验证方法**（上线前在服务器上跑）：

```bash
# 1) 看是否分块下发（应每 ~1s 出 chunk）；用真实 token
curl -N -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"message":"写一篇 800 字的技术文章大纲"}' \
  http://127.0.0.1/api/ai/chat/stream
# 2) 长任务：发起一个 Agent/Workflow 任务，确认 60s 以上不会 504
```

### P0-2 Nginx 默认 1m 请求体上限 与 10MB 上传直接冲突

**位置**：

- `blog-system/deploy/nginx.conf:9-37`（**全文没有 `client_max_body_size`，Nginx 默认 1m**）
- `application.yml:89-92` / `application-prod.yml:63-66`：`max-file-size: 10MB`、`max-request-size: 10MB`
- `blog-system/src/main/java/.../service/impl/LoginServiceImpl.java:209-212`（头像 10MB 校验）、`:254-256`（正文插图 10MB 校验）
- 上传入口：`UploadController.java:22-35`（`/api/users/me/avatar`、`/api/users/me/image`）

**证据**：

```java
// LoginServiceImpl.java:209-212
long maxSize = 10*1024*1024;
if(file.getSize() > maxSize){
    throw new IllegalArgumentException("头像不能超过 10MB,太大了啊！");
}
```

```nginx
# nginx.conf 全文无 client_max_body_size，也没有单独的 upload location
server {
    listen 80;
    ...
    location /api/ {
        proxy_pass http://blog_backend;
```

**上线后的具体表现**：

- 手机拍摄照片 2~8MB 是常态，**上传请求在 Nginx 就被 413 拒绝，根本到不了后端**；后端那段 10MB 报错文案永远不会出现。
- Nginx 413 返回的是 HTML 错误页，前端 axios 拦截器（`src/utils/request.ts:122-130`）只拿到 HTTP 错误，用户看到通用的「请求失败」，完全不知道是文件太大。
- 影响功能：换头像、Markdown 编辑器插图（`/api/users/me/image`），是新用户注册后第一批会用的操作。
- 顺带风险：同样的 1m 限制也卡所有 `/api/` 请求体；如果将来支持大段正文粘贴、导入 Markdown，会以同样的方式静默失败。

**修复建议**：

```nginx
server {
    ...
    client_max_body_size 12m;   # 10MB 文件 + multipart 边界/表单开销，留余量
    client_body_timeout 60s;
}
```

建议同时在前端上传前做大小校验（前端已有 `UploadController` 调用侧），避免用户等待上传完才被拒。**验证**：登录后分别上传 0.5MB / 3MB / 9MB 图片，确认 9MB 返回业务 URL，而不是 413 HTML。

### P0-3 部署资产里没有 HTTPS：只有 `listen 80` + 公网 IP，无证书/无跳转/无 HSTS

**位置**：`blog-system/deploy/nginx.conf:9-12`

**证据**：

```nginx
server {
    listen 80;
    server_name 47.88.86.213;
```

全文没有 `listen 443 ssl`、没有 `ssl_certificate`、没有 `return 301 https://$host$request_uri`、没有 `Strict-Transport-Security`。仓库内也没有 certbot/证书/ACME 相关脚本或文档（`deploy/` 只有 `nginx.conf`、`blog-system.service`、`blog-system.env.example`、`redis.conf.example` 四个文件）。

**为什么按 P0 报**：这不是「安全最佳实践」级别的问题，而是**这套资产的部署拓扑自相矛盾**：

- 如果按资产直接跑：全站 HTTP 明文，登录 token（`Authorization: Bearer`）、密码、AI 内容都在明文上传输；公网 IP 可直接访问。
- 如果实际是靠 Cloudflare 终止 TLS（注释里提到 CF 头，现实中大概率如此）：那 HTTPS 只是「对外」成立，**源站仍然是 80 明文访问**。只要有人知道源站 IP（`server_name` 里就写着 `47.88.86.213`），就能绕过 Cloudflare 直连，TLS/安全策略形同虚设。这一点已登记在 `docs/superpowers/specs/2026-07-13-comment-ip-location-design.md:17`（"Restricting direct origin access remains a later deployment-hardening task"），本次确认**仍未做**。
- `capability-audit-2026-08-06.md:590` 已登记「❌ HTTPS 状态 — 未确认」；本次确认：**仓库里的部署资产确实没有 TLS**，无法按资产复现 HTTPS。

**上线后的具体表现**：

- 直接 IP 访问 → 明文 HTTP，浏览器大概率报「不安全」，OAuth 回调（`GITHUB_OAUTH_REDIRECT_URI=https://your-domain/...`）与站点协议不一致时 GitHub 登录失败。
- 即使用 CF：源站 80 直连存在 → 可绕过 WAF/CF 限流，且 `ClientIpUtils` 优先信任 `CF-Connecting-IP`（见 P1-8），攻击者可伪造来源 IP。
- 没有 HSTS → 用户首次访问仍可能走 http 并被中间人劫持。

**修复建议**（二选一，必须在资产中体现）：

1. **推荐：源站上真 TLS**：certbot 申请证书 → 加 443 server 块 → 80 强制 301 到 https → 加 HSTS；同时把 `server_name` 改成正式域名。
2. 若坚持 Cloudflare 终止：至少补三件事——① 源站只允许 Cloudflare IP 段访问（安全组/iptables）；② Nginx 加 `set_real_ip_from` + `real_ip_header CF-Connecting-IP`；③ 全站 80 只做跳转、不再直出内容。

## 2. P1 级（上线会明显坏事，需要在上线前处理）

### P1-1 生产 ES 地址仍是 `localhost:19200` 且没有 env 覆盖入口

**位置**：

- `application-prod.yml`：**完全没有任何 ES 覆盖**（95 行内无 `elasticsearch`）
- `deploy/blog-system.env.example`：**没有任何 ES 相关变量**
- 依赖的两项能力：站内搜索（`ArticleSearchService`，索引 `article_search_index`）、RAG 向量检索（`AiVectorStoreConfig`，alias `article_rag_active`）

**证据**：

```yaml
# application.yml:94-95（prod 未覆盖，直接继承）
  elasticsearch:
    uris: http://localhost:19200
```

```java
// AiVectorStoreConfig.java:54-61：initializeSchema(false)，所以启动不探测 ES
options.setIndexName(indexName);
options.setDimensions(corpus.getDimensions());
return ElasticsearchVectorStore.builder(...).initializeSchema(corpus.isInitializeSchema()).build();
```

**上线后的具体表现**（坏消息是它不会让应用起不来，所以更隐蔽）：

- 如果目标服务器不是原来那台把 ES 跑在 19200 的机器（换新服务器/重装系统/把 ES 挪到 9200 默认端口）：应用**照常启动**（`initializeSchema(false)` + 建索引失败被 catch，`ArticleSearchService:114-117`），但：
  - 站内搜索**永远静默降级回 `title LIKE`**，没有任何告警，功能「看起来还在」；

### P1-2 时区没有在部署资产中固定（systemd / JVM / MySQL 三处不一致）

**位置**：

- `deploy/blog-system.service:17`：`ExecStart=/usr/bin/java -jar ... --spring.profiles.active=prod` —— 没有 `-Duser.timezone`，也没有 `Environment=TZ=Asia/Shanghai`
- `application.yml:33` / `application-prod.yml:31`：JDBC URL 写了 `serverTimezone=Asia/Shanghai`
- 代码大量使用 JVM 默认时区：
  - `SeckillDailyServiceImpl.java:46-49`：`LocalDate today = LocalDate.now(); ... LocalTime.now().isBefore(daily.getEndTime())`
  - `ArticleSearchService.java:158-160`：`publishedAt.atZone(ZoneId.systemDefault())`
  - 所有 `LocalDateTime.now()` 落库（文章、评论、订单、run、step……）
  - 两个 `@Scheduled(cron = "0 0 3 * * ?")` / `"0 30 3 * * ?"` 清理任务

**上线后的具体表现**（前提：服务器时区不是 Asia/Shanghai，Linux 云主机默认 UTC 很常见）：

- **每日秒杀开场时间错位**：`blog.seckill.daily.start-time: "10:00"`（`application.yml:307-312`，prod 未覆盖，默认开启）在 UTC 机器上等于北京时间 **18:00** 开场；活动的 `LocalDateTime` 也按 UTC 写入，页面显示/窗口判断整体偏 8 小时。
- **所有时间显示偏 8 小时**：`LocalDateTime.now()` 写 UTC，Jackson 序列化成无时区字符串，前端 `new Date(...)` 按浏览器本地时区解释 → 北京用户看到的时间比实际早 8h（或晚 8h，取决于链路）。JWT 的 `expire` 不受影响（用 `Instant`）。
- **凌晨清理任务**在 UTC 机器上变成北京时间 11:00/11:30 执行，可能撞上业务高峰；`notification`/memory 清理失败的影响面扩大。
- JDBC `serverTimezone=Asia/Shanghai` 只影响驱动对 MySQL `TIMESTAMP` 的换算，**救不了** JVM `LocalDateTime.now()` 的偏移，两端反而更容易出现「DB 值 vs 应用值差 8h」。

**修复建议**（三处统一，任选一处固定只会更乱）：

1. systemd 里加：`Environment=TZ=Asia/Shanghai`（最简单，JVM/日志/定时任务全部跟随）；
2. 或 `ExecStart` 的 java 加 `-Duser.timezone=Asia/Shanghai`；
3. MySQL 服务器也同步设置 `default-time-zone='+08:00'`（在 my.cnf 或 init.sql 之外的实例配置里），与 JDBC 参数一致。

**验证**：`curl /api/articles/...` 看 `publishedAt` 与 `date` 是否一致；在服务器 `date` 与 `timedatectl` 确认时区；发一条评论后对比 DB `created_at` 与页面显示。

### P1-3 数据库初始化路径不可靠：账号硬编码 `myRoot`、`init.sql` 不建账号且非幂等、无增量迁移

**位置**：

- `application-prod.yml:31-33`（`application.yml:33-34` 同）：`jdbc:mysql://localhost:3306/blog_system`、`username: myRoot` —— 主机/端口/库名/用户名全部写死，且 **用户名就是本机开发账号**
- `db/init.sql:3`：使用方式 `mysql -u myRoot -p < db/init.sql` —— **依赖 `myRoot` 已存在**，但脚本只 `CREATE DATABASE`（`:31-35`），**不创建用户、不授权**
- `db/init.sql` 的建表语句**不是幂等的**：`:275 CREATE TABLE ai_user_memories (`、`:340 CREATE TABLE ai_workflow_runs (` 没有 `IF NOT EXISTS`
- `db/init.sql` 里还有**裸 `ALTER TABLE`**：`:411-423`（ai_messages 加列+建索引）、`:575-596`（agent token 列、parent_run_id）、`:763-777`（task_plan_json / task_run_id）——补丁式放在建表之后，**在已有库上第二次执行必报 `Duplicate column name` 并以非零退出**（mysql 客户端默认遇错中止，后面的表/列不会执行）
- 迁移机制：`application.yml:255-257` `blog.migration.enabled: false`；`IdMigrationRunner.java:31` 的 `matchIfMissing = true` 被显式关掉；全仓库**没有 Flyway/Liquibase、没有 `db/migration/` 目录、没有版本化 DDL**
- 项目自身约定已登记：「DB schema 变更没有迁移工具（手工执行）」（`AGENTS.md` 的 AI Development Notes）；本次发现的具体新问题是 **init.sql 自身不可重入 + 没有「从 N 版本库升级到 N+1」的脚本/台账**

**上线后的具体表现**：

- **新服务器首次部署**（按资产字面执行）：`mysql -u myRoot -p < db/init.sql` 需要先手工 `CREATE USER 'myRoot'@...` 并授权，否则脚本第一步就 `Access denied`；即便建了账号，生产也在用开发同名的 `myRoot`，权限模型没有收敛。
- **老库升级**：只要这次上线带了新 DDL（本项目几乎每次都有：`plan_json`、`parent_run_id`、`task_step_id`、通知表……），就必须有人凭记忆/翻 `AGENTS.md`/翻设计稿手工挑出该执行的几条 ALTER。**偏偏 `init.sql` 这个"看起来最权威"的脚本不能直接跑**——跑了报 `Duplicate column name`，然后有人加 `--force` 跑完，部分表缺列，运行期才报 `Unknown column`。
- 更糟的是脚本有 828 行、`CREATE TABLE IF NOT EXISTS` 与裸 `CREATE TABLE`/裸 `ALTER` 混排，**新人无法判断哪些是"新建库需要的"、哪些是"老库补丁"**。

**修复建议**（不改业务代码也能做）：

1. 拆成 `db/schema.sql`（新建库专用、可重复执行：全部 `IF NOT EXISTS`）+ `db/migration/YYYYMMDD_xxx.sql`（一次性增量，带台账表 `schema_version`）；
2. 明确「生产 DB 用户名」：`application-prod.yml` 用 `${DB_URL}`/`${DB_USERNAME}` 外置，或至少写死为 `blog_app` 而非开发账号 `myRoot`；
3. 上线清单里固化「比对口径 = 表 + 列 + 索引（含列组合/唯一性/类型）」，不能只看表数（`AGENTS.md` 已踩过两次反向漂移，见 `docs/数据库索引审计.md`）。

**位置**：

### P1-5 systemd 无优雅停机，Spring 也未开 graceful shutdown：发版会砍断进行中的 SSE / 长任务

**位置**：`deploy/blog-system.service:13-27`

```ini
[Service]
Type=simple
User=blog
WorkingDirectory=/opt/blog
ExecStart=/usr/bin/java -jar /opt/blog/blog-system.jar --spring.profiles.active=prod
Restart=always
RestartSec=5
...
StandardOutput=journal
StandardError=journal
```

- 没有 `TimeoutStopSec`、没有 `KillSignal`、没有 `ExecStop`
- `application.yml` / `application-prod.yml` 里没有 `server.shutdown: graceful`，也没有 `spring.lifecycle.timeout-per-shutdown-phase`
- AI 长任务池 `aiTaskExecutor`（`AiTaskAsyncConfig.java:37-50`）没有设置 `setWaitForTasksToCompleteOnShutdown(true)` / `AwaitTerminationSeconds`

**上线后的具体表现**：

- 每次 `systemctl restart blog-system`（这就是当前唯一的发布动作）：进行中的 SSE 连接被**直接切断**，用户看到「连接意外中断」；正在跑的 Agent/Workflow 任务要么半截，要么靠下次启动的恢复逻辑兜（`AiRunStartupRecoveryRunner` 只处理 DB 里遗留的 RUNNING，已消耗的 token / 已预扣的额度要等对账）。
- 长 LLM 调用（单次最多 60s）和准入排队中的任务没有任何 drain 窗口。
- 秒杀消费（`SeckillSettleTask` Stream 消费者）也在同一进程里，重启时未消费完的消息要在下次启动后继续——这一点有对账兜底，但发布期间用户会看到「排队中」卡住。

**修复建议**（部署资产内改）：

```ini
[Service]
KillSignal=SIGTERM
TimeoutStopSec=90
# Spring 侧配套（application-prod.yml）：
# server.shutdown: graceful
# spring.lifecycle.timeout-per-shutdown-phase: 60s
```

若要等 AI 长任务跑完，需要业务侧配置 `aiTaskExecutor` 的优雅关闭（代码改动，优先级可低于 HTTP 层）；至少先让 HTTP 层 graceful，避免普通请求被砍。

### P1-6 前端发布无脚本、无缓存分层：`index.html` 与 hashed assets 同生命周期，半发布 = 白屏

**位置**：

- `blog-system/deploy/nginx.conf:13-25`：`root /var/www/blog;` + `location / { try_files $uri $uri/ /index.html; }`，**没有任何 `expires`/`Cache-Control`**
- `blog-frontend/.gitignore` 忽略 `dist` → 构建产物不入库，靠人工打包上传
- 全仓库**没有前端部署脚本**（无 rsync/scp/发布脚本），也没有回滚脚本；`docs/` 没有部署手册
- 构建产物：`dist/index.html` 引用 `/assets/index-CQyXmOW9.js` 等带 hash 的文件（Vite 默认行为，本地 `dist` 实测）

**上线后的具体表现**：

1. **白屏**：`location /` 的 `try_files ... /index.html` 会把**不存在的 `/assets/old-hash.js` 也返回 index.html（HTTP 200 + text/html）**，浏览器的 `<script type="module">` 直接报 MIME 错误。典型触发场景：
   - 用户浏览器缓存了旧 `index.html`，而服务器已经换上新 dist（旧 hash 文件被删）；
   - 发布过程中先传了 index、后传 assets（或反过来）的非原子窗口。
2. **无缓存收益**：assets 带 hash 却没有任何 `expires`，浏览器每次都回源/重新验证，白丢了强缓存；`index.html` 也没有 `no-cache`，该缓存的没缓存、不该缓存的被启发式缓存。
3. **无回滚**：`/var/www/blog` 只有一份当前版本，出问题只能重新 build + 重新上传，且没有「上一个可用版本」可切。

**修复建议**（部署资产侧）：

```nginx
# 带 hash 的静态资源强缓存
location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
    try_files $uri =404;      # 关键：缺文件返回 404，别回落到 index.html
}

# index.html 不缓存，保证发版立即生效
location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
    expires -1;
}
```

发布流程建议：`dist.new` → `mv dist dist.bak.$(date)` → `mv dist.new dist`（同盘 rename 原子）→ 出问题 `mv dist.bak.* dist` 回滚；上传顺序 assets 先、index 后。

**上线后的具体表现**：

- 即使前面挂了 Cloudflare，**源站 80/8080 仍可能被直连**（IP 就写在 `nginx.conf:11`）。绕过 Nginx 直打 8080 可跳过 Nginx 层任何限制；绕过 CF 直打 80 则看到的是明文 HTTP。

```yaml
# application-prod.yml
server:
  address: 127.0.0.1     # 只让 Nginx 能访问
```

```nginx
# 若确有 Cloudflare 前置
set_real_ip_from 173.245.48.0/20;   # 以及 CF 官方 IP 段
set_real_ip_from 103.21.244.0/22;
# ... 完整列表见 Cloudflare 文档
real_ip_header CF-Connecting-IP;
proxy_set_header CF-Connecting-IP $remote_addr;   # 用 Nginx 校正后的值覆盖客户端头
```

并在安全组/iptables 上只放行 80/443，8080 不对外。

### P1-9 Spring MVC async 超时未显式配置（默认沿用容器默认值，Tomcat 30s）——待实测确认

> **状态说明**：这是**配置缺口确定、后果需要实测确认**的一条。放在 P1 是因为一旦成立，影响面比 Nginx 的 60s 更大（30s 先触发）。

**位置**：

- `application.yml` / `application-prod.yml` 中**没有** `spring.mvc.async.request-timeout`，`WebMvcConfig`（`config/WebMvcConfig.java`）也没有 `configureAsyncSupport`
- 流式入口：`AiController.java:60-63`（Flux + `TEXT_EVENT_STREAM_VALUE`）、`AiWorkflowController.java:55/67/84`

**依据**：Spring Boot 的属性 `spring.mvc.async.request-timeout` 未配置时，异步请求超时「取决于底层 Servlet 容器」（Spring Boot 官方属性说明），Tomcat 默认 async timeout 为 30s；`Flux` 在 Spring MVC 里走 `ReactiveTypeHandler` → `ResponseBodyEmitter`/DeferredResult 异步路径，仍受该超时约束。项目的「首 token / 长回答 / Agent 多步」真实链路里，单次请求从建立到结束超过 30s 是常态（单次 LLM `read-timeout` 已经配到 60s，`application.yml:101-102`）。

**上线后的具体表现（若成立）**：

- 任何超过 30s 的 AI 流（长文章生成、Agent 多步、Workflow 分析/重写）会在 **30s 整**被服务端结束，前端 `ai.ts:858-860` 走「连接意外中断」；用户重试后大概率再次撞上。
- 手测如果只测短问答，这个坑不会暴露，属于典型的「上线后长任务才炸」。

**修复建议**：

```yaml
spring:
  mvc:
    async:
      request-timeout: -1     # 或 300000（5 分钟），按最长 AI 任务定
```

### P2-2 日志文件 + journald 双写；`logs/` 相对路径依赖工作目录权限

**位置**：`application.yml:242-253` + `deploy/blog-system.service:16,25-27`

```yaml
logging:
  file:
    name: logs/blog-system.log
  logback:
    rollingpolicy:
      max-file-size: 50MB
      max-history: 7
      total-size-cap: 1GB
```

- systemd `StandardOutput=journal` 已经把 console 日志收进 journald；Spring Boot 在配置 `logging.file.name` 后**同时**写文件 → 同一份日志写两处

**表现**：磁盘双倍占用（journald 默认按配额滚，logback 按 1GB 滚，两边都不小）；换工作目录即换日志位置；排查时不知道该看 `journalctl` 还是 `/opt/blog/logs/`。

**建议**：prod 关闭 `logging.file.name`（只走 journald），或把 `StandardOutput` 改成 `null` 只留文件；固定 `/var/log/blog-system/` 并写清权限。

### P2-3 systemd 只有 `java -jar`：无堆上限、无 OOM 现场、无 `LimitNOFILE`

**位置**：`deploy/blog-system.service:17`

```ini
ExecStart=/usr/bin/java -jar /opt/blog/blog-system.jar --spring.profiles.active=prod
```

- 没有 `-Xms/-Xmx`（默认堆 = 物理内存 1/4，随机器规格漂移；本项目 Hikari 20 连接 + AI 线程池 8 + ES/Redis 客户端 + 长会话，堆需求与机器规格无关）
- 没有 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...`，OOM 后无法事后定位
- 没有 `-XX:+ExitOnOutOfMemoryError`，OOM 后可能半死不活
- 没有 `LimitNOFILE=65536`（SSE 长连接 + 20 DB 连接 + ES/Redis/LLM 连接，默认 1024 fd 在高并发流式下偏紧）
- 没有指定 `JAVA_HOME`/java 版本检查（`/usr/bin/java` 可能是 8/11，Boot 3 需要 17+）

**建议**：

```ini
Environment=TZ=Asia/Shanghai
Environment=JAVA_OPTS=-Xms512m -Xmx1536m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/opt/blog/logs -XX:+ExitOnOutOfMemoryError
ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/blog/blog-system.jar --spring.profiles.active=prod
LimitNOFILE=65536
```

（`EnvironmentFile` 里的变量不会自动展开到 `ExecStart` 的 `$JAVA_OPTS`，systemd 会展开 `$JAVA_OPTS`，但需确保该变量在同一 unit 的 Environment 中；若放 env 文件，ExecStart 里用 `${JAVA_OPTS}` 需 `EnvironmentFile` 在前——建议直接写在 unit 里，最直观。）

### P2-4 生产继承 dev 演示配置：每日秒杀自动开场、预热管理接口白名单为空

### P2-7 构建工具链未固定：Node 无 engines/.nvmrc、jar 是 SNAPSHOT 且手工改名、mvnw 首次运行依赖外网

**位置**：

- `blog-frontend/package.json:1-33`：没有 `engines` 字段；无 `.nvmrc`；依赖 Vite 8 / TypeScript 6（对本机 Node 版本有要求）
- `pom.xml:13`：`<version>0.0.1-SNAPSHOT</version>`；构建产物名 `blog-system-0.0.1-SNAPSHOT.jar`，而部署目标是 `/opt/blog/blog-system.jar` → 需要人工改名
- `.mvn/wrapper/maven-wrapper.properties`：`distributionType=only-script` + `distributionUrl=https://repo.maven.apache.org/...maven-3.9.16-bin.zip` → `mvnw` 首次运行需要访问 Maven Central（服务器/内网可能不通）
- 前端有 `package-lock.json`（这点是好的），但没有 CI 固定环境

**表现**：换机器构建出来的产物不可保证一致；换人发版容易漏掉「改名」这种手工步骤；内网服务器上 `./mvnw` 可能直接失败。

**建议**：`package.json` 加 `"engines": {"node": ">=20.19"}` + `.nvmrc`；后端用 `finalName` 固定输出名（`<finalName>blog-system</finalName>`）；构建统一在 CI/本地按脚本产出带版本号的 jar。

### P2-8 无探针、无监控、无告警：actuator 只暴露 health，且没有任何地方使用它

**位置**：

- `application.yml:228-240`：只暴露 `health`、`show-details: never`
- `deploy/blog-system.service`：没有 `ExecStartPre` 健康检查、没有 watchdog
- `deploy/nginx.conf`：没有 upstream 主动健康检查（Nginx OSS 也不支持），也没有 `proxy_next_upstream`
- 没有 Prometheus/日志告警/外部 uptime 监控

**表现**：应用挂了/Redis 挂了/ES 挂了，**没有人会收到通知**，只能等用户反馈。`/actuator/health` 虽然存在（本机上 `curl 127.0.0.1:8080/actuator/health` 可用），但没接到任何监控系统；并且 `show-details: never` 意味着 health DOWN 时也看不出是 DB 还是 Redis 还是 ES 的问题。另外 `/actuator/health` 会聚合 DB/Redis（ES 没有 health indicator 依赖），Redis 挂时整体 DOWN，如果将来接 LB 可能误判整机不可用（应用对 Redis 是 fail-open 的）。

**建议**：上线本身不阻塞，但至少：外部 uptime 监控打 `/actuator/health`；日志里 `[PERF-HTTP]` 慢请求做告警；发布后人工检查 `journalctl -u blog-system` 有无 ERROR。

### P2-9 单实例假设没有在部署资产里防呆

**位置**：

- `application.yml:27-30`：`spring.task.scheduling.pool.size: 1`（注释明确「串行调度保证不并发」）

### P2-11 Nginx `server_name` 写死旧服务器 IP，与 env.example 的域名假设矛盾

**位置**：`deploy/nginx.conf:11` `server_name 47.88.86.213;` vs `deploy/blog-system.env.example:19,22` `GITHUB_OAUTH_REDIRECT_URI=https://your-domain/...`、`APP_FRONTEND_URL=https://your-domain`

**表现**：两套资产假设不同的站点形态（IP+HTTP vs 域名+HTTPS）。当前 nginx 只有一个 server 块，所以任何 Host 都会落到它（不带域名的请求也能工作），但：

- 新服务器上线时 `server_name` 是旧 IP，属明显的配置漂移；
- OAuth 回调域名、前端域名、Nginx 域名三者靠人工对齐，任何一个没改都会导致登录跳错（设计稿 `docs/security/sensitive-config-externalization-design.md:315` 记录过同类「线上点 GitHub 登录被跳回用户电脑」的 bug）。

**建议**：把 `server_name` 改成占位符/正式域名并在部署手册里写明三处域名必须一致；用 env/部署参数注入，不写死 IP。

### P2-12 Nginx 缺安全响应头与 `real_ip`（与 01-安全可能重叠）

**位置**：`deploy/nginx.conf` 全文

## 7. 正面结论（避免只报坏消息）

1. **前端 API 地址是对的**：`src/utils/request.ts:89-93` `baseURL: '/api'`；SSE 用相对路径 `fetch('/api/ai/chat/stream')`（`api/ai.ts:743`）；本地 `dist` 里也没有 localhost 残留。部署在同域 Nginx 下无需任何环境变量，**不存在「前端打包进 localhost」的经典上线事故**。
2. **敏感配置外置 + fail-fast 是真做了**：prod 无默认占位符 + `SensitiveConfigStartupValidator` 长度/弱值校验，设计稿还记录了「不配 env 实跑 prod 启动失败」的实测证据。
3. **prod 已关闭 MyBatis SQL 日志**（`application-prod.yml:75` `NoLoggingImpl`），不会把生产 SQL 打到 stdout。
4. **启动对外部依赖是 fail-open 的**：ES 建索引失败只打 error（`ArticleSearchService:114-117`）、秒杀预热失败不挡启动（`SeckillPreheatRunner:36-42`）、AI run 恢复失败不挡启动（`AiRunStartupRecoveryRunner:84-87`）。所以 Redis/ES 挂掉不会让整站起不来——这是好事，**但也意味着这些故障不会大声报错**，必须靠监控（P2-8）。
5. **连接池/线程池参数有实测依据且注释充分**：Hikari 20 vs AI worker 8、`aiTaskExecutor` core==max+AbortPolicy、`spring.task.scheduling.pool.size: 1` 的串行不变量都写清楚了，不是拍脑袋数字。
6. **健康检查端点已存在**且 `show-details: never` 不泄露内部组件信息（`application.yml:228-240`）。
7. **Redis 配置模板质量高**（`deploy/redis.conf.example`）：volatile-lru 的理由、ACL 而非 rename-command、AOF 取舍都写清了，直接合并即可用。
