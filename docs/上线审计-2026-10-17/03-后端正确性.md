## 1. P0 级（上线即踩雷）

**本次审计没有发现 P0。**

在"钱、身份、库存、幂等"四条最容易出 P0 的链路上逐行核对过，最终裁决与幂等都在 DB 侧，不依赖 Redis 或应用内存：

- 钱包 `deduct` 是 `UPDATE ... WHERE user_id=? AND balance>0` 条件更新（`UserWalletMapper:31-39`），流水有 `uk_user_idem (user_id,idempotency_key)` 与 `uk_user_seq`（`db/init.sql:637-638`）；余额变更与流水同事务。
- 充值 `markPaid` 是 `WHERE status='PENDING'` 状态 CAS（`WalletRechargeOrderMapper:24-32`），0 行时用 `SELECT ... FOR UPDATE` 拿已提交快照（`:40-41`），加余额用订单号派生幂等键。
- AI 计费预扣/结算/释放各自带状态 CAS（`AiBillingOrderMapper:27-56`），零消耗走 `release` 而不是 `settle(0)`（`AiRequestBillingSupport:63-106`）。
- 秒杀：库存预留是单条 Lua（`SeckillServiceImpl:64-111`），**最终裁决**是 `UPDATE seckill_activity SET sold_count=sold_count+1 WHERE id=? AND sold_count<total_stock`（`SeckillActivityMapper:27-33`，条件引用列而不是参数），入账与扣库存同事务，账本幂等键由 `(activityId,userId)` 确定性派生（`SeckillSettleServiceImpl:41-93`）。
- 点赞/收藏/关注：唯一键 + `DuplicateKeyException` 兜底 + `like_count = like_count + 1` 原子 SQL（`ArticleLikesServiceImpl:86-103`、`ArticleFavoritesServiceImpl:88-105`、`FollowServiceImpl:68-78`）。
- AI 长任务准入：有界池（core=max=8、queue=32、`AbortPolicy`）+ 每用户上限 2，`submit` 被线程池拒绝时回滚用户名额，worker `finally` 释放名额并清 `UserContext`（`AiTaskAsyncConfig:37-50`、`AiOrchestrationTaskAdmissionImpl:74-148`）。

MyBatis-Plus 3.5.16 的乐观锁行为（反编译 `mybatis-plus-jsqlparser-3.5.16.jar` 的
`PaginationInnerInterceptor` / `mybatis-plus-extension` 的 `OptimisticLockerInnerInterceptor` 确认）：

- `OptimisticLockerInnerInterceptor#doOptimisticLocker` 在版本值**非 null** 时，对 `updateById` 生成
  `... SET version = version+1 ... WHERE id=? AND version=<实体里的值>`（`version` 为 null 时才跳过）。
- 实体里的 `version` 是 **0（非 null）**，所以这里生成的是 `AND version = 0`。

**触发条件**
1. 用户的计划 `learning_plans.version` 已经 > 0。最典型的路径：计划曾经全部勾选完成（`refreshPlanStatus` 把状态改成 COMPLETED，`updateById` 走一次版本 CAS → version 1），或被调整过一次（这条路径第一次成功时也会把 0 写成 1）。
2. 用户再发起一次"调整学习计划"（LEARNING_PROGRESS workflow，`targetPlanId != null`）。

**后果**
- `updateById(plan)` 影响 0 行（`version=0` 对不上），但**返回值没人看**；
- 紧接着旧 `learning_stages` 被删除、新阶段被插入 —— 于是"阶段内容已是新的，计划标题/目标/状态还是旧的"，且没有任何日志或异常；
- 更别扭的是 `status` 永远停在旧值（例如 COMPLETED 的计划调整后仍显示 COMPLETED，直到用户勾选任务触发 `refreshPlanStatus` 才被动纠正；标题/目标则永远不纠正）；
- 这条链路的"重试天然幂等"（`source_workflow_run_id` 唯一键）也被削弱：重试时 `existing` 命中，仍走同一条失败分支。

**为什么测试没抓到**：`LearningProgressWorkflowServiceTests` 里的计划是新建的（version 0），第一次调整 CAS 恰好成功；没有任何用例覆盖"同一计划第二次调整"。

**修复建议**
```java
// 方案 A（最小）：更新分支先把 DB 里的 version 取回来
plan.setVersion(existing.getVersion());
boolean ok = updateById(plan);
if (!ok) {
    throw new IllegalStateException("学习计划已被修改，请重新发起调整");
}
// 方案 B（更稳）：不用整实体 CAS，直接条件更新需要的列：
// lambdaUpdate().eq(id).set(title).set(goal).set(status).set(updatedAt).update()
// 并在计划确实被并发改过时抛错（与 learning_stages 的 CAS 口径一致）
```
同时补一条集成测试：`调整计划 → 再调整一次 → 断言 title/goal/status 与 stages 都是第二次的内容`。

对照：`ArticlesServiceImpl.getArticles`（首页列表）自己做了 `Math.min(pageSize, 50)`（`:203-208`），`NotificationServiceImpl:51-54`、`AgentRunInspectionService:67-70`、`UsersServiceImpl.searchUsers:386-390` 也都做了上限 —— 说明"客户端可控 LIMIT 必须有天花板"是项目已认的口径，**只是上面这批接口漏了**。

**为什么"负数"比"巨大正数"更危险**：MyBatis-Plus 3.5.16 的 `PaginationInnerInterceptor#beforeQuery`
（反编译确认，见 §6 复现命令）在以下条件直接 `return`、**不加 LIMIT**：

```
page.getSize() < 0 && maxLimit == null && 没有 orderBy 追加
```

而 `MybatisPlusConfig.java:14-19` 没有设置 `maxLimit`，所以 `new Page<>(page, -1)` 等价于"查全部"。

**触发条件（任一）**
- `GET /api/articles/hot?pageSize=-1`：热榜 ZSET 为空时（新部署、Redis 被清、`flushdb` 后到下一次重建之间）走 DB 兜底 `lambdaQuery()...page(new Page<>(page,pageSize))`（`ArticlesServiceImpl:1175-1191`），**无 LIMIT 全表取已发布文章**——注意 `select *` 会把 LONGTEXT 正文一起读进内存（VO 层才剥离，DB 层没剥）。
- `GET /api/articles/1/comments?pageSize=-1`：主评论全量加载（含每条 content），再走缓存写入（`saveCommentListToCache`）→ Redis 里再存一份整页 JSON。
- 任意上述接口 `pageSize=1000000` / `page=1`：LIMIT 1000000 实际等于全表，同样把 DB 与响应体打满。

**后果**
- 单个匿名请求即可把 Tomcat 线程占在"大查询 + 大 JSON 序列化 + Redis 大 value 写入"上；文章/评论量越大越接近 OOM；
- `getHotArticles` 还有 `long start = (page-1)*pageSize`，`page`/`pageSize` 极大时 `long` 乘法溢出成负数，`reverseRange(negative...)` 的语义变成"从末尾倒着取"，返回集合大小不可控；
- 评论列表缓存 key 里带 `pageSize`（`CommentsServiceImpl:406-413`），攻击者可以用任意 `pageSize` 值生成大量缓存 key（TTL 3 分钟），属于顺带的 Redis 内存放大面。

**修复建议**
- 统一一个 `PageSizeSupport.cap(pageSize, defaultSize, max=50)`（或直接在 Controller 上加 `@Max(50)`，但注意项目 `@Valid` 只覆盖了用户模块）；
- `getHotArticles` 的 DB 兜底改用固定 `LIMIT`，且只 `select` 需要的列（见 P2-3）；
- `getComments` 的缓存 key 用 cap 之后的值；
- 抽查命令：`curl 'http://host/api/articles/hot?pageSize=-1'`，修复前后看响应条数与 DB `SHOW PROCESSLIST`。

### P1-3 评论点赞计数是"读-改-写"，并发丢更新且可减成负数

**文件**：`blog-system/src/main/java/com/hailin/blogsystem/service/impl/LikeCommentsServiceImpl.java:28-89`

**代码证据**

```java
// :30-49 likeComment
CommentLikes one = lambdaQuery().eq(commentId).eq(userId).one();   // 重复检查
if(one != null) throw ...;
ArticleComments comment = commentsMapper.selectById(commentId);    // ← 读出旧值
comment.setLikeCount(comment.getLikeCount() + 1);                  // ← 内存 +1
commentsMapper.updateById(comment);                                // ← 整行写回（无 version/无条件）
...
save(commentLikes);
```

```java
// :72-83 cancelLike
boolean remove = removeById(lambdaQuery()...one());
if(remove){
    ArticleComments comment = commentsMapper.selectById(commentId);
    comment.setLikeCount(comment.getLikeCount() - 1);              // ← 没有 GREATEST 下限
    commentsMapper.updateById(comment);
}
```

**触发条件**
- 一条评论被两个用户同时点赞（热评、活动/文章发布后集中访问），两个事务都读到 `like_count=N`，各自写 `N+1` → 最终 `N+1` 而不是 `N+2`（InnoDB 行锁只保证两次 UPDATE 串行，不保证读到的值不旧）。
- `cancelLike` 并发/重复：`like_count` 可被减到负数（对比文章点赞用了 `GREATEST(like_count-1,0)`，`ArticleLikesServiceImpl:187-190`）。
- `updateById(comment)` 是**全实体非空字段覆盖**：除了 `like_count`，还会把读到的 `content / user_id / created_at` 等原样写回——若评论内容在并发中被编辑（当前没有编辑入口，但 `deleted_at` 软删是有的），存在"用旧快照覆盖新状态"的理论窗口。

**后果**
- 评论点赞数永久性偏小/为负，且没有任何对账任务能发现（`comment_likes` 行数与 `like_count` 没有一致性巡检）；
- 评论列表 `sort=hot` 按 `like_count` 排序（`CommentsServiceImpl:80`），错值会直接改变热门排序；
- 删除评论软删时不回收 `comment_likes`，行数只会更偏离。

**修复建议**
```sql
-- 与文章点赞同一套口径：原子 SQL + 下限
UPDATE article_comments SET like_count = like_count + 1 WHERE id = #{id}
UPDATE article_comments SET like_count = GREATEST(like_count - 1, 0) WHERE id = #{id}
```
配 `@Transactional` 的前提下，先 `insert comment_likes`（唯一键防重）成功后再 `+1`，失败分支按 `DuplicateKeyException` 幂等返回；顺手补一条"评论存在性校验"（现在 `selectById` 返回 null 会直接 NPE → 500）。

### P2-2 唯一的调度线程会被网络/LLM 长任务堵住（"2 秒一轮"的秒杀消费者被牵连）

`spring.task.scheduling.pool.size: 1`（`application.yml:27-30`）是项目刻意维持的不变量，大量注释都在依赖它。但同一条线程上挂了 3 处**可能长达几十秒**的工作：

1. **RAG canary 健康探针**：`ArticleRagIndexHealthService.inspect()`（`:40-66`，`@Scheduled(initialDelay=1s, fixedDelay=5min)`）→ `canary.probe(vectorStore)`（`ArticleRagCanary:34-64`）→ `VectorStore.similaritySearch(...)`，即**一次 embedding HTTP + 一次 ES 查询**；Spring AI 的 embedding 走 `spring.ai.openai.read-timeout: 60s`（`application.yml:101-102`）。供应商抖动时，这条探针可以把唯一的调度线程按住最长 60 秒。
2. **RAG 重试投递**：`RagRetryTask.drainRetryQueue()`（`:35-47`）调用 `articleRagSyncService.retryFromQueue`，而 `articleRagTaskExecutor` 的拒绝策略是 **`CallerRunsPolicy`**（`ArticleRagAsyncConfig:28`）。队列（100）+ 4 个 worker 都满时，RAG 同步（embedding + ES，可能几十秒）会**在调度线程上内联执行**——`RagRetryTask` 的类注释还写着"本方法立刻返回，重试在独立线程池里跑"，饱和时这个前提不成立。
3. **5b 巡检补偿**：`TaskHandoffReconciliationTask.reconcile()`（`:54-58`，60 秒一轮）→ `TaskWorkflowContinuationService.onWorkflowAdvanced` → `resumeRemaining`（`:128-160`）→ `TaskOrchestrationService.resume`（`:188`）→ 剩余步骤**同步**在当前线程执行。剩余步骤里可能有 `ARTICLE_ANALYSIS`（LLM，`TaskOrchestrationService` 的步骤执行器），而这条路径**没有经过 AI 长任务准入**（不同于 `WorkflowHandoffExecutor` 在已准入的 worker 里跑）。

**后果**：调度线程被按住期间，`SeckillSettleTask`（2 秒一轮，`SeckillSettleTask:90`）停止消费 → 已"抢占成功"的用户一直显示"排队中"；`SeckillLifecycleTask`（5 秒，`:39`）停止 → 到点不开始/不结束；`ArticleViewCountSyncTask`（30 秒，`:23`）与 `RagRetryTask`（60 秒）顺延。不是数据丢失，但"上线后偶发几十秒的秒杀延迟/排队中"，且日志上很难指向根因。
**修复建议**：
- canary 探针改挂在 `articleRagTaskExecutor`（或独立单线程池）上跑，`@Scheduled` 只负责投递；
- `articleRagTaskExecutor` 的 `CallerRunsPolicy` 改成 `AbortPolicy` + 记日志（重试队列里还有失败标记兜底，丢弃一次不影响最终一致）；
- 5b 巡检的续跑改为"投递到 aiTaskExecutor（走 `admission.submit`）"，巡检线程只做 DB 扫描与 CAS。
