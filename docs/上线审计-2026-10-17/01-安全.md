## 0. 结论速览

### 0.1 最重要的三句话

1. **没有发现「未登录即可直读他人私密数据」的接口漏洞。** 逐个核对 29 个 Controller（134 个映射）后确认：文章隐藏/草稿、AI 会话、Agent run、Workflow、长期记忆、学习计划、钱包订单、通知、上传等敏感数据都有 owner 过滤，AI 的读路径（QA 会话锚、文章工具、RAG）也只读「已发布或本人」。JWT 本身（HS256 手工验签 + jti 黑名单 + token_version 代次）设计正确。
2. **真正会被公网利用的是「不存在写权限边界」的那几个匿名入口 + 成本入口**：游客 AI 不收钱、ip 限流可被伪造头绕过、公开分页接口可被当成 Redis/内存放大器、匿名 share 可写库。这些不偷数据，但**上线第一天就能被拿来烧钱、刷库、打挂 Redis**。
3. **一个部署事故级别的隐患**：整套生产安全默认值依赖 `--spring.profiles.active=prod` 被正确传入；漏传时 JWT 密钥就是仓库里的公开开发值，任何人都能伪造任意用户身份。代码对此**不做拦截**（只有 prod profile 下才拒绝开发默认值），详见 P1-3。

**攻击链（两条，任一条成立即可）**

1. **直接绕过 IP 配额**：源站可直连时（02-P1-8 已确认「Nginx 监听公网 IP、后端监听 0.0.0.0、无源站访问限制」），攻击者不走 Cloudflare，直接 `curl` 源站并每次换 `CF-Connecting-IP: 1.2.3.N`（或 `X-Forwarded-For`，因为 `nginx.conf:32` 只是 `$http_cf_connecting_ip` 透传、`:35` 把客户端 XFF 放在最左）。每次都是新「IP」→ 5 次/分钟永远打不满 → **无限次调用 `/api/ai/chat/stream`**，每次输出上限 4000 token（`application.yml:375`），成本完全由站方承担。
2. **前端既有 bug 顺带白嫖**：`05-前端.md` F-01 —— 不勾「记住我」的登录用户 SSE 请求不带 token，后端按游客处理 → **已登录用户静默走不计费路径**。这条不需要伪造头，只要用户不勾记住我（登录页默认勾选，取消即命中）。

**后果**：阿里云百炼账单失控；被当成免费 OpenAI 兼容代理转卖；配合游客可用的 RAG/文章检索，还能放大 ES 与 embedding 调用量。这是「上线即被利用」的定义。

**修复建议（按性价比排序）**

1. 上线前把源站锁到 Cloudflare IP 段（防火墙/安全组），并在 nginx 用 `real_ip` 模块 + `set_real_ip_from <CF 段>`，把 `CF-Connecting-IP` 改为由 nginx 依据可信来源写入；后端 `ClientIpUtils` 只信任可信代理链（或改用 Spring `server.forward-headers-strategy=native` + `ForwardedHeaderFilter`），**不再直接读客户端头**。—— 这一条同时修掉 P1 里 IP 可伪造的整类问题（与 02-P1-8 同源）。
2. 游客 AI 增加**服务端硬配额**：`(IP, 天)` + **全局日预算**（如「游客每日累计 X credit / 每小时 Y 次」），超过即拒绝或降级到最便宜模型；不要只靠「5 次/分钟」这种可绕过的速率限制。
3. 给 `/api/ai/chat/stream` 的游客分支加「会话/轮次」上限（AGENTS.md 里「游客临时会话次数限制（暂缓）」建议上线前至少做全局兜底）。
4. 修复 05-F-01 的 token 读取（SSE 也读两个 storage），避免登录用户落进游客不计费路径。
5. 加账单告警：按小时统计游客 token 消耗，超过阈值自动关闭游客入口（配置开关）。

**关键行为取证（为什么负数更糟）**

`PaginationInnerInterceptor` 在 `size < 0` 且未配置 `maxLimit` 时**直接 return，不拼 LIMIT**（即返回全表）。本报告通过反编译本地仓库 `mybatis-plus-jsqlparser-3.5.16.jar` 的 `PaginationInnerInterceptor#beforeQuery` 确认：字节码先取 `IPage.getSize()` 与 0 做 `lcmp`，`size < 0` 且 `maxLimit == null` 时返回（跳过 `buildPaginationSql`）。`MybatisPlusConfig:16` 没有 `setMaxLimit`，因此该分支在线上可用。

**攻击方式（无需登录）**

```bash

#    article_comments 无单篇上限；pageSize 越大 value 越大）
curl 'https://<site>/api/articles/<articleId>/comments?pageSize=1000000'

# 2) 换不同的 pageSize/page 组合 → 每次生成一个新的 comment:list:* key
#    （TTL 仅 3 分钟，持续循环即可把 Redis 内存顶到 OOM）
for n in 100 200 500 1000 2000 5000 10000 ...; do
  curl "https://<site>/api/articles/<articleId>/comments?pageSize=$n" &
done

# 3) 负数直接跳过分页 → 全表扫
curl 'https://<site>/api/articles/<articleId>/comments?pageSize=-1'
curl 'https://<site>/api/articles/hot?pageSize=-1'
```

补充放大器：`CommentsServiceImpl.getComments` 对结果做 `fillUserInfo`（`selectBatchIds` 大 `IN`，`:465-483`）、`getComments` 还会把结果 JSON 全量序列化。Redis 同时承载限流、token 黑名单、token 代次、分布式锁、缓存——**Redis 被打爆 = 全站安全防护一起失效**（限流 fail-open/异常、黑名单查不到等），比单个接口 500 严重。

**修复建议**

1. 所有公开接口统一 clamp：`page = max(1, min(page, 1000))`、`pageSize = max(1, min(pageSize, 50))`（负数/0 一律按默认值）。
2. `MybatisPlusConfig` 给 `PaginationInnerInterceptor` 设 `setMaxLimit(100L)`（兜底所有漏改的接口）。
3. 评论列表缓存**只缓存默认参数组合**（`page=1 && pageSize==20`），其余不缓存；或从 key 中去掉 pageSize（只缓存固定大小），避免 key 基数由客户端控制。
4. 公开列表接口加轻量限流（可复用 `AiRateLimiter` 的 INCR+EXPIRE，按「接口桶 + IP」）。
5. `getPublicUserCommented`（P1-4）改成 SQL 分页，不要 `selectList` 全量后内存切页。

只要服务曾以非 prod 方式启动（运维手动 `java -jar blog-system.jar`、新机器 systemd 复制漏参数、Docker 化时忘传 `SPRING_PROFILES_ACTIVE`），该 token 对 `JwtInterceptor` 完全有效（它只验签名/过期/黑名单/代次），即可**冒充任意用户**：读/写其文章与草稿、AI 会话与记忆、调用 Workflow approve/写动作确认、充值与秒杀（钱包归属按 token 里的 userId）、`/api/users/me` 全部数据。同时 `/api/dev/mail/check` 变成免费匿名发信机（钓鱼/邮件轰炸）。另外 prod 漏配时 `mybatis-plus.log-impl` 仍是 StdOut，SQL 含参数写满 stdout（日志泄漏面）。

**修复建议（防御纵深）**

1. 启动包装：systemd/Docker/部署脚本统一 `Environment=SPRING_PROFILES_ACTIVE=prod`，并在应用里校验「非 dev 环境必须显式声明」——例如 `SensitiveConfigStartupValidator` 改成：**只有显式 `BLOG_ENV=dev` 才允许弱默认值，未声明/未识别环境一律拒绝**（把安全默认从「prod 才拒绝」翻成「非 dev 才拒绝」）。
2. 更好的做法：把开发默认值从 `application.yml` 移出（放 `application-dev.yml`），`spring.profiles.default` 设为空要求显式 profile，从根上消灭「公开 secret 有默认值」。
3. 把 `MailCheckController` 的 `@Profile("!prod")` 收紧成 `@Profile("dev")`（现在是「不是 prod 就开」，语义太宽）。
4. 上线前轮换一次 `JWT_SECRET`（即使配置正确，仓库里的 dev 值人尽皆知；历史 token 也会因此全部失效，成本低）。

> 与 02 报告的关系：02 只从「部署资产」角度确认 systemd 带 prod；本报告给的是**漏配时的安全后果与代码级 fail-open 证据**，不重复计数。

### P1-3 GitHub OAuth 回跳把 7 天有效期的 JWT 放在 URL query 里 ⇒ 进 access log / 浏览器历史即可被拿走来冒充用户

**位置**

- 后端 302 拼接 token：`blog-system/src/main/java/com/hailin/blogsystem/controller/OAuthController.java:49-50`
- token 有效期：`blog-system/src/main/java/com/hailin/blogsystem/utils/JwtUtil.java:47`（`EXPIRE_TIME = Duration.ofDays(7)`），OAuth 回调签的是默认 TTL（`GitHubOAuthServiceImpl.java:146`）
- 前端从 query 取 token：`blog-frontend/src/views/AuthCallbackView.vue:22`
- nginx 未自定义 `log_format` / 未过滤 query：`blog-system/deploy/nginx.conf`（无 `access_log`/`log_format` 指令，默认 combined 会记录完整 `$request`，含 query string）

**代码证据**

```java

response.sendRedirect(frontendUrl + "/auth/github/callback?token=" + token);
```

```vue

```

**攻击 / 泄露路径**

1. **Nginx / Cloudflare access log 明文记录**：浏览器请求前端回调页时，URL 带 `?token=<JWT>`，默认日志格式会把它写进 `/var/log/nginx/access.log`（以及 CF/日志采集系统）。任何拿到日志的人（运维、日志平台、被入侵的主机、外包）都能用它在 7 天内冒充该用户；token 无 jti 撤销记录，除非用户主动登出或改密，否则**无法作废**。
2. 浏览器历史/录屏/共享 URL：弹窗场景 `window.close()` 前该 URL 已在历史中；非弹窗场景虽然 `location.replace('/')` 会覆盖，但网络代理、企业 TLS 网关、URL 监控类扩展仍会记录。
3. 与 `05-前端.md` F-13 同源（05 已按 P2 报）。**本报告建议提级到 P1**：F-13 只强调浏览器侧；这里补的证据是「JWT 是 7 天长效凭证，且必然进入服务端访问日志」——这是服务端日志侧的密钥泄露，不是 UI 细节。

**修复建议**

1. 改一次性短期 code：OAuth 回调只带 `?code=<32B 随机>`（Redis 5 分钟、`GETDEL` 一次性消费），前端用 `POST /api/auth/oauth/exchange` 换 token（响应体返回，不落 URL）。工作量 1 个接口 + 前端 1 处。
2. 过渡期最少：nginx `log_format` 对 `$request` 做过滤/不记录该路径 query；前端取到 token 后立刻 `history.replaceState` 去掉 query（只能减历史，不能减日志）。
3. 给 OAuth 签发的 token 更短 TTL（如 24h），减少泄露后的可用窗口。

## 6. 审计覆盖与「未发现问题」的证据（避免误以为漏查）

### 6.1 认证/授权接线核对（29 个 Controller / 134 个映射）

- 拦截器只「拦列出的路径」，不在清单里的接口等于公开。逐个核对后：**需要身份的数据接口全部在清单内**，且敏感 Service 有 owner 过滤：
  - `/api/users/me/**`（含头像/图片上传、通知）、`/api/comments/**`、`/api/articles/*/like|favorite`、`/api/users/*/follow`、`/api/learning-plans/**`、`/api/wallet/**`、`/api/seckill/**`、`/api/ai/**`（除 chat/stream）→ JwtInterceptor。
  - 公开接口（articles 读、users 公开主页/搜索、categories/tags、stats、auth/**、seckill activities、dev/mail 仅非 prod）均按产品语义放行；其中 `/api/articles/{id}/comments` POST 虽然只挂可选鉴权，但 Controller 层有 `UserContext == null → LOGIN_FAILED`（`CommentsController.java:41-44`），不构成匿名写。
- IDOR 抽查（均有 owner/可见性过滤，未发现可读他人私密数据）：
  `AiSessionServiceImpl.deleteSession`（`:94-104` 带 user_id）、`AiMessageServiceImpl.getMessages`（`:143-159`）、`streamUserChat` 的 `getOwnedSession`（`:266-270`）、`WorkflowRunManager.getOwnedRun`（`:40-54`）、`AiWorkflowRunServiceImpl.getWorkflowRun/cancel/listStepLogs/approve/reject/retry`（`:388-692` 全部先取 owned run）、`AgentRunInspectionService.getDetail/listSteps/listRawSteps/getDevDetail`（`:49-114`，`:344-355` 归属校验）、`AgentRunSuggestionService`（`:421-444`）、`AgentWriteActionService`（`:209-224`）、`AiUserMemoryServiceImpl.updateMemoryById/disableMemory`（`:128-177`）、`AiEpisodicMemoryServiceImpl.deleteMemory`（`:148-168`）、`AiUserMemoryCandidateServiceImpl.confirm/reject`（`:58-106`）、`AiConversationSummaryServiceImpl.getSummaryStatus`（`:178-189`）、`LearningPlansServiceImpl` 全写路径（`:76,107,144,259,435,565,617`）、`WalletRechargeServiceImpl.pay`（`:165-178` 归属校验）、`SeckillServiceImpl.getResult`（`:238-239` 按 userId+activityId）、`CommentsServiceImpl.deleteComment`（`:324-341` 评论者或文章作者）。
  - 文章隐藏/草稿：`ArticlesServiceImpl.getArticleDetailFromDb`（`:1561-1590`）只有 PUBLISHED 或作者本人可见；详情缓存的「不可见空值缓存」也按身份区分（`:604-637`）。
  - AI 读路径：`ArticleSessionAnchorService.isReadable`（`:140-149`，他人非公开不可读）、`ArticleQaTargetResolver.resolvePageCandidate`（`:161-176`，加载即校验）、`AiArticleTools`（`:32-71`，只查 PUBLISHED）。RAG 索引只建 PUBLISHED（`ArticleRagIndexService.java:99,161`）。
- 注入：全仓无 XML mapper；`${` 在 `src/main` 下 **0 命中**；MyBatis 注解 SQL 全部 `#{}` 参数化；`setSql` 拼接处只有整数/常量（`comment_count + n`、`view_count + n`）。ES 查询用 Java DSL + 参数化（`ArticleSearchService.java:224-265`），高亮 `<em>` 前端过 DOMPurify。LIKE 走参数化（`UsersServiceImpl.searchUsers:405-412`）——无 SQL 注入。

- OAuth：state 校验已实现且 fail-closed；「按已验证主邮箱绑定已有账号」只认 `primary && verified`（`GitHubOAuthServiceImpl.java:218-248`），无账号接管路径。
