# 站内搜索：LIKE 全表扫描 → ES 全文检索

> 状态：✅ **已实施**（2026-09-19）· 实施记录与踩坑见 §9
> 关联：[`capability-audit-2026-08-06.md`](../capability-audit-2026-08-06.md) §3（ES 能力缺口清单）

## 0. 一句话

首页搜索现在是 `title LIKE '%kw%'`——**前置通配用不上索引**（全表扫描）、**只搜标题**、
**没有相关性排序**。本刀把它换成 ES 全文检索（IK 分词 + 多字段权重 + 高亮），
**ES 不可用时降级回原来的 LIKE**。

## 1. 现状

`ArticlesServiceImpl.getArticles()`（:180-187）：

```java
lambdaQuery()
    .eq(Articles::getStatus, PUBLISHED)
    .like(normalizedKeyword != null, Articles::getTitle, normalizedKeyword)  // ← title LIKE '%kw%'
    .eq(categoryId != null, Articles::getCategoryId, categoryId)
    .orderByDesc(...)          // 只有「热度」或「时间」两档
    .page(...)
```

三个问题：

| 问题 | 后果 |
|---|---|
| 前置通配 `%kw%` | **索引失效，全表扫描**；数据量一上来就慢 |
| 只匹配 `title` | 正文里明明有答案却搜不到 |
| 无相关性排序 | 命中的文章只能按时间/浏览量排，跟关键词无关 |

## 2. 先说清楚：这和 RAG 检索是什么关系

**必须先回答这个**，否则很容易被当成「同一件事做两遍」（这个质疑提得对）：

| | **站内搜索** | **RAG 检索** |
|---|---|---|
| 给谁看 | **人** | **LLM** |
| 目标函数 | **相关性**（排序 + 高亮 + 分页） | **召回率**（宁可多给，后面有 rerank 兜） |
| 文档粒度 | **文章级** | **chunk 级** |
| 输出 | 文章列表 | 拼进 prompt 的片段 |
| 参数取向 | topK 大、要翻页 | topK 小（prompt 长度有限）、不要高亮 |

**所以两者的定位是**：

- **复用的**：ES 基础设施、同一份文章数据、分词/停用词这些已有经验
- **不复用的**：**索引**（粒度不同 → 强行走一个索引要不停做 chunk→文章的聚合去重，
  RAG 那边其实已经在按 `articleId` 去重了，那就是混用的代价）、**查询编排**（目标不同）

一句话：**同一份内容、两套索引，因为一个服务人、一个服务模型。**

## 3. 索引设计

**新建独立索引 `article_search_index`** —— 文章级文档：

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | text, ik_max_word | 权重最高（^3） |
| `summary` | text, ik_max_word | 权重次之（^2） |
| `content` | text, ik_max_word | 正文，权重 ^1 |
| `categoryId` | keyword | 分类过滤 |
| `authorId` | keyword | 预留（按作者筛选） |
| `status` | **keyword** | **检索期过滤用**（见 §4） |
| `publishedAt` | date | 「最新」排序 |
| `viewCount` | long | 「最热」排序 |

**为什么单独建索引**：见 §2 表格最后一行。核心是 **mapping 的控制权**——
RAG 那个索引的 mapping 由 Spring AI 自动创建（只显式映射了 `embedding`，`content` 走动态映射
→ 默认 standard analyzer，**中文按单字切**），想加 IK 必须先接管它的索引创建，耦合太深。

## 4. 检索期必须过滤 `PUBLISHED`（越权风险）

**不能只靠索引期约束。**

RAG 那边是「只索引已发布文章」——但索引同步是 `@Async` + 延迟队列重试的，
**存在延迟窗口**：文章刚被设为隐藏，索引还没删掉，这期间搜得到 → **用户看到了他不该看到的文章**。

搜索面向用户，**必须双保险**：索引期保证绝大多数的正确性，**检索期用 `status` term filter 兜底**。

> `status` 用的是 **keyword**（不是 text）——term 查询要精确匹配，分词过的字段查不准。

## 5. 降级：ES 挂了回落到 LIKE

现在那套 `LIKE` 实现**不删除**，它变成 **fallback**：

```
keyword 非空 → ES 检索
                 ├─ ES 正常 → 返回结果（带高亮）
                 └─ ES 异常 / 超时 → log.warn + 回落 LIKE
keyword 为空 → 现有 DB + 缓存逻辑（完全不动）
```

**ES 是加速器，不是唯一真相**——这个定位要写进注释，避免后来人把 LIKE 分支当死代码删掉。

## 6. IK 分词器（**需决策**）

现状：**ES 里一个插件都没装**（`_cat/plugins` 为空），`analysis-ik` 需要**单独安装**。

装它的成本（已实测确认，不是估算）：

```bash
docker exec blog-es bin/elasticsearch-plugin install \
  https://github.com/medcl/elasticsearch-analysis-ik/releases/download/v8.13.4/elasticsearch-analysis-ik-8.13.4.zip
docker restart blog-es
```

- ✅ 容器 **Ubuntu 20.04**、**能连 GitHub**（都实测过）
- ✅ **插件目录是独立卷**（`blog-es-plugins`）→ 插件持久化，重建容器也不丢
- ⚠️ 代价：ES 重启几秒（期间 RAG 检索短暂不可用）

**不装的替代**：用内置 `ngram` tokenizer 做 2-gram（和项目里规则 rerank 的切词方式同档）——
能用，但「秒杀」这类词会被切成「秒杀/杀」这种粒度，召回质量明显弱于 IK。

**建议装**：中文分词质量是搜索效果的决定性因素，且这是面试高频题（「ES 中文怎么做」）。

## 7. 范围

**做**：
1. 新建 `article_search_index` + mapping（需要**接管索引创建**，不再依赖 Spring AI 自动建）
2. 索引同步（复用 `ArticleRagSyncService` 的 **异步 + 重试**模式，但独立一条链路）
3. 查询：`multi_match`（title^3 / summary^2 / content）+ `status` filter + 高亮 + 分页 + 三级排序
4. **按 ES 相关性顺序重排 DB 结果**（`IN (...)` 查出来的顺序是不保证的，这是个经典坑）
5. 降级回 LIKE
6. `/actuator/health` 里带上 ES 状态（**ES 挂了要能一眼看出来**，否则降级是静默的）

**不做（登记）**：
- **同义词**（低优先级，「秒杀↔抢购」这类当前靠语义检索能覆盖）
- **搜索建议 / 自动补全**（未要求）
- **RAG 那边的 keyword 检索不动**（它也吃 standard analyzer 的亏，但改它属于另一条线）
- **ILM**（数据量不大）

## 8. 验证

| 项 | 怎么验 |
|---|---|
| 中文分词 | 建好索引后用 `_analyze` API 看「秒杀」等词被切成什么 |
| 检索正确性 | 对比改造前后同一关键词的结果（**新实现应该召回更多、且正文命中也能搜到**） |
| 越权 | 把一篇文章设为隐藏，**立刻**搜它 → 不应出现在结果里（验的是检索期过滤，不是索引期） |
| 降级 | 停掉 ES 容器 → 搜索应回落到 LIKE 且**不报错** |
| 性能 | 同样关键词对比 `LIKE` 与 ES 的耗时（数据量小的时候差异不明显，可堆数据） |

## 9. 实施记录（2026-09-19）

### 9.1 `multi_match` 默认是 **OR** 语义，导致召回过宽（实测发现）

第一次验证搜「建造者」返回了 **17 条**，看着像「相关文章就是多」。但看**高亮片段**才发现问题：

```
【Java中的@Builder注解详解：优雅创建对象的建造者模式】
   ...优雅创建对象的<em>建造</em><em>者</em>模式      ← 真正命中

【MySQL 核心机制与工程实战：面向进阶开发者的深度解析】
   ...面向进阶开发<em>者</em>的深度解析                ← 只命中了「者」
```

「建造者」分词后是 `建造 | 者`，**OR 语义下命中任一个词就算匹配**，
于是「开发**者**」把所有带这三个字的文章都捞了进来。

**修**：显式 `.operator(Operator.And)` —— 站内搜索要的是「用户搜的词都出现在文章里」。

> 这个坑**靠看条数是发现不了的**（17 条看起来很正常），**是 highlight 把它暴露出来的**。
> 反过来也说明：高亮不只是展示功能，还是个**排查工具**。

**为什么不用 `match_phrase`（要求词相邻）**：那样更精确，但会漏掉「Redis 的缓存」这类
「词都在、只是不相邻」的正常表达。**AND 是召回与精度的折中。**

剩下的一点模糊来自**分词器词库**而非查询：IK 把「建造者」切成 `建造 | 者`
（词库里没收录「建造者」），所以 AND 实际是「这两个词都在」而不是「建造者连在一起」——
搜「建造者」仍会带出正文同时含「建造」「者」的文章。
**真要根治走 IK 自定义词典**（把「建造者」加进去），不是把查询改得更严。

### 9.2 索引初始化：建索引（幂等）+ **仅当为空时**灌全量

每次启动都全量重建，文章一多启动就慢得没法忍；而**只在索引为空时灌**，
覆盖的正是「首次部署 / 清空 ES 之后」这个真会遇到的场景——
否则搜索会**静默地什么都搜不到**（索引是空的，但没有任何报错，看起来像功能坏了）。

### 9.4 高亮一直没进页面（2026-10-11 补）

§9.1 说"高亮不只是展示功能，还是个排查工具"——结果它一年多没展示过。

后端从上线起就把高亮算好、透出到 `ArticleDetailVO.highlight` 了，但**前端从来没人读**：
`ArticleCard` 渲染的是纯文本 `{{ article.title }}`，`types/article.ts` 里连字段都没声明。
所以数据一路算到网络上，就是没进页面。

补的时候发现后端还有第二个问题：`firstHighlight()` 按 **摘要 → 正文 → 标题** 只取第一个非空片段。
于是关键词**只命中标题**时，返回的片段取自不含关键词的摘要，而真正该亮的标题反倒没有数据可用。

**改法（两条一起修）**：

- 后端拆成两处返回：`SearchHits.Highlight(title, fragment)` → VO 的 `highlightTitle` + `highlight`。
  注意 ES 那边三个字段的高亮**本来就都返回了**（`highlight.fields("title"…)` 早就配了），
  丢的是 Java 侧这一层——所以**检索行为零变化、不需要重建索引**。
- 前端：标题/摘要按高亮数据条件渲染。**必须过 `sanitizeHtml`**——ES 不转义源文本，
  文章正文里的 `<img onerror=…>` 会直接进 `v-html`（存储型 XSS）。
  没高亮时保持原来的纯文本渲染，**不让 `v-html` 出现在列表热路径上**（`ArticleCard` 同时被首页和用户主页复用）。
- 兜底：ES 挂了会降级回 LIKE，那时后端一个高亮都没有 → `utils/highlight.ts` 做本地纯文本高亮。
  它只匹配"查询串原样连续出现"，中文多词查询（搜「缓存穿透」命中标题「缓存与穿透」）仍得靠 ES 分词高亮，
  **不要在前端做二次分词**——那会造出第二套与检索不一致的匹配逻辑。

**真实索引实测**（`article_search_index`，31 篇）：

| 关键词 | 命中总数 | 抽样（每词取前 5 条）中带 title 高亮的 |
|---|---|---|
| Redis | 8 | 3 |
| 缓存 | 12 | 2 |
| 秒杀 | 5 | 1 |

左边这些 title 高亮**改造前全部被丢弃**——这就是"标题永远亮不起来"的直接原因。
另外注意：多数命中的标题里其实没有关键词（词在正文），那几条标题不该亮、只亮摘要行的正文片段，属正确行为。

**未做（登记）**：搜索时切"推荐 / 最新"仍无效——`sort` 没接进 ES 排序数组（见 §7 与 `ArticleSearchService.search` 的注释），
接线会改游标段数（现在是 `score|articleId` 两段），属于独立的一刀。
