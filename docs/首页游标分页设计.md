# 首页游标分页（keyset）设计

> 状态：✅ 已实施（2026-10-09）
> 涉及：`ArticlesService#getArticles`、`ArticleSearchService#search`、`PageVO`、`CursorCodec`、`HomeView.vue`、`db/init.sql`

## 1. 问题：交互形态和分页算法不匹配

首页是**无限滚动**（IntersectionObserver 触底加载），后端却是 offset 分页：

```sql
ORDER BY view_count DESC, id DESC LIMIT (page-1)*10, 10
```

这两件事天生冲突：**滚动这个交互的目的就是让用户一直往下滑，而 offset 分页恰恰是"越往下滑越慢"**。
但它一直没暴露，因为本地只有 24 篇已发布文章——`LIMIT 1000,10` 和 `LIMIT 0,10` 的执行计划一模一样。

另外默认排序 `recommend` 连索引都没吃到：`ORDER BY view_count` 用不上当时那条
`(status, published_at)` 复合索引，实测 `Using filesort`。

## 2. 选型：为什么是游标，不是延迟关联

八股通常把两类方案并列，但它们不在一个层次上：

| | 扫描行数 | 每行代价 | 能跳页 |
|---|---|---|---|
| 游标 / keyset | `O(log N + size)` | — | ❌ |
| 延迟关联（子查询 + 主键索引） | **仍是 `O(offset)`** | 从"数据页"降到"索引项" | ✅ |

延迟关联**没有消除 offset**，它只是把常数变小——适合"产品要求能跳页"的后台列表。
而无限滚动不需要跳页，**游标的唯一缺点在这里等于零**，所以首页直接上游标。

## 3. 索引：软删除条件是这里最容易漏的坑

查询形态是 `WHERE status=? AND deleted_at IS NULL ORDER BY <排序键> DESC, id DESC`。
软删除表**每个查询都带 `deleted_at IS NULL`**，它不在索引里的话，扫出来的每一行都要回表判断，
等于白扫。所以索引按「等值列 → 排序列 → tiebreaker」组织，并且把 `deleted_at` 放进去：

```sql
INDEX idx_articles_status_deleted_published (status, deleted_at, published_at, id)  -- latest
INDEX idx_articles_status_deleted_view      (status, deleted_at, view_count,   id)  -- recommend
```

旧的 `idx_articles_status_published_at (status, published_at)` 被第一条完全覆盖，删掉（少一份写放大）。

**实测（本地实库 EXPLAIN）**：

| | 改前 | 改后 |
|---|---|---|
| recommend | `key=idx_articles_status_published_at`，`key_len=1`，**`Using filesort`** | `key=idx_articles_status_deleted_view`，`key_len=7`，`ref=const,const`，**`Backward index scan`** |
| latest | `key=idx_articles_status_published_at`，`Backward index scan` | `key=idx_articles_status_deleted_published`，`key_len=7`，`Backward index scan` |

`key_len` 从 1 变成 7 = status(1) + deleted_at(5) + NULL 标志(1)，说明两个等值列都用上了。

> ⚠️ **索引不是"加了就有用"，要 EXPLAIN 验证**。`deleted_at` 这一条尤其容易被忽略，
> 因为它不影响 SQL 能不能跑，只影响它快不快。

## 4. 游标：不透明 token + 行值比较

游标编码成 URL-safe Base64（`CursorCodec`），内容是 `排序键|id`：

- `recommend` 的排序键是 `view_count`；`latest` 是 `published_at` 的 **epoch 毫秒**
  （不用格式化字符串：冒号会和分段分隔符打架，还引入时区歧义）。
- `id` 必须参与，它保证**全序**。只按浏览量取游标时，浏览量并列的那几行会被整段跳过或重复。

SQL 侧用**行值比较**：

```sql
WHERE (view_count, id) < (?, ?)
```

而不是展开成 `view_count < ? OR (view_count = ? AND id < ?)`。

⚠️ **两者的实测差距比我一开始预想的小，如实记录**：

| 写法 | type | key_len | Extra |
|---|---|---|---|
| 行值比较 | `ref` | 7 | `Using where; Backward index scan` |
| OR 展开 | `range` | 19 | `Using index condition; Backward index scan` |

**两种都消除了 filesort，都是可用计划**。选行值比较的理由是它更贴合 keyset 的语义
（"从那一行之后继续"）：`ref` + 短 `key_len` 说明执行方式是"用等值列定位起点，
再沿索引顺序读 10 条"，正是想要的形态。
**但不要讲成"OR 写法会退化"——本地实测没有**，那是想当然。

**游标解析失败一律抛 `IllegalArgumentException`**（全局 handler 转 40001），
**不静默退化成"第一页"**——那会让"客户端 bug / 用户手改 URL"永远暴露不出来。

## 5. 缓存：从"每页一个 key"改成"只缓存第一页"

这不是可选项——游标分页下**深页根本没法缓存**（cursor 是每个调用方各自的位置，变不出稳定的 key）。
好在也不需要：keyset 是"索引定位 + 取 N 行"，代价与深度无关，回源不疼。

顺带消掉了一个老问题：原来 key 是 `article:list:page:N:...`，**翻多少页就有多少 key**，
而任何一次文章变更都要 `SCAN article:list:*` 全删 + 延迟重删一遍。
现在 key 数量是「分类数 × 排序数」，与翻页深度无关。

代价：**游标模式下不再计算 `total`**（省掉一条 `COUNT(*)`），返回里 `total` / `page` 都是 `null`。
前端判断"还有没有下一页"改用 `nextCursor`。

## 6. ES 侧：`from/size` → `search_after`

ES 的 `index.max_result_window` 默认 10000，`from + size` 越过就**直接抛错**
（不是变慢，是 `Result window is too large`）。换成 `search_after` 没有这个上限，
代价是必须显式排序、且排序键要能保证全序：这里按 `_score → articleId` 两级排。

### ⚠️ 踩坑：`_id` 不能当 tiebreaker，而且它的失败是静默的

第一版用的是 `_score → _id`，理由是"`_id` 唯一、天然全序"。跑起来测试**全绿**——
但测试日志里躺着一行 WARN：

```text
[SEARCH-ES] 检索失败，将降级到 LIKE：keyword=Published
error=[es/search] failed: [search_phase_execution_exception] all shards failed
```

直连 ES 才看到真正的错：

```json
{"type":"illegal_argument_exception",
 "reason":"Fielddata access on the _id field is disallowed,
           you can re-enable it by updating the dynamic cluster setting:
           indices.id_field_data.enabled"}
```

**ES 8 默认禁止访问 `_id` 的 fielddata**，按它排序直接失败。但更值得记住的是**失败的方式**：
`ArticleSearchService` 的契约是"检索失败返回 null，调用方降级回 LIKE"——
所以这个错误被**正常地**吞掉了。搜索功能看起来还在工作，实际查的一直是 LIKE。
**测试不会红、页面不会报错，只有一行 WARN。**

> **教训：「有降级路径」的功能，降级本身必须是可观测的。**
> 否则一个 100% 触发降级的 bug，表现出来和"ES 稍微慢了点"一模一样。
> 这次纯粹是去翻测试日志才发现的。

**修法**：索引里进一个自己的、带 doc_values 的 `articleId`（long）。

```json
// 已有索引补字段（新环境由 ensureIndex 直接建出来，不用手工做）
PUT /article_search_index/_mapping
{"properties":{"articleId":{"type":"long"}}}

// 从 _id 回填存量文档（本地 31/31 成功，1356ms）
POST /article_search_index/_update_by_query?refresh=true
{"script":{"source":"ctx._source.articleId = Long.parseLong(ctx._id)","lang":"painless"}}
```

**修完后的实测**（本地真实数据，恰好撞上并列分数）：

| | articleId | score |
|---|---|---|
| 第 1 页 | 1 | 9.274233 |
| 第 1 页 | 33 | **8.710259** |
| 第 2 页（`search_after`） | 21 | **8.710259** |

两页重叠 **0** 条。注意 **33 和 21 的 score 完全相同**——真实数据里就有并列名次，
没有第二级排序键，这里必然重复或漏条。这比任何构造出来的用例都有说服力。

### 还剩什么

官方完整的 ES 深分页方案是 **PIT + `_shard_doc`**（PIT 给一个时点快照，
`_shard_doc` 做稳定的 tiebreaker），代价是要管 PIT 的 open / close / keep_alive 生命周期。
当前文档量远没到那个规模，所以只用 `search_after` + `articleId`。
要升级时注意：**`search_after` 本身不解决漂移，PIT 那部分才是**。

## 7. 明确没做的三件事（边界）

1. **分页漂移没有彻底解决**。`recommend` 的排序键 `view_count` 每 30 秒被
   `ArticleViewCountSyncTask` 同步一次，所以它会在分页期间变。
   但 keyset 的影响面远小于 offset：offset 会让**后面所有页**错位，keyset 只影响
   **跨越游标值**的那几条。要彻底消除得上排序快照（ES 用 PIT，feed 流用物化列表），
   在当前数据量下是过度设计——**登记，不做**。
2. **`sort` 参数在 ES 侧仍未生效**。`ArticleSearchService.search` 收到 `sort` 但没接进排序数组
   （改造前也一样没用），所以搜索页切"推荐 / 最新"不改变结果顺序。属于既有缺口，
   这次只做分页改造、不动排序行为，避免两类变更混在一起验证。
3. **`total` 超过 10000 时不准**。ES 默认 `track_total_hits` 上限 10000，超过后恒等于 10000
   （`relation=gte` 被丢弃）。分页判断已改用 `nextCursor`，所以它不影响翻页正确性，
   只影响"共 N 篇"这类展示。

## 8. 面试怎么讲

> 深分页要先分清是**扫描成本**还是**回表成本**。offset 的问题是它要跳过前 N 行，
> 而且 `SELECT *` 时跳过的每一行还要回表——这两个代价是叠乘的。
>
> 延迟关联降的是回表次数（先用覆盖索引捞 id，再回表取数据），但它仍然是 `O(offset)`，
> 只是常数小了，适合必须支持跳页的后台列表；游标分页是从行数上消除 offset，
> `O(log N + size)` 与页码无关，代价是不能跳页、排序键要全序。
>
> 所以选型看交互：**无限滚动用游标，有页码的列表用延迟关联**，两个也可以叠加。
>
> 几个容易漏的点：① ORDER BY 的字段必须在索引里；② **软删除表的 `deleted_at IS NULL`
> 也要进索引**，否则覆盖索引失效、延迟关联白做；③ 排序键要带 tiebreaker，
> 否则并列值那几条会在翻页时被跳过或重复；④ 写完必须 EXPLAIN 验证，不能只看写法。
>
> 还有一层：**keyset 解决的是扫描成本，不解决漂移**。排序键在分页期间变化时，
> offset 会让后面所有页错位，keyset 只影响跨越游标值的那几条——要彻底解决得给分页一个快照，
> 业界的做法是 ES 的 PIT、或者 Twitter 那种把排序结果物化成 feed 列表。

还有一个执行层面的坑值得讲（这次真踩了）：

> **有降级路径的功能，降级本身必须是可观测的。**
>
> 我们的 ES 检索契约是"失败返回 null，调用方降级回 LIKE"。这次 `search_after` 用 `_id` 排序
> 被 ES 8 拒绝，于是**每一次搜索查询都在失败、每一次都在正常降级**——
> 测试全绿、接口 200、页面看起来一切正常，**只有一行 WARN**。
>
> 换句话说：一个 100% 触发降级的 bug，表现出来和"ES 稍微慢了点"完全一样。
> 如果降级路径没有计数、没有告警、日志级别是 INFO 随手就刷过去了，
> 那这条"兜底"就从"保护"变成了"掩盖"。这次纯粹是靠去翻测试日志才发现的。
