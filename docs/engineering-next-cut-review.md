## 三、逐项评估

### 3.1 缓存击穿 + 雪崩

**Codex 评估**：Redis 面试高频；设计稿已有可接着做；适合作为 Redis 深度项；不一定比登录安全更急。

**本文主张排第一**，但有 **3 处设计稿偏差需先修正**：

#### （1）写点数量：6 → 16

设计稿 §三 写"6 个缓存写点"，括号内列了 7 项，实测 **16 处**：

**A. 数据缓存（7 处，抖动的主要对象）**

| 写点 | TTL |
|---|---|
| `ArticlesServiceImpl:1070` 文章详情 | 10 min |
| `ArticlesServiceImpl:145` 文章列表 | 5 min |
| `ArticlesServiceImpl:1021` 空值缓存 | 3 min |
| `CommentsServiceImpl:381` 评论列表 | 3 min |
| `CategoryServiceImpl:59` 分类列表 | 30 min |
| `TagsServiceImpl:57` 标签列表 | 30 min |
| `LearningPlansServiceImpl:225` 学习计划列表 | 5 min（**注意：此处用 `Duration` 重载，与其余 6 处的 `TimeUnit` 形式不同**） |

**B. `:loaded` 标记位（9 处，本文主张不抖动）**

`ArticleFavoritesServiceImpl:60 / 99`、`ArticleLikesServiceImpl:67 / 110`、`ArticlesServiceImpl:321 / 393`、`CommentsServiceImpl:504`、`LikeCommentsServiceImpl:55 / 81`

**不加抖动的理由**：这类 key 是「该用户的点赞 / 收藏集合已从 DB 加载到 Redis」的标记，**每用户一个，不是全局共享的热点数据**。它失效的后果是"这一个用户重新查一次 DB"，**不构成 DB 压力峰值**——而雪崩要防的恰恰是"大批 key 同时失效 → 请求同时压到 DB"。抖动它只增加 9 处改动面与回归风险，不带来防护收益。

> 若认为该加，请说明它如何降低 DB 压力峰值。

#### （2）读路径：不是"多了一条"，是"本来就有两条，互斥是第三条"

设计稿 §二 写「互斥路径引入后**多了一条**读缓存入口」，实测现有读路径**已经是两条**：

- `ArticlesServiceImpl:164` — `get(key)` 读一次，判 `CACHE_NULL_VALUE`
- `ArticlesServiceImpl:183` — `getArticleDetailFromCache(id)` 内部**再读一次同一个 key**

两条之间有窗口，且对"空值 / 反序列化失败"的处理**方式不同**（前者判等返回，后者 catch 到 `JsonProcessingException` 就 `delete(key)`）。互斥轮询再接进来就是第三条，三者语义必须一致。

**建议**：接互斥前先把这三条读路径**统一收口到单一读函数**，否则坑 3 防不住。

#### （3）坑 3 已核实为真

`ArticlesServiceImpl:129-136`：`getArticleDetailFromCache` catch 到 `JsonProcessingException` 即 `delete(key)`。轮询路径若读到 `CACHE_NULL_VALUE` 走反序列化，会**把别人刚写的空值缓存删掉**，互斥效果被自己破坏。设计稿识别准确。

### 3.2 登录失败次数限制

**Codex 建议**：只管密码登录不碰 GitHub OAuth / Redis INCR + TTL / 用户名维度 + IP 维度双限制 / 登录成功清理失败计数 / 错误提示保持泛化。

**本文评估**：范围收窄（不碰 OAuth）与提示泛化**认同**；维度策略**建议修改**；脚本复用与计数粒度**需先定**。

#### （1）不建议「双维度等权」

| 维度 | 能拦什么 | 副作用 |
|---|---|---|
| **IP** | 只拦顺手试的；**拦不住有备而来的**（代理池 / 僵尸网络每 IP 试几次就换） | 学校 / 公司 / 运营商 **NAT 出口**下大量正常用户共享一个 IP——一人试错锁掉整栋楼 |
| **用户名** | 能拦定向爆破 | 攻击者拿**别人的用户名**狂试 → 把真实用户**锁死**（账号锁定反模式 / 拒绝服务） |

**建议**：用户名维度为主（阈值放宽 + 锁定时长要短，如 10 次 / 5 分钟）；IP 维度降为宽阈值辅助或不做；或改用 `username + IP` **组合维度**（攻击者换 IP 即失效，但不误伤 NAT 邻居）。

个人博客的用户规模下，**误杀的代价 > 漏拦的代价**。

#### （2）不要新写 INCR + EXPIRE

分两次调用的经典故障：INCR 成功、EXPIRE 失败（或进程崩在中间）→ **计数键永不过期 → 用户被永久锁定**，重启也不恢复。

项目已有正解：`AiRateLimiter.java:29-39` 的 Lua 脚本（INCR + 首次 EXPIRE 一次完成），正是登录需要的原子计数。

**但两处语义差异**：

- 限流器 `tryAcquire` 是「每次调用消费一个配额」；登录是「**只有失败才 +1、成功要清零**」——`tryAcquire` 无清零能力
- 类名 `AiRateLimiter` 是 AI 专用语义

**三个选项**（请选择或提出第四种）：

| 选项 | 改动 | 代价 |
|---|---|---|
| A. 塞进 `AiRateLimiter` | 加 `reset()` + 复用 `tryAcquire` | 类名语义错位（叫 Ai 的类管登录）；两种窗口语义混在一个类 |
| B. 抽成通用 `RateLimiter`，AI 与登录共用 | 改 AI 限流链路 | 有 `AiRateLimiterTests` 兜底，风险可控；但**非必要不动稳定链路** |
| C. 独立 `LoginAttemptLimiter` + **共享 Lua 脚本常量** | 脚本提为共享常量，两边引用 | 需定常量放哪（`RedisScripts` / `RedisConstants` / 其他） |

**本文倾向 C**——保持两个类各自语义清晰（限流 ≠ 失败计数），但不重复写第二份可能写错的原子逻辑。符合"三次法则"：第三处出现时再抽公共组件。

#### （3）计数键的粒度未定

"用户名维度"用**输入原文**还是**查出的 userId**？

- 用原文：大小写变形 / 首尾空格 / Unicode 同形字即可绕过（`admin` / `Admin` / `admin ` 各算一份）
- 用 userId：用户不存在时没有 userId，而"用户名不存在"本身也是攻击面（账号枚举）

**注意**：若"用户不存在"也计数，攻击者可据「是否被限流」**反推账号是否存在**——这与"提示泛化"的目标直接冲突，需一并设计。

#### （4）锁定期间的响应形态未定

锁定提示必须对**不存在的账号同样返回**，否则同样泄露账号存在性。错误码与文案需与"用户名或密码错误"不可区分。

#### 实施结果（2026-09-15）

四问的最终答案与**对本文的三处修正**，完整论述见 `redis/redis-capability-design.md` §5.11：

| 本文结论 | 实施时 |
|---|---|
| （1）用户名维度为主，阈值放宽到 10 次 / 5 分钟 | ⚠️ **改为双维度非等权**：账号维度 5 次 / 15 分钟（严）+ IP 维度 30 次 / 15 分钟（宽）。实施时**先走错了一版**——写成「用户名 + IP」组合维度，那个键只拦得住"单 IP 定向爆破"，拦不住分布式爆破与撞库，等于限流形同虚设；本文的"用户名维度为主"方向是对的，错的是把它和 IP 合成一个键 |
| （2）倾向选项 C：独立类 + **共享 Lua 脚本常量** | ⚠️ **独立类采纳，共享常量放弃**——两句脚本文本相同但契约不同（每次消费配额 vs 仅失败计数），共享会制造隐性耦合 |
| （3）计数粒度"原文 vs userId"未定 | ✅ **归一化后的原文**。实测 `@@collation_database = utf8mb4_unicode_ci`，`Admin` 与 `admin` 在库里本来就是同一个用户——原文不归一化会被大小写变体绕过，用 userId 则"用户不存在"无法计数、变成账号枚举探针 |
| （4）锁定响应形态未定 | ✅ 429 + 明确提示，对不存在的账号走**完全相同的分支**（先查锁定再查库） |
| —— | ➕ 本文未提的第三条泄露：**响应时间**。`users == null` 时不做 bcrypt 会快约 100 ms，与"提示语泛化"自相矛盾。实现里对 dummy hash 补跑一次 `matches` |

**Codex 评估**：后端基础项；会碰很多 DTO / Controller；后面批量做；不适合作为刚切工程化后的第二刀。

**本文认同放后面，补一条未提的风险**：

`@Valid` 会**改变错误响应行为**——现在各 Controller 手动判空返回什么错误码 / 消息，改后统一走全局异常处理器返回什么？前端若依赖现有格式会破。

**动工前必做**：对 `docs/api-convention.md` + 现有 `BusinessException` / 全局异常处理器的实际用法；**按模块分批**，不要一次性扫全部 Controller。

### 3.4 Memory 敏感信息过滤

**Codex 评估**：和 AI 主线关联强；规则要细，避免误杀正常技术内容。
**项目方判断**：不急，放后面。

**本文认同放最后，补充一条更根本的**：

**本项目的记忆内容天然充满"疑似敏感信息"**——这是技术博客：

- 讲正则的文章会写身份证 / 手机号示例
- 讲 Spring 配置会写 `password:` / `api-key:`
- 用户可能主动说「我的 key 是 xxx，帮我看看这个配置对不对」

**误杀代价高，但不能推出"只在注入 prompt 前过滤"**：敏感信息一旦进入长期记忆表，就已经形成持久化风险——后续管理页、调试接口、日志、备份、数据库泄露都可能暴露它。只在注入前过滤只能降低模型侧泄露，挡不住存储侧风险。

**若做，建议两道闸分层**：

- **写入前高置信阻断**：密码、token、API key、私钥、身份证号、手机号等明显敏感内容不进入正式记忆；必要时落一条"已忽略敏感信息"的审计记录，但不保存原文。
- **注入 prompt 前二次脱敏**：对历史存量、低置信疑似内容、技术文章示例做最后一道保护，避免把敏感串塞回模型上下文。

这样既避免"一刀切导致记忆残废"，也不把敏感数据长期保存在数据库里。真正难点是规则分级：高置信 secret 强拦，技术示例低置信标记或放行；这部分需要单独设计，不适合夹在本轮缓存/登录里顺手做。

## 七、Codex 复核结论（2026-09-14）

1. **排序**：同意缓存击穿雪崩可以排在登录失败限制前面，前提是本轮目标明确为"Redis 能力做厚 + 面试高频补强"；若目标改成"认证安全连续收口"，登录失败限制排第一也成立。当前项目已完成敏感配置外置，下一刀做缓存不跳。
2. **缓存写点范围**：同意 9 处 `:loaded` 标记位本轮不加抖动。它们是用户维度的加载标记，不是全局热点数据缓存；改它们不能显著降低 DB 峰值，反而扩大回归面。
3. **缓存读路径**：同意先统一文章详情缓存读取语义，再加互斥回源。尤其要保证 `CACHE_NULL_VALUE` 不进入 JSON 反序列化路径，否则会误删空值缓存。
4. **登录维度**：不同意"用户名 + IP 双维度等权强锁"。更稳的起点是**规范化用户名为主、阈值偏宽、锁定短时；IP 只做宽阈值辅助**，避免 NAT 误伤和账号锁定型拒绝服务。
5. **脚本复用**：倾向 C，但不要只共享一段裸字符串。可以抽一个很小的 Redis 原子窗口计数组件，提供 `incrementWithExpire(key, windowSeconds)` 和 `delete(key)`；AI 限流是否迁过去另看半径，本轮登录也可以先独立使用同一脚本模式。
6. **计数粒度**：用户名侧用 `trim + lower-case + Unicode normalize` 后的输入用户名，不用 userId。原因是不存在用户也要进入同一套响应路径，否则会留下账号枚举口子。日志和 Redis key 不直接明文保存用户名，建议 hash 后入 key。
7. **响应形态**：锁定期间仍返回与普通登录失败一致的业务错误码和文案，不单独提示"账号已锁定"给前端；后端日志可记录 `LOGIN-BLOCKED`，只带 hash / IP / traceId，不带密码或明文用户名。
