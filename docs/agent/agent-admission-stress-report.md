# AI 长任务准入：压测报告（L1）

> 2026-09-19 · 设计稿见 [`agent-admission-stress-design.md`](agent-admission-stress-design.md)
> 结论一句话：**应用层准入没到瓶颈；真正的瓶颈是 LLM 供应商的速率限制。**

## 0. 三句话结论

1. **准入的容量算法实测正确**：小池（worker=2 / queue=3）下 `running` 峰值精确停在 2、`queued` 停在 3，第 6 个请求拿到 `503 POOL_FULL`，`queueWaitMs` 真实增长到 5.7 秒。
2. **真实配置（8+32）下应用层毫无压力**：40 个并发请求只把池用到 `8 在跑 + 2 排队`，`rejected = 0`。
3. **但 40 个请求里只有 10 个真正走了目标路径**——另外 30 个在**意图分类阶段就被供应商限流打挂**，静默降级成了「普通聊天」。**闲聊路径不占准入池**，所以这部分压力完全没进被测系统。

## 1. 环境与方法

| 项 | 值 |
|---|---|
| 被测 | 本地 Spring Boot（`localhost:8080`），MySQL / Redis / ES 均在本机 |
| 施压 | `deploy/ai-stress/stress.mjs`（Node，自签 JWT，`Promise.all` 同步发起） |
| 账号 | 库中现成的 `jmeter_test_*` × 200（秒杀压测遗留） |
| 业务入口 | `POST /api/ai/chat/stream`，消息固定为「我想系统学 Redis」 |
| 观测 | HTTP 状态码由脚本记；准入行为读后端 `[AI-TASK]` 日志 |

**为什么不用 JMeter**：被测协议是 SSE 长连接，要量首字节、要连接保持、要按用户分组构造场景（设计稿 §3.2）。

### ⚠️ 方法上的两个坑（都实际踩到了）

1. **压到了「旧实例」上**：`TaskStop` 只停 Maven 包装进程，**Java 子进程仍占着 8080**，新实例启动失败（`Port 8080 was already in use`）而脚本照打不误 —— 于是「小池参数没生效」的第一轮数据全是假的（8 个请求全 200）。
   **对策**：重启前 `netstat -ano | grep :8080` 找到 PID `taskkill /F`，并比对日志里的 Java PID。
2. **JS 数字精度吞掉了 userId**：雪花 ID 有 19 位（`2100945997778681858`），超过 `Number.MAX_SAFE_INTEGER`，`Number()` 把末位抹成 `000`。于是压测**一直在用一个不存在的用户**——**而后端照单全收**（见 §4.2）。
   **对策**：`userId` 全程按字符串处理，payload 手工拼 JSON。

## 2. L1-a：容量算法验证（小池 2 + 3 = 5）

启动参数：`--blog.ai.task.worker-count=2 --blog.ai.task.queue-capacity=3`，发 8 个请求（8 个不同用户各 1 发）。

| 指标 | 实测 | 期望 |
|---|---|---|
| `running` 峰值 | **2** | = worker-count ✅ |
| `queued` 峰值 | **3** | = queue-capacity ✅ |
| 拒绝 | **1 × `503 / code=50300`** | 池满即拒 ✅ |
| `queueWaitMs` 峰值 | **5724ms** | 排队真实发生 ✅ |

拒绝日志（`precheck` 在**任何 SSE 事件之前**拦下，所以前端拿到的是 HTTP 503 而不是「连接意外中断」）：

```
[AI-TASK] precheck rejected reason=POOL_FULL taskType=WORKFLOW_CREATE
          businessRef=<runId>:learning-plan userId=... running=2 queued=3
```

> **副产物**：8 个请求对 5 个名额，本该拒 3 个，实际只拒了 1 个 —— 有 2 个请求**到达时前面的已经跑完了**。
> 原因：每个请求进准入前要先过**意图分类（一次 LLM 调用，3–5 秒且不稳定）**，
> 所以「同步发出」≠「同时到达准入点」。**这是本方法学上的固有偏差**，看容量时要用日志的 `running/queued` 峰值，不能只看 HTTP 状态码分布。

## 3. L1-b：真实配置（8 + 32 = 40）× 40 用户

| 指标 | 实测 |
|---|---|
| HTTP | **200 × 40**，`rejected = 0` |
| `running` 峰值 | **8**（worker 用满） |
| `queued` 峰值 | **2**（容量 32，远未满） |
| `queueWaitMs` 峰值 | 1326ms |
| `executionMs` 峰值 | 4495ms |
| 首字节 | P50 7599ms · P95 8673ms |
| 总耗时 | P50 22171ms · P95 29041ms · 最长 30990ms |

**准入侧毫无压力**：`8 + 2 = 10`，离 40 个名额还差得远。

### 3.1 但只有 10 个请求真正进了池

日志统计：

```
businessRef:  learning-plan × 20（10 start + 10 done）
intent:       GENERAL_CHAT × 30 · LEARNING_PLAN × 20
WARN:         30 × AI 意图识别调用失败
              30 × AI 意图识别失败，降级为普通聊天
              30 × https://help.aliyun.com/zh/model-studio/error-code#rate-limit
```

**根因：LLM 供应商（阿里云百炼）的速率限制。**

40 个并发请求 → 40 次意图分类调用同时打向供应商 → **触发 rate limit** → 30 次失败 →
**静默降级为 `GENERAL_CHAT`** → 走闲聊路径 → **不占准入池、不占准入名额**。

**所以这一轮的真实含义是**：

| 层 | 状态 |
|---|---|
| 应用层准入（8 + 32） | **绰绰有余** —— 只用到 8+2 |
| **LLM 供应商速率限制** | **40 并发就撞上了** ← **真瓶颈** |

## 4. 本轮暴露的三个问题（都不是准入本身的 bug）

### 4.1 分类失败降级 —— **已有用户提示（本报告初版写错了，此处纠正）**

初版写「不报错、不提示，用户不知道自己想要的功能没执行」，**核实代码后不成立**：

`AiMessageServiceImpl.buildChatStatusFlux()` 有专门分支，降级时下发 `CLASSIFIER_DEGRADED`
状态事件（4001），文案「这次没理解准，先按普通回答处理...」。前端早就有 4001 事件通道，
用户看得到。判据 `isClassifierDegraded(intent)` = `confidence == 0.0`——
因为 `AiIntentClassifierImpl.generalChat()` 兜底构造时固定置 0。

代码注释里写得很清楚，这个坑之前就被发现并修过了：
> 降级是**静默**的，用户看到的是"AI 突然不认我说话了"，而不是"这次是系统故障"——
> 两者对用户的意义完全不同（前者让人怀疑产品，后者只是重试一次）。

**遗留的小瑕疵（登记不修）**：`CLASSIFIER_DEGRADED` 分支的判定排在
`CURRENT_ARTICLE` / `ARTICLE_SEARCH` / `getLearningDashboard` **之后**。
若降级发生时 `routeDecision` 仍带检索意图，提示会被「正在检索站内文章...」覆盖。
触发条件窄（降级后 intent 已是 `GENERAL_CHAT`，通常不带检索意图），暂不处理。

### 4.2 后端不校验 JWT 里的 userId 是否存在 —— **建议不修**

压测用**不存在的 userId**（精度丢失后的假 ID）签名，后端**全部接受并正常建了会话**：
`JwtInterceptor:47` 直接 `UserContext.set(payload.userId())`，没有查库。

**但核实后判断：修它的收益很低。**

- **项目没有用户注销功能**：全仓库搜不到 `注销` / `deleteUser` / `DELETE FROM users`，
  `users.deleted_at` 204 行**全为 NULL**。也就是说合法签发的 token **一定**对应存在的用户。
- 能造出「幽灵 userId」的只有**伪造 token**，而那需要 `jwt.secret`。
- **而拿到 secret 的攻击者可以直接伪造任意*存在的*用户** —— 校验 userId 存在性**挡不住真正的威胁**。

修它 = 每个请求多一次 DB 查询，换来一个防不住攻击者的检查。**不做，登记为已知边界**：
真要做，应该等「用户注销」这个功能出现时一起做（那时才有"token 比用户活得久"的真实场景）。

### 4.3 `executionMs` 波动大（1.3s ~ 5.1s）

同一个任务类型，worker 内执行时间差 4 倍。首字前的 `ragSearch` 是否命中缓存是主因之一。
**影响**：容量规划不能按平均值算，得按 P95/P99。

## 5. 对设计稿的修正

| 原设计 | 实测修正 |
|---|---|
| 「40 个名额，第 41 个 503」 | 名额算法**正确**，但**在当前供应商配额下根本到不了 40 并发**——先撞的是供应商限流 |
| `worker=8` 是「成本闸门」 | 实测坐实：应用层 worker 不是瓶颈，**真正决定花钱速率上限的是供应商侧配额** |
| 面试口径「瓶颈会转移到供应商速率限制」 | **40 并发即触发**——这个数字现在有实测依据了 |

## 6. 下一步（可选）

- **不需要**再跑更大规模的阶梯压测：瓶颈不在应用层，加大并发只会更多地撞供应商限流
- 若要继续深挖，方向是**供应商侧**：
  - 摸清速率限制的具体阈值（QPS / TPM）与配额提升路径
  - 或应用侧加**分类调用自己的限流 + 排队**，把「降级」换成「稍后重试」
- §4.1 已有实现（本报告初版写错，已纠正）、§4.2 评估后建议不修 —— **两者都不需要单开一刀**
