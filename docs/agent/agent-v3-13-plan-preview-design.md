# Agent V3.13：Plan Preview（V4① 观察性试点·阶段一）设计稿

> 前置：V3.11（证据收敛门）+ V3.12（会话结论继承）已完成并手测通过；V3.10 的 thoughtSummary 展示链路为本刀展示层的直接参照。
> **本刀只做阶段一**——计划「生成 + 展示 + 观测」，**不含弱锚定**（阶段二另立，理由见 §〇）。

## 〇、背景

### 现状：三域 Runtime 是「贪心单步」，没有全局计划

决策器每步只看「goal + 最近观察」决定下一个动作，没有全局视野。三范式定位（V3.10 已立）：

```text
三域 Runtime = 受限 ReAct          ← 共享骨架会触及，但本刀只在文章域启用
Workflow     = 预定义 Plan-and-Execute（步骤代码写死）
聊天 @Tool   = function calling
```

自由 ReAct 的「先想清楚要几步再动手」这一环，在受限 ReAct 里被砍掉了。砍得有道理（白名单 + 受控写 + 确认门已经把「想太多」的风险产品化改造掉了），但**代价是用户和我们都看不到 agent 打算怎么走**。本刀就是把这一环以最小代价补回来。

共享组件只增加可空数据字段和默认关闭的钩子；计划采集、持久化、事件与文章域 prompt 规则均受域开关保护，学习域和通用域不启用本能力。

### 定位声明：能力地图补齐，不是痛点修复

**必须先说清楚**。复盘 V3.9 ~ V3.12，每一刀都是「手测发现问题 → 定点修」：

- V3.11 是「证据不足却硬答」
- V3.12 是「跨 run 结论断裂」

**本刀不是**。目前没有任何实测证据表明「agent 因为缺少计划而跑偏」。V3.11 那次 6 步空转是 focus 定位 bug，与规划无关。而 Anthropic 的原则是「能 Workflow 就 Workflow」，我们的场景（文章分析、学习建议）恰恰是能预定义的——这也正是 V3.11 / V3.12 都走受控路径的原因。

所以本刀的产出以**面试讲法 + 架构认知 + 观测数据**为主，**不承诺产品收益**。把它包装成「解决了 agent 跑偏」是自欺，面试时也会被追问穿。

### 与 Plan-and-Execute 的关系：预定义形态已做，动态规划形态还没有

必须先回答一个更大的问题：**那到底做不做 Plan-and-Execute？**

要分清**两种形态**——它们的形状相同（先规划、后执行），但**规划者不同**：

| | 规划者 | 我们有没有 |
|---|---|---|
| **预定义 / scripted Plan-and-Execute** | 代码（人写死步骤、状态、确认门、执行路径） | ✅ **已有，就是 Workflow** |
| **LLM 动态规划型 Plan-and-Execute** | LLM 生成执行计划 → Executor 按计划执行 | ❌ 还没有 |

所以准确的说法是：**我们已经有了它的预定义代码型形态（Workflow），还没有做 LLM 动态规划型**。

（一句话「我们已经在用了，它叫 Workflow」在面试里会被追问穿——Workflow 与 LLM 规划型 Plan-and-Execute 是两回事，混着说等于自己给自己挖坑。）

真正的空缺是**第三种**——目标明确、但步骤无法预定义时的「计划给方向 + ReAct 临场决策」。

### 三层分工（不是三选一）

```text
Workflow   固定业务流程、确认门、状态机、写入执行
Plan       探索性任务的高层目标拆解
ReAct      每个子目标内部动态选择查询、补查和回答动作
```

选型判据：

| 任务形态 | 走哪层 |
|---|---|
| 能预定义流程（文章优化、学习计划生成） | **Workflow**（现状） |
| 目标明确、但需要多个子目标 + 临场判断（文章分析） | **Plan-guided ReAct**（阶段一 → 阶段二） |
| 目标明确、单步可解（不需要计划） | 纯 ReAct（现状） |
| **目标不清** | **ASK_USER 澄清**（已有机制） |

**「目标不清 → 纯 ReAct」是错的兜底。** ReAct 不知道要完成什么，只会重新出现 V3.8 / V3.11 已经修过的猜测与空转。目标不清时的正确行为是**先问清楚**——这也正是现有机制已经在做的（会话文章锚候选缺失 → ASK_USER 澄清；验证器发现缺用户信息 → ASK_USER 转问）。把它写成兜底，等于把修过的坑重新挖开。

### 阶段一不是 Plan + ReAct，只是它的基线观测

**这一点必须说透**，否则会误以为本刀已经在做组合。阶段一的实际结构：

```text
首轮决策 → 同时产出 action + plan
plan  → 展示 / 落库 / 统计          （不影响任何后续决策）
ReAct 循环 → 继续只看 observations    （原样）
```

**能验证**：模型能不能稳定拆出像样的子目标。
**不能验证**：计划是否帮助后续动作选择 / ReAct 会不会根据观察偏离计划 / 计划与 Verifier 如何协同 / 计划会不会造成错误锚定。

后四个问题**全部属于阶段二**（架构登记见 §七）。本刀不假装已经完成组合。

### 为什么拆两阶段

阶段划分不是「求稳妥」，而是**两个阶段回答两个不同问题**：

| 阶段 | 问题 | 产出 |
|---|---|---|
| **一（本刀）** | LLM 能不能稳定拆出**有价值的子目标**？ | 计划内容 + 计划/实际执行对照数据 |
| 二（另立） | 把计划放进后续 prompt，是**帮助执行**还是**造成锚定偏差**？ | 弱锚定的净效果 |

关键在于：**阶段一的观测数据本身就能决定阶段二做不做**。

| 观测结果 | 说明什么 | 下一步 |
|---|---|---|
| 执行**高度跟随**计划（零锚定也跟） | 任务有稳定路径 | **该 Workflow 化**，不是继续做 Plan 层 |
| 执行**经常偏离**，且偏离后结果更好 | 计划没有指导价值 | 阶段二不做 |
| 计划合理、但执行确实会跑偏 | 计划有价值但缺约束 | 阶段二（弱锚定）成立 |

一次做完 = 永远分不清「计划质量差」和「锚定造成偏差」是哪个。**第一种结果最值得期待**——它意味着我们又挖出一个该 Workflow 化的场景，那比做一个 Plan 层有价值得多。

## 一、目标与非目标

### 目标

1. 文章域 Agent 在**多目标请求**下生成 2-4 个用户可理解的子目标
2. 计划走**独立通道**：独立存储、独立展示、独立 inspection
3. 记录「计划 vs 实际执行」的对照数据，**为阶段二的决策提供依据**
4. 简单请求**不高频产生有效计划**（软目标，理由见 §四 验收项 1），原流程一字不变

### 非目标（写死的边界）

| 不做 | 原因 |
|---|---|
| **计划不进后续决策 prompt**（零锚定） | 本刀只验证「能不能拆」。混进来就分不清归因 |
| **计划不进 observations** | Verifier 会把计划当**证据**，污染 V3.11 辛苦建的「证据支撑性判定」。这是本刀最硬的一条边界 |
| 计划不驱动 Workflow / 写动作 | 同上，保持只读语义 |
| 学习域 / 通用域不改 | 文章域有 Verifier + focus + 观察记录，最容易看出计划与执行的对应关系。**但共享组件必须设显式域开关**——见 §3.0 |
| 不做「是否多目标」的后端闸门 | 归决策器自决（§3.3），避免叠一层判定 |
| 不做计划的自动质量评估 | 对应率是语义判断，自动算不准（§3.7） |
| **不称为「完整 Planner」** | plan 只是**用户可读的子目标列表**——不含子目标 ID / 依赖关系 / 完成状态 / 当前执行项 / 重规划结果 / 失败恢复策略。叫它 Planner 会让人以为这些都有了 |

## 二、术语

| 术语 | 含义 |
|---|---|
| **Plan Preview** | 本刀能力名：生成 + 展示 + 观测，**不做执行驱动**。刻意不叫 "Planner" |
| plan | 决策器首轮输出的子目标列表（`List<String>`，2-4 项）。LLM 侧字段名 |
| 机制词 | 动作白名单名（`QUERY_ARTICLE` / `SEARCH_RAG` 等）、`JSON` / `prompt` 等实现术语 |

**plan 是结构化列表，不是一段文本。** 理由：前端要渲染成列表、后端要逐项校验、观测要按项对照实际动作。做成字符串后面三件事都得再做一次解析。

## 三、设计

### 3.0 域开关：只有文章域开启（Codex 评审补）

实现清单里要改的 `AgentStepDecision` / `LlmAgentStepDecider` / `AbstractAgentRuntime` 都是**三域共享**的。只改不设开关，学习域和通用域会被动吃到 plan 逻辑——哪怕字段可空、行为无变化，也是一次隐式的全链路影响，且无法从代码上断言「这两个域没变」。

**做法**：对齐现有域钩子模式（`effectiveGoal` / `verifyBeforeFinalization` / `emptyAnswerFallback` 都已有先例），新增一个钩子：

```java
/** Plan Preview 域开关（V3.13）：默认 false，仅文章域 true。 */
protected boolean supportsPlanPreview() { return false; }
```

各环节的共享边界：

| 环节 | 是否共享 | 位置 |
|---|---|---|
| JSON 字段解析（`plan`） | ✅ 共享——解析层无域语义 | `LlmAgentStepDecider` |
| prompt 规则（「什么时候输出 plan」） | ❌ **仅文章域追加** | `ArticleAgentStepDecider` |
| 采集 / 校验 / 落库 / 发事件 | ❌ 按开关 | `AbstractAgentRuntime` 查 `supportsPlanPreview()` |

学习域 / 通用域的验收断言：**运行行为、prompt、计划持久化与事件零变化**（共享解析层允许读取可选 `plan` 字段，但不得消费或传播它；由 §四 回归项锁）。

**prompt 扩展点必须保持领域隔离**：当前 `LlmAgentStepDecider.buildUserPrompt()` 是共享私有方法，不能让文章域复制整段 prompt，也不能直接把 plan 规则写进基类。实施时将其内部拆出受保护钩子，例如：

```java
protected String planPromptSection(int stepNo, boolean repair) {
    return "";
}
```

基类只负责在 `buildUserPrompt()` 中追加该钩子返回值；`ArticleAgentStepDecider` 仅在首步返回计划规则，学习域 / 通用域沿用空字符串。正常调用返回完整规则，修复调用只返回一条短规则，提示模型在首步且请求确实多目标时保留合法 `plan` 数组。

文章域的 repair system prompt 也必须声明顶层可选 `plan` 字段；学习域 / 通用域 repair prompt 不变。否则首轮 JSON 解析失败进入修复调用时，多目标请求会结构性丢失 plan，在线稳定产出门会被 repair 路径拖低。
文章域的正常 system prompt 同样要声明顶层可选 `plan` 字段；否则 user prompt 虽然给了生成规则，输出格式契约却没有覆盖该字段。学习域 / 通用域的正常 system prompt 不增加该字段说明。

### 3.1 数据模型：独立通道，隔离分两层

核心原则——**计划与证据严格分离**：

```text
决策器 decide() → AgentStepDecision{ actionType, input, thoughtSummary, plan }
                                    │
        ┌───────────────────────────┼──────────────────────────┐
        ↓                           ↓                          ↓
   plan（仅首步）            thoughtSummary（V3.10）       observations
   List<String>                     │                          │
        ↓                           ↓                          ↓
  校验 → 落 run.plan_json      展示，不进决策           决策上下文 + Verifier 依据
        ↓
  SSE 独立事件 → 前端计划块
```

**隔离边界分两层——一层永远不改，一层阶段二放开**：

**永远不改（阶段二也必须守）**：

1. plan **不进 observations**
2. **不影响 Verifier 判定** —— 计划不是证据，Verifier 只认实际观察
3. **不绕过权限 / 白名单 / 确认门** —— 计划再合理也不能跳过写路径的硬校验
4. plan 与 thoughtSummary 是**两个独立字段** —— 语义不同，不能合（见下）

**阶段一专属（阶段二放开）**：

5. plan **不进决策上下文** —— 阶段一零锚定；阶段二作为**独立 plan context** 进决策器（§七），**但仍不进 observations、不进 Verifier**

**为什么不能把 plan 塞进 thoughtSummary**（Codex 评审点）：`thoughtSummary` 是明确的**纯展示副产品**，不进决策、不存原文、空值全链路回退（见 `AgentStepDecision` 类注释）。plan 需要落库、需要被观测、阶段二还要进决策。两者的生命周期和消费方完全不同，合成一个字段会让「这个字符串到底参不参与决策」变成要靠上下文猜的事。

**优先级序**（阶段二锚定时也必须守）：

```text
当前用户要求 > 后端权限与安全约束 > 实际观察 / Verifier 结果 > 初步计划
```

计划排在最后一位——它是最弱的信号，永远不能推翻观察。这条写在这里，是为了防止阶段二被做成「计划说了 A/B/C 就硬着头皮执行」。

### 3.2 计划从哪来：决策器同一次调用

- `AgentStepDecision` 加 `List<String> plan`（可空）
- 决策器 JSON 顶层加 `"plan"`（与 V3.10 的 `"thought"` 同层）
- **只在首步采集**（`nextStepNo == 1`），后续步即使输出也忽略
- 解析层只接受 JSON 数组，且数组每一项必须是 JSON 字符串；缺失、`null`、非数组或含非字符串项均按 `plan = null` 处理，不把对象、数字等值强转成字符串

**JSON 解析失败的准确语义**（三条路径必须分开，不要混）：

| 情况 | plan 取值 | 后续 |
|---|---|---|
| 决策 JSON 整体解析失败 → **repair 成功** | repair 返回里的 `plan`（文章域 repair prompt 已声明该字段，见 §3.0） | 正常进入 §3.4 校验 |
| 决策 JSON 解析失败 **且 repair 也失败** | `null` | 整个决策降级（原 V3.10 路径），plan 自然为空 |
| JSON 正常，但 `plan` **缺失 / `null` / 非数组** | `null` | 原流程不变，不落库、不发事件 |
| JSON 正常，`plan` 是数组但**含非字符串项** | `null`（**整条丢弃，不挑拣**） | 同上 |
| JSON 正常，`plan` 是数组且全为字符串 | 进入确定性校验 | 校验不过仍丢弃 |

**关键：字段级失败不升级为决策级失败**——plan 有问题只丢 plan，决策本身照常执行。

理由：

- 少一次 LLM 调用（延迟 + token 都省）
- 避免「Planner 判断」与「决策器判断」不一致——两次独立 LLM 判断必然有分歧，而分歧的代价要靠额外的裁决逻辑兜，不划算
- 复用 V3.10 已验证的「JSON 顶层字段 + 后端处理」模式，风险已知

**代价**：决策器 prompt 变长（要写清「什么时候输出计划」），可能挤压决策质量——实施后必须跑评测门，并观察决策是否退化。

### 3.3 触发条件：决策器自决

「只针对多目标请求」这个约束由谁执行？三个选项：

| 方式 | 评价 |
|---|---|
| **决策器自决**（prompt 规则） | ✅ **采用**。零额外成本，决策器上下文最全（goal + 页面候选 + 会话锚都在它手里） |
| 分类器加字段 | ❌ 多一次 LLM 判定；分类器已背 4 个分界任务（QA / 点赞收藏 / 跳转 / 优化诉求），不该再加 |
| 后端词表（「先…再…最后」） | ❌ 脆弱。V3.12 刚以同样的理由拒绝过词表路线 |

prompt 规则草案：

```text
当用户请求需要多个可观察子目标才能完成（例如「先看整体结构，再检查某一节，最后结合我的偏好给建议」），
且当前步为 1 时，在 JSON 顶层输出 "plan"：2-4 条，每条是用户能读懂的目标。
后续步不要输出 "plan"。
不要写动作名 / 工具名 / JSON / prompt 等实现术语。
简单请求（如「整篇文章写得怎么样」）不要输出 plan。
```

**风险**：模型过度输出计划（每次都出）→ 由验收项 1 锁（简单请求不高频产出），并由观测指标「计划生成率」持续监控。

### 3.4 后端校验：确定性拒绝，零修补

校验失败 → **整条计划丢弃**（plan = null），不影响原流程。

| 规则 | 阈值 | 理由 |
|---|---|---|
| 数量 | 2 ≤ n ≤ 4 | < 2 不是多目标；> 4 展示过重 |
| 单项非空 | 去空白后非空 | — |
| 去重 | 规范化（去空白 + 统一大小写）后比对 | 重复项是模型偷懒 |
| 单项长度 | ≤ 60 字 | 超长说明在写段落，不是写目标 |
| 总长度 | ≤ 200 字 | 展示空间 |
| **机制词** | 命中即**整条计划丢弃** | 只拦动作枚举/实现标识（如 `QUERY_ARTICLE`、`SEARCH_RAG`、`JSON`、`prompt`、`白名单`、`决策器`、`第 N 步`）；不把 `API` / `工具` / `模型` / `参数` / `接口` 等可能属于文章主题的普通词单独判违规 |

**零修补原则**（对齐 V3.10 `AgentThoughtSanitizer`）：不做「截断 / 改写 / 删掉出问题的项后保留」。字面清洗会制造「看起来正常但语义已经变了」的计划——那比没有计划更糟，因为用户会当真。

**计划与首步动作一致性**：若首轮动作是终态或需要澄清的动作（`FINAL_ANSWER` / `ASK_USER` / `SUGGEST_WORKFLOW` / `SUGGEST_WRITE`），本轮不采集该 plan。原因不是后端替模型判断「是否多目标」，而是没有实际执行基线时，计划无法用于本阶段观测，且可能在澄清前误导用户。文章域首轮可采集计划的动作限定为只读查询动作。

### 3.5 展示：独立事件 + 思考面板顶部

**决策：新增独立 SSE 事件类型（`AGENT_PLAN`），不复用 `AGENT_STEP` 加字段。**

理由：

- 计划是 **run 级**概念，`AGENT_STEP` 是**步级**——混进去会让「一步一事件」的语义变浑
- 展示位置明确：思考面板**顶部的计划块**，不属于任何一步（用户先看到「我打算做什么」，再看具体执行）

**事件时序（必须严格）**：

```text
首轮 decide → action 白名单校验 → plan 校验 → run.plan_json 落库 → emit AGENT_PLAN → emit 首个 AGENT_STEP 事件
```

- **先落库再发事件**（与 V3.12 孤儿锚同一原则：事件不可以先于持久化）
- 上述顺序只在首轮产生**通过校验的 plan**时成立；无有效 plan 时不落库、不发 `AGENT_PLAN`，原流程不变
- **`AGENT_PLAN` 必须在首个 `AGENT_STEP` 事件之前发**——首个步骤事件不保证是 `RUNNING`，也可能是终态或失败事件；否则前端先渲染步骤再插入计划块，视觉顺序会闪

**Java 层最小接口形状**：

```java
@FunctionalInterface
public interface AgentStepEmitter {
    void emit(int stepNo, String actionType, String status, String message, String thoughtSummary);

    /** V3.13：run 级计划事件，默认空实现保持旧调用方和测试兼容。 */
    default void emitPlan(Long agentRunId, List<String> plan) {
    }
}
```

`AbstractAgentRuntime` 只在计划已成功落库后调用 `emitter.emitPlan(run.getId(), plan)`。
SSE 事件数据固定为（ID 按现有前端消息 VO 约定序列化为字符串）：

```json
{"agentRunId":"123","plan":["先看整体结构","再检查重点小节"]}
```

计划事件是展示增强，`emitPlan` 异常只记录日志、不影响 Agent 原流程；不得因为前端连接关闭或事件发送失败把 run 判为 FAILED。

前端流式契约同步增加 `StreamCallbacks.onAgentPlan` 与 `AgentPlanEvent`，解析事件类型 `3002`；计划事件按当前 Agent 占位消息归并，`agentRunId` 仅用于校验和后续多流隔离，不改变现有 `AGENT_STEP` 关联方式。`AiChatEventType` 固定登记 `AGENT_PLAN(3002, "Agent计划事件")`，不得临时复用其他事件编号。

**为什么必须按占位消息索引归并，而不是按 `agentRunId` 找消息**（收口确认）：`AGENT_PLAN` 发生在 `STOP` **之前**——那时后端最终消息尚未落库，前端的占位消息**还没有 `agentRunId`**。如果前端实现成「按 agentRunId 匹配消息」，实时计划会因为 ID 未回填而被直接丢弃，症状是**刷新后才看得到计划、实时看不到**。归并依据只能是当前流的**占位消息索引**。
`onStop` 用后端最终消息替换占位消息时，必须同时保留占位消息上已累计的 `thinkingSteps` 和 `plan`；否则实时计划只显示到正文落库前，刷新前后会出现不一致。

当前 `AiMessageServiceImpl` 使用 `AgentStepEmitter` lambda。由于 lambda 不能覆写默认方法，SSE 适配器必须改为匿名类或等价对象，显式实现 `emitPlan()`；只给接口增加默认方法而不改适配器，计划会落库但永远不会实时展示。

**刷新恢复（方案 A，不扩展 `/steps`）**：

前端历史恢复目前只拉 `/steps`，那是 **step 级**接口，不含 run 级 plan。**不扩展它的形状**——往步级接口塞 run 级数据是语义错位（与本节拒绝复用 `AGENT_STEP` 同一个理由）。

```text
1. 前端新增 getAgentRunDetail()  → 走已有的 run 级入口 AgentRunInspectionService.getDetail()
2. `AgentRunDetailVO` 加 `plan` 字段；前端 `AiMessage` 增加可空 `plan`
3. `hydrateThinkingSteps()` 对每个 `agentRunId` 独立补拉 detail 与 steps；计划恢复失败不能导致 steps 被视为不存在，steps 恢复失败也不能覆盖已经恢复的 plan
4. 计划块与步骤列表是两个独立展示条件：只有 plan 时也能渲染计划块，只有 steps 时保持旧展示
```

**展示形态**（前端）：

```text
我的计划：
1. 先看整体结构
2. 再检查缓存击穿那一节
3. 结合你的写作偏好给建议
────────────────────
▸ 读取文章
▸ 查询记忆
✓ 已生成最终回答
```

无计划时**零变化**（不渲染空块）。

### 3.6 持久化与 inspection

- `ai_agent_runs` 加 `plan_json`（TEXT，可空）——**run 级**，不是 step 级：计划是「这次 run 的计划」；只写通过确定性校验后的 JSON 数组
- 同步修改根目录 `db/init.sql` 与 `blog-system/src/test/resources/schema.sql`
- 存量 MySQL 必须在部署代码前执行 `ALTER TABLE ai_agent_runs ADD COLUMN plan_json TEXT NULL`（`CREATE TABLE IF NOT EXISTS` 不会给已有表补列）；缺少迁移不得被当作计划功能的正常 fail-open
- V2.2 的 inspection 只读 API 返回 plan 字段，读取失败按空计划处理并记录日志
- 对照数据源：`plan_json` + 该 run 的 `ai_agent_steps`（actionType 序列）

**写入方式：单列更新，不复用 `updateById`**（收口确认）

```sql
UPDATE ai_agent_runs SET plan_json = ? WHERE id = ?
```

不能读-改-写整个 `AiAgentRun` 再 `updateById`。原因：复用 `updateById` 会把**计划写失败**和 **run 状态写失败**混成同一个故障——两者抛同一类异常、走同一段 catch，`fail-open`（计划失败不影响主流程）就形同虚设：一次状态写入失败会被当成「计划失败」吞掉，或者反过来，计划失败连带把已经推进的状态覆盖回去。**单列更新让两种失败在代码上就是两件事。**

**持久化失败边界**：

- 计划校验异常：丢弃计划，继续原流程，不发计划事件
- 计划列写入异常：记录日志，不发计划事件，继续原动作路径；但数据库 schema 迁移是上线前置条件，不能依靠该 fail-open 覆盖缺列或全库不可用
- 计划为空：不写列、不发事件、不渲染空块

### 3.7 观测指标（阶段一的核心产出）

| 指标 | 怎么算 | 用途 |
|---|---|---|
| **计划生成率** | 文章域有 plan 的 run / 文章域 Agent 总 run | 触发条件是否精准（过高 = 过度输出） |
| 计划项数分布 | 2 / 3 / 4 项各占多少 | 模型倾向 |
| **计划-执行对应率** | 见下方标注规则（**必须人工标注**） | **决定阶段二做不做** |

**为什么不能直接比对**：计划项是**用户语言**（「先看整体结构」），实际执行是**机制动作**（`QUERY_ARTICLE` / `QUERY_MEMORY` / `SEARCH_RAG`）——两者不同构，直接比对只能得出「看起来大致对应」的主观印象，撑不起阶段二的决策。

**人工标注三分类**（每个计划项标一次）：

| 标注 | 含义 | 性质 |
|---|---|---|
| **FOLLOWED** | 有实际动作服务于该子目标 | 计划有效 |
| **SKIPPED** | 观察后发现不需要（合理跳步） | **ReAct 的灵活性，好事** |
| **PIVOTED** | 根据新观察转向了计划外方向 | **需要归因的偏离**（≠计划错误） |

**SKIPPED 与 PIVOTED 必须分开**——前者说明 ReAct 该有的自适应能力在起效，后者才是需要归因的对象。混成一个「未执行率」就把两类信息搅在一起了。

**PIVOTED 不能直接判定为「计划质量差」**——转向可能是完全合理的。标注时继续归因：

| 归因 | 含义 | 指向 |
|---|---|---|
| 初始计划错误 | 计划项本身就不对 | **计划的问题** |
| 新证据合理转向 | 观察到新情况，转向是对的 | ReAct 的适应能力 |
| 用户目标变化 | 用户中途改口 | 与计划无关 |
| 工具失败被迫换路 | 动作执行失败 | 与计划无关 |

四种归因里**只有第一种**指向计划准确性。不区分就会把 ReAct 的合理适应误记成计划失败，进而误导阶段二的决策。

由四类算：跟随率 / 跳过率 / 偏航率（分归因）。

**不做自动指标**：这是语义判断，自动算不准。人工标注样本 + 记录（阶段一的样本量以手测为主，不求统计显著，求方向明确）。

**最小人工观测记录模板**：

| 字段 | 内容 |
|---|---|
| `runId` / 日期 | 便于回查 run detail 与 steps；样本限定文章域 Agent run |
| `goal` | 用户原始请求 |
| `plan` | 通过校验后展示的 2-4 项；无计划记 `NONE` |
| 实际 action 序列 | 按 stepNo 记录成功、失败与终态动作 |
| 每项标注 | `FOLLOWED` / `SKIPPED` / `PIVOTED` |
| `PIVOTED` 归因 | 初始计划错误 / 新证据合理转向 / 用户目标变化 / 工具失败被迫换路 |
| Verifier | 是否拦截、缺哪类证据、之后是否补查 |

## 四、验收场景

### 手测为主

1. **简单请求不高频产生有效计划**（**软目标，不是硬保证**）：触发归 LLM 自决，后端**没有**独立判断「简单 vs 多目标」的确定性依据——把它写成硬验收要么是自欺，要么逼着加后端闸门（那就违背了「不做判定闸门」的设计）。
   - 评测样例中：文章域简单请求通常不应生成通过校验的 plan；偶发一次不判失败
   - 线上：偶发生成但校验不过 → 按无计划处理（不报错、不展示、零影响）
   - 真正要防的是「每个请求都带计划」，不是「偶发一次」
2. **多目标请求生成计划**：「先看整体结构，再检查缓存击穿那节，最后结合我的写作偏好给建议」→ 2-4 项，用户读得懂、无机制词
3. **计划不污染证据**：计划里写「检查缓存击穿」但文章根本没这节 → Verifier 仍按真实观察判定（该 NEED_MORE 就 NEED_MORE，不会被计划说服）
4. **执行可偏离**：计划 3 项但执行 2 步就够 → 正常收尾，不 FAILED、不被系统拉回计划
5. **计划生成失败零影响**：模型没输出 plan / 校验不过 → 原流程一字不变
6. **回归**：学习域 / 通用域 / 建议桥 / 写动作 / Workflow 创建链路全不受影响
7. **刷新恢复**：刷新会话后计划块仍在

### 单测（确定性，进评测门离线档）

- **校验规则**：数量边界（1 项 / 5 项拒绝）、空项、重复项、超长项、机制词 → 整条丢弃
- **动作一致性**：首轮为 `FINAL_ANSWER` / `ASK_USER` / `SUGGEST_*` 时 plan 不落库、不发事件；只读首轮动作才允许采集
- **首步采集**：非首步输出的 plan 被忽略
- **落库**：plan_json 写入 / 空 plan 不写列；存量 schema 迁移后再验证
- **隔离断言（关键回归锁）**：计划**不出现在 observations 里**、不出现在后续决策输入里
- **fail-open**：校验抛异常、计划事件发送异常不影响 run；计划落库异常不发事件并继续原动作路径
- **兼容迁移**：`AgentStepDecision.of()`、`withInput()`、所有 `new AgentStepDecision(...)` 构造点都保留/传递 plan 字段
- **事件时序**：有有效 plan 时 `AGENT_PLAN` 先于首个 `AGENT_STEP`；无有效 plan 时无 `AGENT_PLAN`

### 评测门（在线）

**只锁两件事**——不能把「简单请求零计划」实现成硬断言（它本来就是软目标，见手测项 1）：

1. **多目标请求应能稳定产出 plan** —— 硬断言
2. **简单请求不应高频产出 plan** —— 偶发不直接失败；只有出现**明显退化**（如 3/3 简单样例全部生成计划）才判失败

否则评测门会逼着实现去加一个后端判定闸门，而那正是 §一 明确不做的。

- **门槛规则补一条**：改决策器 plan 规则 = 上线前必跑评测门

## 六、面试 Q&A 速记

**Q：你们做 Plan-and-Execute 吗？**
要分两种形态说。**预定义代码型**（步骤人写死 + 状态机 + 确认门）我们已经有——就是 Workflow；**LLM 动态规划型**（LLM 生成执行计划 → Executor 按计划执行）还没有。所以真正的空缺是第三种：目标明确、但步骤无法预定义时的 **Plan-guided ReAct**。

**Q：你们做 Reflection 吗？**
部分做了，但要说清是哪一部分。V3.11 的 Verifier 已经构成 Generator → Evaluator → Corrective Loop——但它判的是「证据够不够、能不能出口」，**不是**「策略为什么失效」，所以还不是完整 Reflection。而完整 Reflection 必须**改变后续行为**，否则只是多花 token 生成一段没人用的自我批评。我们把它登记在 V4，**触发条件本身要等 V3.13 的观测数据来定**——如果 PIVOTED 归因里「初始计划错误」占比高，它才有活干。

**Q：那三域 Runtime 是什么？为什么不把它做成经典 Plan-and-Execute？**
受限 ReAct——白名单、受控写、确认门把自由 ReAct 的三个风险（乱调工具、越权改数据、幻觉指令）做了产品化改造。Anthropic 的原则是「能 Workflow 就 Workflow」：预定义路径更可控、可测、更便宜；LLM 规划只在任务无法预定义时才有价值。所以最终形态是**三层分工**——Workflow 管可预定义的流程，Plan 管探索性任务的高层拆解，ReAct 管子目标内部的临场决策。

**Q：那 Plan Preview 解决什么？**
它不解决执行问题，它让 **ReAct 的意图显式化**。原来决策器的规划藏在每步的贪心选择里，用户看不到；现在首轮把 2-4 个子目标摆出来，用户能预判 AI 要干什么，我们也能对照计划和实际执行。

**Q：为什么不直接让计划驱动执行？**
有意分阶段。计划驱动 = 锚定，而首轮计划是**信息最少的时候猜的**（还没读文章、没查记忆）。先验证「计划本身有没有价值」，再验证「锚定是帮助还是干扰」。混在一起做，出了问题分不清是哪个原因。

**Q：观测数据能得出什么？**
三种结果三种结论——执行高度跟随（任务有稳定路径，**该 Workflow 化**）；执行经常偏离且更好（计划没用）；计划合理但执行跑偏（锚定有价值，做阶段二）。**第一种最有价值**：它等于又挖出一个该 Workflow 化的场景。

**Q：计划会不会污染证据链？**
不会，这是设计时划死的边界。计划走独立通道，不进 observations——V3.11 的 Verifier 只认实际观察。优先级序也写死了：用户要求 > 安全约束 > 实际观察 / Verifier > 初步计划。

**Q：为什么计划不做清洗而是整条丢弃？**
清洗会制造「看起来正常但语义已经变了」的计划，用户会当真——比没有计划更糟。这和 V3.10 thoughtSummary 的零修补原则一致：宁可回退到空。

## 七、后续层登记：Plan-guided ReAct 与 Reflection（本刀均不实施）

Codex 评审要求：**阶段二的混合架构与判断标准必须现在就登记**，否则阶段一没有明确的服务对象。

### 目标形态

```text
用户目标
  ↓
初步计划（高层子目标）
  ↓
ReAct 循环：决策 → 动作 → 观察 → Verifier    ← 每个子目标内部自由
  ↓
根据观察：跟随 / 跳过 / 调整计划
  ↓
最终回答
```

### 硬约束（进阶段二设计时不得放松）

1. plan 只作为**独立的参考区块**注入，不与其他上下文混写
2. **不进 observations**
3. **不进 Verifier 的证据输入**——Verifier 只认实际观察
4. ReAct 可跟随 / 跳过 / 偏离，**偏离不算失败**（不 FAILED、不被拉回）
5. 优先级序不变：`用户要求 > 安全约束 > 实际观察 / Verifier > 初步计划`

### 阶段二必须先解决的两个问题（本稿未解）

**①「偏离」与「重新规划」的边界**

- **偏离** = 某一步没按计划第 N 项走，计划整体仍有效
- **重新规划** = 计划整体作废，重新生成

两者判定标准必须分开，否则实现时会糊成一团。选项：

| 方案 | 代价 |
|---|---|
| 每步让 LLM 重新审视计划 | 多一次判断 → 成本 + 与决策器判断不一致的风险 |
| 只在特定信号下重规划（Verifier NEED_MORE / 连续两次偏离） | 规则简单，但可能错过该重规划的时机 |

倾向后者起步，但这是**阶段二的设计题**，不在本刀定。

**② 计划与 Verifier 的分工**

两者管的事不同，不互相干扰：

| | 管什么 | 发言权 |
|---|---|---|
| **Verifier** | 证据够不够（能不能出口） | 决定 FINAL_ANSWER 是否放行 |
| **plan** | 下一步做什么（方向） | 只在动作选择上有弱参考权 |

**Verifier 判定不受计划影响**；计划也不能拿 Verifier 的放行当作「我的方向对了」的证据。

### Reflection（登记，V4 统一决定）

**结论：纳入 V4 能力地图，但不加入 V3.13，也不默认每步都做。**

**它和 Verifier 不是一回事**：

| | 问什么 | 发言权 |
|---|---|---|
| **Verifier**（V3.11 已有） | 证据够不够？当前回答能不能放行？ | 决定 `FINAL_ANSWER` 是否出口 |
| **Reflection**（未做） | 刚才为什么没解决？当前策略是否有效？计划是否还成立？下一轮该调整什么？ | **诊断**，不直接选动作 |

V3.11 已经实现了一部分 evaluator 能力（Generator → Evaluator → Corrective Loop），但**还不是完整 Reflection**——它只判「草案 vs 证据」，不诊断「策略为什么失效」。

**Reflection 有价值的前提：必须改变后续行为。** 如果只是再调一次 LLM 生成「我刚才哪里做得不好」而后续动作不变，那它只是另一种 thoughtSummary——多花 token，多看一段话。

**未来形态（登记，不实施）**：

```text
正常路径：Plan → ReAct 决策 → 动作 → 观察 → 继续 ReAct

特定触发（不是每步）：
  · Verifier NEED_MORE          · 动作连续失败
  · 观察重复、没有新进展         · 计划连续偏离
  · 到达重规划信号
        ↓
  Reflection：诊断策略为什么失效 / 判断计划是否仍有效 / 生成调整建议或 replan 信号
        ↓
  交回 ReAct 决策器：根据 observations + reflection context 选择下一动作
```

**边界（六条不应）**：不直接越过白名单选动作 / 不推翻 Verifier 的出口判断 / 不进 Verifier 的证据输入 / 不每步无条件调用 / 不直接写长期 Memory / 不作为未清洗的内部思维过程展示给用户。

**Claude 补充：先穷尽规则，再上 LLM 反思。**

V3.11 手测那次 6 步空转，最后是用**规则**解决的（R3：本轮观察与前序逐字重复 → 放行）——那是**规则级空转保护**，不是 Reflection：它既不诊断策略、也不生成调整建议，叫「Reflection 替代」会把术语说混。所以：

- 规则能解决的失效（重复、超时、权限）→ **不加 LLM**
- Reflection 只在**规则解决不了**时才值钱（方向性错误、策略整体失效）
- 判断依据同样来自阶段一的观测：如果 PIVOTED 归因里「初始计划错误」占比高 → Reflection 有活干；如果几乎为零 → 它没东西可诊断

### 五层职责关系（V4 完整闭环的骨架）

| 层 | 职责 |
|---|---|
| **Workflow** | 固定流程编排 |
| **Plan** | 高层目标拆解 |
| **ReAct** | 当前动作选择 |
| **Reflection** | 失败或偏航后的策略诊断 |
| **Verifier** | 证据与出口裁判 |

### 与 V4 的衔接

V4 要决定的不是「做不做 Plan-and-Execute」，而是**四档选型的分界 + 五个部件如何协同**：

| 任务形态 | 归宿 |
|---|---|
| 能预定义流程 | Workflow |
| 目标明确、需要多子目标 + 临场判断 | Plan-guided ReAct |
| 目标明确、单步可解 | 纯 ReAct |
| 目标不清 | ASK_USER 澄清 |

外加 Reflection 的触发条件——**哪些失效信号值得一次策略诊断**。

阶段一的观测数据（尤其 FOLLOWED / SKIPPED / PIVOTED 的**归因分布**）是划定这两条分界的实证依据。

### 手测（2026-09-10 通过）

七项全过：计划生成 / 简单请求不出计划 / 实时顺序不闪 / 刷新恢复 / 隔离（计划里有但文章里没有 → Verifier 仍按真实观察判）/ 可偏离（计划 2-3 项、执行步数不等 → 正常收尾）/ 学习域零变化。

手测中发现并处理三件事：

**① 重复查询（已修）**：现象是连续 4 次 `QUERY_MEMORY`（检索到的记忆 id 每次相同），以及两次**一字不差**的 `QUERY_ARTICLE + focus`。

- **排除的假设**：曾怀疑 `clipContext` 从头截断导致 AI 看不到结果——查库 `context_json` 长度 **3446 < 6000**，**未触发裁剪**，假设被证据推翻
- **根因**：决策器 prompt 缺防重复约束——QUERY_ARTICLE 原有那条只覆盖「无 focus」，记忆检索**完全没有**防重复规则
- **修法（不是「禁止重复」而是给终止条件）**：新增「查询一次性语义」——同一动作 + 同一参数重复执行只会得到相同结果；**记忆一次就够，没命中就是确实没有**，此时基于文章本身给建议或说明「没有找到相关写作偏好」，不要用重复查询代替「接受信息不足」。只禁不疏的话，模型会换个 query 继续绕

**② 无指代时选了会话锚（不修，记已知边界）**：跨页场景「A 文章聊完 → 换到 B 文章页 → 问『先看整体结构，再检查 X 那一节』」（消息**无指代词**）→ AI 主动填 `anchorMode: SESSION_LAST` 读了 A。

证据：`ai_agent_steps.input_json = {"anchorMode":"SESSION_LAST", ...}`。按 prompt 规则无指代应为 CURRENT_PAGE，属**遵从度**问题。

**老大判断：产品上这确实是歧义场景**（上一秒在聊 A、下一秒换到 B 页问一句没有指代的话），AI 选哪篇都讲得出道理，**不修**。新会话同问法表现正常 → 与 V3.8 锚机制无关，纯对话历史惯性。

**③ verifier 在线样例 [3] 判定波动（记录待观察）**：全量在线门跑出 1 例失败——「记忆偏好问答有依据」期望 SUFFICIENT、实际 NEED_MORE。该样例为**固定样例直接调验证器、不经决策器**，与本次改动无关；此前全量跑为全绿 → 判定为 LLM 判定波动。是否调样例或 prompt，待后续观察。
