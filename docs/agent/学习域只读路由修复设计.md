# 学习域只读请求被任务编排抢跑：根因与修复

> 创建：2026-10-18
> 触发：真实使用四句话全部没落到"读计划"——两次被直接拉进"制定新计划"工作流，两次被编排成"站内文章检索"。
> 结论：**不是某一句话判错，而是四个层次同时缺边界。** 修复以"不变量"落点，不对任何一句话打补丁。

## 一、现象（真实日志 + 数据库证据）

同一用户 2026-10-18 09:46–09:49 的四句话（`blog-system/logs/blog-system.log`）：

| # | 用户原话 | 实际路由 | 用户看到 |
|---|---|---|---|
| 1 | 讲讲我的Redis的学习计划 | Jev 快速路径 `accepted intent=LEARNING_PLAN goals=[workflow_learning_plan]`（0.83）→ Planner 拉起 `LEARNING_PLAN` 工作流 | 一张"新计划"确认卡（`GENERATE_PLAN` 跑了 14.6s） |
| 2 | 讲一讲我的Redis学习计划 | 同上（0.76）→ 又拉起一次 `LEARNING_PLAN` | 又一张确认卡 |
| 3 | 帮我看看我的Redis学习计划 | Jev 回退（`MULTIPLE_GOALS`）→ plus 判 `intent=LEARNING_PLAN_QUERY / suggestedAction=TOOL`（**正确**），但同一份输出带 `requestKind=TASK + taskGoals=[ARTICLE_SEARCH(query=Redis学习计划)]` → 任务编排抢跑 | 「已全部完成：没有找到与「Redis学习计划」相关的文章」 |
| 4 | 看看Redis的学习计划 | 同上，检索词变成 `Redis` | 「已全部完成：找到 3 篇与「Redis」相关的文章…」 |

**数据侧事实**：用户确实有一个进行中的 Redis 计划——《Redis 核心原理与工程化实战计划（结构优化版）》（`learning_plans.id=2088283195381673985`，ACTIVE），dashboard 读取与名称匹配都能命中它。**"找不到学习计划"不是数据问题，是请求根本没去查计划。**

**铁证**（`blog-system` 库 `ai_agent_runs.task_plan_json`）：

```json
{"schemaVersion":1,"plan":{"goal":"帮我看看我的Redis学习计划",
 "steps":[{"stepId":"s1","type":"ARTICLE_SEARCH","params":{"query":"Redis学习计划"},
 "goalEvidence":["帮我看看我的Redis学习计划"],"after":[],"requires":[],"onFailure":"CONTINUE"}]}}
```

即：分类器主判"查学习计划"（旧字段正确），却同时输出了一份"文章检索"任务计划；任务编排层按后者执行，占掉了前者。

## 二、为什么第一句"找不到"、第二句"找到 3 篇"

两次都执行了文章检索，差别只在检索词：

- 「帮我看看我的**Redis学习计划**」→ `params.query=Redis学习计划`（把"学习计划"当成主题词的一部分）→ 站内 0 命中；
- 「看看**Redis**的学习计划」→ `params.query=Redis` → 命中 3 篇 Redis 文章。

所以"0 篇 vs 3 篇"完全来自**关键词切分**，与"有没有学习计划"无关。两句话都没有执行 `getLearningDashboard`。

## 三、根因：四层结构问题

### 3.1 语义层：学习域"读/讲已有计划"没有归属，两套分类定义还互不一致

- plus 分类器 prompt：`LEARNING_PLAN` 只接"表达学习诉求 / 帮我规划路线"；`LEARNING_PLAN_QUERY` 只定义"询问或查看…列表与状态"；`LEARNING_AGENT` 接"分析、评价"。**"讲讲 / 帮我看看已有计划内容"三头不靠**。
- Jev 决策协议 13 个 goal 里只有 `workflow_learning_plan`（制定新计划）与 `learning_plan_query`（查询进度或内容），且都是**独立的二元判据**。句子里出现"学习计划"这个对象就足以让"制定"判真——「讲讲我的X学习计划」被最近的写目标吸走（0.83 / 0.76，均 ≥ 0.70 门槛）。
- 两套分类体系对同一句的解释不同：Jev 说"内容查询"，plus 说"列表/状态查询"。**谁接手谁有说法**，这是两套定义漂移的典型后果。

### 3.2 协议层：taskGoals 只有文章域类型，"只读查询"没有合法出口

`EXAMPLES_AND_SCHEMA`（常装块）里 `taskGoals.type` 全集是：

```
ARTICLE_WRITE / ARTICLE_SEARCH / NAVIGATE / ARTICLE_ANALYSIS / WORKFLOW_HANDOFF
```

没有"读学习计划"类型；`requestKind` 又只定义了"任务 vs 普通问答/闲聊/纯粹讨论"，**没有把"只读工具查询"归入 CHAT**。而"单目标也要输出""所有字段都必须输出"让模型倾向填 taskGoals——它只能挑最像查询的 `ARTICLE_SEARCH`。

更隐蔽的一层：ON_DEMAND 装载把**域判定规则**（SEARCH 块）裁掉，却把**任务协议**（COMMON 的 `EXAMPLES_AND_SCHEMA`）留着——模型"知道可以拆 ARTICLE_SEARCH，但不知道站内检索该怎么判"。

**结论：这不是模型乱写，是协议没给合法出口。**

### 3.3 路由层：任务编排是"插队者"，不是"仲裁者"

`AiMessageServiceImpl` 的顺序是：分类 → Planner 裁决（`TOOL getLearningDashboard`，正确）→ **无条件**问 `TaskPlanningFacade`。只要返回 `ORCHESTRATE` 就直接 `return`，Planner 的 TOOL 决策被丢弃；而 TOOL 没有独立分发分支，只在普通聊天里启用——**根本没走到**。

`TaskPlanningFacade` 的判据盲区：

- 唯一能拦"单步 ARTICLE_SEARCH"的豁免要求 `intent == ARTICLE_SEARCH`，本例是 `LEARNING_PLAN_QUERY` → 不豁免；
- 四条 fail-closed 判据全部读文章域旧字段（分析证据 / 请求动作 / Workflow 信号），本例全空 → 全部退场；
- 没有任何"计划步骤域 vs 主意图域"一致性校验，也没有"只读意图不得编排"；
- Facade 连 `pageContext` / `AgentDecision` 都不接收，设计稿 §5.1 的"只承接文章域目标、不做跨域编排"没有落地。

### 3.4 观测与评测层：故障不可见、评测抓不到

- 分类器日志与 `AgentDecisionTrace` 都不记录 `requestKind` / `taskGoals`，排障只能靠"`steps=1`" 反推，或翻数据库 `task_plan_json`；
- 评测集里 15 处 `expectedRequestKind` 全是 `TASK`，学习查询样例不断言 `requestKind` / `taskGoals`；断言维度也缺"**taskGoals 必须为空**"（只有"至少几个 / 包含哪些"），于是"多出来一个目标"这一类故障没有任何测试会红；
- `TaskRoute × AgentDecision` 的优先级没有任何入口级测试。

## 四、修复：五个不变量（已实施）

| # | 不变量 | 落点 | 违反时的行为 |
|---|---|---|---|
| I1 | **只读查询不是任务**：只读意图携带的 taskGoals 一律不可信 | `AiIntentClassifierImpl.reconcileReadOnlyContract`（`suggestedAction=TOOL` 或 `intent=LEARNING_PLAN_QUERY` → 清空 taskGoals、`requestKind=CHAT`，WARN 日志留证） | 丢弃模型候选，主意图保留，交给旧链 |
| I2 | **非文章域主意图不得进入任务编排** | `TaskPlanningFacade` 白名单 `ORCHESTRATABLE_INTENTS`（文章域 8 个 intent），在 `planner.plan()` **之前**仲裁，返回 LEGACY | 忽略任务候选，Planner 决策照常执行 |
| I3 | **快速路径只读可快，写意图交完整分类器** | `JevFastPathMapper.WORKFLOW_TYPES` 移除三个学习 Workflow（保留文章两个） | 学习类写请求回退 plus；只读意图（含 `learning_plan_query`）继续快速路径 |
| I4 | **学习域语义边界**："讲讲/看看已有计划内容" = `LEARNING_PLAN_QUERY`（只读），不是制定；要分析评价才 `LEARNING_AGENT` | 分类器 prompt 的 `LEARNING_PLAN` / `LEARNING_AGENT` / `EXAMPLES_AND_SCHEMA` 三块 + 基线文件 | 模型判错时由 I1/I2 兜底，不再产生用户可见错误 |
| I5 | **被点名的计划必须成为 dashboard snapshot** | `AiLearningDashboardTool.selectPlanByQuestion`：问句唯一命中一个 ACTIVE 计划就用它，否则维持"取最新活跃" | 多计划用户不会被喂错计划上下文（事故用户有 9 个 ACTIVE，Redis 计划创建最早，旧实现固定取最新的 C++ 计划） |

配套观测（本次排障的直接教训）：

- 分类器成功日志新增 `requestKind=` / `taskGoalTypes=`；
- `AgentDecisionTrace` 新增 `requestKind` / `taskGoalTypes` 两个字段并落日志；
- `TaskPlanner` 的 `[TASK-PLAN] 计划生成` 打印 `stepTypes` / `uncoveredTypes`；
- Facade 域仲裁命中时打 WARN（含主意图与被忽略的目标类型）。

### 4.1 为什么 I2 选"交接旧链"而不是 CTA

主意图是分类器综合判断的最高级结论（prompt 更大、有评测门）；被忽略的是模型**候选**，不是用户目标。对"只读查询"而言，旧链的 dashboard 能完整回答；对"学习 Workflow"而言，旧链本来就能拉起正确工作流。判据只拦不补，不自行造步骤。

**残余风险（登记）**：如果一句话**真的**是跨域复合（"看看我的计划，再搜一下 Redis 文章"），当前行为是执行主意图、不执行次要目标。分类协议里没有学习只读目标类型，真正的跨域编排是设计稿 §5.1 明确不做的范围，需要单独设计；在此之前，这种请求不会被"执行半份还声称完成"（任务层被整体忽略），但也不会主动提示次要目标未执行。

## 五、明确不做的方向

| 方向 | 为什么不做 |
|---|---|
| 新增学习域 TaskStep（`LEARNING_PLAN_READ`） | 与 dashboard TOOL 链功能重复；确定性渲染器只能回"已全部完成：已读取计划"，比现在 LLM 总结更难用；跨域编排不在设计稿范围 |
| 用"讲讲 / 看看 / 说说"关键词表判意图 | 词表是闭集、表达是开集，补不完；且项目已两次证伪"字面规则复核语义"（`AgentPlannerSupport` 注释、学习域七连修） |
| 让 Planner 决策永远优先于 TaskRoute | 会打回 5b 的合法复合编排（`handoff + 写动作` 必须由新编排执行） |
| 把"讲讲我的计划"判成 `LEARNING_AGENT` | 用户要的是"看内容"；`LEARNING_PLAN_QUERY` 是只读、dashboard 已能返回计划详情并由 LLM 讲解，与"分析/评价才走 AGENT"的既有分界一致 |
| 改 `TaskPlanner` 的校验语义 | 它的"不猜、不丢、不补"边界已被 400+ 行测试锁住，本次问题不在它 |

## 六、取舍与代价

1. **Jev 移出三个学习 Workflow**：这三类请求会多一次 plus 分类（本机实测 plus 约 6s；工作流本身 17s）。换来的是写意图不再被二元判据直接拉起——原判断"确认型 Workflow 判错只是多问一次"被真实代价推翻：**多跑一次完整工作流 + 错误计划卡 + 真实计费**。文章两个 Workflow（创建 / 优化）动词明确、与只读意图在 Jev 判据里分得开，保留快速路径。
2. **I1 与 I2 是两层防御**：I1 让日志与评测里不再出现自相矛盾的意图；I2 保证即使未来又出现新的"只读意图 + 可执行候选"，也不会再抢跑。两者都在离线测试里锁住，不依赖模型遵循度。
3. **prompt 改动**必须过在线评测门（见 §8）。学习计划查询的三条旧样例原本**不断言** `requestKind` / `taskGoals`，本次补了断言维度与新样例。

## 九、手测追加修复：学习 Agent 决策上下文只有元数据（2026-10-18）

上一节的手测清单在「帮我分析我的Agent学习计划，看看有没有问题」这一条暴露了**另一个独立缺口**。它不属于本文件 §三 的四/五层，而是 **P4.1 Token 优化（`LearningAgentState`）的回归**。

### 9.1 现象（真实 run 证据）

- `ai_agent_runs.id=2111647073112850434`：「帮我分析我的Agent学习计划，看看有没有问题」→ 走 `LEARNING_AGENT`。
- step1 `QUERY_LEARNING_DASHBOARD` **成功**，`planRef=两个月 Agent 开发入门到实战计划（Java后端方向）`，执行器 summary 里有完整阶段/任务；
- 但模型最终回答是：「**当前观察仅包含计划元数据，缺乏具体的阶段、任务或记忆细节，无法直接评估内容质量**」，随后 step2~5 全部是同一查询被去重跳过（`SKIPPED`），最后放弃。

### 9.2 根因

学习域 Token 优化后，决策上下文**不再回放 `summary`**，只消费 `LearningAgentState` 从 `payload` 归约出的事实；而执行器给的 payload 只有元数据：

| 动作 | 旧 payload | 模型实际能看到 |
|---|---|---|
| `QUERY_LEARNING_DASHBOARD` | `status/planRef/planCount/activePlanCount/matchedCount/selectedPlanId` | 只知道"匹配到 1 个计划"，**看不到阶段与任务** |
| `QUERY_MEMORY` | `status/query/hitCount` | 只知道"有 N 条偏好"，看不到偏好内容 |
| `SEARCH_RAG` | `status/keyword/hitCount` | 只知道"命中 N 条"，看不到片段 |

于是「分析计划」必然信息不足；再查同一计划 → 状态去重键相同 → `lastStepHadNewEvidence=false` → Runtime 判重复查询跳过 → 直到 `maxSteps` 耗尽。

**设计稿本身也没覆盖这一层**：`docs/superpowers/specs/2026-10-08-learning-agent-state-design.md` 的 payload 表就只列了元数据，并写明"summary 不作为结构化事实的来源"——出发点是去重/预算，但把**证据内容**一起裁掉了。这是"省 token 省掉了回答依据"的典型。

### 9.3 修复（payload 带内容，summary 仍只做展示）

| 动作 | payload 新增 | 上限 | 状态事实 |
|---|---|---|---|
| `QUERY_LEARNING_DASHBOARD` | `planDetail`（计划标题/状态/总进度/各阶段任务 [x]/[ ]）、`planCandidates`（未命中或歧义时的候选标题+状态） | 1400 / 500 字符 | `planFact` 追加"计划内容：…；候选计划：…" |
| `QUERY_MEMORY` | `memoryContent`（命中的常驻/语义/情景记忆行） | 500 字符 | `memoryFact` 追加"记忆内容：…" |
| `SEARCH_RAG` | `ragContent`（标题+文章ID+片段） | 700 字符 | `ragFact` 追加"检索片段：…" |

- 内容仍由**结构化对象直接构造**（不解析 summary），符合原设计"summary 不是事实来源"的约束；
- 各槽位预算不变（`PLAN_BUDGET=1800` / `MEMORY_BUDGET=600` / `RAG_BUDGET=800`），内容有界 + `…（后略）` 标记，不会把上下文撑爆；
- 去重语义不变：同一 `planRef+selectedPlanId` 的重复查询仍是同一事实——但第一次查询就带内容，模型不需要重查。

### 9.4 验证

- `LearningAgentActionExecutorTests`：新增"payload 带 planDetail"用例；多命中/未命中断言 `planCandidates`；记忆/RAG 命中断言 `memoryContent` / `ragContent`。
- `LearningAgentStateTests`：新增三例——`planDetail` 进决策上下文且 summary 仍不回放、`planCandidates` 进上下文、记忆/RAG 内容进上下文；预算用例保持原样（无内容时行为不变）。
- 手测：同一句「帮我分析我的Agent学习计划，看看有没有问题」应直接基于阶段/任务给出分析，steps 不应出现连续"已跳过重复查询"。
