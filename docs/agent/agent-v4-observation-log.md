## 一、怎么跑

每条样本 = 在**文章详情页**发一次请求 → 到 `/dev/agent-runs` 打开对应 run → 记一行。

**样本清单**（按顺序跑一遍，约 8 条）：

| # | 类型 | 请求原文 | 预期 |
|---|---|---|---|
| 1 | 多目标·三子目标 | 先看整体结构，再检查缓存击穿那一节，最后结合我的写作偏好给建议 | 出 plan（3 项） |
| 2 | 多目标·两子目标 | 先看整体结构，再看看缓存击穿那一节 | 出 plan（2 项）——**边界：2 项够不够触发** |
| 3 | 多目标·含检索 | 先看整体结构，再找找站内有没有讲 Redis 高可用的文章对比一下 | 出 plan（含检索子目标） |
| 4 | 单目标·带 focus | 这篇文章的缓存击穿那一节写得怎么样 | **不该出 plan**（单一目标）——对照 |
| 5 | 简单请求 | 整篇文章写得怎么样 | **不该出 plan** ——对照 |
| 6 | 偏航·目标落空 | 先看整体结构，再检查分布式锁那一节 | 出 plan，第 2 项必然查不到 → 看它怎么收场 |
| 7 | 偏航·意图转向 | 先看看整体结构，再帮我优化一下这篇文章 | plan 说"分析"，实际可能直接 SUGGEST_WORKFLOW |
| 8 | Verifier | 这篇文章里分布式锁是怎么实现的 | 文章只提了方案没讲实现 → 看拦不拦、怎么收尾 |

> 样本 1、5 与 V3.13 手测用过的一致，可**纵向对比**修复前后。

## 二、怎么判（FOLLOWED / SKIPPED / PIVOTED）

打开 run 详情，把 **plan 的每一条**与 **steps 的 action 序列**并排看：

| 情形 | 判定 |
|---|---|
| 有一步明显是冲这一项去的 | ✅ **FOLLOWED** |
| 这一项没被执行，但**不做也答出来了**（信息本来就有） | ⏭ **SKIPPED**（合理自适应，不是计划失败） |
| 这一项没被执行，**改做了别的事** | 🔀 **PIVOTED**（记下"换成了什么"） |
| 这一项执行了但**没拿到东西**（FAILED / 观察重复） | ⚠️ 记下 `errorMessage` |

**PIVOTED 归因**——只有第 4 类才指向计划质量：

| 归因 | 例 |
|---|---|
| 新证据转向 | 第 1 步发现文章结构特殊，改查别的 |
| 用户改口 | 请求本身前后矛盾（样本 7） |
| 工具失败 | 查不到、动作 FAILED（样本 6） |
| **初始计划错误** | 计划本身把方向定错了 ← **只有这类说明计划有害** |

1. **分类器判定不可复现** —— 同句同条件（「对比…这两节」+ 新会话）第二轮走 Agent、第三轮走 QA。**上一轮「受对话历史影响」的结论不成立**（那是 1 个对照点的巧合）。

4. **无支持阶段二的证据**：有 plan 的那条反而最坎坷（6/6 + 被拦）；第二轮「有计划更精准」的两条正例，其实**用户请求本身已写明步骤**（「先看…再检查 X 那一节…」），plan 只是复述。

> **教科书案例**（`2098414178940325890`）：用户问的「缓存穿透」**文章里根本没有这一节** →
> ① focus 定位失败静默降级返回结构摘要 → ② 模型凭空评价该节 → **Verifier 拦住**（「未命中缓存穿透的具体段落」）→
> ③ 模型重试同参 focus → **重复拦截拦住** → ④ 步数用满收尾。
> **每层保护都按设计工作了**，但用户体验是「问了 6 步没结果」——问题出在第 ① 步：**降级时没有告诉模型「你要的那一节不存在」**。

## 七、观测结论（2026-09-11，五轮共约 27 条样本）

> ### 阶段二 Plan-guided ReAct —— **不做**

依据 §9.2 决策表，数据落在「**计划与执行高度一致，且路径稳定 → 优先考虑 Workflow 化**」。

| 证据 | 数据 |
|---|---|
| 计划-执行对应 | 几乎全部 FOLLOWED；少数 SKIPPED 均合理（信息已够即不再查） |
| **PIVOTED「初始计划错误」** | **0 次**——计划从未把方向带偏 |
| **「无计划就绕路」的稳定证据** | **无**——唯一疑似案例（第二轮样本 5）被证明是 focus bug，修复后消失 |

**诚实补充**（§9.3）：27 条样本、同一篇文章、同类请求——**不构成统计证明**。但作为决策依据足够：**关键反例一次都没出现，而「不做」是保守选择**（不引入复杂度）。

**V3.13 阶段一的价值不受影响**：计划展示对用户仍有透明度收益（看得见 AI 打算做什么），只是**不需要再往前一步去驱动执行**。

**第一刀的复利**（附带产出）：五轮观测共暴露并修复 3 个真问题——① 重复查询根因（观察缺来源标注）② focus 无法定位时静默降级 ③ 一条静默失效的测试（断言被无关内容满足）。**全都是靠那个只读面板发现的**。

## 五、攒够之后怎么读（§9.2 决策表）

| 观测结果 | 判断 |
|---|---|
| 计划与执行高度一致，且路径稳定 | **优先考虑 Workflow 化**（不该做阶段二） |
| 计划经常被合理跳过 | 不急于加入计划锚定 |
| 计划经常错误、偏离后结果更好 | **不做 Plan-guided ReAct**，先改计划生成或放弃 |
| 计划合理，但**无计划时动作明显跑偏** | 适合做受控弱参考试点 ← **只有这一行支持阶段二** |
| 偏离主要由新证据 / 用户改口 / 工具失败造成 | 不把问题归因于计划 |
| Verifier 经常拦截但规则无法诊断方向错误 | 评估 Reflection |

## 六、观测产出的待办（2026-09-11）

| # | 发现 | 处置 |
|---|---|---|
| 1 | **样本 6 多目标漏出计划**（样本 3 同样 2 个子目标却出了） | **先记录不改**——计划生成率是观测指标，不是必须 100%；且改决策器 prompt 必跑评测门。**复现 3 次以上再动** |
