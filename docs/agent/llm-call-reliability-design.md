# LLM 调用可靠性：重试与失败分类

> 状态：✅ 已实施（2026-09-19）· 复测见 §7
> 上游：[准入压测报告](agent-admission-stress-report.md)（本刀就是它暴露问题的接续）
>
> **实施结果摘要**：`LlmErrorClassifier` 升级为失败分类 + 退避策略；`LlmStreamCaller` 加首字节前重试
> （单点覆盖 5 个 Workflow 步骤）；非流式路径靠 `spring.ai.retry.on-http-codes: 429` 统一覆盖；
> 降级文案改为可行动。实施中发现并修掉一个**原有缺陷**：`classify` 只看最外层异常 message、
> 不看 cause 链（见 §8）。

## 0. 一句话

压测暴露「429 零重试 → 静默降级」，挖下去发现**根因不在项目代码，而在 Spring AI 的默认行为**；
本刀把「什么该重试、重试几次、退避多久、耗尽后怎么降级」变成**显式的、按调用点分级的策略**。

## 1. 实测证据链

| 环节 | 证据 |
|---|---|
| 现象 | 40 并发压测，**30/40** 个请求的意图分类被 429 打挂，静默降级成闲聊（报告 §3.1） |
| 日志 | `NonTransientAiException: HTTP 429 - {"code":"limit_requests"}` × **70** |
| 日志 | `Retry error. Retry count: 1` × **35**，**只有 count=1** → 第 1 次尝试后即放弃 |
| 代码 | `AiIntentClassifierImpl:109-112` catch → `return null` → `generalChat()` 降级 |
| 框架 | `SpringAiRetryAutoConfiguration`：4xx → `NonTransientAiException`（`onClientErrors` 默认 false）→ RetryTemplate 不重试 |
| 框架 | 该 RetryTemplate **只作用于 `.call()`**，`stream()` 路径完全没有重试 |

**一句话**：项目**有**重试框架、**配了**超时，但**默认策略恰好把 429 划成了不可重试**，
而真正需要重试的流式路径又不在框架覆盖范围内。

## 2. 现状盘点（侦察结论）

### 2.1 调用点与失败处理

**22 个 LLM 调用点**，按失败处理分四类：

| 类别 | 行为 | 典型 |
|---|---|---|
| **抛给上层**（最健康） | 抛 RuntimeException，上层记 FAILED / 让用户 retry | Workflow 的 5 个流式生成步骤 |
| **静默降级成别的功能** | catch → 换一种行为，用户无感知 | 分类器 → GENERAL_CHAT |
| **静默吞掉** | catch → `return null` / 空列表 / 默认值 | 记忆提取、摘要压缩、Agent 收尾总结、向量召回 |
| **fail-open 放行** | catch → 跳过检查继续 | 证据收敛门 `ArticleEvidenceVerifier` |

⚠️ **风险最高的是 fail-open 那类**：`ArticleEvidenceVerifier` 两次失败即放行 ——
**校验机制在故障时等于不存在**，而调用方以为它在工作。

### 2.2 现有重试机制（3 套，互不相通）

| 机制 | 覆盖 | 策略 | 问题 |
|---|---|---|---|
| Spring AI `RetryTemplate` | **仅 `.call()`** | maxAttempts=10 + 指数退避，但只重试 `TransientAiException` | 429 被判成不可重试；流式完全不覆盖 |
| `RagRetryQueue` + `ArticleRagSyncService` | 仅 RAG 索引 | 同步 3 次（`Thread.sleep`，非指数）+ 延迟队列 5 次（60s×2^n，封顶 1h） | 结构通用但**强绑 RAG**（member 里硬编码 articleId） |
| Workflow 一次性重跑 | 2 处特例 | 失败后立刻重来一次，无退避 | 覆盖率低、无退避 |

**共同缺陷**：都是 `catch (Exception)` 或 `catch (Throwable)` **全量重试**，
**不区分「重试有意义」和「重试纯浪费」** —— 参数错误、内容违规重试 10 次也是白搭。

### 2.3 面向供应商的控制

**没有**。唯一的 `aiTaskExecutor`（8 worker）只管 Agent / Workflow 编排任务；
意图分类（Tomcat 线程）、聊天流、记忆提取（`memory-extraction-`）、摘要（`conversation-summary-`）、
RAG embedding（`rag-sync-`）**各自为战，没有任何全局约束**。

**熔断 / 舱壁 / `Retry-After`**：均无。

## 3. 关键设计决策

### 3.1 先分失败类型，再谈重试

**这是本刀的核心**。当前项目「全量重试」或「全量不重试」都是错的。

| 失败类型 | 判定依据 | 策略 |
|---|---|---|
| **限流** | HTTP 429 / `limit_requests` / `Throttling` | **必须重试**（暂时性，退避后大概率成功）+ **优先遵循 `Retry-After`** |
| **超时 / 连接失败** | `SocketTimeoutException` / `ConnectException` | 重试 |
| **服务端错误** | HTTP 5xx | 重试 |
| **参数 / 鉴权错误** | HTTP 400 / 401 / 403 | **不重试**（重试改变不了结果，纯烧钱） |
| **内容违规** | 供应商的内容审核拒绝 | **不重试** |
| **JSON 解析失败** | 响应非 JSON / 字段缺失 | 重试（模型输出不稳定，重试常能修好），但应**带上"上次格式错了"的提示** |

> 现有 `LlmErrorClassifier` 已经**识别**了 429（`:39-43`），但只用来**生成中文文案**，
> 没参与任何重试决策。本刀要把这个判定**提升为策略输入**。

### 3.2 流式路径的重试：只在首字节前

Spring AI 不覆盖 `stream()`，而 Workflow 的 5 个生成步骤全是流式 —— **这是缺口最大的地方**。

**难点**：流式已经吐出部分内容后再失败，重试会导致**重复输出**。

**方案**：**只在首字节之前重试**。

```
未收到任何内容 → 可重试（用户什么都还没看到，重试无痕）
已收到内容     → 不重试（重试会重复，不如让本次失败，用户手动 retry）
```

**改造单点**：`LlmStreamCaller` 是 5 个 Workflow 步骤的公共骨架 —— **一处改造覆盖全部**。

### 3.3 退避策略：按「用户在不在等」分档

**这是和对用户的影响直接挂钩的**，不能一刀切：

| 场景 | 退避 | 理由 |
|---|---|---|
| **同步路径**（分类器、主聊天） | **秒级**：1s → 2s → 4s，**最多 2-3 次** | 用户在屏幕前等，退避太久不如直接降级 |
| **异步路径**（记忆、摘要、RAG 索引） | **分钟级**：60s × 2^n，封顶 1h，最多 5 次 | 用户不在等，可以慢慢来（沿用 `RagRetryQueue` 已有策略） |
| **Workflow 步骤** | 秒级 3 次；仍失败 → FAILED + 用户手动 retry | 用户在看进度，但步骤本身耗时长，可以多等一会儿 |

**加抖动**：`delay = base × 2^n × (0.5 ~ 1.5)` —— 避免多个请求**同步重试**再次打成脉冲
（这次压测的 40 个并发就是同步到达，重试若不抖动会复现同样的问题）。

### 3.4 重试耗尽后：降级要「说清楚」

现状是重试耗尽 → 静默降级（分类器已有 `CLASSIFIER_DEGRADED` 提示 ✅，其余多处没有）。

**原则**：
- **用户在等 → 必须让他知道发生了什么**，且必须是**可行动的**（"稍后再试"而不是"出错了"）
- **审计类降级（证据门 fail-open）→ 至少要留可检索的日志**，不能连痕迹都没有

### 3.5 不引入新框架

`resilience4j` / `sentinel` 能一次给全（重试 / 熔断 / 舱壁），但：

- 当前只有**一个**外部依赖（LLM 供应商）
- 项目已有的组件（`RagRetryQueue` 的延迟队列、准入池）**结构可复用**
- 引入框架 = 新的一层配置 + 学习成本，而**真正的问题（429 被判为不可重试）一行配置就能解决**

**先用手写策略把问题解决掉**；真要上熔断时再评估框架（那时是「单依赖」变「多依赖」的触发条件）。

## 4. 范围

### 做

1. **失败分类器**：把 `LlmErrorClassifier` 从「文案映射」升级成「重试决策」（可重试 / 不可重试 + 退避建议）
2. **让 429 可重试**：非流式路径走 `spring.ai.retry.on-http-codes` 配置；流式路径自己实现
3. **流式首字节前重试**：改 `LlmStreamCaller`（单点覆盖 5 个 Workflow 步骤）
4. **分级退避**：同步秒级 / 异步分钟级（异步复用 `RagRetryQueue` 的思路）
5. **抖动**
6. **降级语义**：重试耗尽后的提示改成可行动的

### 不做（登记）

- **面向供应商的全局并发闸**（第二刀）——它要动所有调用点的线程模型，单独做更清楚
- **熔断**——单依赖场景下收益低
- **把 12 处静默降级全部改造**——量大且多数无害（记忆提取失败丢一条记忆可以接受）；
  只改**用户可感知**和**审计类**的
- **换备用模型**——没有第二个供应商

## 5. 验证方式

**复用压测脚本**（`deploy/ai-stress/stress.mjs`），同一场景跑前后对比：

| 指标 | 压测前 | 目标 |
|---|---|---|
| 40 并发下 `GENERAL_CHAT` 降级数 | **30/40** | 显著下降 |
| 429 后重试次数 | 0 | ≥1 |
| 用户侧失败率 | 75% | 下降 |

**成本**：1–2 元（同前）。

> ⚠️ 注意：**重试会把压力重新打回供应商**。若供应商限流是硬配额（而非瞬时限流），
> 重试只会延后失败。所以复测时**要同时观察「重试后成功」与「重试后仍失败」的比例**——
> 后者高说明需要的是**主动限流**（第二刀），而不是重试。

## 6. 风险

| 风险 | 对策 |
|---|---|
| **重试放大供应商压力**（限流时重试 = 火上浇油） | 指数退避 + 抖动；且**限流类错误的退避要更长**（优先遵循 `Retry-After`） |
| 重试导致**重复扣费 / 重复写库** | 重试只包住**LLM 调用本身**，不包业务副作用；写动作在调用返回后执行 |
| 流式重试造成**重复输出** | 只在首字节前重试（§3.2） |
| **超时被重试放大**（60s × 3 = 3 分钟） | 重试的**总时间预算**要有上限（比如 90s），超了就放弃降级 |

## 7. 复测结果（2026-09-19）

同一场景重跑：`deploy/ai-stress/stress.mjs --users 40 --per-user 1`。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 意图分类**调用失败**（`AI意图识别调用失败`） | 30 | **0** ✅ |
| **`降级为普通聊天`** | 30 | **0** ✅ |
| 框架重试次数 | 0 | **95** |
| **进入准入池的请求**（`[AI-TASK] start`） | 10 | **15**（+50%） |
| 首字节 P50 | 7.6s | **34s** ⚠️ |
| rate limit 日志条数 | 30 | **84** ⚠️ |

### 7.1 有效：429 不再直接降级

`AI意图识别调用失败` 从 30 归零、`降级为普通聊天` 0 条 —— **重试确实把被限流打挂的调用救回来了**，
进入目标路径（learning-plan）的请求从 10 涨到 15。

### 7.2 代价：耗时 4.5 倍、供应商压力 2.8 倍

- rate limit 日志 30 → **84**：**重试把压力打回了供应商**（正是 §5 预警的情况）
- 首字节 P50 7.6s → **34s**，其中相当一部分是退避等待

**结论**：`max-attempts: 3` 偏重，**降到 2 次**更合理（保留救回能力，砍掉最长的第三轮退避）。

### 7.3 但暴露了更根本的问题：**判不准**

修复后仍有 **25 个请求被模型判成 `GENERAL_CHAT`** —— 这次**不是降级**
（`降级为普通聊天` 日志 0 条、`AI意图识别调用失败` 0 条），而是**模型自己判的**：

> 同一句「我想系统学 Redis」，40 个请求里**只有 15 个判成了 `LEARNING_PLAN`**。

**这层问题第一次压测时被掩盖了**：那时模型**压根没机会判**（调用就被 429 拒了），
于是 30 个降级和「判错」看起来是同一件事。重试修好之后，**模型能力问题才露出来**。

**重试解决不了它** —— 重试同一个模型，它还是判不准，只是多烧几次钱。

### 7.4 附带发现：`confidence == 0.0` 不是降级的可靠判据

`isClassifierDegraded` 用 `confidence == 0.0` 判断是否降级，但实测**模型自己也会给出 0.0**
（那 25 个非降级的 `GENERAL_CHAT` 置信度全是 0.0）。后果是：
**模型正常判成闲聊时，用户也会看到「这次没理解准」的提示**——提示与事实不符。

修法应该是给降级打**显式标记**（`AiIntent` 加 `degraded` 字段），而不是靠 confidence 反推。
**登记不修**（本轮范围外，且影响只是提示文案不准）。

### 7.5 更深一层：判断链压根没设 temperature（真根因）

跑评测发现 37 例 8 败后继续挖，找到了这条：

**`AiJudgeModelSupport.applyTo()` 只设 model，不设 temperature** ——
所以分类器走的是服务端默认（OpenAI 兼容 API 默认 **1.0**）。

**佐证**：这个类的注释里其实**已经描述过症状**：

> 同一句话「帮我分析我的Agent学习计划」，换模型后判出**完全不同的结果**

但当时的归因是「分类器本质是让 LLM 画一条分界线，换模型就是换把尺子」，
于是解法做成「换个更强的模型」+ 配 `judge-model`。
**模型确实是因素之一，但同一模型内的随机性来自 temperature，这一半当时漏了。**

配上强模型后症状减轻（不再"完全判不出来"），但没消失（边界 case 仍然飘）—— 于是留到了现在。

**修**：`applyTo` 固定 `temperature(0.0)`。判断型任务要的是**确定性**，不是多样性。
影响 3 个判断链调用点（分类器 / Agent 决策器 / 证据验证器）；
**生成链不受影响**（那些调用点不走本方法，保留默认温度——用户要的正是文字多样性）。

**效果（评测 A/B，同一评测集）**：

| | 修前 | 修后 |
|---|---|---|
| 失败数 | **8 / 37** | **4 / 37** |

**但有得有失，必须说清楚**：
7 个原本失败的修好了，**同时 4 个原本"飘对"的变成稳定错** ——
温度 0 让输出**确定了**，而**确定的答案不一定是正确答案**。

剩下的 4 个**全是「分界」case**（区分 `LEARNING_AGENT` vs `LEARNING_PLAN_QUERY`、
`ARTICLE_DETAIL_QA` vs 相邻意图这类极细边界）：

> **温度解决的是「飘」，解决不了「分辨不出」** —— 后者要靠 prompt 调优或更强的模型。

> **📌 本轮到此为止，这 4 例登记为已知缺口**（决策 2026-09-19）：
> 评测门规则是「在线门全绿才能收口」，所以**当前处于未收口状态**——
> 后续任何改动分类器 prompt / 意图枚举 / 路由优先级之前，**先看这个已知缺口是否扩大**。
> 要收口的话，方向是：针对这 4 个分界 case 细化 prompt 规则，或换更强的判断模型。

### 7.6 契约变更：`applyTo` 从「换模型」升级为「判断链参数配置」

`AiJudgeModelSupportTests` 原先锁的契约是「**不配 judge-model 时零行为变化**」
（`applyTo` 完全不动 builder，因此 temperature 随服务端默认）——
这条「零行为变化」当初是当作**优点**写进测试的，事后看**正是它的代价**。

新契约：**temperature 与是否配模型无关，永远压到 0**；model 仍然只在配了 judge-model 时覆盖。
测试已同步更新。

## 8. 实施中发现并修掉的**原有缺陷**

### 8.1 `classify` 只看最外层异常的 message，不看 cause 链

写单测时抓到的：

```java
new RuntimeException("boom", new ConnectException("Connection refused"))
// .getMessage() == "boom"  ← 真正的错误信息在 cause 里，被完全无视
```

而**同一个类**里的 `containsTimeoutException` 一直是**遍历 cause 链**的 —— 两种判定行为不一致。

**影响**：框架包装过的异常（`RuntimeException("AI 服务调用失败", new ConnectException(...))`）
会被判成 `UNKNOWN` → **不可重试** → 网络抖动也不重试、直接降级。
这个缺陷**改造前就存在**，只是原先没有「可重试判定」这个用途，所以没人碰到。

**修法**：`collectMessages(e)` 把整条 cause 链的 message 拼起来再匹配（深度上限 10 防自引用成环）。
