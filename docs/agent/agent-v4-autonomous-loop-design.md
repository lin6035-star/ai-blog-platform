# Agent V4：AI 助手自主闭环整体设计（讨论稿）

> 日期：2026-09-11  
> 状态：讨论稿 v3（2026-09-11 第一轮讨论后 Codex 复核微调），未实施  
> 前置：V3.11 Evidence Verifier、V3.12 Conclusion Inheritance、V3.13 Plan Preview 阶段一已完成并通过当前约定的测试与手测。  
> 目的：把 V3.11～V3.13 的局部试点整理成一套可解释的 Agent 架构，并决定下一批真正值得实施的能力。

## 〇、结论先行

V4 不是一个单独功能，也不是马上开始写代码的版本。V4 是一次架构设计任务，核心问题是：

> **什么应该交给 LLM 动态决定，什么必须由后端写死和裁判？**

当前建议的总体方向：

1. 能预定义的业务流程继续使用 `Workflow`。
2. 单步可解、目标明确的请求使用受限 `ReAct`。
3. 目标明确但包含多个子目标、且每个子目标需要临场判断的请求，才考虑 `Plan-guided ReAct`。
4. 目标不清时先 `ASK_USER` 澄清，不让 ReAct 替用户猜目标。
5. `Verifier` 负责证据和出口判断，不能被计划说服。
6. `Reflection` 只在规则无法解决的策略失效场景触发，不每步调用，也不直接执行动作。
7. 状态、权限、白名单、确认门、并发、失败语义和最终裁决继续由后端手写。
8. 框架先作为能力对照对象，不替换现有 Runtime；如果引入，优先考虑只读观测和调试能力。
9. 第一刀已定为**开发者只读 run/step 可视化**（先降低后续判断成本），全局思考展示列第二，其余能力等各自证据（§10.1）。

这是一组**待讨论的设计原则**，不是已经完成的 V4 实现。

## 一、为什么需要 V4

### 1.1 当前系统已经具备什么

项目已经不是只有一个 LLM 调用，而是形成了多种 AI 执行形态：

```text
普通聊天       → 直接回答，必要时进入通用 Runtime
Tool Calling   → 单次请求内调用工具
Agent Runtime  → 有界决策循环：决策 → 动作 → 观察 → 继续/收尾
Workflow       → 持久化、可确认、可重试的预定义业务流程
```

Agent Runtime 目前已经具备：

- 三域 Runtime：学习域、文章域、通用域
- 动作白名单和后端动作校验
- 有界循环和步骤留痕
- `AGENT_STEP` 实时事件与刷新恢复
- 受控写动作、确认门、权限校验和并发保护
- 会话文章锚和部分跨 run 结论继承
- V3.11 证据收敛门
- V3.13 计划生成、展示、持久化和观测

因此，V4 不是从零设计 Agent，而是解决已有能力之间还没有完全连起来的问题。

### 1.2 当前仍存在的闭环缺口

现有实现仍有四个结构性缺口：

| 缺口 | 当前表现 | 已有基础 |
|---|---|---|
| 任务拆解不进入执行 | 每一步贪心选择动作，V3.13 计划只展示不驱动 | V3.13 Plan Preview |
| 验证范围有限 | 已能验证证据是否支撑回答，但还不能系统判断策略是否失效 | V3.11 Verifier |
| 上下文继承不完整 | 一条文章 Agent → 一个优化 Workflow 已能交接，其他链路仍未统一 | V3.12 Conclusion Inheritance |
| Workflow 内缺少自动评估闭环 | 检查报告通常交给用户，retry 仍由用户触发 | Workflow 现有检查节点 |

另外还有两个横向问题：

- 思考展示主要覆盖 Agent Runtime，QA 和普通聊天还没有统一的过程展示语义。
- 框架能力尚未完成对照，但现有 Runtime 已经拥有持久化、确认态和部分恢复能力。

## 二、V4 的范围和非目标

### 2.1 V4 目标

V4 需要产出：

1. 一套任务选型规则，明确何时使用 Workflow、纯 ReAct、Plan-guided ReAct 或 `ASK_USER`。
2. 一套动态 Agent 内部职责模型，明确 Plan、ReAct、Verifier、Reflection 的输入、输出和发言权。
3. 一套跨 run / Workflow 上下文交接原则，区分用户意图、结论、证据和过程状态。
4. 一套 evaluator-optimizer 闭环设计，明确自动循环的触发条件、次数上限和人工兜底。
5. 一套思考展示设计，明确哪些内容可展示、哪些内容只能审计、哪些内容不能暴露。
6. 一份框架能力对照，回答框架能补什么、会引入什么重复状态，以及是否值得接入。
7. 一个按证据排序的实施路线，而不是把六个评估点都直接实现。

### 2.2 V4 不做什么

本稿暂不承诺：

- 不直接把现有 Runtime 替换为 LangGraph 或其他 Agent 框架
- 不默认每一步都调用 Reflection
- 不让 LLM 直接写库、启动高影响 Workflow 或绕过确认门
- 不把完整聊天历史无条件塞入每次决策
- 不因为“看起来像 Agent 能力”就新增一个独立子系统
- 不把 V3.13 阶段一的 `plan` 直接改成执行指令
- 不把所有 Workflow 强行改造成动态 Agent
- 不以“用了框架”或“完全手写”为目标，技术选择必须服务于业务语义、可观测性和面试可解释性

## 三、核心分层：任务选型与动态闭环

### 3.1 `Workflow` 不是动态 Agent 的一层

`Workflow` 和 `Plan / ReAct / Verifier / Reflection` 不完全处在同一个层级。

- `Workflow` 是一种**任务编排模式**：流程、状态和确认门通常由代码预定义。
- `Plan` 是动态任务的高层拆解。
- `ReAct` 是运行期的动作选择循环。
- `Verifier` 是证据和出口裁判。
- `Reflection` 是策略失效后的诊断机制。

因此 V4 采用“两层模型”：

```text
第一层：任务选型

  能预定义流程 ───────────────→ Workflow
  目标明确且单步可解 ──────────→ 受限 ReAct
  目标明确且多子目标、需临场判断 → Plan-guided ReAct
  目标不清 ──────────────────→ ASK_USER

第二层：动态 Agent 内部闭环

  Plan（可选）
    ↓
  ReAct：决策 → 动作 → 观察
    ↓
  Verifier：证据是否足够、是否允许出口
    ↓
  Reflection（必要时）：策略是否失效、是否调整方向
    ↓
  回到 ReAct 或安全收尾
```

### 3.2 四档任务选型

| 任务特征 | 推荐形态 | 当前状态 |
|---|---|---|
| 流程、步骤和确认门可以提前定义 | `Workflow` | 已有五类 Workflow |
| 目标明确，单次查询或回答即可完成 | 纯受限 `ReAct` | 已有 |
| 目标明确，需要多个子目标，且每个子目标需要临场判断 | `Plan-guided ReAct` | 仅有 V3.13 阶段一观测 |
| 目标、对象或关键信息不明确 | `ASK_USER` | 已有部分机制 |

这里的“需要多个子目标”不是由后端简单词表决定，而是由决策器结合目标、页面上下文、会话候选和已有观察判断。后端负责校验计划结构和执行安全，不负责用脆弱词表替 LLM 判断复杂度。

### 3.3 当前项目的初步归类

| 场景 | 初步归类 | 说明 |
|---|---|---|
| 文章创建、文章优化、学习计划等固定流程 | `Workflow` | 有明确步骤、确认点和持久化状态 |
| 文章域单篇读取和基于证据的分析 | 受限 `ReAct` | 当前已有文章查询、记忆、RAG 和 Verifier |
| 复杂文章分析：结构、重点段落、偏好和建议组合 | 候选 `Plan-guided ReAct` | V3.13 阶段一已完成，仍需按样本记录决定是否进入阶段二 |
| 当前文章不明确、会话锚和页面候选冲突 | `ASK_USER` | 不应靠默认猜测解决 |
| 普通问候和简单事实问答 | 直接聊天或纯 ReAct | 不应高频展示复杂 Agent 过程 |

这些归类是候选规则，必须通过真实样本和错误案例继续验证。

## 四、动态 Agent 的职责与数据边界

### 4.1 五个概念的职责

| 概念 | 负责的问题 | 不负责的问题 |
|---|---|---|
| `Workflow` | 固定流程如何编排、何时确认、如何恢复 | 不负责所有探索性任务 |
| `Plan` | 需要完成哪些高层子目标 | 不直接调用动作、不授予权限 |
| `ReAct` | 当前下一步做什么、需要查询什么 | 不绕过白名单和后端裁决 |
| `Verifier` | 证据是否足以支撑回答、能否出口 | 不决定下一步动作、不把计划当证据 |
| `Reflection` | 当前策略为何失效、计划是否仍有效 | 不直接选动作、不直接写库 |

### 4.2 建议的发言权顺序

```text
用户当前要求
  >
后端权限、安全约束、白名单和确认门
  >
实际观察与 Verifier 结果
  >
Reflection 的调整建议
  >
初步 Plan
  >
thoughtSummary
```

这里的 `>` 表示约束优先级，不表示所有内容都进入同一个 prompt。

尤其要保持以下边界：

1. `plan` 不进入 `observations`。
2. `plan` 不进入 Verifier 的证据输入。
3. `thoughtSummary` 只是展示副产品，不作为决策依据。
4. Reflection 的输出必须经过后端约束，不能直接变成动作执行。
5. 计划、观察、思考摘要和过程状态应分别建模，不能用一个“大上下文”混装。

### 4.3 建议的数据分层

```text
用户目标
  ├─ goal：用户要求，优先级最高
  ├─ plan：高层子目标，弱参考
  ├─ observations：实际动作结果，Verifier 的主要证据
  ├─ reflection：策略诊断结果，按触发条件产生
  ├─ thoughtSummary：面向用户的清洗后展示信息
  └─ runtime state：step、状态、重试、终止和恢复信息
```

其中：

- `goal` 可以跨 run 继承，但必须区分“当前用户新要求”和“历史要求”。
- `plan` 可以被跳过、偏离或作废，但不能代替观察。
- `observations` 必须来自真实动作结果，不能由模型自述填充。
- `reflection` 应记录触发原因和采取的后续动作，避免变成无用的自我批评文本。
- `thoughtSummary` 不应保存未清洗的内部过程。

## 五、六个评估点的现状

### 5.1 ① 运行期任务拆解

**当前状态：V3.13 阶段一已完成。**

已经实现：

- 文章域首轮可选输出 2-4 个子目标
- 确定性校验和整条丢弃
- `plan_json` run 级持久化
- `AGENT_PLAN` 实时事件
- 思考面板展示和刷新恢复
- 计划与 observations / Verifier 隔离

尚未回答：

- 计划是否改善后续动作选择
- 计划是否只是在描述 ReAct 本来就会走的路径
- 哪些偏离是合理自适应，哪些才是计划错误
- 哪些任务应继续动态执行，哪些应该 Workflow 化

因此 V3.13 阶段一只能作为观测试点，不能称为完整 Planner 或 Plan-and-Execute。

### 5.2 ② 显式验证与反思

**当前状态：Verifier 已有，完整 Reflection 未有。**

V3.11 已实现：

```text
Generator → Verifier → 不足时补查 → 再判断 → 收尾
```

它主要判断：

- 当前回答是否被实际文章、记忆或 RAG 观察支撑
- 是否缺少用户才能提供的信息
- 是否应继续补查、转问或允许出口

它还没有系统判断：

- 当前策略为什么失败
- 查询方向是否错
- 计划是否已经失效
- 是否需要放弃当前路径并重新规划

所以面试和设计文档中应区分：

> V3.11 是证据级 evaluator-optimizer 最小闭环，不等于完整 Reflexion。

### 5.3 ③ 跨 run / Workflow 上下文继承

**当前状态：已有一条文章结论交接试点。**

V3.12 已打通：

```text
文章 Agent 结论
  → 会话结论锚
  → OPTIMIZE Workflow 创建链
  → GENERATE_OPTIMIZATION_PLAN 参考上下文
```

这证明跨 run 交接可以作为独立能力实现，但还不能推导出“所有历史上下文都应该继承”。

V4 需要继续区分：

- 用户明确确认过的方向
- Agent 的分析结论
- 实际观察和证据
- 未确认的建议
- 旧 run 的过程状态
- 当前 run 的新要求

建议默认继承“经过筛选的结论快照”，而不是继承完整过程和所有历史消息。

### 5.4 ④ evaluator-optimizer 闭环

**当前状态（2026-09-12 审计后更新）：Agent 循环内有最小版（V3.11）；Workflow 侧在「产物层」已闭环（写作 / 优化 / 学习三域同构），「方案层」有意不闭环。**

现有 Agent 形式：

```text
决策器生成回答草案
  → Verifier 判断证据
  → NEED_MORE 时引导补查
  → 再次决策
```

**已实现的 Workflow 形式**（原文写「仍是开环」，与代码不符——详见 §十四 2026-09-12 审计）：

| 要素 | 实现 |
|---|---|
| 生成 | `GENERATE_DRAFT` / `REWRITE_ARTICLE` / `GENERATE_PLAN` / `GENERATE_TASKS` |
| 评估 | `QUALITY_CHECK(6)` / `CONTENT_CHECK(12)`，**不调用 LLM，纯规则** |
| 失败修正 | 检查问题 → `WorkflowQualitySupport.buildQualityFeedbackForModel` → 喂回模型重写 |
| 停止交给用户 | **固定重试 1 次**（不是循环，成本结构性有界）→ 仍不合格则停确认门 |
| 人工兜底 | 创作 / 优化域：`approve` 被拦截，用户必须提意见重写；学习域：允许带着未通过的结果继续确认（可 reject 给反馈） |

**门槛对照结论**：

- **门槛一（evaluator 与 generator 独立）**：✅ **比要求更干净**——检查是独立 step，且完全不使用 LLM，不存在“自己判自己”的空间
- **门槛二（评价标准可客观化）**：✅ 全部落在规则上——正文字数 / 段落数 / 是否大纲式 / 是否过度删减 / 阶段与任务数量区间 / 任务去重 / 是否与大纲脱节

**为什么「方案层」不闭环**：`GENERATE_OPTIMIZATION_PLAN` 生成的优化方向直接进 `WAITING_PLAN_CONFIRM`，中间没有自动检查——因为“这个优化方向好不好”是主观标准，正好撞门槛二。**这是有意的分层，不是缺口。**

> 因此 §十二 的未决问题 1 **已结案**：能客观化的层已经闭环，主观的层本来就不该闭环，不存在“待筛的节点”。

V4 不应把所有检查节点都自动循环。**是否允许自动闭环，先过两道硬门槛**：

**门槛一：evaluator 与 generator 独立。** 不要求不同模型，但必须**独立角色、独立调用、独立输入边界**——evaluator 只能看产物、证据和规则 / rubric，**不能看 generator 的内部思考**。同一个模型带着同一份上下文自己判自己，会退化成空转（V3.11 的 `Verifier` 就是按这个口径做的：独立角色、独立调用、只评不选）。

**门槛二：评价标准可客观化。** 纯主观标准（如“这篇文章写得够不够好”）不适合自动闭环——可以给用户建议，但**不要自动 retry 到模型自己满意**。能进自动闭环的检查，至少要能落到规则或明确 rubric 上。

过门槛后，每一个自动闭环还需要明确：

- 评估对象是什么
- 失败后补什么信息或改什么策略
- 最大循环次数和成本上限
- 什么时候停止并交给用户
- 自动修正是否可能扩大业务写入风险

**对照结论**：五条全部满足；其中「最大次数 / 成本上限」由**固定单次重试**结构性保证（不存在循环，无需额外的 token 与耗时计数）。

**2026-09-12 审计发现并修复的两条**（详见 §十四）：

1. **学习域三处检查是内联调用、没有独立 step** → 用户看不到「正在检查」，step 日志里没有痕迹 → 已改为与另两域一致的 `workflowStepRunner.run(QUALITY_CHECK, ...)`
2. **学习域三个 Handler 的注释都写着「即使最终质量检查没通过也让用户看到当前结果」，但前端学习卡从未展示检查结果** → 已补（消息卡 + 确认卡，与创作 / 优化卡同构）

### 5.5 ⑤ 思考展示全局化

**当前状态：Agent Runtime 已有局部展示，QA 和普通聊天尚未统一。**

已经有：

- `AGENT_STEP` 实时事件
- `thoughtSummary` 清洗和持久化
- 自动展开、收起和刷新恢复
- 计划块与步骤列表分离

尚未决定：

- QA 是否需要展示检索过程
- 普通聊天什么时候值得展示思考过程
- Verifier 和 Reflection 是否展示为用户可理解的阶段
- 如何避免把重复调用、内部标识和防护机制暴露给用户
- 过程展示是否会让用户误以为系统已经完成了更多工作

候选原则：

> 只展示用户能理解且对结果有帮助的阶段，不展示内部实现细节；审计信息和用户展示信息分开建模。

### 5.6 ⑥ 框架能力对照

**当前状态：✅ 逐项对照已完成（2026-09-12），完整产出见 [`agent-framework-evaluation.md`](agent-framework-evaluation.md) §五。**

现有项目已经拥有：

- run / step 持久化
- 多种 `WAITING_*` 确认态
- SSE 实时事件
- inspection 只读恢复
- 部分重试和失败留痕
- Agent 与 Workflow 的业务状态语义

因此框架评估不能只问“框架有没有这些能力”，而要问：

1. 它补的是当前确实缺失的能力吗？
2. 它是否会引入第二套状态、重试和 interrupt 语义？
3. 它是否能只读接入现有 run / step 数据？
4. 版本升级和调试成本是否抵消收益？
5. 对当前项目的学习和面试价值是否足够？

**对照结论（三条）**：

1. **不引入 Agent 框架接管 Runtime**——除原有「双重状态机」外，新增一条更硬的：**HITL 语义冲突**。LangGraph 的 `interrupt()` 在 resume 时把**整个节点从头重跑**（官方要求 interrupt 之前的副作用必须幂等），而我们的确认门后面接的是真实写入，靠「proposal 旧值锚 → stale 校验 → 条件更新」保证安全，**不承诺节点可重放**。**周边能力（模型适配 / 观测链路 / 只读工具协议）仍属可评估范围**，见 `agent-framework-evaluation.md` §一「分层可用性」。
2. **可视化那句预设判断被推翻**——LangGraph Studio 只能读**它自己的图**，读不了我们的 run / step，「只读接入我们的数据做展示」用 Studio 做不到。可行形态是 **OTel tracing**（待做）+ 自建只读面板（已落地）。
3. **MCP 只接只读工具**——写动作不走：白名单 / 确认门 / 三明治锚定都是针对具体动作手写的，而 MCP 工具是**动态发现**的，且规格明说 annotations 默认不可信。接入后**输出只能进入我们自己的 observation / Verifier 链路**，不能绕过动作白名单、确认门与写入执行器。

**MCP（Model Context Protocol）纳入本节评估范围**，定位为「**工具接入协议评估**」：回答的是“外部工具 / 数据源能否以标准协议接入”，属于能力对照的一部分，**不是让 Agent 变聪明的主线能力**。不单开 MCP 主线（§十一）；详细评估见 `agent-framework-evaluation.md` §5.3。

## 六、V4 的关键设计问题

### Q1：计划何时进入决策上下文

**本节只回答一件事：`plan` 什么时候被注入决策上下文。** 偏航、重新规划与 Reflection 的触发条件属于 Q2 / Q3，不在本节范围内——三者必须解耦，否则会出现「同一个偏航场景被三处认领」的实现冲突。

阶段一已经确认计划可以独立展示，但没有确认它应该驱动执行。

候选方案：

| 方案 | 做法 | 风险 |
|---|---|---|
| A. 不进入决策 | 计划永久只展示和审计 | 失去验证计划对执行的价值 |
| B. 计划驱动执行 | 每步要求决策器选择当前计划项、维护完成状态、解释偏离 | 已经接近完整 Planner，需要新增计划状态机，容易形成错误锚定 |
| C. 弱基线注入（第二个决策步起） | 首步仍由决策器生成初始 plan + 首个动作；**从第二个决策步起**，把计划作为独立 `plan context` 稳定注入，不要求选择计划项、不维护完成状态，ReAct 可参考、跳过或偏离 | 从第二步起成本固定增加；可能弱到只适合观测，需验证是否真能改善动作选择 |

当前倾向：**不采用 B**（它会把阶段二直接推成完整 Planner，而不是最小试点）。如果阶段二实施，优先验证 C，且必须在文章域、只读动作和有限样本中试点。

**C 不是「偏航后再补塞原计划」**：偏航之后要做的是诊断策略（Q2 重规划 / Q3 Reflection），不是把初始计划塞回去——那时计划的价值已经被浪费了。

阶段二的硬约束：

- 计划单独作为 `plan context` 注入（与 `observations` 分开建模）
- 计划不进入 observations
- 计划不进入 Verifier 证据输入
- ReAct 可以跳过或偏离计划
- 计划不能改变权限、白名单、确认门和终止条件

### Q2：偏离和重新规划如何区分

**本节只回答一件事：偏离与重新规划怎么区分。** 计划何时注入属于 Q1；Reflection 何时触发属于 Q3。

建议先区分两个概念：

- **偏离**：某一步没有执行计划中的某个子目标，但计划的其他部分仍可能有效。
- **重新规划**：计划整体不再适用，需要生成新的子目标集合。

候选判定：

| 方案 | 做法 | 评价 |
|---|---|---|
| 每步重新判断 | 每步让 LLM 评估计划是否仍有效 | 成本高，容易和决策器冲突 |
| 信号触发 | 只有特定失败、重复或 Verifier 信号触发 | 更可控，可能漏掉隐性偏航 |
| 后端规则先行 + LLM 诊断 | 规则发现异常后才调用 Reflection | 更符合“先穷尽规则，再上 LLM” |

当前倾向：**规则信号触发，必要时才进 Q3 的 Reflection**。

### Q3：Reflection 什么时候值得调用

**本节只回答一件事：什么时候触发 Reflection。**

Reflection 不应是“每一步再问一次模型我做得怎么样”。它只有在能改变后续行为时才有价值。

触发信号必须是**后端可验证的事实**，不能是模型自报的判断：

| 信号 | 说明 |
|---|---|
| 同一动作 + 同一参数重复执行 | 先由规则拦截；如果规则只能发现重复、但无法决定换路 / 转问 / 收尾，才进入 Reflection |
| `Verifier` 连续 `NEED_MORE` | 单次不足属正常补查，不触发 |
| 观察零增量 | 动作返回了，但没有新信息 |
| 同目标多轮无新证据 | 动作不同但材料不增 |

规则已经能解决的情况**不**调用 Reflection：

- 权限失败
- 参数非法
- 已知重复查询且规则能明确停止或换路
- 超时和步数上限
- 数据库条件更新失败

Reflection 的输出应是结构化诊断：

```json
{
  "diagnosis": "CURRENT_PATH_INSUFFICIENT",
  "planStillValid": false,
  "suggestedDirection": "ASK_USER",
  "reason": "缺少用户对目标读者的要求"
}
```

**不设 `confidence` 字段**：LLM 自报置信度不可靠，且极易被后续实现误用成阈值。需要判定强度时由后端按可验证事实计算（重复次数、连续 `NEED_MORE` 次数、观察增量是否为零）。

这个结构只是候选形状，不能直接视为最终协议。后端仍需校验 `diagnosis`、方向和成本。

### Q4：跨 run 上下文继承到什么程度

**这是继承强度分层，不是「结论快照 vs 用户确认目标」二选一**——两类信息并存，只是继承强度与校验要求不同。V3.12 已经证明：未确认建议不能结构性进锚（强继承的门槛），但普通 final answer 作为弱上下文仍有价值。

按信息性质分层：

| 信息 | 默认继承 | 原因 |
|---|---:|---|
| 当前用户明确的新要求 | 是 | 当前请求最高优先级 |
| 用户确认过的结论或方向 | 有条件 | 可作为强参考，但要校验对象和权限 |
| Agent 普通分析结论 | 有条件 | 作为弱参考，需标记来源 |
| 实际观察 | 快照继承 | 用于解释来源，不自动当作当前证据 |
| 未确认建议 | 否 | 用户没有授权，不应变成后续事实 |
| 完整 thought / 内部过程 | 否 | 机制泄露且噪声大 |
| 旧 run 状态 | 否 | 状态不能跨 run 直接冒充当前状态 |

继承内容必须带：

- source run
- source type
- 目标对象
- 截断和敏感信息处理结果
- 生成时间或版本
- 是否经过用户确认

### Q5：Workflow 内自动闭环的安全边界

自动 evaluator-optimizer 只适合低风险、可评估、可回滚的中间产物。

候选适用：

- 文章优化方案的结构检查
- 文章草稿的格式和引用检查
- 只读分析结果的证据完整性检查

候选不适用：

- 自动发布文章
- 自动修改用户数据
- 自动追加学习任务
- 自动绕过用户确认
- 评估标准本身不明确的主观写作质量

所有自动闭环都必须具备：

```text
最大次数 + token/耗时上限 + 每轮留痕 + 可停止 + 失败后人工兜底
```

## 七、可靠性和安全边界

V4 继续遵守项目已经验证过的原则：

> **LLM 给建议，后端做裁判，用户对高影响动作做确认。**

### 7.1 不交给 LLM 的内容

- 文章和会话的归属校验
- 公开可读和本人可读判断
- 动作白名单
- 写动作权限
- Workflow 类型白名单
- 确认门和状态转换
- CAS、幂等和锁释放
- 最大步数和成本限制
- 最终失败语义
- 数据库写入和事务边界

### 7.2 允许 LLM 建议的内容

- 复杂目标的高层子目标
- 当前可能需要的查询方向
- 基于观察的补查建议
- 策略失效的结构化诊断
- 面向用户的自然语言说明

LLM 输出的所有结构化字段，都必须经过：

```text
解析 → 结构校验 → 业务校验 → 权限/成本校验 → 执行或丢弃
```

### 7.3 失败语义

V4 不能只定义“模型调用失败”。至少要区分：

| 失败类型 | 推荐处理 |
|---|---|
| 结构化输出非法 | 字段级丢弃或一次 repair，不污染主流程 |
| 查询参数非法 | 记录 FAILED step，避免重复重试 |
| 权限或归属失败 | 终局失败，友好收尾，不泄露敏感 ID |
| 观察重复 | **已实现（V4 第一刀）**：观察带来源标注（治本）+ 同动作同参硬拦（兜底），不调用 Reflection |
| Verifier 不通过 | 补查、转问或保守收尾 |
| Reflection 失败 | 回退到规则和原 ReAct，不阻塞安全收尾 |
| 持久化失败 | 根据数据重要性区分：状态不可丢，展示增强可降级 |
| 事件发送失败 | 不改变已持久化的业务状态 |

## 八、框架与手写的边界

### 8.1 当前初步结论

当前不建议用 LangGraph 或类似框架替换 `AbstractAgentRuntime`。原因不是框架没有价值，而是项目已经拥有一套业务状态机：

```text
项目状态：
  ai_agent_runs / ai_agent_steps
  Workflow run / step logs
  WAITING_USER / WAITING_WORKFLOW_CONFIRM / WAITING_WRITE_CONFIRM
  Verifier、确认门、CAS、幂等和结论锚

框架状态：
  graph state / checkpoint / interrupt / retry
```

如果两套状态同时负责中间态，就会出现：

- 哪一套状态是真实状态不清楚
- 框架 checkpoint 和业务数据库不同步
- 框架 retry 与业务幂等重复
- 框架 interrupt 与用户确认态重复
- 调试时需要同时理解两套生命周期

### 8.2 建议手写和复用的边界

| 内容 | 建议 |
|---|---|
| Runtime 状态机和业务终态 | 手写 |
| Agent 动作裁决和安全校验 | 手写 |
| 文章目标解析和权限判断 | 手写 |
| Workflow 确认门、CAS、幂等 | 手写 |
| Plan / observation / reflection 的业务语义 | 手写 |
| ChatClient、模型适配、流式协议 | 使用现有框架 |
| JSON、数据库、Redis、ES、SSE 基础能力 | 使用现有库 |
| 只读 run / step 可视化 | 可评估框架或自建只读页面 |
| 通用重试工具 | 先比较，不直接接管业务状态 |

### 8.3 框架对照必须回答的问题

逐项评估 LangGraph、LangChain4j 或其他工具时，只回答：

1. 它补的是当前缺口，还是重复已有能力？
2. 能否只读接入现有 run / step 数据？
3. 是否必须接管状态、checkpoint 或 interrupt？
4. 是否会影响已有的失败语义和确认门？
5. 调试、升级和学习成本是多少？
6. 这个能力是否值得为当前项目引入依赖？

暂定评估结论：

> 框架可以作为模型适配、基础设施或只读观测工具；不应成为权限、状态、失败语义和最终裁决的所有者。

## 九、观测与决策门

### 9.1 V3.13 阶段一的观测

阶段二是否实施，不能凭“Plan 看起来合理”决定。至少需要收集：

- 文章域简单请求的计划生成率
- 多目标请求的计划生成率和计划项数
- `FOLLOWED / SKIPPED / PIVOTED`
- `PIVOTED` 归因
- 实际 action 序列
- Verifier 拦截和补查情况
- 最终结果是否改善

其中：

- `SKIPPED` 表示 ReAct 合理自适应，不是计划失败。
- `PIVOTED` 只有在归因于“初始计划错误”时，才指向计划质量。
- 工具失败、用户改口、新证据转向不能直接归咎于计划。

### 9.2 阶段二决策规则

| 观测结果 | V4 判断 |
|---|---|
| 计划与执行高度一致，且路径稳定 | 优先考虑 Workflow 化 |
| 计划经常被合理跳过 | 不急于加入计划锚定 |
| 计划经常错误，偏离后结果更好 | 不做 Plan-guided ReAct，先改计划生成或放弃 |
| 计划合理，但无计划时动作明显跑偏 | 适合做受控弱参考试点 |
| 偏离主要由新证据、用户改口或工具失败造成 | 不把问题归因于计划 |
| Verifier 经常拦截但规则无法诊断方向错误 | 评估 Reflection |

### 9.3 不把手测包装成统计结论

当前项目的样本量以发现方向和暴露边界为主，不能声称已经证明某种架构在统计上优于另一种架构。

V4 设计中应明确记录：

- 样本数量
- 模型和 prompt 版本
- 是否经过决策器、Verifier 或 Workflow
- 失败是否可复现
- 结论是事实、推断还是待验证假设

### 9.4 观测结论（2026-09-11，五轮约 27 条样本）

> ## 阶段二 `Plan-guided ReAct` —— **不做**

五轮观测（简单请求 → 复杂多目标 → 模糊 vs 明确对照 → focus 修复后的干净观测）的数据，落在 §9.2 决策表的这一行：

> **计划与执行高度一致，且路径稳定 → 优先考虑 Workflow 化**

| 证据 | 数据 |
|---|---|
| 计划-执行对应 | 几乎全部 FOLLOWED；少数 SKIPPED 均合理（信息已够即不再查） |
| **PIVOTED「初始计划错误」** | **0 次**——计划从未把方向带偏 |
| **「无计划就绕路」的稳定证据** | **无**——唯一疑似案例被证明是 focus bug，修复后消失 |

**诚实边界**（§9.3）：27 条样本、同一篇文章、同类请求，**不构成统计证明**；但关键反例一次都没出现，而「不做」是**保守选择**（不引入复杂度）。

**这不影响 V3.13 阶段一的价值**：计划展示对用户仍有透明度收益（看得见 AI 打算做什么），只是**不需要再往前一步去驱动执行**。

**观测的副产物**：五轮共暴露并修复 3 个真问题——① 重复查询根因（观察缺来源标注）② focus 无法定位时静默降级 ③ 一条静默失效的测试。**全部由第一刀的只读面板发现**。

逐轮明细、待办清单与观测方法论见 [`agent-v4-observation-log.md`](agent-v4-observation-log.md)。

## 十、路线图与优先级

### 10.0 排序依据

候选切口的排序不能靠“看起来重要”。统一按四个因子判断：

| 因子 | 问什么 |
|---|---|
| **确定性** | 这条能力能否被规则或明确 rubric 验证？纯主观的排后面 |
| **收益** | 是用户可见的产品收益，还是工程 / 开发效率收益？ |
| **是否服务后续实验** | 它的产出会不会被后面几件事复用？ |
| **风险半径** | 出错时爆炸半径多大？只读 < 展示 < 写动作 < 自动循环 |

面试时被问“为什么先做这一刀”，依据就是这四个因子。

### 10.1 第一刀（已实施 + 验证，见 §十五）

**第一优先：开发者只读 run/step 可视化。** ✅

原因不是它更炫，而是它**先降低后续判断成本**：V3.13 要标 `FOLLOWED / SKIPPED / PIVOTED`、Reflection 要看重复和零增量、`Verifier` 要看拦截链路——现在这些都靠查库和读 JSON。先做只读面板，后面三件事都会省力。

**边界（提前钉死）**：

- **只读**：不接管 Runtime、不改状态、不触发 retry
- **开发者工具**：不对普通用户开放，**不做成半个管理后台**
- 展示范围到此为止即够支撑 V4 后续判断：
  - run timeline
  - step input / output
  - plan
  - `thoughtSummary`
  - `Verifier` 拦截
  - `missingEvidence`
  - observation 是否重复

**第二优先：全局思考展示** ✅（V4.5，2026-09-11——把已有 Agent step 展示语义扩展到 QA / 普通聊天）。

**⑥ 框架能力对照** ✅（2026-09-12，逐项对照完成，产出见 `agent-framework-evaluation.md`）。

**暂缓**：`Reflection`——等待支撑证据（重复 / 零增量的真实样本）。~~Workflow 自动 evaluator-optimizer~~ → **2026-09-12 审计确认：能过门槛的产物层已经闭环，方案层有意不闭环**（§5.4），无需再做。

**已判定不做**：`Plan-guided ReAct` —— 五轮观测收口（§9.4）。

### 10.2 阶段划分

**阶段 0：设计稿收口**（本文档）

- 把概念和边界与 V3.11～V3.13 实现逐项对齐
- 标出事实、假设、候选方案和未决问题
- 产出：V4 主设计稿、现有代码映射表、未决问题清单

**阶段 1：只读可视化落地**（10.1 第一刀）

- 复用现有 run / step / inspection 数据
- 只展示，不改 Runtime 状态，不触发 retry
- 支撑后续人工标注和排障

**阶段 2：用只读面板补齐证据**

- 完成少量 V3.13 计划与执行对照记录
- 复核 `Verifier` 在线波动样例
- 确认 V3.13 计划落库与事件时序没有隐性分叉

这一步不是新增 Agent 能力，目的是防止架构设计建立在单次手测印象上。

**阶段 3：按 10.1 顺序推进后续切口**

### 10.3 每个切口的收口要求

- 设计边界

## 十五、第一刀实施记录（2026-09-11）

### 15.1 开发者只读 run/step 可视化

**端点**（`/api/ai/dev/agent-runs`，只读 + 白名单门禁 `blog.ai.inspection.enabled` / `allowed-user-ids`，沿用 `Rag.Rebuild` 范式）：

| 端点 | 返回 |
|---|---|
| `GET /` | run 列表（仍是自己的 run） |
| `GET /{id}` | 安全摘要 + 原始 `contextJson` |
| `GET /{id}/steps` | 完整 step（含 `inputJson` / `outputJson`） |

**为什么新开端点而不放宽用户侧接口**：`AgentStepVO` 刻意不返回 `inputJson`（“决策输入可能含内部信息”）。放宽它等于让所有用户拿到原始数据——审计通道与用户通道必须分开建模。

**边界**：只读、不改状态、不触发 retry、无导航入口（不对普通用户开放）；数据范围仍限「当前登录用户自己的 run」，白名单是**额外的门**，不放大可见范围。

**前端**：`/dev/agent-runs` 列表 + `/:id` 详情（基本信息 / plan / steps / 原始 `contextJson`，默认折叠并标注“未清洗”）。「观察重复」标记在前端按 `outputJson` 逐字比对算出——展示层能算出来的不进埋点。

**验证**：门禁 5 例（面板关闭 / 不在白名单 / 未登录 / **空白名单 fail-closed** → 一律 403 且不触达数据层）+ 后端编译 + `vue-tsc`。

### 15.2 上线第一次观测就产出的：重复查询根因链

**现象**：一次多目标请求连发 4 次 `QUERY_MEMORY {"question":"写作偏好"}`，`input_json` 与 `output_json` 四次完全相同——面板的「观察重复」标记一眼看出来（此前只能靠查库读 JSON 诊断）。

**排除的假设**：`context_json` 长度 3446 &lt; 6000，**未触发裁剪**（与 V3.13 手测的怀疑一致，同样被数据推翻）。

**第一次修正（治标）**：Runtime 硬拦——只读动作执行前查「同动作 + 同参数 + 曾 SUCCESS」，命中则不执行、落 FAILED step、给可执行的提示。**但拦完仍重复两次才收尾。**

**根因（治本）**：查 `context_json` 实际内容发现 observations **只有结果、没有来源标注**：

```text
"记忆摘要：\n- 语义记忆(PREFERENCE)：用户喜欢前端UI简洁，不要太花里胡哨。\n"
```

模型在第 4 步看到一段**来路不明**的“记忆摘要”——它需要“写作偏好”，但无法确认这是不是「`QUERY_MEMORY question=写作偏好`」的产物 → **再查一次以求确认**。

**决定性证据**：被拦两次后，第 6 步的回答里**明确引用了第 3 步那条记忆**。信息早就够了，缺的只是「已经查过」这个事实。

**修法**：观察加来源标注（成功 / 失败两条路径都加）：

```text
[QUERY_MEMORY question=写作偏好]
记忆摘要：- 语义记忆(PREFERENCE)：用户喜欢前端UI简洁，不要太花里胡哨。
```

只带语义参数（`focus` / `question` / `keyword`）；`articleId` / `anchorMode` 是内部标识，不进观察。`outputJson.summary` 仍是原始文本（用户侧刷新恢复不受影响），标注只加在给模型的 observations 上。

**软硬互补**：标注是软的（依赖模型理解），硬拦是硬的（确定性）——两者都保留，与「V3.13 prompt 终止条件 + V3.11 R3 规则闸」同一模式。硬拦只拦原样重复，**换关键词一律放行**（那才是有效探索）。

### 15.3 这一节要记住的

> **模型无法可靠监控自己的动作历史。它缺的不是「别重复」这条纪律，而是「我做过什么」这个事实。**

所以修法是**补齐信息**，不是**禁止行为**。这也解释了为什么 prompt 里「一次就够 / 不要重复完全相同的查询」两条软约束无效——它们要求模型执行一个它做不到的自我监控。

**方法论**：两次诊断都靠证据（`context_json` 的实际内容、`input_json` 与 `output_json` 的 MD5 指纹），不靠猜——`clipContext` 裁剪假设两次都被数据推翻。
