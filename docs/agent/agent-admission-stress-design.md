# AI 长任务准入：压测与性能收口

> 状态：设计稿（待评审）· 2026-09-19
> 前置：[`agent-long-task-admission-design.md`](agent-long-task-admission-design.md)（准入本体已实施）

## 0. 一句话

用**真实并发**打准入，把「结构跨过去了、容量没跨过去」那半句补上——
验证行为 → 找瓶颈 → 给容量结论，全过程留数据。

## 1. 为什么是现在

三件事指向同一个缺口：

1. **CLAUDE.md 自己登记着**：
   > 有准入、有硬上限、有明确拒绝、有观测 = **结构**跨过去了；容量没压测过 = **还没跨过去**。
2. **三个数字全是拍的**：`worker=8` / `queue=32` / `HikariCP=20`，
   设计稿里明确写了「起始配置，不是容量结论」。既然迟早要改，**先拿数据再改**。
3. **面试叙事缺一环**：能讲「我做了准入」，讲不了「它扛不扛得住、瓶颈在哪、怎么验证的」。
   而后者才是「玩具 demo vs 真系统」真正的分界线。

## 2. 三层目标（递进，逐层决定要不要往下走）

### L1 · 行为验证（便宜，先做）

**要证伪的假设**：`8 在跑 + 32 排队 = 40 个名额`；第 41 个 **503**；同一用户第 3 个 **429**。

| | |
|---|---|
| 方法 | 40+ 个并发**同时**发起「起 Agent」请求（同步定时器式，不是 ramp-up）|
| 判据 | ① HTTP 状态码分布（200 SSE / 429 / 503）② `[AI-TASK]` 日志的 `running` / `queued` / 拒绝原因 ③ **关键**：拒绝必须在 SSE 首事件之前发生（否则用户看到的是「连接意外中断」而不是 429）|
| 成本 | ≈ 41 次 Agent 调用 |

> **为什么这一层值得单独做**：准入的行为是**设计承诺**，不是自然现象。
> 40 个名额、第 41 个拒绝、每用户 2 个——这些不验证就是纸面设计。

### L2 · 瓶颈定位（有成本，L1 通过后再决定）

**先验假设**（写下来是为了**被证伪**，不是预设结论）：

| # | 假设 | 依据 |
|---|---|---|
| H1 | **长事务吃连接** | `createWorkflowInternal` / `approve` / `reject` / `retry` 全是 `@Transactional`，事务范围**包含** `runInitialSteps` 的 LLM 调用。8 个准入任务同时跑 = 8 个长事务 = 占掉 HikariCP 20 的 40%，且**持续几十秒** |
| H2 | **首 token 慢** | V4.5 已实测 `buildPrompt` 占 3.6s（大头是长期记忆 + 情景记忆两次向量召回）。记忆召回已并行化过一轮，首字仍慢 |
| H3 | **Tomcat 线程被 `runAdmitted` 占** | 建议桥确认跑在调用者线程上（必须同步返回 VO），池满时它会占住 HTTP 线程几十秒 |

**方法**：阶梯加压（8 → 16 → 40 → 80），观察**哪一层先劣化**。

### L3 · 容量结论（面试口径的实答案）

把「几百人同时用会怎样」从**推算**换成**实测**：

> 闲聊走响应式流不占准入池 → 瓶颈转移到供应商速率限制
> 起长任务走准入 → 8 在跑 + 32 排队，第 41 个 503
> **实测在 N 并发下 P95 = X，瓶颈在 Y**

## 3. 关键设计决策

### 3.1 压「起 Agent」，不是闲聊

闲聊（`CHAT` / `TOOL`）走**响应式流、不占准入池**——压它根本测不出准入行为。

必须压「起 Agent / 起 Workflow」（`AiTaskType.AGENT` / `WORKFLOW_CREATE`）。

> ⚠️ **实施第一步是先手工确认一个能稳定触发 Agent 的输入**：
> 路由由 LLM 意图分类器决定，不能想当然。先用真实请求打一发，看日志走的是哪条路，再写进脚本。

### 3.2 为什么不用 JMeter（项目已有先例）

`deploy/seckill-stress.jmx` 压的是「短请求 + 看状态码」，JMeter 很合适，那一刀的选择是对的。

本次不一样，三个硬理由：

1. **场景是 SSE 长连接**——要精确控制发起时刻、读流、量**首字节时间**，JMeter 处理 SSE 要额外插件或脚本元件
2. **并发模型对不上**——秒杀是「N 个一次性请求」，本次要「N 个**保持几十秒**的连接 + 中途探测」
3. **要构造跨用户场景**——「用户 A 发 3 个（第 3 个该 429）」这种需要按 userId 分组控制，JMeter 的 CSV 驱动做起来别扭

改用**脚本**（落 `deploy/`），用 Node 写（前端项目已有 Node，且 SSE 用 `fetch` 天然支持——**前端就是这么调的**）。

> 这个取舍本身是面试材料：「你为什么不用 JMeter」→ 因为压测工具要匹配被测协议的形态。

### 3.3 压本地，不压线上

- **可控**：MySQL / ES / Redis / 日志全在本机，出问题能立刻查
- **不碰公网服务**：压测流量不该出现在对外服务上
- **代价**：脚本与应用抢 CPU。但本次的瓶颈在**外部 LLM**（几十秒的 IO 等待）和**连接池**上，
  CPU 不是主因，本地数据的**趋势**依然可信

脚本里**地址写死 `localhost`**，不给「误压线上」留可能。

### 3.4 观测数据从哪来：大部分埋点已经有了

这是这一刀不写多少生产代码的原因——**观测早就做过了**：

| 层 | 要看的 | 来源 |
|---|---|---|
| HTTP | 状态码 / 首字节时间 / 总耗时 | 压测脚本自己记 |
| 准入 | `running` / `queued` / `inFlightOfUser` / 拒绝原因 | `[AI-TASK]` 日志 ✅ **已有** |
| 排队与执行 | `queueWaitMs` / `executionMs` | `[AI-TASK]` 日志 ✅ **已有** |
| Workflow | `worker_start queueWaitMs` | `[PERF-WORKFLOW]` ✅ **已有** |
| 首字分解 | `resolve` / `buildPrompt` / `ragSearch` | V4.5 埋点（**debug 级，压测时临时开**）|
| Token 成本 | `promptTokens` / `completionTokens` | `[PERF-AI] llm_usage` ✅ **已有** |

**唯一要新增的**：HikariCP 的活跃连接数 / 等待线程数（H1 要看它）。
优先用现成手段（Actuator metrics 或日志），**不为此引入监控系统**。

## 4. 成本与风险

### 4.1 LLM 成本

| 轮次 | 请求数 | 估算 token | 估算费用 |
|---|---|---|---|
| L1 行为验证 | ~41 | ~60 万 | **1–2 元** |
| L2 阶梯（如需） | ~120 | 几百万 | **几块到十几块** |

**分轮次决定**：L1 跑完看数据，再决定要不要 L2。不一次性铺开。

### 4.2 风险与对策

| 风险 | 对策 |
|---|---|
| **污染本地 DB**（每次跑产生 `ai_sessions` / `ai_messages` / `ai_agent_runs` / `ai_agent_steps`） | 压测用**专用测试账号**，跑完按 userId 清理；清理 SQL 写进脚本注释 |
| **烧钱失控** | 脚本必须有**并发上限 + 单请求超时**；不做无限循环模式；跑之前先跑小样本 |
| **误压线上** | 地址写死 `localhost` |
| **压测期间本机卡死** | 并发上限先小后大；RRF/ES 查询会吃 CPU，观察着加 |
| ⚠️ **压到「旧实例」上**（**实际踩到了**） | `TaskStop` 停的是 Maven 包装进程，**Java 子进程还活着**并占着 8080；新实例于是 `Port 8080 already in use` 启动失败，而压测脚本照打不误——**打的是旧配置的实例，数据全是假的**（第一轮 8 个请求全 200 就是这么来的）。对策：① 重启前 `netstat -ano \| grep :8080` 找到 PID 并 `taskkill /PID <pid> /F`；② 压测前比对日志里的 Java PID 与自己起的是不是同一个；③ **启动时打印一行池配置**（见下） |

### 4.3 前置条件（当前不满足，需先解决）

- [ ] 本地后端启动（`./mvnw spring-boot:run`）——当前 `localhost:8080` 无响应
- [ ] 本地 MySQL / Redis / ES 可用（ES 已确认在跑：`blog-es` 容器）
- [ ] 造 N 个测试账号 + 拿 JWT（用于 CSV / 并发用户区分）
- [ ] 手工确认「能稳定触发 Agent」的消息文本

## 5. 优化预案（看到什么修什么，不预设结论）

| 如果实测发现 | 对应方向 | 备注 |
|---|---|---|
| H1 成立（长事务是瓶颈） | LLM 调用移出事务边界（先落状态、再推进） | 独立一刀，改动面较大 |
| H2 成立（首字是瓶颈） | 继续优化 `buildPrompt` / `ragSearch` | 记忆召回已并行过一轮，下一层要看具体是哪次调用 |
| 连接池是瓶颈但长事务不是主因 | 调 HikariCP | 最省，但要写清楚「为什么这个数是够的」 |
| H3 成立（Tomcat 线程） | 建议桥确认改 SSE | 前端契约变更，成本高 |
| **准入行为与设计不符** | 先修行为再谈性能 | L1 就是为这个存在的 |

## 6. 明确不做

- **不用 mock LLM**——瓶颈全在 LLM 的真实耗时上，mock 掉就没意义了
- **不做分布式压测**——单机足够，上分布式是为不存在的问题写工具
- **不做全站压测**——只压 AI 长任务这一条线
- **不引入 Prometheus / Grafana**——第二层已登记「轻量实现」，本次用日志 + 现成埋点

## 7. 交付物

1. 压测脚本（`deploy/`，含清理 SQL）
2. 压测报告（`docs/agent/`，数据 + 结论 + 瓶颈定位过程）
3. CLAUDE.md 的「面试口径」从**「数字是起始配置」**升级成**「实测结论 + 瓶颈」**
4. 若测出瓶颈 → 独立一刀修复，**不在本刀里顺手改**（本刀只负责「测准」）
