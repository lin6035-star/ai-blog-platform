# 钱包 + 秒杀：AI 额度计费系统设计

> **2026-09-17 修订**：经 codex 复审后重写。修订点集中在「预扣闭环」「可靠投递」「Redis 不再是最终裁决者」三处，逐条记录见文末 §10。

---

## 0. 定位

不是独立电商场景，而是**接到已有 token 统计上的计费系统**：虚拟充值 → AI 调用按 token 扣减 → 秒杀抢额度包。

面试价值：秒杀是面试超高频（防超卖 / 限流 / 削峰 / 幂等一条链全占）；钱包提供**「不可丢数据」的对照组**——同一个项目里既有「这里必须纯 DB」，又有「这里必须上 Redis」，取舍本身就是答案。

---

## 1. 核心取舍

```
钱包余额 / 扣减   →  纯 DB（条件更新 + 流水表）
秒杀库存扣减      →  Redis 预占资格 → 可靠投递 → DB 条件更新做最终裁决
```

判据是**「数据可不可以丢」**：

| 数据 | 性质 | 丢了会怎样 | 结论 |
|---|---|---|---|
| 浏览量 / UV / 热度榜 | 近似统计 | 少几个无所谓 | Redis 原子取删 + 异步同步 |
| 余额 | 钱 | 账不平 | **不能引入「Redis 扣了但 DB 没落」的窗口** |
| 秒杀名额 | 不是钱，是资格 | 多发了 → 超发；少发了 → 用户投诉 | Redis 挡流量，**DB 保正确** |

**面试加分点正在这**：面试官听到「我用了 Redis」就等着你讲击穿雪崩。能说出「这个场景我特意不用 Redis，因为……」是反向证明你懂取舍。

⚠️ **一处修正**：初稿写的「秒杀的 Redis 是唯一裁决者」——**这句是错的**。见 §6.4。

## 2. 表设计（6 张）

### ① 钱包：一个用户一行

```sql
CREATE TABLE user_wallet (
  id         BIGINT   NOT NULL PRIMARY KEY,
  user_id    BIGINT   NOT NULL,
  balance    BIGINT   NOT NULL DEFAULT 0,   -- 单位：额度单位（credit）；**允许为负**，见下
  balance_seq BIGINT  NOT NULL DEFAULT 0,   -- 余额变更序号，只用于流水严格排序
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_id (user_id),
  CONSTRAINT chk_wallet_balance_floor CHECK (balance >= -1000000)
);
```

⚠️ **为什么是宽松下界，而不是 `CHECK (balance >= 0)`**：钱包**允许透支一轮**——预扣门槛是 `balance > 0` 而不是 `balance >= reserved`（理由见 §3），所以余额扣成负数**是正常业务状态**，非负约束会直接让预扣报错。

留一个足够大的负数下界，是为了让「符号写反」「扣减跑飞」这类 bug 仍然被 DB 拦住——**放弃非负约束不等于放弃这道防线**。

⚠️ **下界必须与最大预扣额度挂钩**：`-1000000` 只是占位值。**应用启动时校验**「所有 bizType 的最大预扣额度 × 安全系数 < |下界|」，不满足直接 fail-fast。否则某条路径把预扣调大之后，**正常请求**会被 CHECK 约束拒绝，而报错信息（约束冲突）完全指不到根因。

`balance_seq` **不是乐观锁 version**：余额扣减仍用条件更新，不做版本号 CAS。它在每次余额变更时原子 `+1`，并写入同一笔流水，用来还原钱包行真实的串行修改顺序。

### ② 流水：只增不改

```sql
CREATE TABLE wallet_transaction (
  id              BIGINT       NOT NULL PRIMARY KEY,
  user_id         BIGINT       NOT NULL,
  amount          BIGINT       NOT NULL,   -- 有符号：+1000 充值 / -50 消费
  balance_after   BIGINT       NOT NULL,   -- 变动后余额快照
  balance_seq     BIGINT       NOT NULL,   -- 对应 user_wallet.balance_seq
  type            VARCHAR(32)  NOT NULL,   -- RECHARGE / AI_RESERVE / AI_REFUND / SECKILL_GRANT
  biz_type        VARCHAR(32)  NOT NULL,   -- RECHARGE_ORDER / AI_BILLING / SECKILL_ORDER
  biz_id          VARCHAR(128) NOT NULL,
  idempotency_key VARCHAR(128) NOT NULL,
  remark          VARCHAR(255) NULL,
  created_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_idem (user_id, idempotency_key),
  UNIQUE KEY uk_user_seq (user_id, balance_seq),
  KEY idx_user_id (user_id, id)
);
```

**三个设计点**

**a. 单位用 credit，不叫「分」**
余额是虚拟额度，`token 单价` 换算下来往往**远小于 1 分**（一次 3000 token 的对话可能值 0.03 元）。硬套「分」会逼出小数或放大系数，语义还容易和真实货币混淆。就叫 credit——充值是整数 credit，消费按 token 换算成 credit。

**b. 为什么必须有流水表**
只改余额不记流水 = 出争议无法追溯。`balance_after` 快照是关键：对账时可逐笔校验 `上一笔.balance_after + 本笔.amount == 本笔.balance_after`。

⚠️ **逐笔回放要按 `balance_seq` 排序，不能按 `created_at` 或 Snowflake `id`**。时间戳会相同；多实例同毫秒下，Snowflake ID 的大小也不等于钱包行锁的获得顺序。余额行的原子递增序号才是实际变更顺序，`uk_user_seq` 还能检查是否漏流水。

**c. 幂等键唯一约束是 `(user_id, idempotency_key)`，不是全局**
全局唯一时，用户 B 碰巧用了一个被 A 占掉的 key（前端写死、或复制粘贴），会**静默成功但没加钱**。加 `user_id` 前缀后，至少不会跨用户误伤。

流水里的幂等键必须由服务端按操作生成，不能让同一笔业务的预扣、结算退款共用一个值：例如
`AI_RESERVE:{billingOrderNo}`、`AI_REFUND:{billingOrderNo}`、`SECKILL:{activityId}:{userId}`。
客户端 `Idempotency-Key` 只用于接口请求去重，不能直接成为记账键。

### ③ 充值订单

```sql
CREATE TABLE wallet_recharge_order (
  id           BIGINT      NOT NULL PRIMARY KEY,
  order_no     VARCHAR(64) NOT NULL,   -- 服务端生成
  user_id      BIGINT      NOT NULL,
  package_code VARCHAR(32) NOT NULL,   -- 套餐编码，不是金额
  pay_amount   BIGINT      NOT NULL,   -- 应付（分，真实货币口径；虚拟支付下仅展示）
  credit_amount BIGINT     NOT NULL,   -- 到账额度，由套餐决定，前端说了不算
  status       VARCHAR(16) NOT NULL,   -- PENDING / PAID / CANCELLED
  version      INT         NOT NULL DEFAULT 0,
  paid_at      DATETIME    NULL,
  created_at   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user (user_id, created_at)
);
```

**金额和到账额度都落在订单行上**——下单时由后端按套餐快照写入。这样即使以后套餐改价，历史订单仍然可对账。

### ④ AI 计费单（预扣 / 结算 / 退款）— **新增**

```sql
CREATE TABLE ai_billing_order (
  id             BIGINT      NOT NULL PRIMARY KEY,
  order_no       VARCHAR(64) NOT NULL,   -- 业务单号；流水幂等键由「操作类型 + 它」派生，见下
  user_id        BIGINT      NOT NULL,
  biz_type       VARCHAR(32) NOT NULL,   -- CHAT / AGENT / WORKFLOW_ACTION
  biz_id         VARCHAR(128) NOT NULL,  -- 调用前已存在的计费键，见 §5.1
  resource_id    VARCHAR(128) NULL,      -- 调用后回填：assistantMessageId / agentRunId / stepLogId
  status         VARCHAR(16) NOT NULL,   -- RESERVED / SETTLED / RELEASED
  reserved_credit BIGINT     NOT NULL,   -- 预扣额度
  actual_credit  BIGINT      NULL,       -- 实际结算额度（SETTLED 时写入）
  prompt_tokens  INT         NULL,
  completion_tokens INT      NULL,
  total_tokens   INT         NULL,       -- V1 结算依据；prompt/completion 仅作观测
  version        INT         NOT NULL DEFAULT 0,
  expire_at      DATETIME    NOT NULL,   -- 超时释放的兜底时间
  created_at     DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  settled_at     DATETIME    NULL,
  UNIQUE KEY uk_biz (biz_type, biz_id),
  KEY idx_status_expire (status, expire_at)
);
```

状态流转：

```
RESERVED ──结算成功──> SETTLED    （按实际用量扣，差额退回）
    │
    └────调用失败 / 取消 / 超时──> RELEASED（预扣全额退回）
```

**两道幂等，作用不同，别混**：

| 机制 | 防的是 |
|---|---|
| `uk_biz (biz_type, biz_id)` | **重复预扣**——同一次业务调用开了两张单 |
| `UPDATE ... WHERE status='RESERVED'` | **重复结算/释放**——同一张单被结算两次 |

⚠️ **`order_no` 不是流水幂等键，要按操作类型派生**：

```
AI_RESERVE:{order_no}     预扣流水
AI_REFUND:{order_no}      结算 / 退款流水
```

**直接把 `order_no` 当幂等键会炸**：一张单在一次调用里要写**两笔**流水（预扣一笔、退款/结算一笔），共用同一个键 → 第二笔 INSERT 撞上 `uk_user_idem` → **事务回滚，钱退不回来，用户余额永久少一截**。这个错误很隐蔽，因为预扣时一切正常，只在结算时才暴露。

### ⑤ 秒杀活动 + 订单

```sql
CREATE TABLE seckill_activity (

  total_stock   INT         NOT NULL,

  credit_amount BIGINT      NOT NULL,             -- 抢到发多少额度
  start_at      DATETIME    NOT NULL,
```

`uk_user_activity` 是**一人一单的最终防线**——Redis 的 Set 只负责挡住绝大多数重复点击，DB 唯一索引负责兜住漏网的那一个。

## 3. 扣减的核心 SQL（面试必讲）

```sql
-- 预扣（reserved 取该路径的 token 硬上限，见 §5.3）
UPDATE user_wallet
SET balance = balance - #{reserved}, balance_seq = balance_seq + 1
WHERE user_id = #{userId} AND balance > 0
```

影响行数 0 → 余额不足（余额 ≤ 0，或钱包行不存在）。

### 为什么门槛是 `balance > 0`，不是 `balance >= reserved`

**因为 `reserved` 是硬上限，不是报价。**

`reserved` 取的是该路径的最坏情况（最大输入 + `maxTokens` + 最大工具轮数），**可能显著高于实际消耗**。用刚性门槛会**拒绝本可支付的请求**：

> 用户余额 5000，一次 CHAT 的硬上限是 10000 —— 被直接拒绝。而他的钱够一次真实对话（比如实际消耗 2000）。

这是个**存在性**论证：只要存在「硬上限 > 用户余额 > 真实消耗」的情形，刚性门槛就会误杀。误杀的**比例**取决于余额分布，本项目未实测，不宣称「大面积」。

放行后余额扣成负数，下一次 `balance > 0` 不成立，**自动拦住**。

### 负余额的幅度上界

设预扣前余额 `B > 0`、预扣 `R`、实际结算 `A`：

```
预扣后     B − R              （B < R 时为负，即「预占中」）
结算后     B − R + (R − A) = B − A
```

因 `A >= 0`、`B > 0`，所以 **结算后余额 > −A ≥ −R**——负余额幅度**恒小于造成它的那笔预扣**。

所以全局上界就是「最大允许预扣额」，**不需要额外的 `overdraftLimit`**。真要加，那是**风控选择**（收窄坏账面），不是正确性必需品。

**并发也安全**：条件更新是串行执行的，不是「先查询再判断」——第二个并发请求看到的是第一个扣完之后的余额，不可能两个请求凭同一份余额各透支一次。

⚠️ **负余额 ≠ 欠款，两种状态要分开**：

| 时点 | 含义 | 用户提示 |
|---|---|---|
| **预占中**（调用还没结束） | 额度被**临时占用** | 不要提示欠款 |
| **结算后仍为负** | 真的补不上 | 提示充值 |

例：余额 5000、预扣 10000、实际 2000 → 预扣后 −5000，**结算退款后回到 3000**，全程无需充值。只有结算后仍为负才需要充值补足。

**接口要能传达这个区分**——钱包查询不能只返回一个 `balance`：

```json
GET /api/wallet
{
  "balance": -5000,          // 当前余额（可能为负）
  "pendingReserveCount": 1   // 进行中的预扣笔数（status='RESERVED'）
}
```

前端据此判断三态：

| 条件 | 展示 |
|---|---|
| `balance > 0` | 正常，可继续使用 |
| `balance <= 0` 且 `pendingReserveCount > 0` | 「本次调用进行中」——**不要提示欠款** |
| `balance <= 0` 且 `pendingReserveCount == 0` | 「额度不足，请充值」 |

少这一个字段就会误报：只看 `balance` 的话，用户一发起调用就看到负余额，以为已经欠款了。

### 边界：余额缺口有界，不等于平台成本有界

上面的上界约束的是**余额缺口**。它**不约束平台实际承担的模型成本**——

当前失败 / 取消都全额退款。用户可以在 LLM 已经产生 token 消耗之后取消，拿回预扣、恢复正余额，再发起下一次。反复如此，**累计模型成本无界**。

这是产品政策问题，不是 bug，但要说清楚：

- **V1 选择全额退**（简单、对用户友好），代价是承认上面这个窗口
- 缓解：限流桶限制滥用频率（已有），`[BILLING-*]` 日志可审计
- **升级路径**：取消时按**已产生的用量**部分结算。前置是先解决「SSE 断开后工作线程仍在跑」的竞态——否则读到的用量不是最终值

### 两套并发控制的对比

| 方式 | 用在哪 | 冲突时 |
|---|---|---|
| version CAS | 文章编辑 / Workflow run 状态 | 抛冲突，要重试 |
| 条件更新 | **钱包用这个** | 不用重试 |

**为什么钱包不用 CAS**：CAS 的语义是「我读到的版本被改过 = 有人插队 = 我要重读重试」。但余额扣减根本不需要重读——「够就扣」本身就是最终判断，返回 0 行是余额真不够，不是并发问题。少了重试循环，也就少了一类 bug。

更新成功后，在**同一个事务、同一行排他锁尚未释放时**读取 `balance / balance_seq` 并插入流水，确保 `balance_after` 与序号属于这一笔变更。钱包行可在注册时创建，也可首次入账时 `INSERT ... ON DUPLICATE KEY` 懒创建；扣减时不存在一律视为余额不足。

## 4. 钱包本体（虚拟支付，零 Redis）

> **2026-10-19 起，本章的充值部分已被 `docs/redis/充值订单真实化设计.md` 升级**：
> `pay` 不再直接加余额，改成「发起支付 → 渠道回调入账」两段式，并新增 `wallet_payment`（支付单）、
> 超时关单、验签 / 幂等 / 金额校验、补单与订单对账。本章保留作为**历史设计与取舍记录**
> （三层幂等、金额快照、归属校验等结论文档仍然有效），**接口与流程以新设计稿为准**。

### 4.1 流程

```
① 前端选套餐 → POST /api/wallet/recharge/orders  { packageCode: "PACK_100" }
   └─ 后端按 packageCode 查套餐配置，落订单行，status=PENDING，返回 orderNo

② 前端「模拟支付」页 → 点确认支付
   └─ POST /api/wallet/recharge/orders/{orderNo}/pay   header: Idempotency-Key
```

### 4.2 pay 的处理（含状态分支）

⚠️ **初稿这里写错了**：原设计「影响行数=0 → 已支付过，直接返回当前钱包（幂等）」把三种完全不同的情况当成了同一种。正确做法：

```
1. 按 orderNo 查订单
   ├─ 不存在                     → 404
   ├─ 不属于当前登录用户          → 403（越权，不能靠 orderNo 猜别人的单）
   ├─ status = CANCELLED         → 报错「订单已取消」
   ├─ status = PAID              → 幂等成功，返回当前钱包
   └─ status = PENDING           → 继续下面的 CAS
2. UPDATE wallet_recharge_order
     SET status='PAID', version=version+1, paid_at=now()
     WHERE order_no=? AND status='PENDING'      ← 状态 CAS 兜住并发双击
   └─ 影响行数=0：必须重新读取订单状态；确认已是 PAID 才按幂等成功返回，不能继续加余额
3. UPDATE user_wallet
     SET balance=balance+credit_amount, balance_seq=balance_seq+1
     WHERE user_id=?
4. 读取 balance / balance_seq，INSERT wallet_transaction
   （type=RECHARGE, amount=+, idempotency_key=?）
```

步骤 2-4 必须在同一数据库事务内；任一步失败全部回滚。

**归属校验不能省**：orderNo 是可枚举的短字符串，不校验归属等于把别人的订单交给任何人「代付」。

### 4.3 幂等三道防线

| 层 | 机制 | 拦住什么 |
|---|---|---|
| 1 | 前端带 `Idempotency-Key` | 重复提交（用户狂点） |
| 2 | 订单状态 CAS | 并发双击（同一订单两笔事务） |
| 3 | `wallet_transaction` 唯一索引 | DB 层最终防线 |

⚠️ **不要复用现有的 `WorkflowActionIdempotency`**——它是 AI 域专用的（key 里带 runId/action，存 Redis）。**钱的操作不能依赖 Redis**，Redis 挂了幂等就失效。这个差别本身就是能讲的点。

### 4.4 将来接真实支付怎么改

**初稿写的「`RechargeService.pay(orderNo)` 方法签名不变」不准确**——真实支付是**两个入口**，不是一个：

```
现在：POST /pay → 直接置 PAID

将来：POST /pay        → 调起微信/支付宝，订单仍是 PENDING（新增：发起支付）
      POST /notify     → 第三方异步回调（新增入口，验签 + 幂等）
                       → 两者都收敛到同一个内部方法
```

**能复用的是一个** `completePaidOrder(orderNo)` 事务方法——把「置 PAID + 加余额 + 写流水」封装好，现在由 pay 调，将来由回调调。接口入口会变，事务内核不变。

### 4.5 套餐（packageCode）

⚠️ **前端只传 packageCode，金额和到账额度由后端决定**。初稿的 `{amount: 10000}` 是安全洞——前端可以传任意金额，等于自助发钱。

套餐当前用配置（`blog.wallet.packages`，key = packageCode，value = payAmount + creditAmount），够用且不引入运营后台。**触发条件**：套餐需要频繁变更 / 需要分用户分渠道定价时，再升级成表 + 管理接口。

### 4.6 自定义金额充值（2026-09-20 新增）

**先说清楚为什么它和 §4.5 说的那个洞不是一回事。**

洞的实质**不是「请求体里有金额」**，而是**客户端决定了到账多少 credit**：

| 入口 | 客户端能决定 | 到账 credit 由谁算 |
|---|---|---|
| 初稿 `{amount: 10000}` ❌ | **到账额度本身** | 客户端——想写多少写多少 |
| 套餐 | 什么都不用决定 | 后端按 `blog.wallet.packages` |
| 自定义 | 只决定「充多少钱」（1 ~ 1000 的整数元） | 后端按 `blog.wallet.custom.credit-per-yuan` |

最坏情况是多充 1000 元、换来 1,000,000 credit——而这是**点了「确认支付」换来的**（虚拟支付），
和一串任意数字白拿额度是两件事。

**两条入口是两个 DTO，不是给同一个 DTO 加可选字段**：`WalletRechargeDTO` 永远不会有金额字段，
那份「靠类型保证」的强度没有降级。合并成 `{packageCode?, payYuan?}` 就变成「可能发生、靠 if 拦」，
在钱的路径上那是降级。

**金额闸门只有一个**：`WalletRechargeServiceImpl#requireWholeYuan`（整数判定 + 上下界）。
刻意**不放在 DTO 的 `@Min/@Max`** 上——上下限来自 `blog.wallet.custom.min-yuan/max-yuan` 配置，
而注解参数必须是编译期常量，两者天生冲突（改了 yml 注解不会跟着变，那是必然漂移）。
放在 service 还让「守卫 + 元→分换算 + credit 公式」挨在一起，改一个不会漏看另外两个。

**三个写的时候差点踩的坑**（都已锁进测试）：

- **DTO 用 `BigDecimal` 而不是 `Long`**：Jackson 默认开 `ACCEPT_FLOAT_AS_INT`，
  `{"payYuan":1.5}` 配 `Long` 字段会被**静默截断成 1**——不报错、无日志。
- **`1e30` 必须转成 `IllegalArgumentException`**：它的 scale 是 -30，能过整数判定，
  然后在 `longValueExact` 抛 `ArithmeticException` → 落到 `Exception` 兜底 → **50000「服务器坏了」**。
  该说的是 40001「你传错了」。
- **溢出用 `Math.multiplyExact`**：`*` 溢出会静默绕成负数 → 写进一张负金额订单 →
  直到 pay 时才报一个指不到根因的错。

**下单之后复用同一个 `pay`**：自定义订单和套餐订单同构（只多一个 `package_code = 'CUSTOM'`），
走同一个 `completePaidOrder`、同一个幂等键 `RECHARGE:{orderNo}`、同一个状态 CAS。
单开一条「自定义支付」会把 CAS 那道防线绕掉，而那个 bug 只在并发双击时才现形。

**误配的错误方向是「不可用」而不是「漏钱」**：即使闸门被绕过，
`WalletServiceImpl.increase` 的 `amount <= 0` 仍是最后一道防线——0 元 / 负数变不成白拿的 credit，
最坏形态只是「订单建了但付不了款」。

**没做的三件**：自定义入口没接限流；没给 `pay_amount` 加 `CHECK` 约束
（CHECK 的报错是约束冲突 → `50000`，而这本该是 `40001`，方向是反的）；
没做「每人每日充值上限」。前两件登记在验证指南 §七。

## 5. AI 计费（预扣 + 结算 + 退款）

> **前置依赖已解除**：初稿写的「Agent / judge 链完全没有 token 统计」已在 2026-09-17 的**全链路补全**中解决——`ai_agent_runs` / `ai_agent_steps` / `ai_workflow_step_logs` 都已有 token 列，分类器 / Agent 决策器 / Verifier / 记忆链的调用点都已接上。

### 5.1 计费单元（bizType + bizId）

**每次用户可见的 AI 请求 = 一个计费单元**。`bizId` 必须在模型调用前就已存在，否则无法先预扣：

| bizType | bizId | 说明 |
|---|---|---|
| `CHAT` | 用户消息 `ai_messages.id` | 用户消息在生成回答前已经落库，可直接作为预扣幂等键 |
| `AGENT` | 用户消息 `ai_messages.id` | `agentRunId` 在 Runtime 内才创建，生成后回填到 `resource_id` |
| `WORKFLOW_ACTION` | `workflowRunId` + action + **CAS 后 version** | **按 action，不是按 run**；version 就是现成的服务端执行序号 |

⚠️ **Workflow 必须按 action 计费**：一个 run 跨多次 HTTP 请求和多次用户确认（确认大纲 → 生成草稿 → 质量检查 → 确认填充），中间可能隔几小时。按 run 预扣的话那笔 `RESERVED` 会挂很久，还得处理跨会话的超时释放。按 action 则每次请求边界清晰、预扣即扣即结。

不能用 assistant message ID：它在回答生成后才有，和「调用前预扣」的时序冲突。也不能把前端 `Idempotency-Key` 直接当业务主键；它只用于请求去重，计费键必须由服务端已有业务记录或状态版本派生。

### 5.2 计费口径（哪些算用户的账）

| 调用 | 归属 | 现状 |
|---|---|---|
| 本次请求内的意图分类 | ❌ 记平台路由成本，不扣用户 | 当前部分路径会并入 `ai_messages.token_count`，计费时不能直接照搬该总数 |
| Agent 决策器 / 收尾总结 / Verifier | ✅ 计入本次请求 | 已实现：落在 `ai_agent_runs.total_tokens` |
| Workflow 各步正文生成 | ✅ 计入本次请求 | 已实现：落在 `ai_workflow_step_logs` |
| 异步记忆提取 / 会话摘要 | ❌ **记平台成本，不扣用户钱包** | 目前只有 `[PERF-AI] llm_usage` 日志 |

**为什么分类器也归平台成本**：它是系统为了选路产生的固定开销，而且 Workflow 的 approve / retry 根本不经过分类器。统一不扣，三条路径的用户计费口径才一致。普通聊天接计费时需要把 `routeUsage` 与正文生成 usage 分开：`ai_messages.token_count` 仍可保留两者总和用于成本观测，billing order 只吃正文生成 usage。

对账必须按**计费单对应的执行 usage**核对，不能拿 `ai_messages.token_count` 直接和钱包流水做等值比较。

### 5.3 扣费时机：预扣 + 结算

```
调用前：按本路径的 token 硬上限扣 reserved（预扣）
        门槛 balance > 0 —— 允许把余额扣成负数（透支一轮，理由见 §3）
调用后：按实际用量结算 → 只退差额（actual <= reserved 必须成立）
失败/取消/超时：RELEASED 全额退
```

⚠️ **预扣和结算是两个独立短事务，模型调用必须夹在它们中间、不能包在事务里**——见 §5.5。

**为什么不能「先调用后扣」**：余额 0 也能白嫖一次，扣不到就是坏账。这正是支付系统的核心矛盾。

⚠️ **初稿写的「余额扣到 0 为止，超出不追」与「余额不足拒绝调用」是两套口径，必须选一个**。选**补全闭环**——理由不是防透支（虚拟额度白嫖几个 token 代价可控），而是**这是面试必问的骨架**：面试官问「余额 0 能不能白嫖」，答「先扣后调、扣不到算坏账」直接减分。

**预扣不能取 P95**。P95 只能做容量估算，不能保证第 96 百分位以后不会透支。预扣值必须来自该路径的**可执行硬上限**：输入 prompt 有裁剪上限、输出有 `maxTokens`、Agent 有 `maxSteps`、Tool Calling 有最大轮数；结算必须满足 `actualCredit <= reservedCredit`。

第一期接入某条路径前，先补齐该路径缺少的硬边界，再配置 reserve：

| bizType | 预扣依据 | 实施前置 |
|---|---|---|
| CHAT | 最大输入 + 最大输出 + 最大工具轮数 | 当前普通聊天未显式设 `maxTokens`，接计费前必须补 |
| AGENT | `maxSteps` × 单步上限 + 总结 + Verifier | 决策器 / Verifier 也要有输出上限 |
| WORKFLOW_ACTION | 按 step 的输入裁剪上限 + 输出上限 | 草稿生成等大步骤单独配置 |

⚠️ **`WORKFLOW_ACTION` 不能统一给 8000**：`GENERATE_DRAFT` 的 `maxTokens` 是 **8500**（只算输出），而输入侧（需求 + 大纲 + 记忆 + RAG 引用 + 历史修改意见）**没有上限**，且历史修改意见每打回一次就长一截。这个 step 要单独给高值。

如果实际用量仍超过预扣，说明「硬上限」实现或统计口径失效：记录 `[BILLING-OVERRUN]` 并告警，不能静默写成正常结算，**也不能按 `actual` 直接扣**——那等于绕开预扣把余额扣穿。

⚠️ **别把这条和「允许透支」搞混，两个方向相反**：

| | 场景 | 余额为负 | 性质 |
|---|---|---|---|
| **预扣时** | 余额 500，硬上限 3000 → 扣成 −2500 | ✅ 正常 | 有界透支，上界 = 单次预扣 |
| **结算时** | 实际 4000 > 预扣 3000 | ❌ 异常 | 硬上限失效，账算错了，告警 |

结算永远只做**退款**（`reserved − actual`），差额为负说明硬上限没兜住，那是 bug 不是业务。

**超时释放**：`expire_at` 必须大于该路径的最大全链路超时并留余量。定时任务扫 `status='RESERVED' AND expire_at < now()` → CAS 置 `RELEASED` 并退款；晚到的结算因状态不再是 `RESERVED` 必须失败，不能二次扣款。这是**进程崩溃时的兜底**——正常路径永远走不到它。任务按「只捞不执行」写（投给 `@Async`），因为调度池 `pool.size: 1` 是串行的。

**usage 缺失不能按 0 结算**。模型调用成功但 provider 没返回 usage 时——**按预扣全额结算**（`actual = reserved`），记录 `[BILLING-USAGE-MISSING]` 告警。

⚠️ **状态机就只有三个状态，没有 `SETTLEMENT_PENDING`**：

```
RESERVED ──→ SETTLED     结算（含 usage 缺失时按预扣全额收）
         └─→ RELEASED    失败 / 取消 / 超时，全额退
```

不存在「挂起等人工补录」的中间态——下面这段是在解释**为什么不引入第四个状态**，别读成「要用它」。

选「全额收取」而不是挂一个 `SETTLEMENT_PENDING` 状态，理由：

- 场景本身罕见（主流 provider 都返回 usage），而用户**确实拿到了回答**
- 挂起状态要额外付出：状态图多一个分支、`status` 字段要加长、巡检要覆盖它、要定处理期限、前端要能显示「待结算」——**为一个边缘场景引入一条长期挂起的生命周期，不划算**
- 要追溯不需要新字段：`actual_credit = reserved_credit` 且 `prompt_tokens IS NULL` 就是它的特征

⚠️ 无论如何**不能因为 `totalTokens = 0` 就把一次真实调用记成免费**——那等于把「统计缺失」和「零消耗」混为一谈，方向比多扣更糟。

### 5.4 单价配置（V1 统一 total-token 内部价）

当前三个落库口径的共同交集只有 `totalTokens`：`ai_messages` 只有 `token_count`，Agent 虽有 input/output 但混合了生成链与判断链，Workflow step 才能稳定区分 input/output。V1 因此只配置一个统一的**内部积分价**：

```yaml
blog:
  ai:
    billing:
      enabled: true
      credit-per-1k-tokens: 10
```

结算公式统一向上取整，避免整数除法把小请求算成 0：

```text
actualCredit = ceil(totalTokens × creditPer1kTokens / 1000)
```

这不是供应商真实成本价，而是稳定、可解释的产品积分价。判断链模型更贵、输入输出价格不同，属于**平台成本核算**，不必强行映射到用户价格。

**升级触发条件**：真的要按供应商成本定价或做模型级毛利分析时，再新增按调用记录的 usage 明细（`billing_order_id / chain / model / input / output`）。只给 `ai_agent_runs` 加两组汇总列虽然更轻，但会继续遗漏聊天、Workflow 和未来新链路，不建议为了预留现在就加。

### 5.5 事务边界（不能把模型调用包在事务里）

⚠️ **这是最容易写错的地方**。最自然的写法是把「预扣 → 调 LLM → 结算」整个包进一个 `@Transactional` 方法——那样会**长期持有钱包行锁和数据库连接**：LLM 调用几十秒到几分钟，连接池会被迅速占满，并发用户一多就雪崩。

正确链路是**两个独立短事务，中间不持有任何数据库资源**：

```
事务 A（几十毫秒）
  ① INSERT ai_billing_order   status = RESERVED
  ② UPDATE user_wallet        条件扣减 —— 行锁在这里产生，也在这里释放
  ③ 读 balance / balance_seq → INSERT wallet_transaction (AI_RESERVE)
  ④ COMMIT

──── 事务外：调 LLM（可能几十秒到几分钟）────
     此期间不持有任何 DB 连接、不持有行锁

事务 B（几十毫秒）
  ⑤ UPDATE ai_billing_order   CAS: WHERE status='RESERVED' → SETTLED
  ⑥ UPDATE user_wallet        退差额（失败路径则全额退）
  ⑦ 读 balance / balance_seq → INSERT wallet_transaction (AI_REFUND)
  ⑧ COMMIT
```

**为什么事务 A 里要「更新完再读余额」**：UPDATE 拿到的行锁在事务提交前一直持有，同一事务内读到的 `balance / balance_seq` 必然是这次更新之后的值，不会被别人插队。**这个「写后读」必须在锁释放前完成**，否则 `balance_after` 快照会和实际不符，§7.3 的逐笔回放就会报假警。

**同理，这三条各自都是独立短事务、互不嵌套**：超时释放（§5.3）、异常退款、死信处理（§6.5）。

## 6. 秒杀

### 6.1 Redis 结构

```
seckill:{activityId}:stock   String   剩余库存
seckill:{activityId}:users   Set      已抢到 userId（一人一单，快速路径）
seckill:{activityId}:meta    Hash      status / startAt / endAt（时间统一用**秒**，与 TIME 对齐）
seckill:{activityId}:events  Stream   待入账事件（消费组 seckill-settle）
```

四个 key 共用 `{activityId}` hash tag。当前单机 Redis 不依赖它，但将来切 Cluster 时，同一段 Lua 的多个 key 必须落在同一槽；现在统一命名几乎零成本。

### 6.2 抢购 Lua（查重 + 发事件 + 扣库存，一次原子完成）

```lua
-- KEYS[1]=stock  KEYS[2]=users  KEYS[3]=meta  KEYS[4]=events
-- ARGV[1]=userId  ARGV[2]=activityId
local stockType = redis.call('TYPE', KEYS[1])['ok']
local usersType = redis.call('TYPE', KEYS[2])['ok']
local eventType = redis.call('TYPE', KEYS[4])['ok']
local metaType = redis.call('TYPE', KEYS[3])['ok']
if stockType ~= 'string' then return {-3, 'BAD_STOCK_KEY'} end
if usersType ~= 'none' and usersType ~= 'set' then return {-3, 'BAD_USERS_KEY'} end
if metaType ~= 'hash' then return {-3, 'BAD_META_KEY'} end
if eventType ~= 'none' and eventType ~= 'stream' then return {-3, 'BAD_STREAM_KEY'} end

local status = redis.call('HGET', KEYS[3], 'status')
local startAt = tonumber(redis.call('HGET', KEYS[3], 'startAt') or '0')
local endAt = tonumber(redis.call('HGET', KEYS[3], 'endAt') or '0')
-- ⚠️ TIME 返回 {秒, 微秒}，元素是**字符串**，必须 tonumber 才能比较，否则 Lua 报
--    "attempt to compare string with number" —— 脚本抛错 = 抢购全挂
local now = tonumber(redis.call('TIME')[1])
if status ~= 'ACTIVE' or now < startAt or now >= endAt then return {-2, 'NOT_ACTIVE'} end

if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end   -- 已抢过
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock <= 0 then return 0 end                                        -- 已抢完

-- 先生成可靠事件，再更新快速路径状态。Lua 运行时错误不会回滚；
-- 类型预检先排除最常见的 WRONGTYPE，event-first 避免"扣了资格却没有事件"。
local eventId = redis.call('XADD', KEYS[4], '*',
                           'activityId', ARGV[2], 'userId', ARGV[1])
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return {1, eventId}                                                     -- 预占成功
```

**为什么必须 Lua**：`GET` 判断 + `DECR` 两步分开执行，中间能被插队 → 超卖。

⚠️ **`XADD` 也必须在脚本里**：如果 Lua 只扣库存、事件由 Java 侧补投，那么「扣成功但进程崩溃 / 投递失败」= 名额凭空消失，用户永远停在「排队中」。

⚠️ **顺序只能降低风险，不能制造数据库事务式回滚**：如果 `XADD` 成功后 Redis 因内存故障导致后续写命令失败，会留下「有事件、快速路径状态没更新」。这个方向比「扣了库存却没事件」更可恢复：消费者仍由 DB 库存和唯一索引最终裁决，巡检负责发现 Redis 三个视图不一致。脚本异常必须打带 activityId/userId 的可检索日志。

**生产脚本不做 `MAXLEN` / `XTRIM`**。裁剪可能删掉仍在 PEL 的消息内容，和“额度不可丢”的目标冲突。成功消费后按 `XACK → XDEL` 顺序清理；如果 ACK 后、删除前崩溃，只会残留一条已完成消息，后续低频清理即可，不会丢待处理事件。

⚠️ **`XDEL` 的前提是「只有一个消费组」**：`XDEL` 是**物理删除，所有消费组一起受影响**。将来加了对账组 / 监控组之后，单个消费者**不能**再直接 XDEL——那会删掉别的组还没处理的消息。届时的清理规则要改成「所有消费组都 ACK 过的消息才可删」，用 `XTRIM MINID` 或按组逐一确认，而不是谁处理完谁删。

⚠️ 注意返回值语义变了：`1 + eventId` 现在是**「预占成功」**，不是「已入账」。

### 6.3 可靠投递（不能复用 RagRetryQueue）

⚠️ **初稿写的「复用 `RagRetryQueue` 模式」是错的**。核实 `RagRetryQueue.takeDue()`：Lua 里 `ZRANGEBYSCORE` + `ZREM` 一次做完，**取走即删**，然后才交给 `@Async`。取出后进程崩溃 → 任务永久消失。

RAG 能接受这个，因为它有**失败标记 + 人工修复入口**兜底；额度入账没有这层。

**选 Stream 消费组，不要手工改 ZSet**：把 ZSet 改成「取出只改 score（可见超时），成功才 ZREM」就是**手工实现 PEL**——那正好是 Stream 已经做好的事，还要自己处理重复投递和死信。而且 `RagRetryQueue` 的类注释里已经写了升级触发条件：「需要多消费者分组、需要 at-least-once 保证时，再换 Stream」——秒杀入账正好命中 **at-least-once**。

```
投递：在 §6.2 的 Lua 里完成（XADD 与资格预占在同一个脚本内）
消费：XREADGROUP GROUP seckill-settle consumer-{n} COUNT 10 BLOCK 2000 STREAMS seckill:{id}:events >
   ├─ 入账成功 → XACK，再 XDEL
   └─ 入账失败 → 不 ACK（留在 PEL，下一轮 / 超时回收再取）
回收：XAUTOCLAIM seckill-settle consumer-{n} 60000 0-0 COUNT 10   （处理消费者崩溃留下的 pending）
```

> 实现注意：`XAUTOCLAIM` 若 Spring Data Redis 版本未封装，用 `RedisConnection.execute(...)` 原生调用。

**API 语义**：Redis 预占成功后**返回「排队中」，不能返回「抢到了」**——此刻 DB 还没入账，返回成功却最终失败会让用户觉得被吞了。前端轮询结果接口（或复用现有 SSE）。

**重投幂等不能只靠“插入时报唯一键冲突”**：消费者拿到 `(activityId, userId)` 后，若已存在 `GRANTED` 订单，说明上次事务已成功、只是来不及 ACK，本次直接 ACK；若不存在才开启新事务。钱包流水幂等键固定为 `SECKILL:{activityId}:{userId}`，不能每次重试随机生成。

### 6.4 最终裁决在 DB（Redis 不是裁判）

⚠️ **初稿写的「Redis 是唯一裁决者」是错的**。

前提核实：`redis.conf.example` 里的 `appendonly yes` 只是**部署模板建议**，不代表所有环境都开了；就算开了，`everysec` 也最多丢 1 秒。真正的危险是**重建**——Redis 挂了之后重新预热，如果源数据取「总库存」而不是「总库存 − DB 已发放」，直接超发。

```sql
UPDATE seckill_activity
SET sold_count = sold_count + 1
WHERE id = #{activityId} AND sold_count < total_stock   -- 列比列，不依赖传入值
```

影响行数 0 → DB 说已售罄。

⚠️ 条件里**引用 `total_stock` 列，不要把总库存当参数传进来**：传参意味着判定依据来自调用方，一旦传入值和行内值不一致（活动被改过库存、参数拼错），限制就失效了。让 DB 用自己那一行做判断。

**Redis 挡流量，DB 保正确**。代价比想象中小：Redis 已经挡掉了重复请求和售罄请求，能走到 DB 的只有**中签者**——**DB 压力是 O(库存)，不是 O(QPS)**，削峰并没有失效。

### 6.5 失败分类与补偿（两种失败不能混）

⚠️ 初稿写的「DB 失败 → 补偿 Redis 资格」把两种完全不同的失败当成了一种：

| 失败类型 | 特征 | 正确处理 | Stream 侧 |
|---|---|---|---|
| **业务失败** | 条件更新影响 0 行（DB 说已售罄） | Redis 多发了名额。**不要把库存退回去**——名额已经给出去了，收回来再发别人只会更乱。标记该用户 `FAILED` + **告警** | **ACK**（终态，重试也不会有不同结果） |
| **技术失败** | DB 超时 / 连接异常 | **不确定是否落库**（事务可能成功了但响应超时）。此时退库存可能造成超发。正确做法是**重试**，靠 `uk_user_activity` 幂等 | **不 ACK**（留在 PEL 等重试） |

⚠️ **业务失败必须 ACK，否则是死循环**：售罄是**永久状态**，不 ACK 的话这条事件会被无限重投——每轮都走一遍「条件更新影响 0 行 → 标记 FAILED」，永远出不来。所以终态要落地、消息要清掉。

对应的消费入口要判三种已存在的状态：

```
已有 GRANTED 订单 → 上次已成功只是没来得及 ACK → 直接 ACK
已有 FAILED 订单  → 已终态，重投也不会有不同结果 → 直接 ACK
两者都没有        → 开启 DB 事务执行
```

这条和 §6.3 串起来：**可靠投递不是可选项，而是 DB 重试的前提**。没有 at-least-once，技术失败就没法安全重试。

#### 技术失败的重试上限与死信

「不 ACK + 重试」不能没有终点——DB 持续异常（表被删、磁盘满、连接池枯竭）时，消息会**永久趴在 PEL 里**，对账也分不清「暂时延迟」和「永久故障」。

| 项 | 设计 |
|---|---|
| **重试次数从哪来** | Stream 的 **delivery count**（`XPENDING` 可查，每次重投自动 +1）——**不需要自己维护 attempt 字段**。这正是选 Stream 而不是手搓 PEL 的红利 |
| **退避** | `XAUTOCLAIM` 的 `min-idle-time`：首轮 60s，之后随 delivery count 递增（`60s × count`）。Stream 没有延迟投递，靠「静默多久才可回收」间接实现 |
| **上限与死信** | 超过 N 次（建议 5）→ 停止回收，**持久化终态** `seckill_order.status = FAILED_RETRY` + 告警，然后 **ACK**（必须清出 PEL，否则它永远占着） |
| **人工重投** | 允许：把状态改回待处理，再 `XADD` 一条**新事件**——不要试图复用旧消息 ID |

⚠️ **死信状态必须有**，否则「技术失败重试中」和「消费者崩了」在 PEL 里长得一模一样，对账无法区分二者。

### 6.6 完整链路

```
① 活动开始前：预热库存到 Redis（+ 活动元数据缓存）
② 用户抢购 → Redis Lua：类型预检 + 查重 + XADD 事件 + 资格预占（一次脚本完成）
   ├─ 返回 0 / -1 → 直接拒绝，不打 DB
   └─ 返回 1 → 返回「排队中」（名额已占、事件已入队）
③ 消费者（先查已存在状态，再决定要不要开事务）：
   a. 已有 GRANTED 订单 → 上次已成功、只是没来得及 ACK → 直接跳到 e
   b. 已有 FAILED 订单  → 已终态，重投不会有不同结果     → 直接跳到 e
   c. UPDATE seckill_activity 条件扣减        ← 最终裁决
   d. INSERT seckill_order（uk_user_activity）← 一人一单最终防线
      + 钱包加钱 + 写流水（幂等键 = SECKILL:{activityId}:{userId}）
   e. DB 事务提交成功后 XACK，再 XDEL
④ 失败分支（按 §6.5，两种处置相反）：
   ├─ 业务失败（售罄）→ 持久化 FAILED → ACK + XDEL + 告警   ← 终态，必须 ACK
   └─ 技术失败        → 不 ACK（留 PEL 等重试 / XAUTOCLAIM 回收）
⑤ 定时对账（§7）
```

限流：秒杀接口挂**第 4 个桶** `seckill`。前面说了，`AiRateLimiter` 不用改。

### 6.7 活动生命周期（2026-09-20 新增）

**为什么需要它**：`status`（DRAFT / ACTIVE / ENDED）在本次之前**没有任何地方写入**——
两个常量定义了但零引用。后果全在运营侧：新建活动只能手工 INSERT 且必须直接填 ACTIVE
（填 DRAFT 就是**死状态**，没代码会把它变成 ACTIVE）；开始要手工 UPDATE + 手工调预热接口，
**两步漏一步就不能抢**；到期和售罄后状态永远停在 ACTIVE。

⚠️ **先说清楚：抢购的正确性没有 bug**，Lua 一直在管时间窗和售罄。这次补的是运营自动化，
不是修正确性——下面所有取舍都以这条为前提。

**三层时间边界，各管各的**：

| 层 | 管什么 | 迟到的代价 |
|---|---|---|
| 抢购 Lua（`now < startAt` / `now >= endAt` / `stock <= 0`） | **正确性**——能不能抢 | 无，它就是权威 |
| `SeckillLifecycleTask`（5 秒一轮） | **运营视图**——status 字段 | 状态晚几秒翻转，无实际影响 |
| 前端 `activityPhase` | **展示**，且本地时钟只能推向「更不可抢」 | 早显示几秒「已结束」 |

**定时任务不能替代 Lua。** 调度池 `pool.size: 1` 串行，同池还有 2 秒一轮的入库消费者、
浏览量同步、RAG 重试——任务被前面拖住 10 秒，用户就晚 10 秒能抢。同理，
**前端绝不能本地判断「开始了」**，那会造出「前端说能抢、后端说没开始」的窗口；
前端的边界定时器只做一件事——到点了去问服务端要新状态。

**ENDED 的前置条件是「已排空」，不是「时间到了」**（本节最要紧的一条）：

`SeckillSettleTask` 消费的活动列表只查 `status = ACTIVE`，所以活动一置 ENDED，
消费者**立刻不再看它**——而 Stream 的 PEL 里可能还有在途事件（用户已经抢到、正等入账）。
那条事件会永远烂在 PEL 里，用户永远停在「排队中」。

| | 放宽消费者查询 | **排空门（采用）** |
|---|---|---|
| 改动面 | 消费者 + 对账两处查询 | 只在生命周期内 |
| 不变量 | 「ENDED 后仍会被消费」 | **「ENDED ⟺ 无在途工作」**（更强，可断言） |
| 代价 | 每 2 秒为每个 ENDED 活动花 3~4 次 Redis 往返，持续到 events key 过期（30 天） | status 晚翻转（正常 <2 秒；卡死事件由 `MAX_DELIVERY` 5 次 × 60 秒兜底） |

判据要**两个都查**：`XLEN == 0`（没有还没被读走的）**且** PEL 为空（没有读了还没 ACK 的），
只看一个都会漏。副产品很划算——活动连同它的排空期都还在 ACTIVE 集合里，
所以**消费者和对账一行都不用改**，「卡住的排空」本来就还在被对账盯着。

⚠️ **`pendingCount` 的失败语义必须保守**：查不到时抛出去（= 当作没排空），
**不能**像对账任务那样返回 0。「未知」被当成「已排空」会让一个还有在途事件的活动被结束
——那是这个模块唯一会丢数据的方向。

**为什么是 `status_changed_at` 而不是 `updated_at`**：`increaseSoldCount` 每发一份额度
就 UPDATE 一行，`ON UPDATE CURRENT_TIMESTAMP` 会让时间戳每次抢购都跳，
「这次 ENDED 是超时判的还是售罄判的」就再也查不出来了。这一列**只在 CAS 流转时显式写**，
顺带保证 MySQL 与 H2 行为一致（测试才锁得住）。

**预热修复的探针是 `HGET meta status`，不是 `hasKey`**：CAS 置 ACTIVE 后要确保 Redis 有状态，
但**不能每轮无条件 `preheat(id)`**——`preheatOne` 是 delete + 重建，会清掉在途预占的
`users` 成员、重置 `reservedBase`/`stockBase` 基准，对账下一轮就会报「名单增量 ≠ 库存减量」。
`hasKey` 又只能发现「没建起来」，发现不了**「建起来了但 `meta.status` 是错的」**——
而后者正是这条流程最容易产出的坏状态（拿 CAS 之前的旧实体去预热，写进 meta 的就是 DRAFT）。
一次 HGET 同时覆盖两种：没建起来才重建，只是状态位不对就一条 `HSET` 修好。
这个探针还是**多实例下唯一的补救**——A 实例 CAS 成功、预热前崩溃，B 实例 CAS 返回 0 静默忽略，
活动会永远 ACTIVE 且无 Redis 状态。

**运维约定**：

- **重开一场活动必须同时改 `end_at`**。任务是个「向时间窗收敛」的循环，任何与
  `start_at` / `end_at` 矛盾的中间状态都会在下一轮被覆盖——只把 ENDED 改回 ACTIVE，
  用户只有 5 秒窗口。改完还要调一次 `POST /api/seckill/admin/preheat`，
  否则 `meta.status` 还是 ENDED，Redis 一路拒绝
- **多实例不需要分布式锁**：流转走 CAS（`WHERE status = expected`），输家静默返回 0

**顺手修掉的一个既有 bug**：`SeckillReconcileTask.pendingCount` 原本用
`connection.execute("XPENDING", ...)` 原生命令读 PEL，而 Lettuce 的 `ByteArrayOutput`
**解析不了 XPENDING summary 里的整数**，会抛 `UnsupportedOperationException`
（被包成「Unknown redis exception」）；那个方法的 `catch (RuntimeException) { return 0; }`
把它一起吞了 → **恒返回 0** → 「在途多于 PEL 待处理」永远按 pending=0 判，
正常的在途（刚抢到、正在入账）被报成「事件可能已经丢失」。
改成类型化的 `opsForStream().pending()`。**这个坑是写生命周期时踩到并定位的，
回头才发现对账那边一直在静默失效。**

### 6.8 每日自动开场（2026-09-20 新增）

**只做一件事：建一场 DRAFT 活动。** 到点激活、预热、结束全交给 §6.7 的生命周期流转
——每日任务一行都不重复实现。这正好验证了那层抽象拆得对不对：加一个「每天定时开场」
不需要碰激活/预热/结束里的任何一行。

**活动 id = `yyyyMMdd`**（如 `20260921`），**幂等完全靠主键**：重复创建直接撞主键，
不需要任何额外机制，也不用给表加唯一列改两张 schema。8 位数和 19 位雪花不冲突，
所以手工建的临时活动照常共存。

id 段位约定（也写进了验证指南）：

| 位数 | 形式 | 用途 |
|---|---|---|
| 8 | `yyyyMMdd` | 自动创建的每日活动 |
| 12 | `yyyyMMddHHmm` | 手工开「一天两场」 |
| 19 | 雪花 | 手工建的临时活动 |

> ⚠️ **不要把这招推广到别的表**：`articles.id` 是 `AUTO_INCREMENT`，
> 在那张表手写 `20260921` 会把自增计数器顶到两千万，后面所有插入的 id 全跳。
> 这里成立是因为 `seckill_activity.id` 是裸 `BIGINT PRIMARY KEY`。

**「下一场」而不是「今天那场」**：`LocalTime.now() < endTime ? today : today + 1`。
于是 10:30 那一刻，今天的卡被列表的 `end_at` 过滤掉、明天的卡**同时**被建出来——
列表无缝衔接、**永不空**。用户下午 15:00 打开看到的是「明日 10:00 · 未开始」，
而不是一个空页面。

**这道判据还顺带堵掉一个坑**：如果不判，10:30 之后启动的服务会建出一场窗口全在过去的活动
——`activateDueActivities` 要求 `end_at > now`，那场会**永远停在 DRAFT、永不激活、
无异常无日志**，还会以「未开始」的置灰卡片永久挂在列表上。

**每分钟轮询，不是 `cron = "0 0 0 * * ?"`**：零点那一刻服务若在重启/宕机就漏一天；
每分钟检查能**自愈**——10:15 启动的进程会在几秒后建出当天那场（窗口还没过），
生命周期任务 5 秒内激活并预热，用户 10:15:08 就能抢。成本是每分钟一次主键点查
（亚毫秒），量级不到同池 60 秒一轮的 `SeckillSettleTask` 的百分之一。
⚠️ 前提是服务层必须 O(1)——写成 `selectList` 再遍历会让成本翻几十倍，
还会和 2 秒一轮的消费者抢 `pool.size: 1` 的单线程调度池。

**列表过滤口径：`end_at > now`，不是 `status != 'ENDED'`。**

**决定性理由是它和抢购谓词同构**——Lua 里判的就是 `now < endAt`。所以：

> 列表过滤条件 = 「现在还能不能抢」。不存在「藏起来但还能抢」的活动。

`status != 'ENDED'` 反而危险，会漏出两类：排空门期间仍是 ACTIVE 的活动
（到点了但 PEL 没清，会以「已结束」的置灰卡片挂着），以及上面那种**永不激活的死 DRAFT**。
这条已用反向验证锁住：把过滤换成 `status != 'ENDED'`，列表用例精确变红。

**排序也必须一起改**：原来是 `orderByDesc(startAt)`，列表语义从「历史流水」变成
「接下来能抢什么」之后，DESC 会把最晚开始的排最前，而配合 `LIMIT 20` 截掉的恰好是
**最老开始的那批**——也就是今天正在跑、此刻唯一能抢的那场。改成 `orderByAsc(endAt)`
（最快结束的排最前），截断时先保住最紧急的。

**⚠️ 窗口配反是唯一「静默全废」的方向**：`end-time` 早于 `start-time` 时，
`start_at <= now AND end_at > now` 在同一天内恒为假，活动永远停在 DRAFT、不报错不打日志。
由 `SeckillDailyValidator` 在启动时 fail-fast 堵住。
（对照：yml 里 `10:00` 忘了加引号是**响亮**的——YAML 1.1 把它当 60 进制整数解析成 `600`，
绑定 `LocalTime` 失败，启动直接挂，不需要额外兜。）

**删掉了 `db/init.sql` 里的种子活动**（原 id=1、100 份、30 天窗口的 ACTIVE）：
有了自动开场它就多余了，而且会一直挂在列表上且能抢，让「每天 50 份」看起来是坏的。
手工建临时活动仍然可以，按上面的 id 段位约定来。

## 7. 对账与补偿

### 7.1 秒杀对账

每 5 分钟比对这些观测值：

- **Redis 侧已预占数** = `SCARD(seckill:{id}:users)`（或 `total_stock - seckill:{id}:stock`，两者应一致）
- **DB 侧成功订单数** = `COUNT(seckill_order WHERE activity_id=? AND status='GRANTED')`
- **在途数** = Stream consumer group 的 `lag + pending`（只看 PEL 会漏掉尚未投递给消费者的新消息）

**这些值不是严格恒等式**：Lua 极端部分失败、Redis 重建、重复事件都可能让 Set / stock / Stream 短暂分叉。判据是「多个视图最终收敛」，并同时检查正负两个方向：

```
reservationGap = Redis 预占数 − DB 已入账数
记录连续 N 轮：
  - reservationGap > 在途数且持续不降 → 可能有丢失/卡死事件
  - reservationGap < 0                  → Redis 状态丢失或重建口径错误
  - SCARD(users) != total_stock - stock → Lua 部分失败或 key 被外部改坏
```

⚠️ **不能简单「不等就告警」**——异步落库天然有延迟。这个「最终收敛」的判据在面试里很加分。

### 7.2 深度对账（低频补偿）

每 1 小时跑一次**逐个核对**：用 `SSCAN` 分批扫描 `seckill:{id}:users`，某个 userId 在 `seckill_order` 里找不到对应 `GRANTED` 记录、且 Stream 的未消费 / pending 中也找不到对应事件 → 说明链路没有收敛，需要人工介入（或自动补单，取决于是否还能确定当时的资格）。

Set 大时抽样，或按批次扫。

### 7.3 钱包对账

```sql
-- 逐笔回放校验（按 balance_seq 排序，不是 created_at / id）
SELECT id, user_id, amount, balance_after, balance_seq,
       LAG(balance_after) OVER (PARTITION BY user_id ORDER BY balance_seq) AS prev_balance,
       LAG(balance_seq) OVER (PARTITION BY user_id ORDER BY balance_seq) AS prev_seq
FROM wallet_transaction WHERE user_id = ?
```
校验 `prev_balance + amount == balance_after` 且 `balance_seq = prev_seq + 1`；不一致 → 有并发写绕过条件更新、漏流水或错误回放，告警。

### 7.4 AI 计费单巡检

扫 `status='RESERVED' AND expire_at < now()` → 释放并退款（§5.3 的兜底任务同时承担巡检职责）。

## 8. 面试价值映射

| 设计点 | 对应面试题 |
|---|---|
| 钱包纯 DB / 秒杀才用 Redis | 什么场景**不该**用 Redis |
| 余额用 credit 而非「分」 | 金额精度 / 单位选择 |
| 条件更新 `WHERE balance > 0` | 乐观锁 / 防超扣 / 并发控制选型 |
| **预扣是上界不是报价 → 允许透支一轮** | 授权额度 vs 实际扣款 / 为什么宁可留坏账窗口也不误杀 |
| 流水表 + `balance_after` | 记账 / 对账 |
| **回放按 `balance_seq` 排序** | 并发下时间戳不可靠；Snowflake ID 也不等于加锁顺序 |
| 订单状态 CAS + 归属校验 | 状态机 / 幂等 / 越权 |
| `(user_id, idempotency_key)` 唯一约束 | 幂等三道防线 |
| **硬上限预扣 + 结算 + 退款** | 支付系统核心模式 / 为什么 P95 不能当授权额度 |
| **计费单元 / 平台成本分离** | 成本归属 |
| Lua 原子预占 | 秒杀防超卖 |
| **Lua 出错不回滚 → 预检 + 可恢复方向 + 对账** | Redis 脚本的原子性边界 |
| **Stream 消费组 + PEL + XAUTOCLAIM** | 可靠投递 / at-least-once |
| Set + 唯一索引双保险 | 一人一单 |
| **DB 条件更新做最终裁决** | 缓存与 DB 谁是权威 |
| **失败分类（业务 / 技术）** | 补偿的正确性 |
| **对账判「收敛」而非「相等」** | 分布式一致性 |
| 秒杀独立限流桶 | 限流 / 防刷 |

## 9. 实施顺序

```
1. 钱包账户 + 流水 + 模拟充值        ← 零 Redis，纯正确性          ✅ 批次 A
2. 聊天 + AI billing order 端到端    ← 先跑通「充值后可消费」的产品闭环  ✅ 批次 B
3. 秒杀                              ← 发放的额度此时已有真实消费出口  ✅ 批次 C
4. ~~推广到 Agent~~                  ← 2026-09-21 决定不做
5. ~~推广到 Workflow（按 action 计费）~~ ← 同上
```

**为什么先接聊天再做秒杀**：这个系统的定位不是独立电商。钱包如果只能充值和抢额度、却没有消费出口，产品链路仍是断的。普通聊天是最短的扣费路径，先把它跑通。

**第 4、5 步明确不做（2026-09-21）**：聊天侧已经有完整的预扣 → 结算 → 差额退回，
把同一套在 Agent / Workflow 上再接一遍是**重复劳动**，收益不匹配。
所以「Agent / Workflow 不扣费」是**产品边界**而不是待补的缺口——
它连带消掉了一条本来要防的隐患（Agent 若接上预扣，0 余额用户会在
`streamAgentReply` 之前被 402 拦住 →「因为没钱所以不能充钱」）。

**秒杀直接上 Stream**，不做「Redis 预占 + 同步落库」的过渡版：异步落库 + 对账才是秒杀的面试重点，同步版等于没讲。而且 §6.2–§6.3 已经把可靠性细节定死了（PEL / lag / XAUTOCLAIM / `XACK → XDEL`），没有回头做简化版的理由。

### 复核时新发现（codex 与初稿都未覆盖）

- **事件投递必须在 Lua 脚本内**：初稿的抢购脚本只做了「查重 + 扣库存」，事件靠 Java 侧补投。扣成功但投递失败 = 名额凭空消失，用户永远停在「排队中」。已把 `XADD` 并入脚本（§6.2）。
- **Redis Lua 出错不回滚**：脚本中途抛错时，已执行的命令不撤销。类型预检 + event-first 只能把故障导向更可恢复的一侧，仍要靠 DB 最终裁决和巡检收口（§6.2）。
- **`XTRIM` 不保证保留 PEL**：`MAXLEN` 裁剪掉的消息即使还在 pending 列表里也取不回内容。可靠队列不在生产脚本裁剪，成功后 `XACK → XDEL`（§6.2）。
- **Agent 层无法分模型结算**：这个判断成立，但当前不需要为它加列。V1 统一 total-token 内部价；真的需要成本级精度时再加调用明细（§5.4）。
- **`WORKFLOW_ACTION` 不含分类器成本**：进一步统一为「分类器属于平台路由成本，所有路径都不向用户收费」。普通聊天接计费时拆开 route usage 与生成 usage（§5.2）。
- **Lua 类型预检是保险而非必需**：它防的是运维事故（key 被误设类型），正常路径遇不到。真风险（扣了库存却没事件）靠 event-first 已挡住。保留可以，但要知道它是为小概率付固定开销（§6.2）。

### 第二轮调整（允许透支一轮）

**触发**：`reserved` 改成「硬上限」之后，刚性门槛 `balance >= reserved` 会**大面积误杀**——余额 5000 的用户在硬上限 10000 的对话面前被拒绝，而他的钱够一次真实消耗。门槛必须跟着预扣口径一起改。

| 位置 | 调整 |
|---|---|
| §2① `user_wallet` | `CHECK (balance >= 0)` → `CHECK (balance >= -1000000)`。非负约束会让预扣直接报错；留宽松下界仍能拦住「符号写反 / 扣减跑飞」这类 bug |
| §3 | 门槛 `balance >= reserved` → **`balance > 0`**；补「为什么门槛不能是硬上限」的论证 |
| §5.3 | 拆分两个方向：**预扣时**扣成负数是正常业务（有界透支），**结算时**超出预扣去扣是异常（硬上限失效，告警） |
| §8 | 补面试题：授权额度 vs 实际扣款 |
| §9 | 撤掉「秒杀是否上 Stream」的待拍板 —— 方向已定 |

**口径**：透支上界 = 单次预扣额度（有界、可算）——负余额幅度**恒小于造成它的那笔预扣**，不需要额外的 `overdraftLimit`；真要加，那是风控选择，不是正确性必需品。
