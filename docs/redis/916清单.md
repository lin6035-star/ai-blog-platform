# Redis 高频但项目没用上的点（清单）

## A 类 · 做，成本低收益高 ⭐ 优先做这 4 个

### 1. HyperLogLog → 文章 UV

|          |                                                              |
| -------- | ------------------------------------------------------------ |
| **缺口** | 项目**只有 PV（浏览量），没有 UV（独立访客）**               |
| **落点** | 浏览文章时 `PFADD article:uv:{id} {userId 或 IP}`，详情页展示 UV |
| **成本** | 极低——一个常量 + 两行代码 + VO 加个字段                      |
| **能讲** | 固定 **12KB** 内存 / 标准误差 **0.81%** / **不能取元素、只能计数** / `PFMERGE` 合并多天 / 为什么不用 Set（1 亿 UV 要 800MB） |

**面试频率 ★★★★★**——"怎么统计 UV"是必问，而且这题**项目里天然缺一半**，接上去毫无违和感。

### 2. Bitmap → 用户活跃 / 留存统计

|          |                                                              |
| -------- | ------------------------------------------------------------ |
| **缺口** | 没有任何活跃统计                                             |
| **落点** | 每天一个 key `active:20260916`，用户登录或发文时 `SETBIT {userId} 1`；`BITCOUNT` 算日活；**`BITOP AND` 算连续活跃（留存）** |
| **成本** | 低——一个组件 + 定时任务 + 一个展示接口                       |
| **能讲** | 1 亿用户 = **12.5MB** / `BITCOUNT` / `BITOP AND/OR/XOR` 做留存 / 和 Set 的对比 |

**面试频率 ★★★★★**，而且**留存统计是真产品需求**（博主想知道周活跃），不是硬凑。

### 3. Pipeline → 热榜重建

|          |                                                              |
| -------- | ------------------------------------------------------------ |
| **落点** | `ArticlesServiceImpl.java:1192-1207`，现在是 **GET × N + ZADD × N = 2N 次往返** |
| **成本** | 极低，改 10 行                                               |
| **能讲** | Pipeline 把 N 次 RTT 压成 **1 次** / **和事务的区别（Pipeline 只打包、不保证原子性）** / 和 Lua 的区别（Lua 服务端执行、Pipeline 客户端打包） |

**面试频率 ★★★★**——这题必被问"Pipeline 和事务有什么区别"，而且**你现在真有个批量场景可以讲**。

### 4. ZSet 延迟队列 → RAG 索引失败自动重试

|          |                                                              |
| -------- | ------------------------------------------------------------ |
| **缺口** | 失败标记存了，**但没有自动重试**——现在只能人工触发重建       |
| **落点** | 失败时 `ZADD retry:queue {下次重试时间戳} {任务ID}` → 定时任务 `ZRANGEBYSCORE 0 now` 取到期任务 → **Lua 原子取出**（防并发重复消费）→ 失败则**指数退避**重推 → 超 N 次转人工 |
| **成本** | 中——一个组件 + 定时任务 + 改造现有失败分支                   |
| **能讲** | 延迟队列的 ZSet 实现 / **为什么用 Lua 取出**（取与删必须原子）/ 指数退避 / **和 Stream、和专业 MQ 的区别** |

**面试频率 ★★★★★**——"Redis 能做消息队列吗？怎么做？"是必问，而现在项目里 Redis **完全没有承担队列职责**。

## B 类 · 做，工程量大

### 5. 秒杀 + 钱包

补的是**唯一的结构性缺口**——项目里所有 Redis 数据都是"可丢的"。详见上一轮。

**建议顺序**：钱包 DB 版（零 Redis）→ 接进已有 token 统计 → 秒杀 + 对账。

------

## C 类 · 不用做场景，**能讲清楚就够**

| 考点                       | 你现在手里的答案                                             |
| -------------------------- | ------------------------------------------------------------ |
| **Redis 事务 MULTI/WATCH** | 项目**刻意不用**——「Lua 不独占连接，事务会」。**这个理由本身就是好答案** |
| **GEO**                    | 讲 GeoHash + 底层是 ZSet（geohash 值当 score）。项目有 `ipLocation` 但不需要"附近"功能 |
| **主从 / 哨兵 / 集群**     | 讲原理 + 为什么没做 + 触发条件                               |
| **Redlock / Redisson**     | 讲为什么不做（锁内毫秒级操作，不需要 watchdog）              |
| **分布式 Session**         | 讲为什么用 JWT（无状态），代价是无法主动失效 → 所以补了黑名单 |

**这 5 个千万别去做场景**——做了反而显得"为了技术而技术"。它们的高分答案是"**我知道它，我评估过，我不需要**"。

## D 类 · 零成本，跑一遍就有素材

| 动作             | 命令                                 | 收益                                                         |
| ---------------- | ------------------------------------ | ------------------------------------------------------------ |
| **大 key 扫描**  | `redis-cli --bigkeys`                | 从"我看过手册"变成"**我扫过，我的 `article:hot` 有 X 个成员**" |
| **慢查询分析**   | `SLOWLOG GET 10`                     | 同上                                                         |
| **AOF 恢复实测** | `kill -9` Redis 再重启，验证数据还在 | "**我验证过持久化**"——这句话很多人不敢说                     |

**半小时能做完，但面试时是"做过"和"读过"的分界线。**

------

# 建议的执行顺序



```
1. D 类（半小时，零成本，马上有素材）
2. A 类 4 个（每个半天~一天，加起来 ≈ 秒杀的一半工作量，但补 4 个考点）
3. B 类秒杀 + 钱包（工程量大，放最后）
4. C 类不用做，过八股时记住"能讲"就行
```

**A 类 4 个加起来的工作量可能还不如秒杀一个**，但补的考点数量是它的 4 倍。这是我建议先做 A 类的唯一理由。

------

明天你把剩下几题过完，这份清单就可以直接开干。做的时候有几条我可以顺手一起定掉：

- **UV 要不要做进缓存统计**（比如"这篇文章 3 天 1.2 万 UV"）
- **活跃统计的口径**（登录算活跃？还是浏览算？——口径不同实现差很多）
- **延迟队列要不要一步到位上 Stream**（我倾向先 ZSet，因为**要能讲清楚两者边界**，而不是直接上最复杂的）
