# 充值订单真实化设计（虚拟支付，但按真实支付模型跑）

> 2026-10-19。目标：把「虚拟支付」从「点一下直接加余额」升级成「订单 + 支付单 + 回调驱动入账」
> 的完整模型，让超时关单、回调幂等、验签、补单、对账这些真实支付要素都能在项目里被验证和讲清楚。
>
> 不接真实渠道（微信/支付宝需要资质、证书、商户号），但渠道抽象、回调入口、对账框架全部按真实形态落，
> 将来只换 `PaymentChannel` 实现。

---

## 1. 现状与缺口

已有（`docs/redis/钱包与秒杀计划.md` §4）：

- `wallet_recharge_order`：下单快照金额 + `PENDING/PAID/CANCELLED` 状态 + 状态 CAS
- `pay`：`PENDING → PAID` 的 CAS + 加余额 + 写流水，三层幂等（订单号 / 状态 CAS / 流水唯一键）
- 前端一次点击 = `createOrder` + `pay` 两个请求

缺口：

| 缺口 | 后果 |
|---|---|
| `CANCELLED` 只有读、没有写入口 | 死状态；下单不付的订单永久 `PENDING` |
| 没有 `expire_at` / 关单任务 / 惰性关单 | 「订单超时未支付」没有答案 |
| 没有支付单层 | 无法表达「同一个订单多次支付尝试」，对账没有渠道凭证 |
| `pay` 直接入账 | 前端返回成功 = 入账成功，与真实支付「回调说了算」相反 |
| 没有回调入口 | 验签、重复投递、金额篡改、乱序这些真实问题都不会发生，也就不会有人解 |
| 没有对账 | 掉单（渠道成功、本地未入账）无法发现 |
| 没有订单查询/列表 | 用户关掉页面就找不回订单 |

## 2. 目标模型

### 2.1 订单 ≠ 支付单

| | 订单 `wallet_recharge_order` | 支付单 `wallet_payment` |
|---|---|---|
| 视角 | 业务凭证：一次充值意图 | 渠道凭证：一次支付尝试 |
| 创建者 | 用户下单 | 用户点「支付」（后端发起预支付） |
| 状态 | `PENDING → PAID / CLOSED`；`PAID → REFUNDED`（后续） | `CREATED → SUCCESS / FAILED / CLOSED` |
| 数量关系 | 1 | N（取消后重试、切换渠道） |
| 对账对象 | 最终入账结果 | **与渠道账单逐笔对账的就是它** |

**为什么必须拆**：真实场景中「下单」和「支付」之间隔着渠道，用户可能发起 3 次支付才成功 1 次。
只有订单表时，无法回答「这笔钱是哪次支付尝试打进来的」，对账、退款、纠纷都查不下去。

### 2.2 入账由回调驱动

```
前端返回成功 ≠ 入账成功。只有「验签通过的渠道回调」才能推进订单 PAID。
```

虚拟支付把这一步做成真实的 HTTP 回调（HMAC 签名），而不是内部方法直接调。

## 3. 状态机

```
订单：  PENDING ──回调成功（金额校验通过 + CAS）──> PAID
          ├── 用户取消        ──> CLOSED（close_reason=USER_CANCELLED）
          └── 超时（定时/惰性）──> CLOSED（close_reason=TIMEOUT）

支付单：CREATED ──回调成功──> SUCCESS
           ├── 回调失败/渠道拒绝 ──> FAILED
           ├── 订单关闭联动      ──> CLOSED
           └── 超时（由订单关闭联动）──> CLOSED
```

规则：

- 订单 `PAID` **只能**由「支付单 `SUCCESS` + 金额校验通过」驱动
- 所有状态推进一律 CAS：`UPDATE ... WHERE order_no = ? AND status = ?`，影响 0 行必须重新读取再判断
- 订单关闭时必须联动关闭其下 `CREATED` 的支付单（同一事务）
- 同一订单两个支付单同时成功：订单 CAS 只放一个进去，另一个记 WARN 并按「重复支付」处理

## 4. 表设计

### 4.1 `wallet_recharge_order` 扩列

```sql
ALTER TABLE wallet_recharge_order
  ADD COLUMN expire_at   DATETIME    NULL COMMENT '支付截止时间；空 = 历史订单不过期',
  ADD COLUMN closed_at   DATETIME    NULL COMMENT '关闭时间',
  ADD COLUMN close_reason VARCHAR(32) NULL COMMENT 'TIMEOUT / USER_CANCELLED';
```

### 4.2 新增 `wallet_payment`

```sql
CREATE TABLE IF NOT EXISTS wallet_payment (
  id                BIGINT       NOT NULL PRIMARY KEY COMMENT '主键（雪花）',
  payment_no        VARCHAR(64)  NOT NULL COMMENT '商户支付单号（真实场景即 out_trade_no）',
  order_no          VARCHAR(64)  NOT NULL COMMENT '对应 wallet_recharge_order.order_no',
  user_id           BIGINT       NOT NULL COMMENT '下单用户（冗余，回调无登录态，靠它定位）',
  channel           VARCHAR(32)  NOT NULL COMMENT '支付渠道：MOCK（将来 WECHAT / ALIPAY）',
  channel_trade_no  VARCHAR(64)  NULL COMMENT '渠道交易号（回调回填）',
  pay_amount        BIGINT       NOT NULL COMMENT '应付金额（分），下单时快照',
  status            VARCHAR(16)  NOT NULL COMMENT 'CREATED / SUCCESS / FAILED / CLOSED',
  pay_token         VARCHAR(128) NULL COMMENT '模拟支付页凭证（真实场景是 prepay_id）',
  paid_at           DATETIME     NULL COMMENT '渠道支付成功时间',
  fail_reason       VARCHAR(255) NULL COMMENT '失败原因',
  callback_payload  TEXT         NULL COMMENT '原始回调报文（验签通过后落库，对账/纠纷用）',
  created_at        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_payment_no (payment_no),
  UNIQUE KEY uk_channel_trade_no (channel, channel_trade_no),
  KEY idx_payment_order_no (order_no),
  KEY idx_payment_status_created (status, created_at)
);
```

> `uk_channel_trade_no` 是回调幂等的第二道防线：渠道重复投递同一交易号时必须撞唯一键，而不是靠应用层记忆。
> `callback_payload` 真实支付里必须有——出纠纷时「回调原文长什么样」是唯一证据。

## 5. 接口契约

| 方法 | 路径 | 登录 | 说明 |
|---|---|---|---|
| POST | `/api/wallet/recharge/orders` | 是 | 下单（套餐），返回订单 + `expireAt` |
| POST | `/api/wallet/recharge/orders/custom` | 是 | 下单（自定义金额） |
| POST | `/api/wallet/recharge/orders/{orderNo}/pay` | 是 | **发起支付**：创建支付单，返回 `paymentNo / payToken / payUrl`，订单仍 PENDING |
| POST | `/api/wallet/recharge/orders/{orderNo}/mock-pay` | 是 | **模拟支付页确认**（扮演用户在渠道内付款），由 Mock 渠道构造签名回调后交回调内核 |
| POST | `/api/wallet/recharge/notify/mock` | **否** | 渠道异步回调入口：验签 → 幂等 → 金额校验 → 入账 |
| POST | `/api/wallet/recharge/orders/{orderNo}/cancel` | 是 | 用户取消待支付订单 |
| GET | `/api/wallet/recharge/orders/{orderNo}` | 是 | 订单详情（**惰性关单**） |
| GET | `/api/wallet/recharge/orders?page=&pageSize=` | 是 | 订单列表（待支付 / 已支付 / 已关闭） |
| POST | `/api/wallet/recharge/orders/{orderNo}/sync` | 是 | 主动查单（回调丢失时手动补单；定时任务也会跑） |

`/notify/mock` 必须加入 `WebMvcConfig` 的 `jwtInterceptor` 免登录白名单——**真实渠道回调不可能带用户 JWT**。

## 6. 核心流程

### 6.1 下单 → 发起支付

```
① POST /orders                 → 订单 PENDING，expire_at = now + order-timeout-minutes
② POST /orders/{no}/pay        → 幂等：已有 CREATED 支付单则直接复用，否则新建
                                 payment_no = OrderNoGenerator.next("P")
                                 pay_token  = 随机串（绑定 payment_no）
                                 返回 payToken，订单仍 PENDING
```

### 6.2 模拟支付页确认（等价于用户在微信里付款）

```
③ POST /orders/{no}/mock-pay { payToken }
   → MockPaymentChannel.confirm(payToken)：
       校验 payToken 归属、支付单仍 CREATED，生成 channel_trade_no
       构造回调报文 {paymentNo, channelTradeNo, amount, timestamp}
       用 mock-secret 做 HMAC-SHA256 签名
   → 调用回调内核 handleCallback(channel=MOCK, body, sign)（与真实回调同一入口）
```

### 6.3 回调处理（核心，步骤顺序不能乱）

```
① 验签：HMAC(secret, 报文) 比对；timestamp 超窗（默认 300s）拒绝（防重放）
② 解析 payment_no → 查支付单；不存在 → 记录 + 告警（伪回调/串单）
③ 幂等：支付单已 SUCCESS → 直接返回成功（渠道会重复投递）；已 FAILED/CLOSED → 记录拒绝
④ 金额校验：回调 amount 必须 == 支付单 pay_amount；不等 → 告警 + 拒绝入账
⑤ 状态 CAS：支付单 CREATED → SUCCESS（影响 0 行回到 ③ 重新判幂等）
⑥ 订单 CAS：PENDING → PAID（影响 0 行：订单已关闭 → 走「关单后到账」告警分支，不自动入账）
⑦ 入账：walletService.increase(..., idempotencyKey = "RECHARGE:" + orderNo)
⑧ 落 callback_payload（验签通过即落，包括被拒绝的）
```

⑤⑥⑦ 同一事务。回调返回渠道约定响应（成功/失败），由 controller 转成 `Result`。

### 6.4 超时关单

```
主动：WalletRechargeOrderCloseTask（每分钟）
  扫 status='PENDING' AND expire_at < now（LIMIT 100），逐单：
    ① 查该订单是否有 CREATED 支付单 → 调 channel.query()
         SUCCESS → 走 6.3 ⑥⑦ 补单（渠道已扣款，不能关）
         FAILED / 未知 → 继续关单
    ② 订单 CAS：PENDING → CLOSED(close_reason=TIMEOUT)
    ③ 联动：支付单 CREATED → CLOSED
被动：GET 订单详情 / GET 列表 / 发起支付 时，先判断 expire_at < now → 当场走同一关单逻辑
```

> 关单前查渠道是真实支付的硬要求：出现过「本地关了单、用户其实已经付了」的事故。
> 虚拟支付把 `query()` 模拟出来，这段逻辑就真的被执行到了。

### 6.5 主动补单

```
WalletPaymentSyncTask（每 2 分钟）：
  扫 status='CREATED' AND created_at < now - query-pending-after-seconds（LIMIT 100）
  → channel.query(payment)：
       SUCCESS → 走 6.3 ⑥⑦（与回调共用内核）
       其它    → 跳过，等订单超时关单
```

### 6.6 取消

```
POST /orders/{no}/cancel
  归属校验 → 订单 PENDING 且未过期 → CAS 置 CLOSED(USER_CANCELLED) → 联动关闭 CREATED 支付单
  已 PAID：提示「订单已支付，不能取消」
```

---

### 6.7 AI 发起支付（2026-10-19）

Agent 的「充值确认卡」走同一套订单链路，但**只做到创建订单 + 发起支付**：

```
用户说「充 10 块」
  → 分类器 WALLET_AGENT → 确定性决策器（不调 LLM）→ 确认卡（SUGGEST_WRITE, payYuan）
  → 用户点「创建订单」→ WalletAgentWriteActionExecutor：
       createCustomOrder + initiatePayment（**不调 mockPay**）
  → confirmWrite 返回 { message, actionType, result: { orderNo, paymentNo, payToken, payAmount, creditAmount, expireAt } }
  → 前端打开与钱包页共用的 MockPayDialog → 用户在窗口里「确认支付」/「取消订单」
  → 支付成功：渠道回调入账 + 侧边余额刷新；取消：订单 CLOSED
```

**边界**：AI 可以发起支付，**不能确认支付**。真实支付下前端跳渠道收银台，
`WalletAgentWriteActionExecutor` 返回的就是收银台参数；它**永远不调 `mockPay`**——
这一点由 `WalletAgentWriteActionExecutorTests` 的 `verify(mockPay, never())` 锁住。

## 7. 幂等与并发

| 场景 | 防线 |
|---|---|
| 重复点击「支付」 | 订单下已有 `CREATED` 支付单 → 直接复用（`idx_payment_order_no` 查询 + 状态 CAS） |
| 回调重复投递 | 支付单 `SUCCESS` 幂等返回 + `uk_channel_trade_no` 唯一键 |
| 回调与超时关单并发 | 订单状态 CAS；关单前查渠道；关单后到账 → 告警分支（见 6.3 ⑥） |
| 同一订单多个支付单 | 订单 CAS 只放一个 PAID，另一个记 WARN |
| 入账重复 | 流水 `uk_user_idem` + 幂等键 `RECHARGE:{orderNo}`（订单维度，订单只入账一次） |
| 关单任务重复跑 | CAS 幂等；已是 CLOSED 的影响 0 行直接跳过 |

## 8. 安全

- **回调免登录**，但必须验签；签名密钥只在服务端（`.env` / 配置），前端拿不到
- **金额以服务端订单快照为准**，回调金额只用于校验，不参与计算
- **越权**：所有用户侧接口校验 `order.user_id == 当前用户`；回调侧靠支付单归属
- **防重放**：回调 timestamp 超窗拒绝（默认 300s）
- **不信任前端**：`packageCode`、支付单号、金额全部服务端决定

## 9. 对账

`WalletRechargeReconcileTask`（每 10 分钟）：

| 检查 | 判据 | 处理 |
|---|---|---|
| 掉单 | 支付单 `SUCCESS` 但订单非 `PAID` | ERROR 日志，人工/补单接口处理 |
| 脏单 | 订单 `PAID` 但无 `SUCCESS` 支付单 | ERROR 日志 |
| 金额不一致 | 支付单 `pay_amount != order.pay_amount` | ERROR 日志 |

**不自动修复**：钱的问题只有人知道哪个是对的（沿用 `WalletReconcileTask` 的原则）。

## 12. 测试与验证

后端（`-Dtest=...` 定向跑）：

- 下单：`expire_at` = now + 配置；未知套餐拒绝
- 发起支付：重复调用复用 CREATED 支付单；payToken 不复用在支付单之间
- 回调：验签失败拒绝；时间戳过期拒绝；金额篡改拒绝且不入账；重复回调幂等；成功后订单 PAID + 余额 +1 次
- 关单：过期订单被定时任务/CAS 关闭；关单后支付提示已关闭；关单后回调到账 → 告警且不入账
- 取消：用户取消 PENDING → CLOSED；已 PAID 取消被拒
- 补单：CREATED 支付单被同步任务补单
- 对账：构造脏数据 → 任务输出 ERROR（断言日志可跳过，断言查询条件即可）
- 越权：他人订单 pay/cancel/get 全部拒绝

前端：`wallet-custom-recharge.spec.ts` 适配新两段式流程（下单 → 发起支付 → 模拟支付页 → 轮询确认）。

## 12.1 实施踩坑：MySQL collation 必须显式声明（2026-10-19）

**现象**：本地后端启动后对账任务报
`java.sql.SQLException: Illegal mix of collations (utf8mb4_0900_ai_ci,IMPLICIT) and (utf8mb4_unicode_ci,IMPLICIT) for operation '='`。

**根因**：`wallet_payment` 建表时只写了 `DEFAULT CHARSET=utf8mb4`、没写 `COLLATE`，
在新表上落成 MySQL 8 的字符集默认 collation `utf8mb4_0900_ai_ci`；
而既有 `wallet_recharge_order` 是 `utf8mb4_unicode_ci`（历史库建表差异）。
对账 SQL 里 `p.order_no = o.order_no` 的 JOIN 两边 collation 不同 → 直接报错。

**修法**：

1. 两张钱包表在 `db/init.sql` 里**显式** `COLLATE=utf8mb4_unicode_ci`（不依赖库/字符集默认值）；
2. 本地已有库：`ALTER TABLE wallet_payment CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;`
3. 升级脚本：`db/migrations/2026-10-19_充值订单真实化_DDL.sql`（含「先查目标库 collation」的提示）；
4. 历史数据：`db/migrations/2026-10-19_充值订单真实化_历史支付单补录.sql`——
   改造前直接入账的 PAID 订单没有支付单，不补的话对账会一直报「脏单」。

**为什么升级时不能照抄本地值**：现有线上库是 2026-10-18 用旧 init.sql 建的，
旧脚本里 `wallet_recharge_order` 带 `DEFAULT CHARSET=utf8mb4` 但没写 COLLATE，
**大概率是 `utf8mb4_0900_ai_ci`**；而本地开发库是历史建的 `utf8mb4_unicode_ci`。
**两张表必须同 collation**，具体以目标库 `SHOW CREATE TABLE wallet_recharge_order` 为准。

**教训**：只要新建表要参与 JOIN / 字段比较，`COLLATE` 就不能省——
`DEFAULT CHARSET` 不等于「跟随库默认」，MySQL 8 会按**字符集默认排序规则**落。

## 13. 明确不做

- 真实渠道对接（证书、商户号、公网回调地址）
- 部分退款、分账、发票、退款审批流
- 渠道对账文件解析（模拟渠道 = 本地 `wallet_payment`，对账框架保留）
- 支付页 UI 还原真实渠道（只做「模拟支付页」：金额 + 倒计时 + 确认/取消）
