# 缓存击穿与雪崩防护

> 创建：2026-09-14
> 定位：补上「用了 Redis 必被追问」的三道防线里缺失的两道（穿透早已做）
> 登记来源：`docs/capability-audit-2026-08-06.md` 第一层

## 一、现状盘点

先看清已经有什么，避免重复造：

| 防线 | 状态 | 证据 |
|---|---|---|
| **穿透** | ✅ 已做 | 空值缓存 + 3 分钟 TTL：不存在与不可见分开编码，不可见缓存带作者与状态 |
| **fail-open** | ✅ 已做 | 读写 Redis 异常都降级到 DB——缓存故障绝不挡住用户看文章 |
| **脏数据自愈** | ✅ 已做 | 反序列化失败即删 key，下次重建 |
| **击穿** | ❌ **缺失** | 缓存 miss 时**无互斥**——热点 key 失效瞬间，N 个并发请求全部打到 DB |
| **雪崩** | ❌ **缺失** | TTL **全是固定值**——批量写入的 key 会在同一时刻集体失效 |

## 二、击穿防护：文章详情互斥回源

**改哪**：文章详情（最典型的热点 key；列表/分类/标签不加，理由见边界）

**流程**：

```text
读缓存 miss
  ↓
SET NX 抢锁
  ├─ 抢到 → 查 DB + 写缓存（沿用 getArticleDetailFromDb 内聚的写缓存）
  └─ 没抢到 → 短轮询读缓存（50ms × 10 ≈ 500ms）
                ├─ 命中 → 直接返回（别人已经填好）
                └─ 超时 → 自己查 DB（fail-open：宁可退化，不让人等死）
```

**锁的实现**：**复用 `WorkflowActionLock` 的模式，不复用它的类**——`setIfAbsent(key, token, ttl)` + Lua 校验 token 后删除。
它的 TTL（120s）与失败语义都是 Workflow 专用的，缓存击穿锁要的是短 TTL（5s）+
非阻塞获取 + 拿不到就轮询降级，所以实现独立（自有 `UNLOCK_SCRIPT`），只共享模式。
key 空间也独立（`cache:lock:article:detail:`）。详见 `redis-capability-design.md` §5.1。

### 三个必须避开的坑

1. **释放锁必须校验持有者**（Lua 比对 token）——否则慢请求会把别人的锁删掉，
   后续请求又进来一轮，互斥形同虚设
2. **锁必须有 TTL 兜底**（5s）——持锁进程崩溃时不能永久死锁
3. **轮询里要认得空值缓存**：读到空值缓存直接返回 null，
   **绝不能走反序列化**——现有 `getArticleDetailFromCache` 遇到非 JSON 会**删 key**，
   会把别人刚写好的空值缓存误删（这个陷阱在现有代码里靠"外层先判空值"的顺序规避，
   互斥路径引入后多了一条读缓存的入口，必须显式处理）
4. **空值缓存要带可见性语义**：不存在文章对所有人都是空；隐藏 / 草稿等不可见文章要记录
   `authorId + status`，只允许隐藏文章作者本人绕过空值回源。否则一律返回会挡住作者预览，
   一律登录态回源又会让普通登录用户绕开穿透防护。

## 三、雪崩防护：TTL 抖动

**改哪**：7 个缓存写点（文章详情 / 文章列表 / 空值缓存 / 分类列表 / 标签列表 / 评论列表 / 学习计划列表）

**做法**：

```java
TTL = 基础值 × (1 ± 20% 随机)
```

**为什么是 20%**：
- 太小（±1%）打不散——同批写入的 key 仍然几乎同时失效
- 太大（±100%）让 TTL 语义失真——"10 分钟的缓存"可能 20 分钟才过期
- 20% 足以把同一秒写入的一批 key 在时间轴上摊开，且 TTL 量级不变

**抽成工具类**：`CacheTtlSupport`（一个方法 `jitter(Duration base)`），
各写点从 `set(key, val, 10, TimeUnit.MINUTES)` 改为 `set(key, val, ttlSupport.jitter(...))`。
**只改 TTL 的算法，不改缓存的语义**——命中率、失效规则、fail-open 全部不动。

> **实施状态登记（2026-09-15 更新）**：`CacheTtlSupport` **已接线**（第一刀）。
> 7 处数据缓存写点全部改用 `jitter(...)`，抖动比例 ±20%。
> 9 处 `:loaded` 标记位**有意不抖**——每用户一个的加载标记，失效只让该用户重查一次 DB，
> 不构成 DB 压力峰值。详见 `redis-capability-design.md` §5.2。

## 五、边界

- **不做多级缓存**（Caffeine + Redis）：引入一致性维护成本，当前场景不需要。
  触发条件：单 key QPS 高到 Redis 网络往返成为瓶颈时
- **不做缓存预热**：没有大规模冷启动场景。触发条件：服务重启后出现明显的
  "第一批请求集体慢"
- **只对文章详情加互斥**：列表/分类/标签的击穿影响面小（查库快、不是单点热点），
  加锁反而增加复杂度与延迟。触发条件：某个列表查询成为慢查询且并发高
- **不引入 Redisson**：现有 `SETNX + Lua` 模式已经够用，为一把锁引入一个重依赖不划算
