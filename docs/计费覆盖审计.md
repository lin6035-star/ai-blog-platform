## 1. 结论

**计费只有一个接入点**：`AiMessageServiceImpl.streamNormalChatFlow()`——

全仓 `AiBillingService` 只有这一个业务调用方（另外两处是单测与超时释放定时任务）。

只有最后一条"普通聊天 / 文章问答"能走到预扣：

## 3. 根因

1. **接入点位置错了**：计费写在"最终落点方法"里，而分发器在它之前 return。
   正确位置是**分发之前**（拿到 `routeDecision` 之后），或**每个分支的出口各自接入**。
2. **文档记录与实现不符**：AGENTS.md 曾记"推广到 Agent / Workflow 不做，理由：聊天侧已有完整链路，
   再铺一遍属于重复劳动"。这个理由不成立——Workflow / Agent 是独立分支，
   根本不经过那条链路，不存在"重复"。真实情况是**从未接上**。

---

## 4. 影响

- 付费用户能白拿全部重活：写文章、优化文章、改学习计划、Agent 分析。
- 充值额度与注册赠送额度（`initial-credit: 10000`）、秒杀额度基本花不出去
  （只有闲聊与文章问答会动余额）。
- 站内额度不扣 ≠ 不花钱：这些请求照样烧供应商 token，成本全由平台承担。
- 面试角度：这是"埋点覆盖面"的典型缺口——**有 exploit 场景、有修复边界、有对账手段**，
  比再堆一个技术点更好讲。

## 5. 补全方案

### 5.1 计费单位选型

| 维度 | 方案 A：按请求 | 方案 B：按 run |
|---|---|---|
| 计费单元 | 每次用户可见的 AI 请求（含每次 approve / retry） | 一个 Workflow / Agent run 全程 |
| 边界 | 与 HTTP 请求同生共死，清晰 | 跨多请求，pre 与 post 相隔可能几十分钟到几天 |
| 超时释放 | 直接复用 `reserve-expire-minutes=30`（单步最长几分钟） | **必须重做**：run 挂起等确认期间不能释放，否则等于免费 |
| 悬挂风险 | 低 | 高（用户不确认也不取消，预扣永久悬挂） |
| 用户体验 | 一次诉求分多次扣（每次确认都真的调了 LLM，公平） | 一次扣（更接近"一次诉求一次钱"） |
| 改动面 | 中（各分支出口挂钩） | 大（run 生命周期 + 释放策略 + 启动恢复/巡检补偿路径） |
| 与现有实现契合 | 高（聊天路径已是这个模型） | 低 |

**推荐方案 A（按请求）**，理由：唯一真正的难点是"超时释放"，方案 A 直接复用现有兜底，
方案 B 必须为长挂起 run 重新设计一套释放策略（且启动恢复 / 低频巡检补偿会再引入两个悬挂入口）。

### 5.2 推荐方案：三处接入，一个共用组件

新增 `AiRequestBillingSupport`（`ai/billing` 包），封装：

```java
BillingHandle begin(String bizType, String bizId, Long userId, long reservedCredit); // 余额不足抛 402
void close(BillingHandle handle, long totalTokens);   // totalTokens>0 → settle；==0 → release
void abort(BillingHandle handle);                     // 无条件全额 release
long reserveCreditFor(String bizType, String promptOrInputText); // 复用 ChatReserveCalculator 公式，按 bizType 取 cap
```

`close(...)` 里的规则（重要）：

- `totalTokens > 0` → `settle(usage)`，按实际用量退差额；
- `totalTokens == 0` → **必须 `release`**。
  不能 `settle(0)`：`AiBillingServiceImpl.computeActualCredit` 在 `totalTokens <= 0` 时
  **按预扣全额收**（[AiBillingServiceImpl.java:155](../blog-system/src/main/java/com/hailin/blogsystem/service/impl/AiBillingServiceImpl.java#L155)），
  那是为"用户确实拿到了回答但 provider 没给 usage"设计的。

#### 接入点 1：`/api/ai/chat/stream`（`AiMessageServiceImpl.streamUserChat`）

- 预扣：`routeDecision` 出来之后、任何分支 return 之前，按落点选 bizType：
  Workflow → `WORKFLOW_ACTION`；`AGENT` / TaskPlan 编排 → `AGENT`；
  纯动作批次 / CTA → 不预扣（不调 LLM）。
- 结算：各分支出口。
  - Workflow 启动：handler 初始步骤同步跑在同一请求内，run 是本请求新建的，
    `run.totalTokens` 即本次用量；
  - Agent：`AgentRunResult.totalTokens` 已带（[AgentRunResult.java:26](../blog-system/src/main/java/com/hailin/blogsystem/ai/agent/AgentRunResult.java#L26)）；
  - Task 编排：计划内各步 run 的 token 合计。
- 普通聊天 / QA 保持现状（已在计费），但顺手把 `streamFallbackChatFlow` 这条漏扣分支补齐——
  它与主路径同构，共用同一个预扣。

#### 接入点 2：`AiWorkflowStreamServiceImpl.streamAction`（approve / reject / retry）

`streamAction` 已经在正确的位置：有 `userId`、有准入前置、有 worker 的 try/catch。
在 worker 内用**执行前后 token 差量**取本次用量：

```java
int before = safeTokens(workflowRunManager.getOwnedRun(id, userId).getTotalTokens());
... actionInvoker.apply(emitter) ...
int delta = safeTokens(after) - before;   // after 从重读 run 或 VO 取
```

`AiWorkflowRunVO` 目前**没有** `totalTokens` 字段（[AiWorkflowRunVO.java](../blog-system/src/main/java/com/hailin/blogsystem/entity/vo/AiWorkflowRunVO.java)），
需要重读一次 run（一次额外读，可接受），或给 VO 补该字段。

#### 接入点 3：Task 编排

随接入点 1 一起覆盖（编排入口在同一个分发器里），分析步的 token 从计划执行结果汇总。

### 5.3 bizId 设计（受 `uk_biz(biz_type, biz_id)` 约束）

| 路径 | bizId | 幂等性 |
|---|---|---|
| 普通聊天（现状） | `userMessageId` | 已有 |
| Workflow 动作 | `WF:{runId}:{action}:{UUID}` | 每请求唯一即可。**刻意不用 run version**：并发点击时两个请求会读到同一 version，撞 `uk_biz` 直接变 500；重放由「差量 = 0 → 全额退」兜住 |
| Workflow 启动 | `WF:{runId}:START` | run 新建，唯一 |
| Agent | `AG:{agentRunId}` | run 新建，唯一 |
| Task 编排 | `TASK:{userMessageId}` | 同一请求唯一 |

### 5.4 失败 / 取消 / 余额不足策略

| 场景 | 处理 | 理由 |
|---|---|---|
| 余额 ≤ 0 | 预扣处抛 `InsufficientBalanceException` → HTTP 402 | 与聊天一致；SSE 提交前抛出 |
| handler 失败但有 token 消耗 | `settle(delta)` | token 真烧了 |
| handler 失败且零消耗 | `release`（全额退） | 没实际成本 |
| 用户取消（worker 仍在跑） | 不动，让它正常结算 | worker 不可中断；聊天侧的"取消全额退"是 V1 产品取舍，不扩散 |
| 排队期间取消 | 预扣在 worker 外、worker 仍会执行 → 照常结算；若 worker 从未执行则释放 | 准入池的 Runnable 不能中断，需实测确认 |

### 5.5 必须保持不变的三条不变量

来自 [AiBillingServiceImpl](../blog-system/src/main/java/com/hailin/blogsystem/service/impl/AiBillingServiceImpl.java#L26)：

1. 预扣与结算是**两个独立短事务**——因此计费必须放在 `@Transactional` 业务方法**之外**
   （`AiWorkflowRunServiceImpl.approve/reject/retry` 都带 `@Transactional`，
   `streamAction` 的 worker 在事务外 ✅）。
2. 结算只会退款（`actual <= reserved`）。
3. 一张单只产生一次退款（`status='RESERVED'` 条件更新 + 同一流水幂等键）。

### 5.6 明确不做（登记，不实现）

- **游客计费**：无钱包，硬扣不合理。要防刷应做"游客每日 N 次"——那属于另一刀（本就是暂缓项），
  本次只在文档登记为已知成本敞口。
- **附带调用收费**（分类器 / 记忆 / 摘要 / embedding / rerank）：全部维持平台成本。
  embedding 与 rerank 没有用户级归属，按调用点归属也不公平。
- **按已产生用量部分结算取消请求**：维持聊天侧 V1 取舍。

### 6.1 B1 实施记录（2026-10-11）

**改动**

- 新增 `ai/billing/AiRequestBillingSupport`：按 bizType 取 `max-reserve-per-biz-type` 硬上限预扣；
  `close(handle, promptTokens, completionTokens)` 在**零消耗时走 release**（不能 settle(0)，见其类注释）；
  `abort(handle)` 无条件全额退。
- `AiWorkflowStreamServiceImpl.streamAction`（approve / reject / retry 的公共外壳）在 worker 内接入：
  执行前读 `ai_workflow_runs` 的 token 快照 → 预扣 → 执行 → `finally` 里按**差量**结算。
- bizId：`WF:{runId}:{action}:{UUID}`。**不复用 run version**——并发点击时两个请求可能读到同一 version，
  撞 `uk_biz` 会变成 500；而重放同一次点击由「差量 = 0 → 全额退」兜住，不需要靠唯一约束防重。

**为什么差量**：run 是跨请求持久化的（启动 / approve / reject / retry 各是一次 HTTP 请求），
直接读 `totalTokens` 会把这个 run 之前所有动作的用量重复计一遍。

**测试**（`WorkflowActionBillingTests`，4 例全绿，全离线）

- 有消耗 → 按实际结算 + 退差额（预扣 10000 → 1000 token 结算 10 credit）
- **零消耗 → RELEASED 全额退**（锁住"不能 settle(0) 白收预扣"这条）
- 动作失败但烧了 token → 按实际扣，且错误事件照常下发
- 余额 ≤ 0 → 在调 handler 之前就被拒，且**不留 RESERVED 孤儿单**

**跑测试的环境坑（本地 shell 有、CI/其他会话没有）**

- `@SpringBootTest` 上下文需要 `ALIYUN_API_KEY`（`spring.ai.openai.api-key: ${ALIYUN_API_KEY}` 无默认值），
  否则 `PlaceholderResolutionException` 让**所有** Spring 测试在加载上下文阶段就失败。
- `AiWorkflowRunServiceTests`（21 例）是**真 LLM 测试类**：LLM 调用失败 → run 变 `FAILED` →
  后续 approve/reject 断言全崩（表现为"当前状态不允许同意操作"）。
  **不要用假 key 跑它**，也别把它当回归基线——它失败不代表代码回归。

**回归**（离线部分）

- ✅ `WalletBillTests` 6/6、`WorkflowStepTokenTests` 8/8、`CreateArticleWorkflowHandlerTests` 9/9、
  `AiBillingServiceTests` + `ChatReserveCalculatorTests` 全绿
- ⚠️ `AiWorkflowRunServiceTests` 15 例失败 = 假 key 导致 LLM 失败，与本次改动无因果关系

### 6.2 B2 / B3 / B4 实施记录（2026-10-11）

**B2：5 个 Workflow 启动分支**

- 接入点：`AiMessageServiceImpl` 里 `streamCreateArticleWorkflowFromIntent` /
  `streamArticleOptimizeWorkflowFromIntent` / `streamLearningPlanWorkflowFromIntent` /
  `streamLearningProgressWorkflowFromIntent` / `streamLearningAssistWorkflowFromIntent`
  的准入 worker 内——**每处只改两行**（预扣 + finally 结算）。
- bizId：`WF:START:{userMessageId}`。
- runId 从 `session.activeWorkflowRunId` 取（create 内部会绑定），
  不从 create 返回值接——五个分支的局部变量结构不一致（两个自己持有 `AtomicReference`、
  三个共用 `buildLearningWorkflowEmitter`），统一从 session 取才不会漏改某个分支而静默免费。
- 取不到 run（create 没成功）→ 全额退。

**B3：Agent 四域 + 任务编排**

- Agent：`streamAgentReply`——用量直接取 `AgentRunResult.totalTokens()`。
- 编排：`runOrchestrationBody`——用量取 `taskOrchestrationService.subtreeTokens(outcome.agentRunId())`
  （与 `message.token_count` 的编排部分同源，但不含分类器）。
- bizId：`AG:{userMessageId}` / `TASK:{userMessageId}`。
- **预扣位置与前两批不同：放在方法体（流构建之前、请求线程）**，不是为了省事，
  而是因为踩到了真实回归：放在 worker 里时，余额不足的异常会落进
  `catch (Throwable)` 的兜底文案「抱歉，AI 助手暂时不可用」——
  **把「欠费」说成「系统坏了」**。`ArticleAgentDirectStreamTests` 就是这么红的两例
  （测试用户没有钱包余额 → 预扣失败 → 正常流式用例全崩）。
  上移到方法体后，余额不足走 `InsufficientBalanceException` → HTTP 402，
  与聊天路径完全一致（前端已有额度不足提示）。
  为此 `runOrchestrationBody` 多接两个参数（`BillingHandle` + `AtomicBoolean billed`）。

**B4：续跑降级聊天**

- `streamFallbackChatFlow` 与主聊天路径**完全同构**（同一个 `streamChat`、同样落 `token_count`），
  此前唯独漏了 `reserve/settle`。补齐后口径与主路径一致：

### 6.3 遗留差异（登记，未修）

- **「余额不足」的呈现方式两套**：
  B1（Workflow 动作）/ B2（Workflow 启动）在 worker 内预扣 → 走 SSE 错误事件
  （`emitRejectedOrError` 对 `InsufficientBalanceException` 一般返回 null → `sink.error`）；
  B3（Agent / 编排）+ 普通聊天在方法体预扣 → HTTP 402。
  **不是数据正确性问题**（两边都不免费、也不误扣），只是前端提示不一致。
  统一到 402 需要把 B1/B2 的预扣也上移到方法体——留到真流程手测看过实际提示再定。
- B1/B2 在 worker 内预扣的好处是**不会因为 Flux 未被订阅而留下悬挂 RESERVE 单**；
  上移到方法体会把这点风险换回来（30 分钟超时兜底仍在）。
- **「流结束」比「账单定下来」早几十毫秒**：Workflow 启动 / 动作路径的结算在准入 worker 的
  `finally` 里，而 STOP / complete 事件在它之前发出。前端若在 STOP 那一瞬间刷余额，会看到
  「预占中」（钱包页本就有三态区分，所以不会误解）。要消掉这个窗口就得把结算提到 complete 之前，
  代价是异常兜底会再走一次（CAS 挡得住，但会打 warn 日志）——**有意保留现状**。
  真流程探针因此必须轮询等结算落库，不能流一结束就查库。
- `AiEditorDraftGenerator` 仍无调用点，接入时同样要计费。
- 启动恢复 / 低频巡检补偿触发的续跑仍不计费（没有用户请求 → 没有预扣），平台成本。

### 6.5 执行中「额度负几千」的修复：展示归一（2026-10-11）

**现象**：补全计费后，用户在执行 AI 任务期间看到额度掉到远低于预期、甚至负几千，
执行完刷新才恢复。

**根因**：预扣额度用了配置里的**硬上限**，而不是估算。那个配置的本意是**绝对上界**
（防超长输入把余额扣穿，启动时由 `BillingReserveLimitValidator` 校验 `cap × 2 < |CHECK 下界|`），
不是"每次都要占这么多"。实测放大倍数：

| biz_type | 预扣 | 实际平均 | 放大 |
|---|---|---|---|
| CHAT | 751（按输入估算） | 43.6 | ~17× |
| AGENT | 8000（固定 cap） | 74.5 | **~107×** |
| WORKFLOW_ACTION | 10000（固定 cap） | 40.5 | **~247×** |

聊天路径一直按输入长度估算（`ChatReserveCalculator`），所以只有它没这个问题；
Workflow / Agent 是新接入的，把「上界」当成了「预扣额」。

**修法：展示层把在途预占加回去**（账务侧一个字不改）

```text
展示额度 = balance + pendingReserveCredit
```

- 执行中：`balance 30000 + 预占 10000` → 显示 **40000**（任务开始前的额度，数字不跳）
- 结算后：预占归零 → 显示 **39960**（一次性扣掉真实消费）
- 真欠费（`pendingReserveCount = 0` 且 `balance < 0`）：原样显示负数，不掩盖

**为什么不改成「跑完再扣」**：预扣真的占着额度，是**防「余额 0 也能并发跑多个任务」**那道闸。
不占钱就得重新设计余额门槛、并发上限与崩溃补偿（跑了没结算 = 平台白掏）；
展示归一能拿到同样的观感，闸门原样保留。

**改动**

- 后端：`WalletVO.pendingReserveCredit`（在途预占**总额**）。此前只有笔数——
  知道"有 1 笔在跑"但不知道占了多少，根本加不回去。
  `WalletServiceImpl.getWallet` 改成一次查询同时得笔数与总额（在途天然是个位数，不值得两次 SQL）。
- 前端：`utils/format.ts` 新增 `displayCredit()`，三处显示点统一走它
  （AI 助手余额 chip / 钱包页「当前额度」/ 个人中心余额卡）；
  余额 chip 的悬浮说明在有调用在途时改为「有 N 次 AI 调用进行中，额度已临时占用，结束后按实际用量结算」。

**测试**：`WalletBillTests.pendingReserveExposesAmountSoDisplayCanAddItBack`（账务侧）
+ `utils/format.spec.ts` 的 `displayCredit` 5 例（展示侧，含「真欠费不掩盖」与字段缺失兜底）。

⚠️ **未做**：预扣额度本身仍是硬上限。展示归一之后它不再影响观感，
但意味着余额门槛是按「占满上界」判定的。若将来要精确控制并发占用，应改成按估算预扣——
届时 `actual > reserved` 的概率会上升，得先想清楚「封顶少收」能不能接受。

---

**取舍结论（姐夫已确认）**：计费单位选 **A（按请求）**；失败但已烧 token **按实际扣**；
零消耗一律全额退。B1-B4 均已按此实施；执行中「额度负几千」按 §6.5 的展示归一处理。
