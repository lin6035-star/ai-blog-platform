# 数据库索引审计（2026-10-09）

> 范围：`blog_system` 全库 **28 张表 / 89 个索引**
> 方法：实库导出索引 → 自动检测前缀冗余 → 从代码提取真实查询 → **EXPLAIN 验证 `possible_keys`**
> 目的：① 供新服务器建库时一次性修正；② 面试能讲清"索引是怎么和查询对应的"

## 结论速览

|---|---|---|
| **P0** | 表**没有主键**（注释写着"主键（雪花）"，建表语句漏了子句） | **6 张** |

## P0：6 张表没有主键（本次最严重的发现）

```
ai_billing_order   seckill_activity   seckill_order
user_wallet        wallet_recharge_order   wallet_transaction
```

**全部是钱包 / 秒杀 / 计费——恰恰是高并发写入的表。**

现象：每张表的 `id` 列注释都写着 `'主键（雪花）'`，但建表语句里**只有列定义，没有 `PRIMARY KEY` 子句**。
`db/init.sql` 里同样如此（第 565 / 583 / 605 / 629 / 654 / 674 行），所以**新服务器照脚本建库会原样复现**。

**为什么这比"少一个索引"严重**：

1. InnoDB 在无显式主键时会建**隐式聚簇索引** `GEN_CLUST_INDEX`，用一个 **6 字节全局自增 row_id**。
   这个计数器是**全实例共享**的——多张表高并发插入时会争抢同一个 `dict_sys` 互斥量，成为写入热点。
   雪花主键本来是每表独立的，退化之后反而多了一个全局争用点。
2. 二级索引里指向的是 row_id 而不是业务 id，**无法用主键回表定位**。
3. 无主键表的行锁在某些执行计划下会退化成扫描到的所有行都锁住（走全表扫描时尤其明显）。
4. 复制（row 模式）时每行都要全列比对才能定位，效率更低。

**修复**（已验证 6 张表的 `id` 唯一且无 NULL，可以直接加）：

```sql
ALTER TABLE user_wallet            ADD PRIMARY KEY (id);
ALTER TABLE wallet_transaction     ADD PRIMARY KEY (id);
ALTER TABLE wallet_recharge_order  ADD PRIMARY KEY (id);
ALTER TABLE ai_billing_order       ADD PRIMARY KEY (id);
ALTER TABLE seckill_activity       ADD PRIMARY KEY (id);
ALTER TABLE seckill_order          ADD PRIMARY KEY (id);
```

> 验证过：6 张表都是 `COUNT(*) = COUNT(DISTINCT id)` 且 `SUM(id IS NULL) = 0`，加主键不会因重复失败。

## P0.5：`articles.id` 缺 `AUTO_INCREMENT`（同样是上线阻塞）

**这条只有"先别动手、去看代码"才能发现——只看索引清单永远看不到它。**

`Articles` 实体是 `@TableId(type = IdType.AUTO)`，`application.yml` 里的全局配置也是
`mybatis-plus.global-config.db-config.id-type: auto`。也就是说**插入文章时 MyBatis-Plus 不提供 id，
指望数据库自己生成**。实测：

| | `articles.id` |
|---|---|
| 开发库 | `bigint unsigned NOT NULL auto_increment` |
| `db/init.sql`（改前） | `BIGINT UNSIGNED NOT NULL PRIMARY KEY` ← **没有 AUTO_INCREMENT** |

照改前的 `init.sql` 在新服务器建库，**第一次发布文章就会失败**：
`Field 'id' doesn't have a default value`（严格模式下）。

**为什么一直没暴露**：开发库是在更早某次建表时带上 `auto_increment` 的，而 `init.sql` 里的定义
少了这一句，两边漂移了很久没人发现——**因为从来没人拿 `init.sql` 在一个空库上跑过**。
这正是"准备上线到新服务器"才会踩到的那一类问题。

```sql
-- init.sql 已修正
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
```

> **判据是"实体怎么产生 id"，不是"表里有没有 id 列"。** 对照看：
> `users.id` / `categories.id` 的实体都是 `ASSIGN_ID`（应用生成雪花），所以**不需要** `AUTO_INCREMENT`；
> `categories` 脚本里虽然有，但那是给种子数据用的，无害。

## P1：4 处缺失索引（EXPLAIN 证实）

判定标准看的是 **`possible_keys` 是否为 `NULL`**——它表示"优化器连候选索引都找不到"，
**与当前行数无关**：即使表涨到千万行也仍然是全表扫。这比"看 EXPLAIN 有没有走索引"更硬，
因为小表上优化器选全扫是合理的，看不出问题。

| 表 | 查询 | 代码位置 | 现状 |
|---|---|---|---|
| `ai_billing_order` | `WHERE order_no = ? AND status = ?` | `AiBillingOrderMapper` 的 `markSettled` / `markReleased` / `bindResource` | `type=ALL`，`possible_keys=NULL` |
| `ai_messages` | `WHERE agent_run_id = ?` | `TaskWorkflowContinuationService:264` | `type=ALL`，`possible_keys=NULL` |
| `ai_agent_runs` | `WHERE status = 'RUNNING'` | `AiRunStartupRecoveryRunner:104,121`、`TaskHandoffReconciliationTask:98` | `type=ALL`，`possible_keys=NULL` |
| `ai_workflow_runs` | `WHERE status = 'RUNNING'` | `AiRunStartupRecoveryRunner:95` | `type=ALL`，`possible_keys=NULL` |

**为什么 `ai_billing_order.order_no` 最要紧**：它不只是查询，是**写路径**——
`markSettled` / `markReleased` 每次 AI 调用结算都要跑，而 `AiBillingExpireTask` 每 5 分钟
批量扫超时单做释放。三种操作全部按 `order_no` 定位，却一行索引都没有。

```sql
-- 业务单号，天然应该唯一（顺便挡掉「程序 bug 开出两张同号单」）
ALTER TABLE ai_billing_order ADD UNIQUE KEY uk_order_no (order_no);

-- Agent 续跑时按 run 找消息
ALTER TABLE ai_messages ADD INDEX idx_ai_messages_agent_run_id (agent_run_id);

-- 启动恢复 / 巡检：等值 + 按 id 排序取一批（RUNNING 的行数受并发上限约束，很少，索引很有效）
ALTER TABLE ai_agent_runs    ADD INDEX idx_agent_run_status (status, id);
ALTER TABLE ai_workflow_runs ADD INDEX idx_workflow_run_status (status, id);
```

> `ai_messages.agent_run_id` 这条是**老账**：`db/init.sql` 第 362 行早就建了
> `idx_ai_messages_agent_run_id`，但开发库当年漏执行了 DDL。这次一并补上。

## P2：3 个前缀冗余索引（可删）

判定规则：**索引 A 的列序列是索引 B 的严格前缀 → A 完全冗余**（B 的最左前缀就能顶替 A）。

| 表 | 冗余索引 | 被谁完全覆盖 |
|---|---|---|
| `ai_agent_steps` | `idx_agent_step_run (agent_run_id)` | `uk_agent_task_step (agent_run_id, task_step_id)` |
| `ai_user_memories` | `idx_user_enabled (user_id, enabled)` | `idx_user_importance (user_id, enabled, importance)` |
| `comment_likes` | `idx_comment_id (comment_id)` | `uk_comment_user (comment_id, user_id)` |

**冗余索引的代价不是"浪费空间"（那是最小的），而是每一次写都要多维护一棵 B+ 树**：
INSERT / UPDATE / DELETE 都要在这三个索引上做插入删除与可能的页分裂。
`comment_likes` 那种高频点赞路径尤其明显。

```sql
ALTER TABLE ai_agent_steps  DROP INDEX idx_agent_step_run;
ALTER TABLE ai_user_memories DROP INDEX idx_user_enabled;
ALTER TABLE comment_likes   DROP INDEX idx_comment_id;
```

**删之前确认过**：这三个索引的查询（`WHERE agent_run_id = ?`、`WHERE user_id = ? AND enabled = ?`、
`WHERE comment_id = ?`）都能被覆盖它的复合索引的最左前缀满足，`EXPLAIN` 里也确实已经在走复合索引。

> 注：`article_likes` / `article_favorites` 的 `idx_article` 早前已经删过一轮（同样理由），
> 这次是同一模式在另外三张表上的残留。

## P3：2 个存疑索引（建议删，但请先核实）

```sql
articles.idx_articles_deleted_at (deleted_at)
article_comments.idx_deleted_at  (deleted_at)
```

**这里有一个我一开始想当然、后来被 EXPLAIN 纠正的判断**，值得记下来：

我原以为"`deleted_at` 几乎全是 NULL，选择性≈0，所以这种索引没人会用"。
**实测是错的**——单独执行 `SELECT * FROM articles WHERE deleted_at IS NULL` 时，
优化器**确实选中了它**（`type=ref`，`key=idx_articles_deleted_at`）。

真正的问题不在"会不会被选中"，而在**项目里不存在这种查询形态**：

| 真实查询 | 实际走的索引 |
|---|---|
| `WHERE id = ? AND deleted_at IS NULL` | `PRIMARY` |
| `WHERE status = 1 AND deleted_at IS NULL ORDER BY ...` | `idx_articles_status_deleted_published`（复合索引优先） |

`deleted_at IS NULL` 是通过 MyBatis-Plus 的 `@TableLogic` **自动附加到每个查询**上的，
它永远和其他条件一起出现，而那时复合索引/主键总是更优。所以这两个索引服务的是一个
**只按软删除状态过滤**的场景——项目里没有。

**建议删，但先用真实负载核实**（别拿"我觉得没用"当依据）：

```sql
-- MySQL 8 自带：列出从未被使用过的索引（需要 performance_schema 且实例跑够久）
SELECT * FROM sys.schema_unused_indexes WHERE object_schema = 'blog_system';

-- 或者用 pt-index-usage 分析慢查询日志
```

删了之后如果发现某条 SQL 变慢，重建成本也只是几秒。

## 索引设计原则（这次审计里能直接讲的几条）

1. **索引的价值只能由查询决定，不能由表结构决定。**
   这次每一条结论都是"先提取代码里的 WHERE / ORDER BY，再对照索引"。同一种索引在 A 表合理、在 B 表冗余。

2. **软删除表的索引必须带上 `deleted_at`。**
   `@TableLogic` 会给每个查询自动加 `deleted_at IS NULL`。它不在索引里，扫出来的每一行都要回表判断，
   等于白扫。项目里 `articles` 的两条排序索引都是 `(status, deleted_at, <排序列>, id)` 这个形状。

3. **找冗余索引看"前缀"，不看"像不像"。**
   `(a)` 被 `(a, b)` 覆盖是硬结论；`(a, b)` 和 `(a, c)` 不互相覆盖（b、c 都得靠索引外过滤）。

4. **复合索引的列序：等值列 → 排序列 → tiebreaker。**
   例：`(status, deleted_at, published_at, id)` —— status/deleted_at 等值，published_at 排序，
   `id` 保证全序（游标分页要靠它，否则并列值会跳条/重复）。

5. **判断"该不该建"要看 `possible_keys` 是不是 NULL，不要只看当前 EXPLAIN 有没有走索引。**
   小表上优化器选全表扫是**正确**决策，看不出任何问题——但那是"因为数据少"，
   不是"不需要索引"。数据涨上来才会突然变慢。

6. **没有主键是设计缺陷，不是"少个索引"。**
   InnoDB 会退化到全局自增的隐式 row_id，多表并发写时争抢同一个计数器。

## 这次的验证清单（每条改动凭什么敢动手）

改 schema 最容易出事的不是"想不到"，而是"想当然"。所以每一条都先对着代码验证过：

| 改动 | 风险点 | 怎么验证 | 结论 |
|---|---|---|---|
| 6 张表补主键 | 若实体是 `IdType.AUTO`，加主键后 MySQL 期望 `AUTO_INCREMENT`，**插入会直接失败** | 逐个查实体注解 | 6 张全是 `ASSIGN_ID`（应用生成雪花）→ 安全 |
| 同上 | 有没有 INSERT 不提供 id | 全库搜这 6 张表的 `INSERT INTO` | 只有 `UserWalletMapper.insertWallet` 一处，**显式带了 id**；其余走 `save()` + `ASSIGN_ID` |
| 同上 | 加主键会因重复 / NULL 失败 | `COUNT(*) = COUNT(DISTINCT id)` 且 `SUM(id IS NULL) = 0` | 6 张全部满足 |
| `ai_billing_order` 加 `uk_order_no` | 会不会有重复单号 | 读 `OrderNoGenerator`：前缀 + 秒级时间戳 + 6 位随机码（32⁶ ≈ 10.7 亿），**本身没有唯一性保证** | 现有 47 行唯一。加 UNIQUE 是**补上"不会更新到错单"的防线**，不只是为了快 |
| 删 3 个冗余索引 | 删了会不会有查询变慢 | `EXPLAIN ... IGNORE INDEX (冗余索引)`，看能否改用别的索引 | 这三个**当前根本没被优化器选中过**，排除后仍走复合索引 → 安全 |
| 索引形状取 `(status, id)` | 列序对不对 | 对着 `AiRunStartupRecoveryRunner` / `TaskHandoffReconciliationTask` 的真实 WHERE + ORDER BY | 等值列在前、排序列在后，匹配 |
| `articles.id` 加 `AUTO_INCREMENT` | 会不会和实体冲突 | 查实体注解 + 全局 `id-type` + 实库列属性 | 实体 AUTO、全局 auto、实库有 `auto_increment` → **只有 `init.sql` 漏了** |

**验证过程中被纠正的两次"想当然"**（比结论本身更值得记）：

1. **以为"软删除列选择性≈0，所以这个索引没用"** —— 一 EXPLAIN 发现优化器**确实会选中它**。
   结论改成"它服务的是一个项目里不存在的查询形态"。方向没变，但**理由完全不同**——
   拿着原来的理由去面试，会被一句"那它为什么会被选中"问倒。
2. **以为"`possible_keys` 为空就是没索引"** —— 第一版解析脚本有 bug（`\G` 在 PowerShell 里没生效），
   把所有查询都报成"无可用索引"，差点得出"28 张表全都没索引"的荒谬结论。
   后来**先拿一组明确有索引的表做对照**，才确认是工具坏了、不是库坏了。

> **教训：验证脚本本身也要有对照组。**
> 一个无论好坏都输出同一个结论的检查，和没有检查一样危险——
> 前两次跑出来的"全部全表扫"如果直接写成报告，这份审计就是错的。
