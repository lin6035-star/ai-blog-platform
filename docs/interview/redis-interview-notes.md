## 一、缓存三大问题

### 1.1 缓存穿透 🟢

**做法**：空值缓存。文章不存在 / 当前身份不可见时，往详情 key 写哨兵值，TTL 3 分钟（也走 ±20% 抖动）。

**关键点：哨兵值不是一个裸的 `__NULL__`，而是带身份编码的。**

| 值 | 含义 |
|---|---|
| `__NULL__:not_found` | 文章不存在——对**所有**身份都是空 |
| `__NULL__:invisible:{authorId}:{status}` | 文章存在但不可见（隐藏 / 草稿） |

**为什么必须带身份编码**：隐藏文章的作者本人来预览时，不该被空值缓存挡住。裸哨兵值把"不存在"和"没权限"混成一个值，作者就永远看不到自己的隐藏文章了。带编码后，读路径能判断「访问者是不是作者本人 + 状态是不是 HIDDEN」，是就删掉空值缓存回源一次。

另外还留了一个兼容分支处理旧格式 `__NULL__`：无法判断身份，只能回源一次并用新格式重写。

**代码**：读 `ArticlesServiceImpl.java:299-370`，写 `:1261-1276`

> **一句话**：空值缓存要防的不只是"穿透"，还要防"把作者本人一起挡在门外"。

---

### 1.2 缓存击穿 🟢🟢

**做法**：互斥回源。热点 key 失效的那一瞬间，只让一个请求查库重建，其他请求短轮询等结果。

**完整链路**：

1. `SETNX cache:lock:article:detail:{id}`，值为 UUID token，TTL **5 秒**
2. 抢到锁 → 查库 + 写缓存 → `finally` 释放
3. 没抢到 → `50ms × 10` 次 ≈ **500ms** 轮询读缓存
4. 轮询超时 → **fail-open 自己查库**（宁可退化，不让人等死）

**四个设计细节，每个都能被追问**：

| 细节 | 理由 |
|---|---|
| 锁 TTL 只有 **5 秒** | 持锁进程崩溃后最多 5 秒自动释放。对比 Workflow 锁的 120s——那个锁内是一次完整的业务操作，这个锁内只是一次 DB 查询 |
| 释放走 Lua 校验 token | `GET == token` 才 `DEL`。不校验的话，慢请求会删掉**别人的**锁，互斥形同虚设 |
| Redis 故障时**直接回源** | 锁不可用不能挡住用户看文章。这里不是 fail-open 放行，是根本不依赖锁也能工作 |
| 轮询必须走**统一读入口** | 轮询路径若自己反序列化，会把别人刚写好的空值缓存当脏数据删掉——互斥自我破坏 |

**代码**：`ArticlesServiceImpl.java:379-443`（锁流程），`:299-329`（统一读入口）

**测试**：`ArticleDetailMutexTests` 4 例。8 线程 latch 并发验证"只回源一次"——数 DB 查询次数用的是自定义 MyBatis `Interceptor` 拦 `Executor.query`（不能 spy mapper：MyBatis mapper 是 JDK 动态代理，`@SpyBean` 取不到 `MybatisMapperProxy` 的内部状态）。

> **一句话**：击穿的解法不是"让请求都去查库"，是"让它们排队，而且排队超时还要有退路"。

---

### 1.3 缓存雪崩 🟢

**做法**：TTL 抖动 ±20%，封装在 `CacheTtlSupport.jitter()`。

**抖动比例为什么是 20%**（代码注释里写了）：

- 太小（±1%）打不散——同一批 key 仍然几乎同时失效
- 太大（±100%）让 TTL 语义失真——"10 分钟的缓存"可能 20 分钟才过期
- 20% 足以摊开，且 TTL 量级不变

**一个值得讲的区分：只抖数据缓存，不抖 `:loaded` 标记。**

数据缓存（详情 / 列表 / 分类 / 标签 / 评论 / 学习计划 / 空值）7 处都抖；用户集合的 `:loaded` 标记 9 处写点**一个都不抖**。原因是标记和集合之间存在一条 TTL 大小关系的不变量（Set 必须比标记活得久，见 [3.2](#32-set--状态标记用户态集合)），两边都抖会让这条不变量变成概率性的。而标记是按用户维度分散写入的，本来就不存在"集体失效"的问题——雪崩风险只在那几个被高频共享读的 key 上。

**代码**：`component/CacheTtlSupport.java:35-49`

## 二、缓存一致性

### 2.1 模式：Cache-Aside 🟢

读：查缓存 → miss 查库 → 回填。写：更新 DB → **删**缓存（不是更新缓存）。

没上 Spring Cache 抽象（无 `@Cacheable` / `CacheManager` / `@EnableCaching`），缓存全是手写的。理由：失效时机（尤其是"提交后删"这件事）需要业务侧精确控制，注解给不了。

### 2.2 删除时机：提交后删 🟢🟢

**问题**：Cache-Aside 的"写库后删缓存"如果发生在**事务内**，会留下一个必然出现的窗口：

```
事务内更新 DB → 删除缓存 → 另一请求 miss，读到"尚未提交"的旧值并回填
  → 原事务提交 → 缓存里留着旧值，直到 TTL 过期
```

**这不是"概率很低"的竞态**——从删完到事务提交之间的**任何一次缓存 miss** 都会走这条链，窗口宽度由事务本身的耗时决定（含后续的 RAG 同步等操作）。

**做法**：`component/AfterCommitExecutor`——有事务就注册到 `TransactionSynchronization.afterCommit`，无事务就地执行。

```java
if (!TransactionSynchronizationManager.isSynchronizationActive()) {
    action.run();          // 无事务：行为与改造前逐字节一致
    return;
}
TransactionSynchronizationManager.registerSynchronization(... afterCommit -> action.run());
```

**为什么不用 `@TransactionalEventListener(AFTER_COMMIT)`**（这是最容易被追问的）：

事务事件在**没有事务时默认不执行**。本项目大量缓存失效发生在**非事务**方法里（删文章 / 隐藏 / 发布 / 评论 / 收藏），一旦有人给某个方法去掉 `@Transactional`，缓存就**永远不再失效**——这种失效是静默的，比"删早了"更难发现。

`AfterCommitExecutor` 的 fallback 是**显式的**：没有事务就地执行，行为与改造前逐字节一致。

**为什么 `afterCommit` 里必须兜异常**：抛出去的异常会传播到 `commit()` 的调用方，让一次**已经提交成功**的操作返回失败——用户以为没成功、其实库里已经改了，比缓存脏更难排查。

### 2.3 收口范围：10 个方法 🟢

改造不是只改"事务内那 4 处"。全量清点后发现受影响的是 **10 个方法**，跨 3 类缓存 5 个文件：

| 类别 | 方法数 |
|---|---|
| 文章（详情 / 列表） | 2 |
| 点赞 | 2 |
| 评论点赞 / 评论 | 2 |
| 收藏 | 1 |
| 学习计划列表 | 5 |

**为什么全部收口**：缓存的失效时机应该由**统一的出口**决定，而不是靠调用方自觉。改造做在封装方法内部，**调用点一个没动**。

### 2.4 残留窗口：已收窄（仍非强一致）🟢🟢

还剩一个窗口：

> 某次读请求在事务提交**之前**查库（拿到旧值），而它把结果写进缓存的时刻**晚于**我们的删除动作。

注意**不是**"提交后、删除前读到旧值"——那段时间缓存里还是旧值，读到的是**命中**不是 miss，不触发回填。

⚠️ **但它不是"恰好并发"**（这个说法我们纠正过）：窗口宽度 = 读请求「查库 → 写缓存」的**耗时**，
有几十毫秒宽；而删除紧跟在提交之后，所以近似等价于「**读请求的处理区间跨越了提交时刻**」——
**对热数据，只要提交前那段时间有并发读进库就会中**，不是"概率极低"。

**第六刀上了延迟双删**（`component/DelayedCacheEvictor`）：提交后删一次 + **D 毫秒后再删一次**，
覆盖那次迟到写回。**D 是实测定的，不是拍脑袋**：

| 读路径 | 样本（16 并发强制 cache miss） | P99 | max |
|---|---|---|---|
| 文章详情 | 320 | 16ms | **28ms** |
| 文章列表 | 320 | 22ms | **26ms** |

→ **`delay-ms: 200`**（≈实测 max 的 7 倍。本地 MySQL/Redis 同机、无网络 RTT，
生产要叠加网络往返 / GC / 更大数据量；**偏大是安全方向**——代价只是多一次回源）。

**三个能讲的取舍**：

| 点 | 做法 | 理由 |
|---|---|---|
| 延迟载体 | **进程内** `ThreadPoolTaskScheduler`，**不用** Redis ZSet 队列 | 延迟只有几百毫秒，ZSet + 定时捞的精度受扫描周期限制（秒级起步）；而任务**可丢**（丢了退化成单次删除），用不上持久化。项目别处用 ZSet 延迟队列是因为那里延迟是**分钟级且不能丢**——**场景不同，结论不同** |
| 调度器 | **私有 `new`，绝不声明成 Bean** | 上下文里出现任何 `TaskScheduler` bean，会让自动配置的 `taskScheduler` 因 `@ConditionalOnMissingBean` 退避 → `pool.size: 1` **静默失效**，8 个 `@Scheduled` 全被搬走，串行调度不变量无声破坏 |
| 范围 | **`UserSetCache` 不纳入** | 它的读路径回填是 **`markLoaded` 全量快照覆盖**，窗口形态是"增量被旧快照覆盖"，**"删两次"根本关不上**（删掉集合后回源重建的是快照时刻的数据） |

**测试**：`DelayedCacheEvictTests` 7 例。核心用例用**可控挂起的 MyBatis 拦截器**精确复现
「读请求跨提交」，全程不靠赛跑；**反向验证**砍掉重放 → 精确红 5 条。

**代码**：`component/AfterCommitExecutor.java`（只管时机）、`component/DelayedCacheEvictor.java`（延迟重放）；
测试 `AfterCommitCacheEvictTests` 6 例（用 `TransactionTemplate` 手动控事务边界，事务内断言一次、提交后再断言一次）；
设计稿 `docs/redis/delayed-double-delete-design.md`

### 3.1 String 🟡

四类用途，同一个类型四种玩法：

| 用途 | 例子 |
|---|---|
| 缓存 | `article:detail:{id}` 存 VO 的 JSON，业务侧 `ObjectMapper` 自己序列化 |
| 计数器 | `article:view:{id}`、`login:fail:account:{user}`、`ai:rate:...` |
| 锁 | `cache:lock:article:detail:{id}`、`ai:workflow:action:{runId}` |
| 状态标记 | `{setKey}:loaded` 存 `FULL` / `EMPTY` |

### 3.2 Set + 状态标记（用户态集合）🟢🟢

**这是全项目最有故事的一块。**

**背景**：点赞 / 收藏要展示"我点过哪些"，每次查 DB 太浪费 → 缓存成 Set。

**为什么要一个额外的 `:loaded` 标记**：Set 为空有两种含义——"用户确实没点过"和"还没加载"。不区分的话，要么每次都回源（缓存没意义），要么把未加载当空集（显示错误）。

**标记的三种状态**：

| 值 | 含义 |
|---|---|
| `FULL` | 集合非空，且是 DB 全量快照，可信任 |
| `EMPTY` | 查过了，用户确实没有数据 |
| 不存在 | 未加载，调用方**必须**回源 DB |

**三条不变量**：

1. 只有从 DB 全量加载过的分支才能写标记；点赞 / 取消**只在标记已存在时**维护集合
2. `FULL` 但集合缺失 = 异常（部分淘汰 / 被误删）→ 按未加载处理回源重建，**不能当空集合返回**
3. **Set TTL(40min) > 标记 TTL(30min)**，且先写 Set、后写标记。反过来会出现"标记还在、Set 已空"的窗口，读到空集合 = 静默显示"没点过赞"

**坑 1：`SADD` 是追加不是覆盖（存量 bug）**

触发链：标记过期（30min）但集合还在（40min）→ 这期间用户取消了点赞（未加载状态下维护逻辑正确地什么都没做，DB 已删）→ 随后回源重建时，残留成员被 `SADD` 保留 → **已取消的点赞"复活"**。

修法：`markLoaded` **先 `delete` 再 `add`**。中间那个窗口是安全的——读路径看到集合为空会判为"状态不可信"去回源。

**坑 2：维护集合必须原子（Lua）**

拆成多次调用时，检查标记与写入之间标记可能过期，于是 `SADD` 会重新创建一个**只有新元素的集合**——又变回"集合自称全量但只有一条"的老问题。

**坑 3：维护走 `AfterCommitExecutor`，但回填不走**

调用方（点赞 / 取消）在事务里，提交前动集合会出现"事务回滚了、集合却已经改了"的错位——最坏是取消最后一项把状态写成 `EMPTY`，而那条取消根本没生效。

而读路径的 `markLoaded` **不走** executor：回填必须立即生效给后续请求用，且读路径本就没有事务。

**代码**：`component/UserSetCache.java`（Lua 在 `:52-81`，三条不变量在类注释 `:27-31`）

### 3.3 ZSet：热度榜 🟢🟢

**双轨设计**：

- **实时增量**：浏览 +1 / 点赞 +2 / 取消赞 -2 / 收藏 +3 / 取消收藏 -3 / 评论 +4 / 删评论 -2（每条受删评论）
- **定时全量重建**：每 30 分钟从 DB 重新算一遍

**为什么双轨**：实时增量保证新内容立刻上榜；全量重建纠正长期漂移（Redis 重启会丢增量）。

**坑：实施中实测复现的并发 bug**。两个执行者共享热榜临时 key 时，后到的那个 `RENAME` 直接报 `ERR no such key`。

拆解下来是两个约束：

1. `RENAME` 的源 key 不存在会直接抛错——先完成的执行者已经把临时 key RENAME 走了
2. **`RENAME` 会把目标 key 的 TTL 覆盖成源 key 的**，而临时榜每轮新建、无 TTL → `EXPIRE` 必须在 `RENAME` **之后**，写在前面等于白写

生产只有定时任务一个调用方（调度池 `size=1`）撞不上，但测试 / 手工触发会成为第二个调用方——**这个错就是这么暴露的**。

**修法**：整段打包成 Lua（`EXISTS` 检查 + `RENAME` + `EXPIRE`），两个约束都不再由调用方保证。

**代码**：`ArticlesServiceImpl.java:110-120`（脚本），`:1181-1210`（重建）；测试 `ArticleHotRankTests` 3 例锁住，含反向验证

**顺带**：补 TTL 之前，热度榜是全项目**唯一没有 TTL 的 key**——而 `volatile-lru` 的前提是"允许丢失的数据都有 TTL"。

### 3.4 Hash：秒杀活动元数据 🟢

key `seckill:{activityId}:meta`，字段只有三个：`status` / `startAt` / `endAt`。

**为什么是 Hash 而不是 String 存 JSON**——这是"结构由使用方式决定"的典型案例。

抢购的 Lua 脚本要在 **Redis 服务端**判断"活动是否在进行中"：

```lua
local status = redis.call('HGET', KEYS[3], 'status')
local now = tonumber(redis.call('TIME')[1])
if status ~= 'ACTIVE' or now < startAt or now >= endAt then
    return {-2, 'NOT_ACTIVE'}
end
```

meta 若存成 String JSON，脚本就得把整个 JSON 取回来自己在 Lua 里解析——**又慢又容易出错**。
Hash 让脚本能**按字段读**，只取需要的那三个。

> **一句话**：需要服务端脚本按字段读 → Hash；只做整体读写 → String JSON 更省事。

**踩过的坑 · `TIME` 返回的元素是字符串**：`TIME` 给的是 `{秒, 微秒}`，两个元素**都是字符串**，
必须 `tonumber` 才能和 `startAt` 比。不转的话 Lua 直接报
`attempt to compare string with number`——**脚本抛错 = 抢购全挂**。

**代码**：`SeckillKeys.meta()`，写入 `SeckillServiceImpl.java:303`

### 3.5 HyperLogLog：文章 UV 🟢🟢

**做法**：浏览文章时 `PFADD article:uv:{articleId}:{yyyyMMdd} {userId 或 IP}`，
详情页展示**当天的**基数（`ArticleDetailVO.uvCount`）。

**为什么按天分 key**——这是本节的题眼：

HyperLogLog **不支持删除元素**，只有 `PFADD`，**没有 `PFREM`**。如果全站一个 key 然后续 TTL，
历史访客会**永远留在基数里**，越算越虚。按天分之后每天一个 key，TTL 8 天自然过期，
语义干净地落在"**这一天的**独立访客"。

**这就是它和 PV 的本质区别**：PV 是累计值（能一直加），UV 是**窗口值**（必须能重新开始）。
所以 UI 上必须标清楚是"今日访客"，**不能和浏览数并列当累计看**。

**能讲的数字**：固定 **12KB** 内存 / 标准误差 **0.81%** / `PFMERGE` 可合并多天（做"近 7 天 UV"）。
**这笔账**：1 亿 UV 用 Set 存要 800MB，HLL 用 12KB 换 0.81% 误差——任何真实场景都划算。

**写入同样走 Lua**（与浏览量同构、理由相同）：`PFADD` 与 `EXPIRE` 分两次调用，
中间故障会留下**无 TTL 的 key**——而"允许丢失的数据都有 TTL"是 `volatile-lru` 能正常淘汰的前提。

**代码**：脚本 `ArticlesServiceImpl.java:106`，写入 `:588`，读取 `:603`（`opsForHyperLogLog().size()`）

> **追问"为什么不用 Set 精确统计"**：Set 要存每个 userId，1 亿 UV = 800MB，
> 而且**永远不能过期**（一过期基数就归零）。UV 的价值在"量级对不对"，不在"精确到个位"。

### 3.6 Bitmap：用户日活跃 🟢🟢

**做法**：登录用户浏览 / 发文 / 评论时 `SETBIT active:user:{yyyyMMdd} {userId} 1`，
配合 `BITCOUNT` / `BITOP` 做日活、周活、留存。

| 指标 | 命令 |
|---|---|
| 日活 | `BITCOUNT active:user:20260920` |
| 周活跃 | `BITOP OR` 近 7 天 → `BITCOUNT` |
| 次日留存 | `BITOP AND` 昨天 + 今天 → `BITCOUNT` |

**为什么用 Bitmap 而不是 Set**：统计只需要回答"这个用户在不在"，**不需要知道"是谁"**。
一个用户 1 bit——1 亿用户的日活是 **12.5MB**，换成 Set 存 userId 至少要几个 GB。
**bit 的语义就是"在 / 不在"，正好对上这个需求。**

**坑 1 · offset 用 userId 的前提是自增主键** 🟢🟢

项目用 `IdType.AUTO`，ID 连续、从 1 开始，offset 不浪费。
**换成雪花 ID 就必须先做一层映射**——否则 offset 会冲到 10^18，
**一次 `SETBIT` 就能让 Redis 试图分配天文数字的内存**。

代码里有 `MAX_USER_OFFSET = 1000 万` 作为闸门，越界直接不记——
"宁可不统计，也不能让一条脏 ID 把位图撑爆"。

> **这个坑的价值**：它把「用什么 ID 生成策略」和「能不能用位图」这两件看起来无关的事连起来了。
> 面试里被问"位图有什么限制"，答"offset 不能太大"是八股；答"**我们的主键策略一旦换掉，
> 这段代码就会炸内存，所以我加了闸门**"是工程。

**坑 2 · `BITOP` 必须写到临时 key 再计数，而且临时 key 要用 UUID 命名**

`BITOP` 本身不返回计数，必须落到一个 key 再 `BITCOUNT`。这个临时 key 会被
**并发的统计请求互相覆盖**——用固定名字的话，两个人同时查周活会读到对方的中间结果。
UUID 命名 + `finally` 删除；删失败也只是留个孤儿 key，不会污染正式数据。

**代码**：`component/UserActivityTracker.java`，写入点 3 处，消费方 `service/ActivityStatsService.java`

### 3.7 Stream：秒杀入账事件 🟢🟢

**这是项目里唯一用到 Stream 的地方**，也是唯一"Redis 承担可靠性职责"的地方。

**为什么秒杀入账必须用 Stream**——和 [11.4 的 ZSet 延迟队列](#114-延迟队列zset-实现)对照着讲最清楚：

| | ZSet 延迟队列 | Stream 消费组 |
|---|---|---|
| 取出语义 | **取走即删**——取出来后进程崩溃，任务**永久消失** | 取出后留在 **PEL**，不 ACK 就能被接管 |
| 投递保证 | at-most-once | **at-least-once** |
| 投递次数 | 得自己塞进 member 字符串里带着走 | `XPENDING` **直接给** |
| 用在哪 | RAG 索引重建（失败了有失败标记 + 人工入口兜底） | **额度入账（丢了就是丢钱）** |

> **一句话**：RAG 索引重建失败还有失败标记兜底，**额度入账没有这层**——它要的是 at-least-once，
> 而那正好是 Stream 消费组已经做好的事。

**链路**：抢购 Lua 里 `XADD` 生成事件 → 消费组 `seckill-settle` 消费 → 落库成功才 `ACK` + `XDEL`。

**四个设计点**：

| 点 | 做法 | 理由 |
|---|---|---|
| 拿投递次数 | `XPENDING` 扩展形式 `[id, consumer, idle, deliveryCount]`，而非 `XAUTOCLAIM` | 死信判据要的 deliveryCount，一个命令拿全，不用自己维护 attempt 字段 |
| 接管超时消息 | `XCLAIM` + `idle > 60s` 才算 | 给正常处理留足时间，别抢正在跑的那条 |
| 技术失败 | **不 ACK**，留在 PEL 等回收重试 | 此刻不确定 DB 是否已落库（可能提交成功但响应超时），**退库存可能造成超发**，唯一安全的做法是重试 |
| 到重试上限（5 次） | `markDeadLetter` + **ACK 清出 PEL** | 不清的话它永远占着 PEL，对账分不清"还在重试"和"已经放弃了" |

**`ACK` 与 `XDEL` 的顺序不能反**：先 `ACK` 再 `XDEL`。反过来的话，两步之间崩溃会留下
「消息已经删了、却还挂在 PEL」的**悬空条目**；先 ACK 再删最坏只是残留一条已完成消息。

⚠️ **`XDEL` 是物理删除，所有消费组一起受影响**。当前只有一个消费组所以安全；
将来加了对账组 / 监控组之后，就不能再"谁处理完谁删"，要改成"所有消费组都 ACK 过才可删"。

**两个"刻意不用"**：

- **不用 `BLOCK`**：调度线程池 `pool.size=1` 是**串行**的（浏览量同步依赖这一点），
  一个阻塞读会把同池的浏览量同步 / RAG 重试 / 计费单过期**全部卡死**。
  `COUNT 10` 的非阻塞读本身是毫秒级的。
- **不用 `StreamMessageListenerContainer`**：自建容器要配线程池和生命周期，
  项目零 Stream 先例，收益不匹配。

**踩过的坑 · `MKSTREAM` 制造孤儿 stream** 🟢🟢

`XGROUP CREATE` 带 `MKSTREAM` 的语义是「stream 不存在就**创建**它」，
而消费任务**每 2 秒跑一轮** → 一个已经被清掉的活动会被它**一遍遍把空 stream 建回来**。

实测本地积了 26 个永不消失的空 stream，**占 db0 全部 key 的 86%**。

修法：先 `hasKey` 确认再建组，并**去掉 `MKSTREAM`**——events 由抢购脚本的 `XADD` 创建，
所以「key 不存在」就等于「没人抢过」= 没有东西要消费。

> **这个坑是从 `--bigkeys` 扫出来的，不是调试调出来的**（见 [10.5](#105-慢查询--大-key--热-key)）。
> 而且根因**不在测试**——`@AfterEach` 早就在删 key 了，是消费任务在删完之后又把它建回来。

**代码**：`task/SeckillSettleTask.java`，写入在 `SeckillServiceImpl.java` 的抢购脚本里（`XADD`）

### 3.8 List：确实没用 🔴

没有队列 / 栈形态的业务。

**如果被问"为什么不用 List 做消息队列"**：`LPUSH` + `BRPOP` 确实能做到"取走即删"，
但**没有 ACK**——取出来的那一刻消息就没了，消费失败只能靠应用层自己补，
也没有消费组、没有 PEL、没有投递次数。要用 Redis 做队列，**该上的是 Stream 而不是 List**
（List 的定位是"列表"，不是"队列"）。

## 四、原子性

### 4.1 为什么用 Lua 不用 MULTI/EXEC 🟢

| 判据 | Redis 事务 | Lua |
|---|---|---|
| 能否回滚 | **不能**（运行期错误不中断，语法错才整段不执行） | 不适用，但脚本内可以写逻辑分支 |
| 是否独占连接 | **是**——所以需要连接池 | **否**——不独占，共享连接可用 |
| 需要重试吗 | WATCH 是乐观锁，冲突要重试 | 不需要 |
| 能写条件逻辑吗 | 不能 | 能（`if TTL < 0`、`if EXISTS`） |

**项目选择**：原子性需求全部由 **13 段 Lua** 覆盖，**一处 MULTI / WATCH 都没有**。

> 「Lua 不独占连接，事务会」这条还能反向用：它是 [10.2 不引连接池](#102-连接池决策是不引-commons-pool2) 那条决策的直接依据之一。

### 4.2 十三段脚本 🟢🟢

每段都有"为什么必须原子"的真实理由——**没有一段是为了炫技**。

| # | 脚本 | 位置 | 干什么 / 为什么必须原子 |
|---|---|---|---|
| 1 | `UNLOCK_SCRIPT` | `ArticlesServiceImpl:66` | `GET == token` 才 `DEL`。防止慢请求删掉别人的锁 |
| 2 | `VIEW_INCR_SCRIPT` | `ArticlesServiceImpl:79` | `INCR` + 判 `TTL < 0` 才 `EXPIRE`。分两次调用中间故障 → 留下**无 TTL 的计数键**。注意判的是 `TTL < 0` 而不是 `INCR == 1`——后者补不上"上线前就存在的无 TTL 旧 key" |
| 3 | `VIEW_TAKE_SCRIPT` | `ArticlesServiceImpl:91` | `GET` + `DEL` 一次完成。用 Lua 而非 `GETDEL` 是为了兼容 Redis < 6.2 |
| 4 | `UV_ADD_SCRIPT` | `ArticlesServiceImpl:106` | `PFADD` + 判 `TTL < 0` 才 `EXPIRE`。与 #2 **同构、理由也相同**——分两次调用中间故障会留下无 TTL 的 key |
| 5 | `RENAME_HOT_RANK_SCRIPT` | `ArticlesServiceImpl:133` | `EXISTS` + `RENAME` + `EXPIRE`，见 [3.3](#33-zset热度榜) |
| 6 | `UNLOCK_SCRIPT` | `WorkflowActionLock:21` | 与 #1 同型（刻意不共享常量——两者契约不同） |
| 7 | `MAINTAIN_SCRIPT` | `UserSetCache:52` | 查标记 → `SADD`/`SREM` → 刷两个 TTL；`SREM` 到 `SCARD == 0` 时转 `EMPTY`。见 [3.2](#32-set--状态标记用户态集合) |
| 8 | `INCR_AND_EXPIRE_SCRIPT` | `AiRateLimiter:29` | `INCR`，首次 `EXPIRE`。分开写的话并发下计数与 TTL 不一致 |
| 9 | `RECORD_FAILURE_SCRIPT` | `LoginAttemptLimiter:81` | 同上。**INCR 成功而 EXPIRE 失败 → 计数键永不过期 → 用户被永久锁定** |
| 10 | `MARK_ACTIVE_SCRIPT` | `UserActivityTracker:52` | `SETBIT` + 判 `TTL < 0` 才 `EXPIRE`。同样是"写数据 + 兜底 TTL"三兄弟之一 |
| 11 | `TAKE_DUE_SCRIPT` | `RagRetryQueue:40` | `ZRANGEBYSCORE` + `ZREM`。**读与删必须原子**——分开调用时上一轮还没删完、下一轮读到同一批 → 同一任务被投递两次 |
| 12 | `ENQUEUE_SCRIPT` | `RagRetryQueue:56` | `ZADD` + `EXPIRE`。避免 `ZADD` 成功而 `EXPIRE` 失败留下**永不过期的队列** |
| 13 | `GRAB_SCRIPT` | `SeckillServiceImpl:63` | 秒杀预占五步，见 [11.8](#118-秒杀redis-挡流量db-保正确) |

**注意 #2 / #4 / #10 是三兄弟**：`INCR` / `PFADD` / `SETBIT` 三个写操作，
配的都是同一个"判 `TTL < 0` 才 `EXPIRE`"的兜底模式。**判 `TTL < 0` 而不是判"是不是第一次写"**，
是因为前者能补上**任何原因**造成的无 TTL 残留（包括上线前就存在的老 key），后者不能。

> **能讲的一句话**：这 13 段里有一半是"写数据 + 补 TTL"这两件事必须一起成功——
> 分开写的话，**中间那一次故障会留下一个永不过期的 key**，而它不会被淘汰策略清掉（`volatile-lru` 只淘汰有 TTL 的），
> 最后表现为"内存满了 Redis 开始报错"。**这个问题不会立刻暴露，是攒出来的。**

**第 9 段值得单独讲**：它的字节内容与第 8 段**完全相同**（`INCR` + 首次 `EXPIRE`），
但代码里**刻意不共享同一个常量**——因为两者的**契约不同**（一个管限流窗口，一个管登录锁定），
**4 行重复 < 错误抽象**。这种"看起来该复用但故意不复用"的判断很容易被问到。

## 五、分布式锁

三个使用点，一个实现模式：**`SETNX` + UUID token + Lua 校验释放 + 短 TTL + fail-open**。没有 Redisson，没有续期。

### 5.1 详情互斥锁 🟢

见 [1.2 缓存击穿](#12-缓存击穿)。TTL 5 秒，拿不到锁短轮询，超时 fail-open 回源。

### 5.2 Workflow 动作锁 🟢

- key `ai:workflow:action:{runId}`（Agent Run 用自定义前缀 `ai:agent:action:{agentRunId}`，复用同一个锁组件）
- TTL **120 秒**
- 拿不到锁抛 `WorkflowActionBusyException`（HTTP CONFLICT + "Workflow 正在处理中"）
- **Redis 故障降级放行**——因为后面还有 DB `version` CAS 条件更新兜底

### 5.3 为什么不上 Redisson / 不续期 🟢🟢

**这是一个"不做"比"做了"更能体现判断力的点。**

- 锁内操作是**毫秒级**的 DB 更新。Redisson 的 watchdog（看门狗续期）是为"业务执行时间不可预估"设计的——本项目没有这个场景
- 5s / 120s 的 TTL 已经**远大于**实际执行时间
- 引 Redisson = 为一个不需要的能力引入一个重依赖

**追问"锁过期了业务还没跑完怎么办"**：详情锁超时了，拿不到锁的请求会 fail-open 自己查库——结果是多查一次 DB，不是数据错误。动作锁超时了，DB 层的 version CAS 会拦住重复提交。

### 5.4 锁 + DB CAS 双保险 🟢

`AgentRunSuggestionService` 的类注释写得很明确：

> 并发保护 = Redis 锁（SETNX + Lua + fail-open）**+ DB 状态 CAS**

Redis 锁负责**挡住绝大部分并发**（快速失败），DB CAS 负责**正确性兜底**（锁失效也不会写坏）。

### 5.5 Redlock 🔴

没做。设计稿里逐条否定了（时钟漂移假设、需要多主、本项目单机部署）。**面试时按"为什么不需要"讲，不要说"没来得及做"。**

## 六、过期与淘汰

### 6.1 全 key 有 TTL 🟢🟢

**项目现在没有任何一个无 TTL 的 key。** 这是刻意设计的结果，不是巧合。

推导链是这样的：

```
选了 maxmemory-policy = volatile-lru
  → 前提是"允许丢失的数据都有 TTL"
  → 否则内存打满时，没有 key 可淘汰，Redis 直接对写入报 OOM
  → 所以逐 key 核实了一遍 TTL
  → 扫尾补上两个漏网的：article:view（30min）、article:hot（2h）
```

**这条推导链本身就是答案**——从淘汰策略倒推出全 key 治理，比单独说"我给 key 设了 TTL"高一个层次。

**但这个不变量后来"换过守门人"** 🟢：热度榜补上 TTL 之后，**秒杀那套 key 成了新的风险点**——
`stock` / `users` / `events` 都是**抢购时才创建**的，创建出来天然无 TTL。

补法分两种，差别很能讲：

| key | TTL 从哪来 | 值 |
|---|---|---|
| `stock` / `users` / `meta` | **预热时**设 | `endAt − now + 7 天` |
| 抢购时才建的 `users` / `events` | **抢购脚本里**判 `TTL < 0` 补 | 固定 30 天 |

**为什么不能"一律给个短 TTL"**：秒杀 key 不是可重建的派生数据，
**活动进行中把状态弄丢 = 直接出事**。所以 TTL 必须**远长于活动本身**。

> ⚠️ **代码注释与实现不符的地方**（看代码时会撞上）：`RedisConstants.java` 里写着
> "秒杀 key **刻意不设 TTL**"，那是**设计初期的决定**，后来运维实测后改成了"设一个远长于活动的 TTL"，
> 注释没跟着改。**以 `SeckillServiceImpl.preheatOne()` 的实际行为为准。**

**踩过的坑 · `EXPIRE` 收到负数会立即删除 key** 🟢🟢

`endAt − now + 7 天` 这个式子，在**活动已经结束时剩余时间是负数**——
而 `EXPIRE` 对负数的处理**不是"不设置"，是"立即删除"**。

后果：预热一个刚过期的活动，就把状态全清掉了，对账任务下一轮立刻看到
"Redis 预占数少于 DB 订单数"，报一个**根本不存在的错**。

**修法：下限取 buffer 本身，不随剩余时间下沉**——`max(endAt − now, 0) + 7 天`。

> 这条值得单独记：**`EXPIRE` 的负数语义是"删除"而不是"忽略"**。
> 任何"用时间差算 TTL"的地方都有这个雷。

### 6.2 volatile-lru 而不是 allkeys-lru 🟢🟢

**判据**：Redis 实例里住的不只是缓存，还有**锁 / 幂等键 / 限流计数**这类"丢了会出错"的状态。

`allkeys-*` 会一视同仁地淘汰它们——锁被淘汰 = 互斥失效，幂等键被淘汰 = 重复提交，限流计数被淘汰 = 限流失效。

`volatile-lru` 只淘汰**设了 TTL 的** key，天然把"可丢的缓存"和"不可丢的状态"分开了。而它成立的前提，是 [6.1](#61-全-key-有-ttl)。

### 6.3 maxmemory 设多少 🟢

`512mb`，约占机器内存的 **60~70%**。

**为什么不设 90%**：要给 **fork 的 COW**（写时复制）和复制缓冲留余量。设太满的典型后果是——**执行 RDB / AOF 重写时 fork 失败或 OOM**。

### 6.4 惰性删除 + 定期删除 🟡

原理知道（惰性：访问时判断过期；定期：每 100ms 随机抽一批）。**项目里没有实测过**，被追问采样逻辑时按通用八股答。

### 6.5 关键不变量：Set TTL > 标记 TTL 🟢

见 [3.2](#32-set--状态标记用户态集合)。这条不是通用八股，是项目特有的——**两种 key 配合使用时，它们的 TTL 大小关系本身就是一条不变量**。

## 七、持久化

### 7.1 AOF 取舍 🟢

`appendonly yes` + `appendfsync everysec`。**并且实测过**——`kill -9` 掉 Redis 进程再重启，
验证数据还在（记录在 `redis-ops-runbook.md` §七）。

> **"我验证过持久化"**这句话很多人不敢说——因为它需要真的去 kill 一次。
> 实测的门槛很低，但它把这条从"配置项"变成了"我做过"。

**写在配置文件注释里的边界**（这句话可以直接背）：

> AOF 解决的是"Redis 自己重启后数据还在"，**它不解决 Redis 与 MySQL 的跨系统一致性，也不替代补偿逻辑**。

理由是项目里 Redis 存的都是派生数据（缓存 / 计数 / 榜单），真正的数据源是 MySQL。AOF 的价值是"重启后不用全部回源"，不是"数据可靠性"。

### 7.2 fork 与 COW 🟡

讲得出，因为 [maxmemory 的取值](#63-maxmemory-设多少)就是为它让路的。

RDB / 混合持久化没启用，AOF 够用。

## 八、限流

### 8.1 算法：固定窗口 🟢

`INCR` + 首次 `EXPIRE`，一次 Lua 完成。

**key 的设计有个小技巧**：`ai:rate:{bucket}:{user|ip}:{identity}:{windowSeconds}`

**窗口号放进 key 里**——窗口变了 key 自然就变了，不需要额外的清理逻辑。这是用固定窗口而非滑动窗口的底气之一。

（滑动窗口 / 令牌桶的适用场景要能讲：滑动窗口解决固定窗口的临界问题、令牌桶能应对突发流量。项目选固定窗口是因为——够用，且实现和排查都简单。）

### 8.2 四桶 + 分级 🟢

| 桶 | 阈值 | 窗口 | 为什么是这个值 |
|---|---|---|---|
| `chat` | 10 次 | 60s | 正常的对话节奏远远够用 |
| `workflow` | 3 次 | 600s | 工作流贵且慢，10 分钟 3 次是**成本闸门** |
| `rag` | 30 次 | 60s | 检索类操作轻、频次天然高 |
| `seckill` | 20 次 | 60s | **比 chat 宽**——网络抖动、手速都会让用户多点几次，但仍挡得住脚本级频率 |

**秒杀桶的阈值哲学值得单独讲**：它的定位**不是防刷**，是防"脚本级频率"。
真正的"一人一单"防线在更前面——`GRAB_SCRIPT` 里的 `SISMEMBER` + DB 的 `uk_user_activity` 唯一索引。
**把限流当防重手段是错位的**：限流拦的是"频次"，不是"重复"。这个分工要在架构上分清。

**分级**：登录用户按 `userId`；游客按 IP，限额 = 登录用户的**一半，下限 1**。

**超限响应**：HTTP 429 + `Retry-After` 头（`RateLimitExceededException` 带 `windowSeconds`，`GlobalExceptionHandler` 转）。

**fail-open 还是 fail-close**：默认 `failOpen=false`（**严格模式**）——Redis 挂了就拒绝请求，而不是放行打垮下游。

### 8.3 路由判定：哪些请求不占配额 🟢

只拦四类：

- `POST /api/ai/chat/stream`（chat 桶）
- `/api/ai/rag/articles/search`（rag 桶）
- `/api/ai/workflows/**` 的**非 GET** 且**非** cancel / approve / reject / retry（workflow 桶）
- `POST /api/seckill/*/grab`（seckill 桶）——**只有"抢购"这一个动作**

**为什么每个桶都要挑着拦而不是整段前缀**：

| 排除的 | 理由 |
|---|---|
| Workflow 的 GET（查状态） | 查询不消耗 LLM |
| Workflow 的 confirm / retry / cancel | **流程内正常交互**，次数天然受步骤数限制——否则"一个流程连续确认几次就被 429 误伤" |
| 秒杀的 `/result` 轮询 | **前端每秒轮询**是正常行为，算进配额等于"用户还没抢到就先被 429 了" |

> **这个细节很能体现"限流是给人用的还是给指标用的"**——按 URL 前缀一把梭是最省事的写法，
> 但它会把正常交互一起打掉。判据是**这个请求是不是真的在消耗你要保护的资源**。

**代码**：`security/AiRateLimiter.java`，路由判定 `security/AiRateLimitInterceptor.java:103-142`

## 九、登录安全

### 9.1 失败计数：双维度非等权 🟢🟢

| 维度 | 阈值 | 拦什么 |
|---|---|---|
| 账号 | **5 次 / 15 分钟**（严） | 定向爆破 + 分布式爆破 |
| IP | **30 次 / 15 分钟**（宽） | 撞库 |

**判据是一张攻击形态覆盖矩阵**：

| 攻击形态 | 特征 | 谁能拦 |
|---|---|---|
| 定向爆破 | 一账号、同 IP 狂试 | 账号维度 ✅ |
| 分布式爆破 | 一账号、代理池多 IP | **账号维度** ✅（IP 维度拦不住） |
| 撞库 | 多账号、同源 IP | **IP 维度** ✅（账号维度拦不住） |

**「用户名 + IP」组合键只拦得住第一种**——方案第一版就错在这里，实施时退回去了。

**要承认的残留代价**：账号维度仍然可以被拿来**锁死真实用户**（攻击者故意用别人的用户名试错）。代价限制在 15 分钟，且**本人登录成功即清零**。

### 9.2 成功登录只清账号键、不清 IP 键 🟢🟢

**清了等于留后门**——攻击者只要有一个自己的账号，就能靠反复登录成功把 IP 计数刷掉，IP 维度形同虚设。

**追问"那用户被 IP 维度误伤了怎么办"**：IP 阈值 30 次远宽于账号的 5 次，正常用户撞不到；真撞到了（比如公司出口 IP 共用），等 15 分钟窗口过期。

### 9.3 防账号枚举三条一起做 🟢🟢

| # | 做法 | 为什么 |
|---|---|---|
| 1 | 不存在的账号**同样计数** | 否则"会不会被限流"本身就是探针 |
| 2 | 提示语统一 | "账号不存在" / "密码错误" 分开提示 = 白送枚举 |
| 3 | **补跑一次 bcrypt** | 查不到用户直接返回会**快 ~100ms**——响应时间本身就是探针 |

**第 3 条最容易漏**，它把"防枚举"从"文案层"拉到了"时序层"。

### 9.4 归一化：被数据库 collation 逼出来的 🟢🟢

`trim` + `toLowerCase(Locale.ROOT)` + 截断 50 字符（对齐 `users.username` varchar(50)）。

**为什么必须归一化**：实测 DB collation 是 `utf8mb4_unicode_ci`——`Admin` 与 `admin` **在库里本来就是同一个用户**。不归一化的话，大小写变体在 Redis 里是三个不同的 key，**5 次阈值被拆成 15 次**。

`Locale.ROOT` 是为了避免土耳其语的 `i` 大小写问题（`I`.toLowerCase() 在土耳其语环境会得到 `ı`）。

> 这个坑的价值在于：**它不是 Redis 的问题，是"Redis 的 key 语义必须和 DB 的语义对齐"**。

### 9.5 `checkBlocked` 必须在查库之前 🟢

不消耗 bcrypt（省 CPU）、也不泄露账号是否存在（被锁的和不存在的走同样路径）。

### 9.6 窗口与锁定共用一个键 🟢

窗口自然过期即解锁，**不需要第二个"锁定标记"键**。

**追问**：那怎么知道还要等多久？——只在**超限这条罕见路径**上多查一次 `getExpire`，换一个准确的 `Retry-After`。正常路径不多这一次往返。

### 9.7 Token 黑名单 🟢

| 设计点 | 理由 |
|---|---|
| 按 **`jti`** 而非 `userId` | RFC 7519 的设计意图。按 userId 等于"登出踢掉全部设备" |
| **TTL = token 剩余有效期** | 不是固定时长。token 本来就快过期了，拉黑它不需要存 7 天 |
| `jti == null` 直接跳过 | 加 `jti` 之前签发的老 token 没有这个字段 |
| **两个拦截器都查** | `JwtInterceptor` + `OptionalJwtInterceptor`——只改强制登录那个的话，登出后 token 在公开接口**仍算登录态** |
| Redis 故障按"未拉黑"放行 | JWT 自身 7 天过期是兜底防线 |

**顺带修掉一个前端死代码**：`authApi.logout()` 定义了却**从未被调用**，登出只清 localStorage——后端做完黑名单也没人触发。已接上（失败忽略 + 单独 3s 超时）。

## 十、运维与治理

### 10.1 KEYS → SCAN + UNLINK 🟢

`KEYS` 是 O(N) 且**阻塞 Redis 服务端单线程**——Redis 里同时住着限流、分布式锁、业务缓存，一次 `KEYS` 会让它们**全部一起卡**。

| 手法 | 说明 |
|---|---|
| `SCAN` | 游标迭代，`COUNT 200`，每次只扫一批 |
| `UNLINK` | 删除用异步回收内存，不用同步的 `DEL` |
| 边扫边删 | 不把全部 key 堆在内存里 |

**原代码有 5 处在用 `KEYS`，现在清零。**

**SCAN 的代价必须知道**（面试官爱追问）：

- **不保证快照一致性**——扫描期间新增的 key 可能扫不到（缓存场景由 TTL 兜底）
- **可能重复返回同一个 key**——调用方需保证幂等

**代码**：`component/RedisKeyScanner.java`

### 10.2 连接池：决策是"不引 commons-pool2" 🟢🟢

**这是一个"不做"的决策，论证过程比结论重要。**

三条"需要池"的常见理由，逐条核实**全不成立**：

1. "多线程要用连接池" → Lettuce 基于 Netty **多路复用**，单连接即可并发，不像 Jedis 必须池化
2. "有些命令会独占连接" → 项目里**没有** `BLPOP` / `MULTI` / `WATCH` 这类命令（原子性全走 Lua，Lua 不独占）
3. "配一下总没坏处" → pom 里没有 `commons-pool2`，配了 `lettuce.pool.*` 会被**静默忽略**，反而误导后来人

**Jedis 必须池化 vs Lettuce 可共享连接**——这个对比是标准追问，要能讲。

### 10.3 超时参数保护的是谁 🟢

`timeout: 3s` —— **不是给 Redis 减负**。超时后命令**仍在服务端跑完**，它保护的是**应用线程**（不会无限等下去）。

**为什么是 3s**：项目最重的操作是 `ZREVRANGE(10)` / `SCAN(COUNT 200)`，都是毫秒级。3s 是"绝不可能是正常慢"的量级。

`connect-timeout: 2s` —— 不可达时**快速失败**，走 DB 兜底。

### 10.4 ACL 🟢

```
user blog-app on #<sha256> ~* +@all -@dangerous
```

| 决策 | 理由 |
|---|---|
| 按账号禁用 `@dangerous` | 应用账号不需要 `FLUSHALL` / `CONFIG` / `SHUTDOWN` |
| **不用 `rename-command KEYS ""`** | 全局、不可逆，而且**管理员和迁移脚本也要用 KEYS** |
| 用 `~*` 而非按前缀收敛 | 换取可维护性；真正的护栏是**禁危险命令**，不是限制 key 空间 |

**踩坑记录（查源码确认的，不是猜的）**：Redis 6.x 上 ACL 会把整个 `CLIENT` 命令组禁掉，而 Lettuce 建连时会发 `CLIENT SETINFO`（7.2+）。**不影响连接**——`RedisHandshake.applyConnectionMetadataSafely()` 把元数据命令的失败**整个吞掉**。

回归测试：`RedisAclRuleTests`。

### 10.5 慢查询 / 大 key / 热 key 🟢

`slowlog-log-slower-than 10000`（10ms）、`slowlog-max-len 128`。

**这里是"读过"和"做过"的分界线**——`redis-cli --bigkeys` 真的跑一遍，
**扫出了真问题**：db0 里 **86% 的 key 是空 stream**（根因见 [3.7 的 `MKSTREAM` 坑](#37-stream秒杀入账事件)）。

> 这个发现**没有靠任何监控系统**，就是把手册上的命令真的跑了一遍。
> **很多"生产问题"的门槛不是能力，是"有没有真的去扫一次"。**

排查手法（慢查询 / 大 key / 热 key / ACL / 连接）写成了运维手册：`docs/redis/redis-ops-runbook.md`，
含 **bigkeys / slowlog / AOF 崩溃恢复（`kill -9` 实测）** 三份实测记录。

### 10.6 调度池 size=1 🟢

浏览量同步（每 30s）与热度榜重建（每 30min）读同一批数据，**靠串行调度而不是分布式锁**保证不并发。

**这里推翻了原设计**：原方案要"给定时任务加互斥锁"，核实后发现 Spring 默认单线程调度器、**本就不并发**——加锁是为不存在的问题写代码。改为显式声明 `spring.task.scheduling.pool.size: 1`，把"不并发"从**默认行为**变成**显式约定**。

> 这条很值钱：**加锁不是越多越好，"确认它本来就不并发"比"加个锁保险"更专业**。

## 十一、场景题

### 11.1 计数器（浏览量）🟢🟢

**链路**：

1. 用户看文章 → `INCR article:view:{id}` + 兜底 TTL（一次 Lua）
2. 定时任务每 30 秒：`GET` + `DEL` **原子取走**增量（Lua）→ 累加写 DB
3. 详情页展示 = DB 值 + 缓存值

**为什么用 Lua 而不是 `GETDEL`**：兼容 Redis < 6.2。

**最关键的是这条定性**（比实现本身值钱）：

> 浏览量是**可接受丢失的近似统计**。`Lua 原子取删 → 更新 DB` **不是可靠投递**——取走之后、写库之前宕机，这批增量就丢了。
> 这个方案**不能套到库存 / 余额 / 订单**。那些场景要的是可靠投递（本地消息表 / 事务消息 / binlog 订阅）。

**追问"取走之后写库失败呢"**：丢一次增量，下一次同步照常。因为是近似统计，不值得为它上补偿。

### 11.2 UV 统计（HyperLogLog）

完整实现见 [3.5](#35-hyperloglog文章-uv)。要点复述：

- **按天分 key 是必须的**——HLL 不能删元素，单 key 续 TTL 会让历史访客永远留在基数里
- 12KB / 0.81% 误差；1 亿 UV 用 Set 存要 800MB
- 展示口径是"**今日**访客"，不能和浏览数并列当累计看
- `PFMERGE` 可合并多天做"近 7 天 UV"（**项目里没做，能讲边界**）

### 11.3 活跃与留存（Bitmap）

完整实现见 [3.6](#36-bitmap用户日活跃)。要点复述：

- 一个用户 1 bit；1 亿用户日活 = **12.5MB**
- 日活 `BITCOUNT` / 周活 `BITOP OR` / 留存 `BITOP AND`
- **offset 用 userId 的前提是自增主键**——雪花 ID 会让 offset 冲到 10^18，
  一次 `SETBIT` 就能炸内存，所以有 `MAX_USER_OFFSET` 闸门
- `BITOP` 的临时 key 必须用 **UUID 命名**——并发统计会互相覆盖结果

### 11.4 延迟队列（ZSet 实现）🟢🟢

**问题**：RAG 索引同步失败后，原先的"重试 3 次"全在**同一个异步线程里同步等待**（1s + 2s），
耗尽后只写一个失败标记——**那是墓碑，不是待办**，没有任何机制会再去碰它。

**做法**：失败时 `ZADD rag:retry:queue {下次执行时间戳} {actionKey}:{articleId}:{attempt}`，
定时任务捞到期的 → 失败则**指数退避**重推 → 超上限才真正转人工。

**ZSet 当延迟队列的原理**：score 存"下次该执行的时间戳"，取任务就是 `ZRANGEBYSCORE 0 now`
——**到点的自然排在前面，没到点的取不出来**。不需要额外的调度器，也不需要给每个任务建一个 key。

**三个必须讲对的点**：

| 点 | 做法 | 为什么 |
|---|---|---|
| **取任务必须原子** | `ZRANGEBYSCORE` + `ZREM` 打包进一段 Lua | 分开调用时，上一轮还没删完、下一轮已经读到同一批 → **同一个任务被投递两次** |
| 重试次数放在 **member 里** | `{actionKey}:{articleId}:{attempt}` | **ZSet 的 score 只能存时间**，没有第二个字段放 attempt——得自己带着走 |
| 队列 TTL 是**空闲过期** | 每次入队都刷新；7 天没有新任务就自己消失 | 与浏览量那种"数据保质期"语义不同——**队列是活动集合，没有新任务进来就该消失**，不留常驻 key |

**为什么不用 Stream 做这个**——这正是 [11.5](#115-消息队列stream-消费组) 的对照答案：

> Stream 有 ACK、有消费者组、能持久化重投，能力确实更强；但代价是要维护 pending 列表、
> 处理死信、做 ACK 超时回收。当前只有"一个应用、一个动作、失败重试"这一种用法，ZSet 的 20 行够用。
> **触发条件**：需要多消费者分组、需要 at-least-once 保证、或者要跨服务解耦时，再换 Stream 或专业 MQ。

**代码**：`ai/rag/RagRetryQueue.java`（两段 Lua：`TAKE_DUE_SCRIPT` / `ENQUEUE_SCRIPT`）

### 11.5 消息队列（Stream 消费组）🟢🟢

**"Redis 能做消息队列吗"是必问题。项目的答案是：能，而且真的在用，但要知道边界。**

完整实现见 [3.7](#37-stream秒杀入账事件)，这里只给选型框架：

| 方案 | 投递保证 | 代价 |
|---|---|---|
| List（`LPUSH` + `BRPOP`） | at-most-once，**取走即删、无 ACK** | 最简单，但消费失败就丢了 |
| **ZSet 延迟队列** | at-most-once，**取走即删** | 适合"失败了还有人工兜底"的 |
| **Stream 消费组** | **at-least-once**，PEL + ACK + `XCLAIM` | 要维护 pending、死信、超时回收 |
| 专业 MQ（RocketMQ 等） | at-least-once + 事务消息 + 顺序 + 堆积 | 多一个中间件 |

**选型判据就一条线：这个任务丢了会不会出事？**

```text
丢了不致命（RAG 索引能人工重建）  → ZSet，20 行搞定
丢了就是丢钱（额度入账）          → Stream
跨服务 / 要顺序 / 要海量堆积      → 专业 MQ
```

> **面试时最值钱的回答不是"我用了 Stream"，而是**：
> 「我**两个都用了**——RAG 重试用 ZSet、额度入账用 Stream，判据是**这个任务丢了会不会出事**。
> 而且我能说清什么时候该换成 RocketMQ。」

**RocketMQ 设计稿**：`docs/mq/rocketmq-integration-design.md`——**有评估、没实施**，
按"什么规模才需要"讲，别说成做过。

### 11.7 幂等 🟢

`Idempotency-Key` 请求头 + **SHA-256 指纹** + 24h 结果缓存。

**命中但指纹不符 → 抛冲突**（同一个 key 被用来做不同的操作，是客户端 bug，不能直接返回旧结果）。

key 格式：`ai:workflow:idempotency:{uid}:{runId}:{action}:{sha256(key)}`

**追问"为什么不直接拿请求参数当 key"**：参数会变（时间戳、随机数），
而幂等的语义是"**同一个客户端意图**"——所以由客户端显式声明一个 key，服务端只负责存和比对。

### 11.8 秒杀：Redis 挡流量、DB 保正确 🟢🟢

**这是项目里唯一"Redis 数据不可丢"的场景**——前面所有 Redis 数据丢了都能从 DB 重建，
秒杀的状态不能（见 [6.1 全 key 有 TTL](#61-全-key-有-ttl) 里"秒杀 key 刻意不设 TTL"那条）。

**四个 key**：`seckill:{activityId}:stock / users / meta / events`，
**共用 `{activityId}` 这个 hash tag**——同一段 Lua 里的多个 key 在 Cluster 下必须落在同一个槽。
当前单机用不上，但现在统一命名几乎零成本，**将来切 Cluster 不用回头改一片 key**。

**抢购一次 Lua 走完五步**（`GRAB_SCRIPT`）：

```text
类型预检 → 活动状态（TIME 比对）→ SISMEMBER 一人一单 → 库存判断 → XADD + DECR + SADD
```

**三个设计点**：

**① 为什么先做类型预检**：Lua 里**运行时错误不会回滚**——前面 `DECR` 成功了、后面 `SADD` 报
WRONGTYPE，库存就凭空少一个。预检把最常见的失败提到**任何写操作之前**。

**② 为什么 event-first（先 `XADD` 再 `DECR`）**：两种残留的代价**不对称**——

| 残留 | 后果 | 可恢复吗 |
|---|---|---|
| 有事件、库存没扣 | 消费者仍由 DB 库存 + 唯一索引裁决 | ✅ 可恢复 |
| 扣了库存、没事件 | **这个名额永远不会被入账**，用户停在"排队中" | ❌ 不可恢复 |

**让残留落在可恢复的那一侧**——这是"Lua 不回滚"这个约束下的正确应对。

**③ 为什么 `users` / `events` 要在脚本里补 TTL**：这两个 key 是**抢购时才创建**的
（预热时给它们设 TTL 是**空操作**——key 还不存在，`EXPIRE` 静默返回 false）。
而 `volatile-lru` **只淘汰设了 TTL 的 key**，没 TTL 的会一直占内存，内存满了直接 OOM 而不是淘汰。
判 `TTL < 0` 才补——**不能无条件 `EXPIRE`**，否则每次抢购都把过期时间往后推，等于永不过期。

**削峰效果：DB 压力是 O(库存) 而不是 O(QPS)** 🟢🟢

这是整个方案最值钱的一句话。**能走到 DB 的只有中签者**——
1000 人抢 50 份，只有 50 个请求会触发 DB 落库，其余 950 个在 Redis 就被挡住了。

**Redis 故障走 fail-closed**：整条链路依赖"预占 + 事件"，放行到 DB 只会让用户**永远等**
（没有事件就没有入账，用户停在"排队中"）。

**"排队中 ≠ 抢到了"是这部分的语义核心** 🟢

`grab` 成功只代表**名额占住、事件入队**，钱要等消费者落库才到账。
所以前端必须轮询 `/result`，UI 上「排队中」（暖黄）和「已到账」（绿色）**必须是两个状态**。

> 合并成一个提示，用户就会问「我抢到了为什么额度没到」。

**对账判据与钱包正好相反**：

| 对账线 | 判据 | 为什么 |
|---|---|---|
| 秒杀 | **收敛**——单轮不一致只 warn，**连续 3 轮**才 error | 异步落库有延迟，单轮不一致是正常的 |
| 钱包流水 | **必须相等**——发现即 error | 只增不改的账本，断档**不会自愈** |

两个任务都**刻意不自动修复**——**哪个数是对的只有人知道**。

**对账基准是自己补的盲区** 🟢：对账要比三个视图——Redis 的预占数（`SCARD users`）、
DB 的订单数、DB 的 `sold_count`。但有个陷阱：**预热时就存在的 `soldCount`**
（上一轮遗留 / 手工发过货）会被误判成"Redis 三个视图不一致"——因为 Redis 那边只有**本轮新增**。

所以预热时把两个基准写进 meta：`reservedBase`（已有名单数）、`stockBase`（剩余库存），
对账时**比增量而不是比绝对值**。

> **这两个字段是设计稿里没有、实施时才发现的**——"设计稿写了要做对账"和
> "对账到底比哪两个数"之间，隔着一次真实的误报。

**压测实战（200 并发）**：结果 `sold_count = 45` 而非 50，日志 5 条入账失败 + 流水幂等键冲突。
**根因不是并发也不是代码**——是压测重来时 `DELETE FROM seckill_order` 只清了订单、
没清流水（流水是账本，删不得），同一批用户二次抢到时撞上幂等键 `SECKILL:{activityId}:{userId}`。

> **链条上每一环都在正常工作**：幂等键挡住了一次重复发钱，事件留在 PEL 等重试，
> `sold_count` 没超过 `total_stock`。**这是"防护生效"，不是"系统出错"**——
> 但如果只看结果那个数字（45 ≠ 50），很容易误判成超卖 bug。
> 修法：① 重来一次**新建活动**，不要重置旧活动；② 加 `[SECKILL-DIRTY-RESET]` 日志把根因直接点出来
> ——否则堆栈里只有一个唯一键冲突，**完全指不到"重置"这个动作**。

**预热踩过的两个坑**：

| 坑 | 后果 | 修法 |
|---|---|---|
| 预热**清空了 `events`** | Stream 里是已预占、未入账的名额，删了等于凭空抹掉——**用户永远停在排队中，而库存已经少一份** | 只清 stock / users / meta |
| 预热灌的是**总库存** | 取错口径，**每重建一次就多发一批** | 灌 `totalStock − soldCount` |

**代码**：脚本 `service/impl/SeckillServiceImpl.java:63`、消费 `task/SeckillSettleTask.java`、
对账 `task/SeckillReconcileTask.java`、预热 `component/SeckillPreheatRunner.java`

### 11.9 Pipeline：热榜重建 🟢

**场景**：热度榜每 30 分钟全量重建，要对几百篇文章各发一条 `ZADD`。
原实现逐篇 `ZADD`——**N 次往返**；改成 pipeline 后打包成**一次往返**。

**和事务、Lua 的区别（这题必被问）**：

| | Pipeline | MULTI/EXEC | Lua |
|---|---|---|---|
| 在哪打包 | **客户端** | 服务端 | 服务端 |
| 原子性 | **没有**（只打包，不保证一起成功） | 有（但运行期错误不回滚） | **有**（整段原子执行） |
| 能否写逻辑 | 不能 | 不能 | **能** |
| 主要收益 | **省 RTT** | 原子性 | 原子性 + 逻辑 |

**关键澄清**：Pipeline **不是**为了原子性——它是**网络层的优化**，把 N 次 RTT 压成 1 次。
项目里"原子性"的职责**全部归 Lua**（13 段），Pipeline 只负责批量命令的往返开销。

**踩到的坑 · pipeline 里拿不到序列化器**：`executePipelined` 的 callback 拿到的是
**底层连接**，不走 `RedisTemplate` 的序列化器——**key / value 都得自己转字节**。
第一次写很容易在这里写进去一堆乱码。

**边界（写在代码注释里）**：文章数到**万级**时，`MGET` 结果与 pipeline 缓冲会一起堆在内存里，
**届时才需要分批**。现在几百篇，一次打包没问题。

**代码**：`ArticlesServiceImpl.java:1349-1370`

## 十二、项目没做的（边界答案）

**这部分的作用是：面试官问到时不慌，也不硬编。** 每条都按"什么规模才需要"来答。

| 没做的 | 为什么现在不做 / 什么规模需要 |
|---|---|
| **主从 / 哨兵** | 单点故障尚可接受——Redis 挂了全站**降级但不宕机**（缓存 fail-open 回源、锁降级放行、限流 fail-close 拒绝）。需要的是"Redis 不可用时间要压到秒级"时 |
| **Cluster 集群** | 单机内存装得下 + 写入 QPS 远未到单机上限。触发条件：单机内存不够，或写入 QPS 打满单线程。**秒杀 key 已预留 hash tag**，切 Cluster 不用改一片 key |
| **Redis 事务 MULTI/WATCH** | 原子性需求已被 **13 段 Lua** 完全覆盖，且 **Lua 不独占连接、事务会**——这也是[不引连接池](#102-连接池决策是不引-commons-pool2)的依据之一 |
| **布隆过滤器** | 有"空值缓存 + 限流"两层挡着。触发条件：大量**随机** key 攻击（空值缓存挡不住每次不同的 key） |
| **多级缓存（Caffeine）** | 触发条件：某个热点 key 的 QPS 打满 Redis |
| **监控告警** | 触发条件：有 SLO 要求时 |
| **Redlock** | 单机部署不需要；且 Redlock 本身的时钟漂移假设有争议。**按"为什么不需要"讲，别说成"没来得及做"** |
| **List** | 没有队列 / 栈形态的业务。**要用 Redis 做队列，该上的是 Stream**（List 没有 ACK） |
| **专业 MQ（RocketMQ）** | 单应用内没有跨服务解耦需求，事件量也远没到需要堆积能力的规模。触发条件：跨服务 / 要顺序消息 / 要事务消息。**设计稿在 `docs/mq/rocketmq-integration-design.md`——有评估、没实施** |
| **GEO** | 讲 GeoHash + 底层是 ZSet（geohash 值当 score）。项目有 `ipLocation`，但没有"附近的人 / 店"这类需求 |
| **分布式 Session** | 用 JWT（无状态），代价是**无法主动失效**——所以才补了 [token 黑名单](#97-token-黑名单) |

> ⚠️ **这张表自己也在变，要维护**：上一版里 **Stream / Hash / Pipeline** 全在"没做"这一栏，
> 现在三个都做了（秒杀 Stream、秒杀 meta Hash、热榜重建 Pipeline），只剩 List。
> **不维护的"没做清单"会变成"我明明做过却说自己没做"**——那比答不上来更亏。
