# Agent 面试讲法合集

> 项目：Spring Boot + Vue3 博客系统内的全站 AI Agent（三域 Runtime + Workflow + Verifier）
> 每条都是项目里真实发生过的，不是设想。

## 一、六个手写核心踩过的坑

### 1. 校验通过 ≠ 原子执行（V3.7 可见性切换）

- **场景**：AI 提议隐藏文章 → 后端先查状态是否 PUBLISHED，再更新为 HIDDEN
- **根因**：两步之间有窗口期，查与更新之间状态可能已变（TOCTOU）
- **修法**：合并为条件更新 `WHERE id=? AND author_id=? AND status='PUBLISHED'`，影响行数 0 即拒绝
- **一句话**：校验通过不等于原子执行，中间永远有窗口

### 2. 先落主体，再落引用（V3.12 孤儿锚）

- **场景**：agent run 结束时写「会话结论锚」，第一版设计是先写锚、再落 run
- **根因**：落库失败会留下**指向不存在 run 的孤儿锚**
- **修法**：`finish()` 先落 run，再调钩子写锚
- **一句话**：顺序反了不会报错，只会在很久以后以脏数据的形式爆出来

### 3. 状态在跑，前端在转圈（V3.1.1）

- **场景**：用户点「生成学习计划」，前端转圈 **30s ~ 2min**，一个步骤卡片都不出
- **根因**：后端状态机正常推进，但三个创建流的 `emitter` 是**空实现**——事件一个没推。单测全绿，因为单测测的是状态推进，不是事件推送
- **修法**：与文章类对齐，实时推 `WORKFLOW_STEP`
- **一句话**：状态推进和状态通知是**两条独立链路**，只测前者会漏掉后者

### 4. 同一个特性里，两处事务边界故意相反（V3.12）

| 写点 | 边界 | 判据 |
|---|---|---|
| confirm 时刻 | 随 `confirm()` 的事务提交 / 回滚 | 锚与 Workflow 要么都成、要么都不成 |
| FINAL_ANSWER 终态 | **fail-open**，写失败不影响回答 | 锚是增强，不是依赖 |

- **一句话**：事务边界不是「统一就好」，判据是**它是不是主流程的必要条件**

### 5. SUCCESS 不等于有产出（V3.11 六步空转）

- **场景**：问某小节写得怎么样 → agent 连跑 6 步，**每步状态都是 SUCCESS**，最后什么都没答出来
- **根因**：SUCCESS 只表示执行没抛异常，不表示拿到了有效材料——focus 定位有 bug，只返回标题行、正文为空
- **修法**：修 focus 命中算法（纯标题节不参与命中 + 取命中最多者）+ R3 规则闸（观察与前序重复即放行，防空转）
- **一句话**：执行层的「成功」和业务层的「有效」要分开

### 6. 模型看不见自己的动作历史（V4 第一刀）

- **场景**：一次多目标请求连发 4 次 `QUERY_MEMORY {"question":"写作偏好"}`，输入输出四次完全相同，纯空转
- **先试的修法是错的**：加 prompt 规则「一次就够 / 不要重复完全相同的查询」——**之前已经加过，无效**；改成 Runtime 硬拦同参重复后，**仍然重复两次**
- **真根因**：observations 里只有结果文本、没有来源标注。模型看到一段「记忆摘要：用户喜欢前端 UI 简洁」，**无法确认它是不是「我要查的那个查询」的产物** → 再查一次**以求确认**
- **决定性证据**：被拦两次后，它最终回答里**引用了那条记忆**——信息早就够了，缺的只是「已经查过」这个事实
- **修法**：给观察加来源标注（`[QUERY_MEMORY question=写作偏好]`），让「已执行过」成为模型可见的事实；同参硬拦作为兜底保留
- **一句话**：**模型缺的不是「别重复」这条纪律，是「我做过什么」这个事实——修法是补齐信息，不是禁止行为**

### 7. MDC 跨线程丢失要逐层验证（V4⑥ 可观测性）

- **现象**：给全站加 traceId 后，分类器日志有 traceId，**Agent 全程没有**（创建 / step / 结束全空）
- **走过的弯路**：先怀疑 `onScheduleHook` 没生效 → 补了显式快照后仍空 → 再怀疑 MDC 被 Spring 的请求清理清掉
- **真根因**：`Flux.create` 的 sink lambda **在订阅时执行**，而 Spring MVC 处理 `Flux` 返回值是「**异步订阅 + 请求线程立即返回**」——lambda 跑的**订阅线程本身就没有 MDC**。钩子做的是「提交时捕获、执行时恢复」，**源头是空的，捕获出来还是空的**
- **决定性证据**：在订阅点打一行 `MDC.get("traceId")` —— 有值；再往下 Agent 就是空。断点被夹在相邻两点之间，只剩一步可怀疑
- **修法**：**请求线程抓快照 → 显式传参 → 执行线程恢复**（`MdcContext`），不依赖任何隐式钩子
- **还有一层**：**光恢复 MDC 不够**——必须同时把 Micrometer 的 `TraceContext` scope 回当前线程，否则后续 tracing scope 切换会把 MDC 覆盖/清掉。**MDC 和 TraceContext 要成对处理**，只做一半会在部分路径上失效
- **一句话**：**ThreadLocal 类问题要逐层验证「哪一层还有、哪一层没了」，别跳步猜原因**——中间两次弯路都是因为跳过了一层观测

**共通点（第 1-6 条）**：都不是框架能自动解决的——全是**业务语义**层的坑。框架给得了 checkpoint 和重试，给不了「隐藏文章的前置状态是什么」。核心逻辑手写是对的，前提是每个坑自己想不到就踩一遍。

**第 7 条不同**：它是**基础设施层**的坑（ThreadLocal 跨线程传播），而且是**用框架解决的**（Micrometer Tracing）——它印证的是另一半：**周边能力该用框架就用**，判据是「不持有业务状态、不做业务裁决」。

## 三、架构 Q&A

**Q：做 Plan-and-Execute 吗？**
分两种形态说。**预定义代码型**已有——就是 Workflow；**LLM 动态规划型**还没做。空缺是第三种：目标明确、但步骤无法预定义时的 **Plan-guided ReAct**。

**Q：做 Reflection 吗？**
部分做了。Verifier 已构成 `Generator → Evaluator → Corrective Loop`，但它判的是「证据够不够、能不能出口」，不是「策略为什么失效」。完整 Reflection 必须**改变后续行为**，否则只是多花 token 生成一段没人用的自我批评。触发条件要等观测数据来定——**先穷尽规则，再上 LLM 反思**（V3.11 那次空转最后是用规则解决的）。

**Q：为什么不用 LangGraph / LangChain4j 接管 Agent Runtime？**
两条理由：

① **双重状态机**。我们已有完整状态模型（run/step 落库、三种待确认态、CAS、确认门、结论锚），框架的 graph state / checkpoint / interrupt 会与它重叠，而两者对中间态的定义不同。**框架最容易重新定义的地方，恰恰是我们手写的那部分。**

② **HITL 语义冲突**（查官方文档后补的硬理由）。LangGraph 的 `interrupt()` 恢复时会把**整个节点从头重跑**，官方文档明确要求 interrupt 之前的副作用必须幂等（原话举例：把扣款放在 interrupt 前可能重复扣款）。而我们的确认门后面接的是**真实写入**，靠「proposal 旧值锚 → stale 校验 → 条件更新」保证安全——**不承诺节点可重放**。这不是适配问题，是两套正确性模型。

**Q：那 LangGraph Studio 的可视化呢？**
是真强项（图渲染 / step-through / state 检查 / time travel），但**只能读 LangGraph 自己的图**，读不了我们的 run/step 表——「用框架做可视化」和「只读我们的数据做展示」不能同时成立。我们走的是自建只读面板（只读 / 开发者工具 / 白名单门禁），后续再补 OpenTelemetry tracing。

**Q：MCP 呢？**
**工具接入协议**，解决「外部工具 / 数据源如何以标准协议接入」，不是让 Agent 变聪明的东西。2026-07-28 版把协议核心改成了无状态的（移除 `initialize` 握手与 session id），对我们有利。但只打算接**只读工具**——写动作不走 MCP：白名单 / 确认门 / 三明治锚定都是针对具体动作手写的，而 MCP 工具是**动态发现**的，规格本身也写明 tool annotations「默认不可信」。

**Q：那框架用在哪？**
基础设施和协议适配全用现成的：Spring Boot / MyBatis-Plus / Jackson / Redis-MySQL-ES 客户端 / SSE / Spring AI 调模型。判据：**可以用 Spring AI 调模型，但不能让它决定 Agent 状态机；可以用框架做适配，但不能让它成为写入权限的最终裁判。** 状态、裁决、权限、失败语义——这四样永远手写。

**边界要说到层，不要说成一刀切**：LangChain4j 作为 Java 模型 / RAG / 工具适配基础库是有价值的，我们否决的只是它的 **agentic 编排模块**（2026 年仍是 beta）接管 Runtime；后续补 OTel tracing、MCP 只读工具接入，都属于可评估的周边框架能力。

**Q：手写不会有问题吗？**
会。风险是漏重试超时、并发状态不完整、事务边界不清、状态不一致、后人看不懂。所以我补了：域钩子化边界、状态快照、55 个测试类、56 例评测门、CAS 幂等、审计留痕、每刀一份设计文档。**还欠 traceId 和系统性失败注入测试**——这两条也一并讲，比只讲优点可信。
