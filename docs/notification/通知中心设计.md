# 站内通知中心：把互动的结果回流给用户

> 状态：✅ **第 1 批已实施**（2026-10-11）· 实施记录、三处前置修复与两处产品简化见 §18
> 关联：[`docs/mq/rocketmq-integration-design.md`](../mq/rocketmq-integration-design.md)（**本刀不上 MQ**，理由见 §2）
> 上游约定：[`api-convention.md`](../api-convention.md) §访问权限第 4 条（"站内消息通知、私信……暂缓，后续作为独立通知业务设计"——本刀就是那个独立设计）

## 0. 一句话

补一个通知中心：**4 类互动事件**（点赞 / 收藏 / 评论 / 回复）+ 未读数 + 列表 + header 红点。
**通知行与业务写在同一个事务里**，不上 MQ、不做实时推送、不做聚合、不做私信。

---

## 1. 为什么做（三条实的，不是"面试高频"）

### 1.1 互动的闭环缺了回流

点赞 / 收藏 / 评论 / 关注四个域全部上线（`article_likes` / `article_favorites` / `article_comments` / `user_follows` 四张表都在写），
但**互动的结果没有任何回流**：

- 别人赞了你的文章 → 你只能自己回文章详情看点赞数变没变
- 别人评论了你 → 你得重新打开那篇文章才知道
- 别人关注了你 → **完全无感**（连计数都只在个人主页才看得到）

这不是"加个功能"，是**互动做了一半**：四个域都在"写入"，没有一处负责"告诉对方"。

### 1.2 它是本项目最合适的「可靠异步 / 幂等」载体

对比一下两边失败代价：

| 现有缺口 | 失败后用户感受 | 撑得起引入中间件吗 |
|---|---|---|
| AI 记忆提取失败即丢（MQ 设计稿的原始理由） | **无感**（AI"忘了"一件事） | ❌ 设计稿 §9.2 自己承认"没有失败率数据" |
| **通知丢失** | **有感**：明明被赞了却没收到 | ✅ 但它该用事务解决，不是 MQ（§2） |

### 1.3 现有基建能直接复用

- **事务内写库**（本刀主路径，不需要新基建）
- 现有的"失败留痕 + 定时重试"骨架（`RagRetryQueue`）——**扇出**那一批才用得上（§14）
- 幂等靠 DB 唯一键（`user_follows` / `article_likes` / `comment_likes` 已经是这个口径）
- XSS 统一出口 `sanitizeHtml`（通知里有用户输入：昵称、评论摘要）
- 接口约定 `/api/users/me/...` + `Result<T>` + 传统分页（与评论 / 账单一致）

## 2. 为什么不上 MQ（**对原设计稿判据的修正**）

MQ 设计稿的触发条件写的是「跨服务 / 要顺序消息 / 要事务消息」（[`redis-interview-notes.md`](../interview/redis-interview-notes.md) §"没做的"表）。
**通知三个都不满足**，但更关键的是：**它该用「同事务写库」解决，而不是任何形式的异步投递。**

### 2.1 三种投递方案对比

| 方案 | 不丢怎么保证 | 失败后的下场 | 本场景合适吗 |
|---|---|---|---|
| **A. 同事务写通知表**（本刀选择） | 与业务写共享事务 → **业务成功 ⟺ 通知在** | 一起回滚，没有"通知丢了"这个状态 | ✅ |
| B. `AfterCommitExecutor` 里写 | 不保证 | ⚠️ 见下 | ❌ |
| C. 独立 outbox 表 + 消费者 | 与业务同事务写 outbox | 多一跳 + 一套状态机 | ❌（本场景） |

**方案 B 被排除的硬理由（两条都在那个类自己的注释里）**：

1. **失败处理是 `catch` + `log.error`**（[`AfterCommitExecutor.java:54-60`](../../blog-system/src/main/java/com/hailin/blogsystem/component/AfterCommitExecutor.java)）
   ——不重试、不落库、无补偿入口。事务已经提交了，此时通知写失败 = **永久静默丢失**，
   只在日志里留一行 `[AFTER-COMMIT]`。
2. **它的契约明确不接受 DB 写**：`@param action 只操作 Redis / 内存的动作`（`:42`），
   类注释还专门解释了原因——"把 DB 写操作放在这里等于**绕过了原事务的原子性**"（`:29-31`）。
   而"不丢"恰恰是本刀最想要的属性，放进 afterCommit 就是主动放弃它。

它自己的定位也写得很清楚：只服务 Redis / 内存类的可丢动作（`WorkflowHandoffResumeListener:22-23` 明确写了不复用它）。

**方案 C 被排除的理由**：outbox 的价值在于「业务库与消费者之间隔着**不稳定通道**（跨库 / 跨服务 / 有外部 IO）」。
而这里的"消费者"就是对**同一个库、同一张表**的一次 INSERT，没有网络、没有外部依赖。
多一张表 + 一个消费者 + 一套重试状态机，换不到任何隔离收益，只换来"延迟"和"要维护的东西"。

**同事务的代价**：业务事务多一条 INSERT（微秒级）。
点赞事务从「INSERT 点赞行 + UPDATE 计数」变成三条写，仍在同一个本地事务里，没有额外锁竞争（不同表）。

### 2.2 原来的触发条件太窄，建议补两条

| 触发条件 | 说明 |
|---|---|
| （原有）跨服务 / 顺序消息 / 事务消息 | 保持 |
| **（新增）一个事件 ≥ 3 个消费者** | 「文章被点赞」要同时驱动 通知 + 作者统计 + 热榜 + 检索索引 +（未来）AI 记忆——塞进一个 `@Async` 方法里会变成一坨 |
| **（新增）单次扇出 ≥ 几十** | 大众号发新文要推给所有粉丝（§14） |

**所以本刀不是"不上 MQ"，是"用对了不需要 MQ 的那把工具"**——而且 §14 的扇出会给 MQ 留下一个**现成的生产者**。

## 3. 范围

**做**（第 1 批）：

1. `notifications` 表 + 4 类点对点事件（点赞 / 收藏 / 评论 / 回复）
2. 未读数
3. 通知列表（传统分页）+ 标记已读 / 全部已读
4. header 铃铛 + 红点 + `/notifications` 页面
5. 落地前先修 3 处现网不一致（§13）

**不做**（登记，各有理由）：

| 不做 | 理由 |
|---|---|
| **私信** | 独立 IM 域：会话 + 消息 + 已读位点 + 拉黑。实时性要求也不同（私信"对方在线要立刻看到"）。见 §14.4 |
| **实时推送（WebSocket / SSE）** | 项目**没有 WebSocket**；现有 SSE 是"一次请求一条流、AI 结束即关"，**无连接注册表、无 userId→连接映射、无心跳**（`AiController.java:60`）。复用要先自建这一整套。通知"下次打开看到红点"就够了 |
| **聚合折叠**（"3 人赞了你的文章"） | 见 §6.3：不做聚合反而让幂等更简单。索引已按聚合形态留位 |
| **关注的作者发新文（扇出）** | 唯一真扇出场景，单独一批：§14 |
| **邮件 / 浏览器 Web Push** | 需要 SMTP / VAPID，与站内通知是两套通道 |
| **评论点赞 / 关注你的通知** | `comment_likes` 是"赞评论"——通知谁？评论作者。**可以加**，但先跑通 4 类 |

## 4. 数据模型

### 4.1 `notifications` 表

风格照 `article_comments`（雪花主键、不加 `AUTO_INCREMENT`、`DATETIME` 时间列）：

```sql
CREATE TABLE IF NOT EXISTS notifications (
    id BIGINT NOT NULL PRIMARY KEY COMMENT '主键（雪花，与全站一致，不走自增）',
    receiver_id BIGINT UNSIGNED NOT NULL COMMENT '接收者用户 ID —— 所有查询/更新都必须带上它',
    actor_id BIGINT UNSIGNED NOT NULL COMMENT '触发者用户 ID（渲染"谁干的"）',
    type VARCHAR(32) NOT NULL COMMENT '事件类型，见 §5',
    target_id BIGINT UNSIGNED NOT NULL COMMENT '事件指向的对象 ID：文章 / 新评论 / 被关注者',
    article_id BIGINT UNSIGNED DEFAULT NULL COMMENT '跳转用文章 ID（评论类事件也带上，省一次回查）',
    is_read TINYINT NOT NULL DEFAULT 0 COMMENT '0=未读 1=已读',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    -- 幂等：同一人（actor）对同一对象（target）的同一类事件，只打扰一次
    UNIQUE KEY uk_notification (receiver_id, type, actor_id, target_id),
    -- 列表：WHERE receiver_id=? ORDER BY created_at DESC
    INDEX idx_receiver_created (receiver_id, created_at),
    -- 未读数：WHERE receiver_id=? AND is_read=0
    INDEX idx_receiver_read (receiver_id, is_read)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='站内通知表';
```

**类型对齐**：`BIGINT UNSIGNED` 是照 `users.id`（`db/init.sql:41`）和 `articles.id`（`:111`）写的。
⚠️ 但 `user_follows` 用的是**非** UNSIGNED 的 `BIGINT`（`:64-65`）——**这个项目没有外键约束兜着，类型漂了不会报错**。
DDL 落地前先 `SHOW CREATE TABLE users` 对一眼（照项目既有习惯：结构变更以实库为准）。

**为什么两条索引而不是一条 `(receiver_id, is_read, created_at)`**：
列表查询是 `WHERE receiver_id=? ORDER BY created_at DESC`（**不带** `is_read` 条件）——
联合索引第二列不参与约束时，第三列不再有序，会退化成 `Using filesort`。
两条各司其职：一条管排序，一条管未读计数。
（如果将来加"只看未读"筛选且数据量大，把 `idx_receiver_read` 扩成 `(receiver_id, is_read, created_at)` 即可。）

### 4.2 唯一键里的 NULL 陷阱（写下来免得踩）

四列**全部 NOT NULL**，一个都不能省。MySQL 唯一索引**不约束 NULL**——
只要有一列允许 NULL，同一件事就能插进去任意多行，**幂等会静默失效**（不会报错、测试也不会红）。

### 4.3 `target_id` 的语义（评审重点，见 §17.2）

`target_id` = **事件指向的那个对象**：

| type | `target_id` 是什么 | 为什么 |
|---|---|---|
| `ARTICLE_LIKED` / `ARTICLE_FAVORITED` | 文章 ID | 事件作用于文章 |
| `ARTICLE_COMMENTED` / `COMMENT_REPLIED` | **新产生的评论 ID** | ⚠️ **不是**被回复的那条评论 ID——用后者的话，"同一条评论被回复两次"只会通知一次 |
| `USER_FOLLOWED` | 被关注者 ID（= `receiver_id`） | 事件作用于"这个人"。看起来与 `receiver_id` 冗余，是为了保持四段结构、且四列都非空 |
| `AUTHOR_PUBLISHED`（第 2 批） | 文章 ID | — |

## 5. 事件 → 接收者映射（含"别重复打扰"规则）

| # | 事件 | 触发点 | 接收者 | 幂等键里的 actor / target |
|---|---|---|---|---|
| 1 | 文章被点赞 | `ArticleLikesServiceImpl.likeArticle:91`（计数更新后） | **文章作者** | actor=点赞者，target=articleId |
| 2 | 文章被收藏 | `ArticleFavoritesServiceImpl.favoriteArticle:94` | **文章作者** | actor=收藏者，target=articleId |
| 3 | 文章被评论 | `CommentsServiceImpl.postComment:243`（`parentId == null`） | **文章作者** | actor=评论者，target=新评论 id |
| 4 | 评论被回复 | 同上（`parentId != null`） | **父评论作者** | actor=回复者，target=新评论 id |
| 5 | 被关注 | `FollowServiceImpl.followUser:66` / 复活分支 `:93` | **被关注者** | actor=关注者，target=receiverId |

**三条"别重复打扰"规则**（都是 §15 要验的）：

1. **不给自己发**：`actorId.equals(receiverId)` 直接跳过。
   自己评论自己的文章、自己回复自己的评论、自己赞自己的文章——全都不发。
2. **回复优先于评论**：回复场景下接收者是**父评论作者**。
   如果父评论作者**恰好就是文章作者**，只发一条 `COMMENT_REPLIED`——
   否则作者会同时收到"有人评论了你的文章"和"有人回复了你"两条，同一件事打扰两次。
3. **只认 `APPLIED`**（见 §6.2）。

## 6. 幂等：唯一键 + 只认 APPLIED

### 6.1 唯一键承担什么

`uk_notification (receiver_id, type, actor_id, target_id)` 的语义是：
**「同一个人，对同一个对象，同一类事件，只打扰一次」**。

于是这些行为都天然收敛：

| 用户行为 | 结果 |
|---|---|
| 连点两次点赞 | 第二次走 `ALREADY_SATISFIED`，不发（§6.2）；即使发了也被唯一键挡掉 |
| 点赞 → 取消 → 再点赞 | **不重复通知**（键相同，插入被忽略）。这是**有意的防刷**，不是漏发 |
| 不同人点赞同一篇 | 各发一条（actor 不同） |
| 同一篇文章被评论两次 | 两条（target 是新评论 id，天然不同） |

插入用 `INSERT ... ON DUPLICATE KEY UPDATE id = id`（或捕获 `DuplicateKeyException` 忽略），
**不要**先 `SELECT` 判存在再插入——那是"检查后使用"，并发下会插两条（虽然唯一键会兜住，但白跑一次查询）。

### 6.2 只认 `APPLIED`：这是最容易错的一处

点赞 / 收藏 / 关注在**重复操作**时返回的是
`ArticleInteractionResult.success(..., ALREADY_SATISFIED, ...)`（[`ArticleLikesServiceImpl.java:67-74`](../../blog-system/src/main/java/com/hailin/blogsystem/service/impl/ArticleLikesServiceImpl.java)）
——**`resultCode` 不是 `APPLIED` 但整体仍是 success**。

所以通知的触发条件必须是 **`resultCode == APPLIED`**（真的产生了状态变化），
不能是"方法没抛异常"。否则**重复点击会重复打扰**（用户按两下赞，作者收到两条）。

### 6.3 为什么第一版不做聚合

聚合（"3 人赞了你的文章"）看起来更优雅，但它把幂等从"唯一键"变成"**计数 + 去重集合**"：
要记住"哪几个人赞过"才能保证重复点赞不重复计数，就得在通知行上再挂一个集合或子表。

**第一版的取舍**：一人一条、不聚合，幂等完全交给唯一键（零额外状态）。
代价是"10 个人点赞 = 10 条通知"——**在真实使用量下这是对的**（博客不是微博）。
索引形态 `(receiver_id, type, article_id)` 是为聚合留的位（加一列 `article_id` 到唯一键或另建查询索引），到那时再改。

## 7. 事务边界：本刀最关键的决策

### 7.1 现状（挂通知的落点各不相同）

| 事件 | 事务现状 | 能不能直接挂 |
|---|---|---|
| 点赞 | ✅ `@Transactional`（`ArticleLikesServiceImpl:51`） | ✅ 事务内加一条 INSERT |
| 收藏 | ✅ `@Transactional`（`ArticleFavoritesServiceImpl:56`） | ✅ |
| 关注 | ✅ `@Transactional`（`FollowServiceImpl:44`） | ✅ |
| **评论 / 回复** | ❌ **无事务**（`CommentsServiceImpl.postComment:212`） | ⚠️ **必须先补事务**（§13.1） |
| 发新文（扇出） | ❌ 无事务（`ArticlesServiceImpl.publishArticle:1130`） | 第 2 批，见 §14 |

### 7.2 为什么通知必须和业务同事务

写通知本身**不可能失败得比业务更晚**：它就是一次同库单表 INSERT。
放进同一个事务后：

```
BEGIN
  INSERT article_likes            -- 业务
  UPDATE articles SET like_count  -- 业务
  INSERT notifications            -- 通知（同一事务）
COMMIT
```

- 业务成功 → 通知一定在（**不丢**）
- 业务回滚 → 通知一起回滚（**不会出现"点赞失败了却通知了作者"**）
- 不需要补偿、不需要对账、不需要重试——**没有中间态**

### 7.3 这个决定什么时候该被推翻（写清边界，免得后人以为它永远对）

| 触发条件 | 该换成 |
|---|---|
| 通知要写**另一个库 / 另一个服务** | outbox（本地消息表） |
| 通知要带**外部 IO**（发邮件、调推送服务） | outbox（不能把网络调用放事务里） |
| 单次事件要写**几十条以上**（扇出） | outbox（见 §14） |
| 通知写入明显拉长业务事务（实测） | 重新评估 |

## 8. 不存快照，渲染时回查

**决策**：通知表**不存**文章标题、不存评论内容，只存 id（`actor_id` / `article_id` / `target_id`）。
列表渲染时批量回查。

| | 存快照 | **只存引用（本刀）** |
|---|---|---|
| 文章标题改了 | 通知里是旧标题（与点进去不一致） | 显示新标题 |
| 文章删了 / 隐藏了 | 快照还在，点进去 404 | 按当下状态降级（§8.2） |
| 评论删了 | 快照还在，显示"幽灵评论" | 显示"评论已删除" |
| 数据冗余 | 每行多几百字节 | 0 |

与项目既有口径一致：评论是**软删除 + 递归软删除**（`api-convention.md` §评论规则），
通知若存快照就会与"评论已删"这个事实打架。

### 8.1 批量回查：3 次 IN 查询，不是 N+1

一页 20 条通知，收集去重后：

```sql
SELECT id, nickname, avatar_url FROM users            WHERE id IN (:actorIds);
SELECT id, title, status FROM articles                WHERE id IN (:articleIds);
SELECT id, content, deleted_at FROM article_comments  WHERE id IN (:commentIds);
```

### 8.2 降级规则（**含一条越权细节**）

| 情况 | 渲染 |
|---|---|
| 文章已删（查不到） | 不显示标题，不可点击 |
| **评论已删**（`deleted_at` 非空） | "（评论已删除）"，不带内容 |
| **接收者 ≠ 文章作者，且文章不是 `PUBLISHED`** | **不显示标题、不可点击** |
| 触发者已注销 / 查不到 | 显示"某位用户" |

那条越权细节值得单独说：`AUTHOR_PUBLISHED`（第 2 批）的接收者是**粉丝**，
如果作者事后把文章改成隐藏或草稿，**粉丝不能从通知里看到标题**——
标题本身就是内容。点赞 / 收藏 / 评论的接收者是作者本人，不受这条约束。

## 9. 未读数

```sql
SELECT COUNT(*) FROM notifications WHERE receiver_id = ? AND is_read = 0
```

走 `idx_receiver_read`。单用户的通知量是"几百到几千"，这条 COUNT 是索引内计数，微秒级。

**第一版不加 Redis 缓存**，理由（这是个可以讲的取舍）：

- 加了就有**不一致窗口**：计数缓存与真实未读会短期不一致，还要设计失效与重建
- 现在没有性能问题——`COUNT` 走覆盖索引，且这只是 header 红点，不需要强一致
- 与钱包「纯 DB、零 Redis」的判据呼应：**Redis 是加速器，不是真相**。这里连加速都不需要

**什么时候该加**（触发条件）：实测 COUNT 耗时 > 10ms，或红点请求 QPS 明显上来。
加的时候也用"Redis 只做缓存、DB 是唯一真相、缓存丢了重算"的口径，**不要把 Redis 计数器当账本**。

## 10. 接口（遵守 `api-convention.md`）

```text
GET  /api/users/me/notifications?page=1&pageSize=20        通知列表（传统分页）
GET  /api/users/me/notifications/unread-count              未读数
POST /api/users/me/notifications/read       {"ids":[...]}  标记指定通知已读
POST /api/users/me/notifications/read-all                  全部已读
```

**为什么是传统分页而不是游标**：通知列表是有页码语义的后台型列表，
与"我的文章 / 账单 / 评论"一致；游标分页只为首页无限滚动服务（`api-convention.md` §返回格式）。

**为什么 `read` 和 `read-all` 分开**：不要用"`ids` 为空 = 全部"这种隐式语义——
项目里"用类型保证契约"的先例是钱包（请求体里根本没有金额字段）。分开是两个明确的接口。

返回体（扁平 VO，与 `ArticleDetailVO` 风格一致）：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [
      {
        "id": 100,
        "type": "COMMENT_REPLIED",
        "actorId": 9,
        "actorName": "张三",
        "actorAvatarUrl": "https://...",
        "articleId": 10,
        "articleTitle": "Redis 缓存穿透实战",
        "commentExcerpt": "写得不错",
        "isRead": false,
        "createdAt": "2026-10-11 20:31:00"
      }
    ],
    "total": 42,
    "page": 1,
    "pageSize": 20
  }
}
```

`articleTitle` / `commentExcerpt` 可空，语义见 §8.2。
`commentExcerpt` 截断到 ~50 字（列表只需要够看）。

**标记已读必须带归属校验**：`UPDATE notifications SET is_read=1 WHERE id IN (...) AND receiver_id = :me`。
只按 id 更新就是**越权**（能改别人的已读状态）。

## 12. 安全

| 面 | 措施 |
|---|---|
| **越权读** | 列表 / 未读数 / 标记已读的 SQL **一律带 `receiver_id = UserContext.get()`**，不靠前端传 |

### 13.1 `CommentsServiceImpl.postComment` 没有事务 ⚠️ 最该修

### 13.2 被回复人 ID 拿不到（作用域问题）

## 14. 第 2 批：扇出与 MQ 的关系

### 14.1 扇出是唯一真异步场景

「关注的作者发新文」→ 要写给 **N 个粉丝**（N = `user_follows` 里 `following_id = 作者` 的行数）。
这**不能**放业务事务里（N 条 INSERT 会拖长事务）。查询侧索引已经现成：
`INDEX idx_following (following_id, deleted_at)`（`db/init.sql:71`）✅。

### 14.2 三个入口都要覆盖（别只切一个）

| 入口 | 位置 | 事务 |
|---|---|---|
| A 手工发布 | `ArticlesServiceImpl.publishArticle:1130` | ❌ 无事务 |
| B Agent 受控写 | `ArticlesServiceImpl.updateArticleVisibility:1046` | ✅ `@Transactional` |
| C 创建即发布 | `ArticlesServiceImpl.writeArticle:943`（`status=PUBLISHED`） | — |

只给 A 加通知会漏掉 B / C——**Agent 发的文章与"创建即发布"都不会通知粉丝**。

### 14.3 这里才轮到 outbox（以及它为什么是 MQ 的现成生产者）

扇出要"业务成功 → 消息必达 → 异步展开"，这正是**本地消息表**的适用场景：

```
业务事务内：INSERT notification_outbox(event_type, biz_id, status=PENDING)
定时任务：  扫 PENDING → 查粉丝列表 → 批量 INSERT notifications → 标记 DONE
```

然后——**这张 outbox 表就是 RocketMQ 的现成生产者**：
将来触发条件满足（消费者 ≥ 3 / 扇出更大 / 多进程），把"定时任务扫表"换成"投递到 MQ"，**换的是投递器，不是整体重写**。
这也是那份搁置的 MQ 设计稿第一次有了落点。

⚠️ **但不要照抄 `RagRetryQueue`**：它是 `ZRANGEBYSCORE + ZREM` 的**取出即删**（at-most-once），
进程在"取走但没执行完"时崩溃这个任务就永久消失（设计稿 §1 缺口②自己写了）。
通知的扇出要**落库**（outbox 表的 `status`），不是放 Redis 队列。

### 14.4 私信为什么最后做（或不单做）

| | 通知 | 私信 |
|---|---|---|
| 数据模型 | 单表 | 会话 + 消息 + 已读位点 |
| 实时性 | "下次打开看到" | "对方在线要立刻看到" |
| 需要上行通道 | 不需要 | **需要**（发送 + 接收推送） |
| 额外安全 | 越权读 | 加：陌生人骚扰 → 拉黑 / 开关 |

现有 SSE 是"**一次请求 = 一条流、AI 结束即关**"，服务端**没有连接注册表、没有 userId→连接映射、没有心跳**
（`AiController.java:60`，前端用 `fetch().body.getReader()` 消费，不是 `EventSource`）。
要拿它做私信推送，得先自建：长驻订阅接口 + `Map<userId, sink>` + 心跳 + 离线落库补偿。

**建议**：通知做完、验证过"落库 + 拉取"这条主链路之后再做私信；
那时 SSE 从"AI 专用"升级成"通用推送通道"，又是一次能讲的演进。
面试价值上，私信与通知高度重叠（幂等 / 未读 / 时序），成本却翻倍。

## 16. 面试三问（本刀的验收标准）

§7 已经写明「我用了 X」本身不加分。这一刀的验收不是"通知能弹出来"，是这三问能用本项目代码回答：

| 问 | 答（本项目的具体做法） |
|---|---|
| **怎么保证不丢？** | 通知行与业务写在**同一个本地事务**里（§7）。业务成功 ⟺ 通知在，不需要补偿。**并且能说清为什么不选 afterCommit**——`AfterCommitExecutor` 失败只 `log.error`，事务已提交，那就是永久静默丢失 |
| **怎么保证不重？** | DB 唯一键 `(receiver_id, type, actor_id, target_id)` + 只认 `APPLIED`（§6）。**唯一键四列必须全 NOT NULL**——MySQL 唯一索引不约束 NULL，可空列会让幂等静默失效 |
| **未读数怎么保证一致？** | DB 是唯一真相（`COUNT` 走 `idx_receiver_read`），第一版**不加 Redis**。要加也是"缓存丢了重算"，不把计数器当账本（§9） |

**加分项**：能讲清"什么时候**不**该上 MQ"（§2）——`一个事件 ≥ 3 个消费者`、`扇出 ≥ 几十`、
`出现第二个进程`才是触发条件，而本刀用同事务 + 唯一键把问题解决在了更前面。

## 17. 关键决策点（**供评审逐条挑刺**）

### 17.1 通知写在业务事务内 —— 会让点赞事务多一条写，值吗？

- **我的倾向**：值。同库单表 INSERT 是微秒级，且**换到了"不可能出现不一致"**这个性质。
- **反方**：把通知放进业务事务，等于"通知的可用性"绑架了"点赞的可用性"——通知表出问题（比如锁等待）会让点赞变慢。
- **需要评审的**：是否接受这个耦合？还是宁可走 outbox（多一跳，但业务事务不被通知影响）？

### 17.2 `target_id` 四段唯一键 —— 语义够清楚吗？

评论类事件用**新评论 ID** 而不是"被回复的评论 ID"（§4.3），这是为了让"同一条评论被回复多次"能各发一条。
`USER_FOLLOWED` 的 `target_id` 等于 `receiver_id`，**看起来冗余**，是为保持四列非空。
**有没有更干净的键设计？** 请挑。

### 17.3 不做聚合 —— "10 个人点赞 = 10 条通知"能接受吗？

- **我的倾向**：第一版接受。聚合会把幂等从"唯一键"升级成"计数 + 去重集合"，复杂度上一个台阶。
- **反方**：真实使用中"一条文章被 20 人点赞"就足以让通知列表刷屏，用户会关掉它。

### 17.4 不做实时推送 —— 红点靠路由切换拉取，够吗？

- **我的倾向**：够。通知不是聊天，"下次打开看到"完全可接受，而 WebSocket / 长驻 SSE 的基建成本（连接注册表 + 心跳 + 离线补偿）在这个阶段明显不划算。
- **反方**：用户开着页面时红点不更新，会以为功能坏了。

### 17.5 §13 那三处前置修复 —— 该不该夹在这一刀里？

- **我的倾向**：该。它们是**现网不一致**（评论的两次写不自洽、作者 id 白查一次），且不修就没法把通知放进事务。
- **反方**：`@Transactional` 加在评论上是**行为变更**（原先计数失败评论还在，现在会一起回滚）——严格说这是另一个 bugfix，混在一起会让"通知这一刀"的 diff 不纯。

### 17.6 第 2 批的扇出 —— 现在就把 `notification_outbox` 设计出来吗？

- **我的倾向**：先不建表。第 1 批不做扇出，也就用不上 outbox；**提前建一张没有消费者的表**属于投机。
- **反方**：既然已经论证出"outbox 是 MQ 的生产者"，早点建表能让 MQ 那一刀更顺。

## 19. 第二批增补（2026-10-11）：聚合折叠 / 评论点赞 / 保留期清理

### 19.1 聚合折叠（一条 = 一组）

「张三 等 10 人赞了你的文章」。

**聚合放在 SQL 里做**（`NotificationsMapper.selectGroupPage`，窗口函数），不是在 Java 里合并——
因为**分页必须按组算**：先按行分页再在内存里合并的话，同一组会被页码切开，
第 1 页显示"3 人赞了"、第 2 页又冒出"7 人赞了"，而且两个数字都不对。

新增两个 VO 字段：`actorCount`（组内人数）、`groupUnread`（组内还有几条未读）。
判断"这条读没读"要看 `groupUnread`，**不是** `isRead`——后者只是代表行的状态。

**已读的粒度也跟着变成"组"**：列表项的 id 是组内最新那条的"代表 id"，
`markRead` 收到后展开成整组更新。只标最新那条的话红点只减 1，用户会以为"点了已读没生效"。

### 19.2 评论点赞通知（第 5 类事件）

`COMMENT_LIKED`：接收者是**评论作者**（不是文章作者）——
文章作者收"有人评论了你的文章"，评论作者收"有人赞了你的评论"，这是两条不同的通知。

零额外查询：`LikeCommentsServiceImpl.likeComment` 本来就要 `selectById(评论)` 去算 likeCount，
作者 id 与文章 id 都已经在那个返回值里。

### 19.3 保留期清理（30 天）

通知是**只增不减**的表，而它是时效性信息。新增 `NotificationCleanupTask`：
每天 3:30 删 `created_at < now - 30d`，分批（1000/批，最多 20 批 = 2 万条/天）。

**新增了一条索引 `idx_created_at`**，这是必须的：现有两条索引都以 `receiver_id` 开头，
而清理查询 `WHERE created_at < ?` **不带 receiver**——一条都用不上，会退化成全表扫描。
（这是"索引要对着查询建"的又一个实例：判据不是"列重不重要"，而是"有没有对应查询"。）

单次限总量的原因：三个定时任务**共享同一条调度线程**（`pool.size: 1`，见 `RagRetryTask` 的注释），
一次删几万行会把 RAG 重试和浏览量同步一起卡在它后面。

### 19.4 分页：**不做游标分页**（决策记录）

讨论过"消息列表要不要改成游标分页，不然以后很多怎么办"。结论是**不**，三个理由：

1. **场景不对**：游标分页解决的是"无限滚动越滑越慢"。通知列表用户最多翻前几页，
   没人会翻到第 50 页——首页那种无限滚动才是它的主场。
2. **聚合之后游标很难做对**：游标要求排序键**稳定且全序**，而聚合组的排序键是"组内最新时间"，
   **新通知一进来这个值就会变**（组会往前跳）；改用"按行游标"则会在翻页时把同一组切开。
   要做对得同时游标化"组的排序键 + 组内位点"，复杂度上一个档。
3. **真正的痛点是数据膨胀，不是分页深度**：那个由 §19.3 的保留期清理解决。

所以 **保留期清理做、游标分页不做**——两者不是"都要"的关系，后者解决的是一个不存在的问题。
哪天真变成"无限滚动 + 深翻"，再回来做（那时要连同 §19.3 的删除口径一起设计）。
