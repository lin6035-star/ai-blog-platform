## 2. Redis

### 市场常见能力

| 能力 | 说明 |
|------|------|
| 数据缓存 | String/Hash 缓存热点数据 |
| 缓存穿透防护 | 布隆过滤器 / null value 缓存 |
| 缓存击穿防护 | 热点 key 互斥锁 |
| 缓存雪崩防护 | 随机 TTL、多级缓存 |
| 分布式锁 | Redisson / SETNX |
| 限流 | 令牌桶 / 滑动窗口 |
| 计数器 | INCR 原子操作 |
| 排行榜 | ZSET |
| 幂等控制 | SETNX 唯一键 |
| 延迟队列 | ZSET score 时间戳 |
| Session/Token 管理 | 黑名单、刷新令牌 |
| 发布订阅 | 轻量消息通知 |

### 当前状态

- ✅ 文章详情/列表缓存（String JSON，10min/5min TTL）
- ✅ 分类/标签列表缓存（30min TTL）
- ✅ 缓存穿透防护（`CACHE_NULL_VALUE = "__NULL__"`，3min TTL，不存在的 key 返回占位符不穿透到 DB）
- ✅ 文章浏览量（String INCR，30s 定时刷回 DB）
- ✅ 热门文章排行榜（ZSET，点赞/收藏/评论加权分数）
- ✅ 用户点赞/收藏/评论集合（Set，30min 按需加载标记）
- ✅ RAG 索引同步失败标记（String + 7 天 TTL）
- ❌ 缓存击穿防护 — **缺失**（热点文章过期瞬间大量请求打到 MySQL，需要 SETNX 互斥锁）
- ❌ 缓存雪崩防护 — **缺失**（批量缓存同时过期，需要随机 TTL 偏移）
- ❌ 分布式锁 — **缺失**（无 SETNX/Redisson，并发写保护）
- ❌ 限流 — **缺失**（API 无任何频次控制，LLM/ES 昂贵资源无保护）
- ❌ 登录失败计数 — **缺失**（Redis INCR + TTL 即可，暴力破解无防护）
- ❌ 游客会话次数限制 — 前端 sessionStorage 有 3 次硬限制，但后端无强制
- ❌ 幂等控制 — **缺失**

### 建议

| 项目 | 优先级 | 理由 |
|------|--------|------|
| 限流 | **高** | LLM API、ES 都是昂贵资源，没有限流很容易被打爆 |
| 缓存击穿防护 | 高 | 热点文章场景，用 Redis SETNX 互斥锁即可 |
| 登录失败计数 | 中 | 防暴力破解，Redis INCR + TTL，实现简单 |
| 缓存雪崩防护 | 中 | 给各缓存 key 加随机 TTL 偏移，改动小 |
| 分布式锁 | 中 | 文章编辑并发、计数扣减等场景需要 |
| 游客次数限制 | 中 | 已计划，后端需强制校验 |
| 幂等控制 | 低 | 创建文章等操作可用，当前需求不强 |

## 4. RAG 体系

### 市场常见能力

| 能力 | 说明 |
|------|------|
| 文档切分 | chunk splitter（定长/语义/递归） |
| Embedding | 向量化 |
| 向量检索 | 语义搜索 |
| 关键词检索 | BM25 / match |
| 混合检索 | 向量 + 关键词融合 |
| Rerank | 模型重排 / 规则重排 |
| Query Rewrite | 查询改写、多轮对话中的指代消解 |
| Metadata 过滤 | 按来源/类型/时间等过滤 |
| 引用溯源 | references、citation |
| 评测集 | RAGAS、人工标注 |
| 一致性保证 | 索引与源数据同步 |
| 权限隔离 | 不同用户搜到不同内容 |
| 知识更新策略 | 增量更新、全量重建 |

### 当前状态

- ✅ 5 层递降 chunk 策略（段落→句子→逗号→token→字符，上限 800）
- ✅ DashScope text-embedding-v3（1024 维）
- ✅ ES 向量检索（topK=3, similarityThreshold=0.65）
- ✅ 向量 + keyword 混合检索（ARTICLE_SEARCH 意图）
- ✅ 规则 rerank（标题命中 +10、正文命中 +3、原始召回顺序加权、文章去重）
- ✅ MySQL LIKE 兜底（title/summary，top 3，snippet 50 字符截断）
- ✅ 引用编号 `[1]` `[2]`
- ✅ 当前文章问答
- ✅ 一致性巡检 + 手动修复（ES scan 上限 1000 条，超出有静默遗漏）
- ✅ source 过滤
- ✅ RAG 索引同步失败重试（最多 3 次，线性退避，Redis 失败标记 7 天 TTL）
- ⚠️ 文档与代码偏离：CLAUDE.md/rag-notes 声称 chunkIndex=0 加分，实际代码无此逻辑
- ❌ Query Rewrite — **缺失**（指代消解、多轮追问优化）
- ❌ 模型 rerank — **计划但未做**（接口已预留，当前用规则版）
- ❌ 评测集 — **缺失**（无法量化检索效果）
- ❌ references 服务端不持久化 — `ai_messages` 表无 references 字段，换设备丢失引用
- ❌ 相关文章推荐 — **计划但未做**
- ❌ chunk overlap — 仅硬拆分时有 100 字符重叠，常规路径无重叠窗口
- ❌ 一致性巡检 ES scan 上限 1000 — 超出的文章静默遗漏

### 建议

| 项目 | 优先级 | 理由 |
|------|--------|------|
| Query Rewrite | 中 | 多轮对话 "那第二篇呢" 等指代消解直接依赖 |
| 评测集 | 中 | 面试必问 + 后续优化决策依据，10-20 条问答对即可起步 |
| references 服务端持久化 | 中 | 当前只存 localStorage，换设备/清缓存丢失所有引用 |
| 模型 rerank | 中 | 接口已预留，效果提升明显 |
| ES scan 上限 | 低 | 当前文章量远不到 1000，但上限存在是隐患 |
| 相关文章推荐 | 低 | 已列在 rag-notes 后续计划中 |
| chunk overlap | 低 | 当前 chunk 策略下丢失的上下文很少 |

## 补充：跨模块发现

1. **文档/代码偏离**：CLAUDE.md 和 rag-notes 声称 rerank 有 `chunkIndex=0` 加分，实际代码无此逻辑。后续维护文档时建议同步核实代码。
2. **日志不统一**：部分 service（如 RAG、AI tools）有 `@Slf4j` 关键路径日志；`ArticlesServiceImpl`、`CommentsServiceImpl` 没有任何日志，出问题无法排查。
3. **无统一异常处理日志**：`GlobalExceptionHandler` 的通用 `Exception` 处理吞掉了异常 message（直接返回"服务器内部错误"），建议至少 `log.error` 记录原始异常。
4. **无拦截器级 access log**：没有统一的请求日志（耗时、状态码、userId），排查性能问题时无从下手。

> 补充建议：以后每次新开一个技术方向（比如上 MQ、上监控），在编码前先花 10 分钟列一下这个技术的能力地图，然后对照本报告决定补哪些。这样不会出现"上了 Redis 但只用它做缓存"的情况。
