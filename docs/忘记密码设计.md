# 忘记密码 + 账号模型收敛设计

> 2026-10-16 实施完成（第 1~5 步）。**其中第 3 步（GitHub 自动绑定）和第 4 步的实际发信
> 需要人工验证**——它们依赖外部系统，自动化测试覆盖不到，见 §7。

## 0. 一句话

「忘记密码」不是加个页面，它逼你先回答一个更根本的问题：**两种登录方式（密码 / GitHub）的账号，是不是同一个账号？** 现在不是 —— 同一个邮箱可以存在两个互不知情的账号。

## 1. 账号模型：为什么必须先定这个

### 现状（改造前）

- `users.login_type` 是**单值**：`password` 或 `github`
- GitHub 登录按 `(login_type='github', github_id)` 匹配，匹配不到就建新号
- **全程没有用邮箱**，连拿都没拿（scope 只有 `read:user`）

**后果**：先用邮箱注册、后来用同一个邮箱的 GitHub 登录 → **两个账号**。文章、评论、钱包、关注关系全部裂开，而且当时不会有任何报错。

### 三个选项

| | 做法 | 代价 |
|---|---|---|
| A. 保持分离 | 邮箱只属于密码账号 | 零改动；但同邮箱两个号，且 GitHub 用户点"忘记密码"永远收不到信、还不能告诉他为什么 |
| **B. 邮箱唯一 + 自动绑定** ✅ | `email` 唯一索引；GitHub 登录按 `email` 匹配到已有账号就**绑定**而不是建新号 | 要改 scope、要处理"拿不到邮箱"的情况 |
| C. 拆身份表 | `user_identities(user_id, provider, provider_uid)` | 最规范，能挂 N 种登录方式，但现有登录代码全要改 |

**选 B**：收益/成本比最好 —— 一个字段 + 一段匹配逻辑就是真实产品的标准做法；而 C 的额外收益（支持更多登录方式）现在用不上。

## 2. GitHub 收敛：三段式匹配（已实施）

`findOrCreateUser(githubUser, email)` 按顺序：

```
1. 按 github_id 找          → 找到就更新资料，返回（老行为）
   ⚠️ 只按 github_id，不带 login_type
2. 按 email 找已有账号      → 找到就**绑定 github_id**（不建新号）★
3. 都没有                   → 建新号，带上 email
```

**三个关键决定**（都是会埋坑的地方）：

**① 第 1 步去掉 `login_type` 条件**
`login_type` 表达的是"注册来源"，**绑定不会改它** —— 改了的话用户就用不了密码登录了（`login` 查询带 `.eq(loginType, "password")`）。但带上它查询会出现一个很隐蔽的 bug：**刚绑过的账号，第二次 GitHub 登录又找不到自己**，于是重复走绑定路径。

**② 只认 `primary && verified` 的邮箱**
未验证的邮箱是用户随手填的，可能是**别人的地址** —— 拿它匹配账号等于"谁把这个邮箱填进自己的 GitHub，谁就拿到那个账号"。两个条件缺一不可。

**③ 绑定时不覆盖昵称 / 头像 / bio**
账号是他自己的，GitHub 上的资料不该盖掉他在站内改过的设置。只写 `github_id`。

（顺带：这条决定让 §7 的验证变得一眼可判 —— 看昵称就知道是绑上了还是建了新号。）

**scope**：`read:user` → `read:user%20user:email`。必须加 `user:email`，否则调 `/user/emails` 会 403；而 `/user` 返回的 `email` 字段在用户把邮箱设为私密时是 `null`，那个设置在 GitHub 新账号里默认就开着。
**副作用**：已授权过的用户需要重新授权（旧 token 没这个权限）。项目未上线，影响可忽略。

## 3. 忘记密码流程（第 4 步，待实施）

```
POST /api/auth/password/forgot { email }
   → 恒定返回：「如果该邮箱可用，重置链接已发送」
   → 后台：只对 login_type='password' 且 email 匹配的用户发信；其它情况什么都不做
   → 限流：按邮箱 + 按 IP

邮件里的链接 → /reset-password?token=xxx
POST /api/auth/password/reset { token, newPassword }
   → Redis 校验 token（一次性）→ 改 password_hash
   → TokenVersionStore.bump(userId)   ← 顺手踢掉所有设备
   → DEL token
```

**防用户枚举是核心**，而且**响应耗时也要恒定**：只做到"文案一样"不够 —— 如果"邮箱存在"这条路径因为要发信慢了 200ms，那个时间差本身就是探针。

**GitHub 用户必须收到"已发送"然后永远收不到信**。这是**刻意的**：告诉他"你是 GitHub 用户"就等于确认"这个邮箱在站内注册过"。这个取舍要写进代码注释，否则后人会当成 bug"修"掉。

### 唯一豁免：邮件服务不可用要说出来（2026-10-16 补）

「响应恒定」**不能无差别地套用到所有分支上**。这里混着两件不同的事：

| 分支 | 性质 | 响应 |
|---|---|---|
| 邮箱存在 / 不存在 / 是 GitHub 账号 / 被限流 | **用户级**信息 | 全部恒定"已发送" ✅ |
| 邮件服务未配置 | **全局**状态，与任何用户无关 | **明确报错 `50301`** ✅ |

**这条是真实踩出来的**：第一版把"邮件未配置"也归进了静默分支，结果没配 mail 时点"忘记密码"，
界面提示"已发送"、收件箱什么都没有 —— 只能翻后端日志才发现配置根本没生效。

说出来不削弱防枚举（它跟"这个邮箱如何"没有任何关系），却能让配置错误在**第一次点击时**暴露。
另外这个检查刻意排在**限流之前**：配好邮件之前点的那几次，不该消耗"3 次 / 15 分钟"的配额。

对比一下第一版的注释「刻意返回 void，让调用方没有任何分支可以泄露」—— 方向是对的，
但**把"全局故障"也一起按住了**。粒度错了，不是原则错了。

## 4. token 代次（第 1 步，已实施）

**解决的问题**：JWT 无状态，签发之后作废不了。现有 `TokenBlacklist` **只能按 `jti` 拉黑单个** —— 而"用户改了密码，把他其它设备上的登录全部踢掉"需要的是**批量作废**，服务端根本不知道这个用户签发过哪些 jti。

**做法**：`users.token_version` 计数器 → 签发时写进 payload 的 `ver` → 拦截器比对。

| 决定 | 理由 |
|---|---|
| 权威值在 **DB**，Redis 只做缓存 | 只存 Redis 的话，一次 `flushdb` 就让已作废的 token 集体复活，且毫无迹象 |
| 缓存读失败**回源 DB**，不放行 | fail-open 成 0 正好等于放行所有旧代次 |
| 查不到用户返回哨兵 **-1** | 软删用户的 token 不该还能用；返回 0 会让 `ver=0` 的老 token 继续有效 |
| 老 token 无 `ver` **按 0** 处理 | 与列默认值一致 —— 否则加这个字段的那一刻会把所有在线用户全部登出 |
| `bump()` 用 `token_version + 1` 原子自增 | 读出来 +1 再写回，并发改密会丢计数 |

拦截器里是**黑名单 → 代次**两道比对，共用同一个「登录已失效」提示（不区分，不给攻击者反馈）。

## 5. 邮件通道（第 4 步，待实施）

**选型：QQ 邮箱 SMTP**（先用它跑通，将来可升级到自有域名）。

- 本地和服务器**用同一套配置**，避免"上线时再折腾一遍"
- 配置全部走环境变量（`MAIL_HOST` / `MAIL_PORT` / `MAIL_USERNAME` / `MAIL_PASSWORD`），复用项目已有的敏感配置机制
- ⚠️ QQ 邮箱要的是**授权码**不是 QQ 密码，用密码连会认证失败且报错模棱两可

## 7. 验证方法

### 第 3 步（必须人工，需要真实 GitHub 授权）

1. 用邮箱 X **注册一个密码账号**，昵称填一个能认出来的（如"站内昵称"）
2. 退出，用**同一个邮箱 X** 的 GitHub 账号登录（授权时会出现新的 `user:email` 权限请求，必须同意）
3. **判据：看昵称**
   - 昵称**还是"站内昵称"** → ✅ 绑到了原账号（因为绑定刻意不覆盖昵称）
   - 昵称**变成 GitHub 上的名字** → ❌ 建了新号，绑定失败

权威判据（查库）：

```sql
SELECT id, username, nickname, login_type, github_id, email
FROM users WHERE email = 'X';
-- 1 行 = 收敛成功；2 行 = 账号裂开
```

`login_type` 保持 `password` 是**对的**：它表达注册来源，绑定不改，这样密码和 GitHub 两种方式都能登录。

### 第 4 步（待做后验证）

- 后端：`forgot` 接口对「存在的邮箱 / 不存在的邮箱 / GitHub 账号邮箱」三种输入返回**完全一致**的响应
- 邮件：用自检接口发一封到自己的真实邮箱
- 全链路：`forgot` → 收信 → 点链接 → 改密 → **旧 token 失效**（另开一个浏览器用旧 token 访问受保护接口应 401）

## 8. 已知边界 / 有意不做

- **老数据（email 为 NULL）走不了找回流程**，也不做强制补填入口 —— 项目未上线，无真实存量用户
- **逻辑删除 + 唯一索引**：软删用户的 email 仍占用唯一键，同邮箱无法重新注册。这是项目既有模式（`username` 也一样），本次不引入新方案
- **GitHub 拿不到邮箱时**退回"只按 github_id 认人"的旧行为 —— 用户照样能登录，只是不会自动绑到他已有的密码账号上
- **不做"修改密码"入口**：本次只做忘记密码。但 `TokenVersionStore.bump()` 已经就位，将来加"修改密码"时直接调它即可
